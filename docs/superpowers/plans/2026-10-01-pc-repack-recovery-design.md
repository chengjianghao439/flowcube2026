# A3：塑料盒还原整件的跨刷新恢复设计

2026-10-01，本地实现、规格及质量复审完成；真实浏览器故障链路与限定 ID 数据库守恒已验证，迟到详情竞争由实际 Portal 探针独立复验。只针对 PC `plastic_box.repack.<盒ID>`，不替换所有支付 hook，不改后端库存、打印和回执事务。

## 具体变化

点击还原前，先保存当前账号、原盒 ID、完整动作、原请求键、提交时间和原数量参数。刷新或关掉详情后，塑料盒页面仍显示“盒 #A 的原操作待确认”，可以查询原回执或明确用原内容重试。查看 B 盒时不会把 A 的结果当作 B 的结果，也不会清空 B 的草稿。

恢复不自动发送写操作，不自动补打。服务端成功只说明业务成功，不能说明纸张已打印。后端仍是权限、数量守恒和回执的权威来源。

原盒的最新详情可复用现有 `GET /plastic-boxes/:id`（已核对后端路由及仓库范围校验）；如需打开原盒，只补前端 API 封装。不能为了找原盒把列表拉全、猜当前盒，或另建重复详情接口。

## 存储与会话

使用版本化、最小字段的本地记录。允许的载荷只有合法盒 ID 与原 `perBoxQty/boxCount` 或 `items` 数量数组；不保存 Token、口令、商品/客户名称、自由备注或整个表单。存储按当前账号隔离；退出后保留原账号恢复线索，但另一账号不读取或显示其参数。

首发前保存失败：不发送 POST，说明恢复记录保存失败。已发请求的清理失败：保留内存阻断，显示业务结果与“记录尚未清理”，允许再次查询/清理，不偷偷换键。读取失败、未知版本或非法结构：停止自动执行并解释；不删除唯一恢复来源，不依据当前输入重新构造原请求。

同一页面内多个调用点使用同步共享记录，原记录入内存与持久化先于第一次 await，防止同一时刻连点或两份组件各建一笔。每个盒的未确认记录不能被新的参数覆盖；页面能查看同账号的多个盒原操作。

每次查询/发送捕获账号、`sessionGeneration`、原记录身份；回调到达时核对全部身份。旧账号或旧会话响应不更新当前页面、不清掉当前记录、不调用当前草稿回调。请求期间退出不会把原操作交给下一账号。

还需绑定发送时的实际 API 地址：当前 `api/client.ts` 存在网络故障后切换 ERP 候选地址的重试，地址不同可能是另一套数据库。恢复记录除账号外保留规范化的原请求端点身份，不保存认证信息；当前端点不同不得把相同用户 ID/盒 ID 当成原资源。首个试点的发送及回执查询固定原端点，并通过已有请求配置阻止自动改投候选地址。仅扩展相关 API 的可选配置，普通调用和 PDA 默认行为保持，不借机改全局网络回退。换服务器后保留原记录并说明须回到原服务器确认，不能向新服务器重放。

## 结果规则

- `success`：显示服务端原结果，刷新原盒对应缓存；只有安全清理原记录后才允许新操作。
- `failed`：显示服务端明确失败；安全清理后允许新的显式提交。
- `pending/not_found`：继续保留原键和原内容；查不到不能证明没送到。
- 查询报错或回执归属不一致：说明无法确认，保持原记录，禁止本地猜结果。当前回执路由刻意只限定本人账号，业务权限调整后仍允许确认自己的原操作，不能另加执行权限阻断查询。执行权限撤销时禁止新提交与重试；原盒详情因当前范围拒绝时说明无法读取最新详情，服务端已明确的成功/失败仍如实展示，不能改称未知。
- 原内容完整、结构校验通过、当前权限可执行时，用户可点“按原内容重试”；同一键只针对原盒和原参数。恢复数据只是线索，服务端照常验证。
- 第一次提交收到明确 4xx 拒绝沿用现有确定失败原则；原本结果不明的重试收到 4xx 时不能仅据此抹掉旧操作身份，仍应查询原回执确认。

## 验收
