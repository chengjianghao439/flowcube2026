# 财务与会计分批修复 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to execute each approved batch and its verification steps. 本计划已在用户“开始修复”后进入批次A实施；B、C、D仍单独推进，不自动扩展范围。默认在当前会话顺序执行，不派生代理；不推送、不合并、不发布。

**Goal:** 先修复已复现的报表金额方向错误，再校准现有能力说明，最后按明确的会计政策分批设计财务增强。

**Architecture:** 报表读取修复与资金/库存写入规则分开交付。首批只改两处资产项目的符号解释，保留凭证、资金事实、历史金额、接口及账套作用域；后续功能分别先明确来源、冻结时点、期间和历史处理，再给出各自实施计划。

**Tech Stack:** Node 22 / CommonJS、mysql2、node:test / VM、React / TypeScript、Vitest、Vite、真实浏览器与独立 MySQL 测试实例。

## 2. 批次 A：资产负债表金额方向修复

**确定改动范围：**

1. `backend/src/modules/accounting/accounting.ledger.service.js` 的 `getBalanceSheet` 资产分支。
2. `backend/src/modules/accounting/consolidation.service.js` 的 `getConsolidatedBalanceSheet` 资产分支。
3. 新增 `tests/accounting-statement-balances.test.js`，进入根 `test:accounting` 原有 CI 路径。
4. `package.json` 仅追加该测试到既有脚本。
5. `docs/finance-permission-time.md` 记录报表资产使用借方净额、抵减资产以负额展示及证据边界。

**计算规则：** 科目明细账继续使用其正常余额方向；资产负债表资产金额统一使用 `借方累计 − 贷方累计`。因此累计折旧贷方余额10显示为资产项目−10。不按科目编码硬编码1602，不夹成零，不通过倒算权益或修改 balanced 标记掩盖不平。

**验收样例：**

| 资料 | 预期资产 | 预期负债 | 预期权益 | 预期等式 |
| --- | --- | --- | --- | --- |
| 固定资产100，应付100 | 100 | 100 | 0 | 成立 |
| 上述资料再有折旧10 | 90 | 100 | −10 | 成立 |
| 固定资产10，累计折旧12、费用12，应付10 | −2 | 10 | −12 | 成立且不截零 |
| 两账套分别有资产净额90和180 | 汇总270 | 300 | −30 | 成立；单账套仍90/180 |

**保持项：** 不改凭证生成/红冲、结账/补录、损益归期、资金余额、税务计算、库存成本、cash-cents-v1、现有API字段及权限。不执行生产SQL，不改种子或历史分录，不反结账。利润表/税/结转如发现相似问题，先记录并核对三者共同口径，不借此次只读资产修复单边变更。

## 4. 批次 C：费用类别→科目映射，先专项设计

现代码存在 `expense_claim_items.category_id` 和每行金额；资金凭证入口 `buildFundVouchers` 目前只按资金流水整笔借6602。不是简单把一个字段接到一个科目：一张报销单可以有多种费用类别，而资金事实仍只有原一笔。

**设计输入文件：**
- `backend/src/modules/finance/expense-claims.service.js`：明细、付款与历史分精度依据。
- `backend/src/modules/accounting/voucher-engine.js:315–359`：当前资金凭证。
- `backend/src/modules/accounting/accounting.period-completeness.js`：期间来源完整性复核。
- `backend/src/modules/accounting/finance-backfills.service.js`：补录逐笔凭证验证。
- `frontend/src/pages/finance/expense-categories/index.tsx`：类别维护入口。

- [ ] 明确映射按账套作用域配置；业务费用类别当前是公司级事实，不能直接保存一个他账套 account_id 并到处复用。
- [ ] 明确分类冻结时点与映射版本，保证类别改名/停用、更换映射不会偷偷改写已发生报销和已结账凭证。
- [ ] 明确已付款旧报销的兼容策略：保留原解释并可列出待分类项，不无依据重分类，不补造一笔现金流。
- [ ] 明确可选科目范围：对应账套有效、可记账末级费用科目；跨账套、停用、汇总或不存在科目拒绝，不能静默回落6602。
- [ ] 明确费用明细混合分类的凭证分拆、取消/更正及来源指纹规则；与期间完整性、补录验凭证采用同一来源构建结果。
- [ ] 完成设计稿后再确定迁移与DTO；新增迁移用届时最大编号+1、幂等，已执行迁移不改。

**必须通过的业务样例：** 办公60、销售40、实际付款100，应生成借管理费用60、借销售费用40、贷原资金科目100；资金流水仍只有100，账户余额及现金流净额不因分录拆分而重复变化。重跑生成不重复入账；映射变化不越过闭期；历史分类不明时显式待核；补录仍落原批准期间。

本批的当前交付是可核对的政策/来源契约与测试矩阵。未确定冻结与历史规则前，不写映射迁移、不修改凭证引擎。

## 5. 批次 D：分别设计，不作为首批“顺手修”

| 专项 | 建议边界 | 验收的关键问题 |
| --- | --- | --- |
| 会计政策说明 | 先明确适用准则、移动加权平均现状、资金账户科目映射；只支持一种方法时用只读说明，不伪造FIFO切换能力 | 科目与报表政策一致，不能凭注释认定合规 |
| 完整现金流量表 | 先补投资/筹资来源分类能力；历史不能可靠分类的金额显式待核，不能用缺数据当0 | 三类活动与真实资金净变动勾稽，业务日期/补录日期不混淆 |
| 预收预付 | 复用现有汇款余额与继续核销能力，补管理视图和适用准则下的科目/列报规则 | 收钱/付款只记一次，后续核销不重复影响资金，往来身份不串户 |
| 坏账 | 按适用准则区分实际损失核销与减值计提，不为所有账套套同一政策 | 证据、审批、会计期间、核销后追收及坏账与退款的区别 |
| 退货贷项 | 独立生命周期设计，保留现有负余额闸门直到替代方案闭合 | 待生效/生效/抵扣/退款/取消，部分退货、退款额度占用、并发、跨期、幂等 |
| 预占时长 | 先只读超期清单与提醒；自动释放单独决策 | 未派发、已派发、已拣货、续期、实物归还及并发不能混为一个超期状态 |
| 凭证联查 | 优先只读单据↔凭证关联，再另评生成频率 | 原来源/期间/修订链身份正确，两端权限独立核验，不能以可见凭证放开单据 |
| 发票差额 | 先区分数量差、价格差、税额差与舍入差；明确阈值和审批 | 不因差额较小就自动改应付、税额或历史金额 |
| 集团抵消 | 当前先明确只汇总；真正多法人/内部交易抵消单独立项 | 主体范围、内部往来身份、抵消分录、重跑、跨期与审计追溯 |
| 调度与术语 | 日终生成/销售“下达出库”分别处理 | 生成不嵌入业务事务；改文案不改ship API、状态值、权限与请求键 |
| 打印例外 | 不在本轮引入主管跳过箱贴完成的豁免 | 领取/完成回执与实际出纸分层证明，异常恢复另有专项流程 |

“前期差错一律在审批当期处理”和“某资金类型一律计入银行存款可接受”不能仅凭现代码判定。专项政策设计应参照适用准则；例如财政部要求执行企业准则时对重要前期差错按规定追溯重述，小企业准则第八十八条另有未来适用法口径。

参考原文：[财政部关于前期差错的答复](https://www.mof.gov.cn/bd/mhwzzxly/hjs/202303/t20230315_3872858.htm)、[小企业会计准则](https://kjs.mof.gov.cn/zhengcefabu/201111/P020111118325852319878.pdf)。本计划不替企业选择准则，也不以系统自动补录机制代替会计判断。
