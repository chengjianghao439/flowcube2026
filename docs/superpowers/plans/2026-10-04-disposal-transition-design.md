## 已核实的现状

当前用户已采纳推荐业务规则并授权继续本地实施。未完成项的最新规则见[剩余项执行计划](2026-10-04-go-live-remaining-execution.md)及[有限来源与签认实施契约](2026-10-04-disposal-handling-implementation.md)；后者已通过独立静态规格计划门，代码分批状态仍以执行记录为准。本文下方“待决定”保留为当时设计记录，不再重复请求相同授权。

- `backend/src/modules/disposal/disposal.service.js` 的 `dispose` 对促销1、退供应商2、报废3全部调用 `adjustContainerStock(qty<0)`，写库存流水；类型3额外写 `disposal_scrapped`。没有正常销售或采购退货单。
- 处置状态仍为1草稿、2待审批、3已批准、4已处置、5已驳回、6已取消；取消只允许1/2，驳回只允许2，旧3没有真实退出动作。提示“先处置或驳回”不成立。
- 处置写接口未接 `operation_requests`；状态CAS可防第二次扣库，却不能在响应丢失后回放原成功结果。
- 建议参考数量为 ACTIVE 余量减缓存 reserved；`unitValue` 当前是 `MAX(remaining_qty * 成本)`，前端再次乘圈选数量导致错误估值。实际创建单保存的成本另由商品单位成本读取；都不是成交价或采购原价。
- 正常销售 `sale.service.create` 自开事务，末端 `commitFulfillment` 真正提交；只有仓库实际出库才扣容器、消耗预占、累加实发和重算应收。
- 采购退货 `returns-purchase.service` 读取准确采购行、原价、已收及剩余可退量；创建自开事务，服务端覆盖原价；确认生成仓库任务，实发扣容器并冲原应付。
- 普通销售草稿保存、占库改单和执行期改单会删除重建明细；单一 `sale_order_item_id` 不能作为永久关联身份。
- `refund-orders`只接销售来源。补充静态核对`returns-purchase.confirmPR`、`warehouse-tasks.ship.syncPurchaseReturnShipped`、`returns.helpers.adjustPaymentRecordForReturn`及资金登记/核销：现有采购退货只冲减原应付总额，不减少已付额、不登记供应商退款。正式入口未形成供应商退款收入及准确采购退货/原付款关联闭环，不能套用客户退款或余额调整。
- 采购退货锁来源前已有普通查询，锁后预算也普通读。RR等锁后可能读旧快照是**离线推断**，需隔离数据库并发证伪，不能声称已经超退或已经安全。

## 新操作方向

| 员工意图 | 入口与正常事实 | 完成依据 |

| 本单优惠成交 | 建正常销售，员工选择客户、当前商品、数量及成交价，保留手工价留痕 | 正常仓库实际销售出库；保存/审批/占库不等于处置完成 |

## 历史状态与转换边界

| 历史类别 | 推荐处理 | 约束 |
|---|---|---|
| 4已执行，任何类型 | 原单、批准快照、流水和成本只读，标历史直接处置 | 不补正常单、不反推金额、不二次扣库 |
| 1/2含促销或退供应商 | 明示旧语义，沿原取消退出，再主动新建正常业务 | 不静默改为报废、不删除旧行 |
| 3全报废 | 继续原报废执行，补回执保护 | 原审批、范围和库存可用量规则保留 |
| 3含促销/退供应商或混合类型 | 转换或终止必须锁整单、保留批准快照、记录签认 | 谁签认及原批准可否承接子单待决定，不能自行赋权 |
| 5/6终态 | 原样保留 | 不借隐藏菜单改历史 |

旧 `dispose` 是整单执行。部分行已关联正常单后，原整单仍可执行会再次扣库；转换门必须先冻结整张旧单直接执行，再逐行记录去向。混合单报废部分不能顺带执行1/2。**没有合法转换/终止出口时，不能把隐藏状态3按钮称为完整修复。**

## 第二段候选：有限来源关联与原子创建

本段是尚未实施的候选方案，待独立设计复核及下列技术验证门。建议圈选、正常业务导航与改价不创建来源或额度。员工明确保存处理意图时，生成并持久保存逐行`intentUuid`，重挂、未知结果和首次保存重试复用原UUID；数据库唯一约束覆盖UUID，同UUID载荷或创建身份冲突拒绝。商品、仓库、意图与员工确认的基本量Q首版保存后不改。

- 同一持久来源防重、控量；不同UUID的重复圈选尚不防重，不能按商品、数量或观察时间自动合并，也不宣称跨来源库存互斥。Q是处理意图，不是观察值、占库或另一套库存账。
- 旧转换来源以准确旧处置明细ID建立唯一约束，处理版本不能另开同旧行额度。签认未明确前整个转换动作关闭，旧4不生成来源或自动补单。
- 候选`disposal_handling_sources`保存UUID、创建身份/载荷摘要、不可变商品仓库/意图/Q、revision；`disposal_handling_links`保存来源、目标类型/头与实际行ID、商品仓库及分配量快照、合法解除量、持久操作身份和原响应。不级联删除历史。
- DDL明确`target_line_id`是不可变历史身份快照，不对会重建/删行的`sale_order_items/purchase_return_items`加RESTRICT、CASCADE或SET NULL外键；保留目标类型/头ID及准确任务/采购退货行实发证据，缺行按解除证据核实或待核对。来源自身FK可保留，来源/关联历史禁止物理删除；目标头关联也不得级联抹去历史。
- 只新增幂等迁移，索引/外键按名字、列序与引用目标核验；此轮不建空表。

首版目标只支持普通、单仓、单行：一目标单只接一来源，一来源可分到多张目标单；采购退货每张指定准确采购行。成套、多来源合并、关联后增量改单、商品换仓和行重绑另列后续，不新增全销售稳定token。表单明确提示限制，保留输入与取消/归还后的合法解除出口。

保持原正常创建函数和HTTP入口，在原事务内增加可选窄接点；无来源请求不进入新逻辑，不抽通用创建核心。有来源时同一`conn`：当前正常创建与来源权限/范围→来源锁→持久操作重放检查→新操作revision/额度→原正常创建→准确新行→关联与原响应落痕→原回执→原提交。销售仍用`commitFulfillment`一次提交及原提交后通知；采购退货仍用原提交，来源版必须准确`purchaseOrderId/sourceItemId`，不得借pool按单号查来源包装为同事务。

关联创建用明确领域action和持久`operationUuid`，原指纹包含来源及完整载荷；数据库在整个关联领域唯一该UUID，不能仅来源内唯一，相同UUID跨来源并发也拒绝。关联持久保存原操作者、原键、action、摘要和原响应；相同UUID而载荷/action/键不同拒绝。持久重放用当前共享读、不修改关联状态/R，核当前写权和原来源/目标当前范围后返回原响应，revision只闸新操作；已有目标头锁之前不取得关联X锁，避免与正常目标→关联S顺序反向等待。禁止回放普通创建旧回执后再补关联、先HTTP建单再关联、在处置事务调用自行提交的service、先扣库再补单或两个提交冒充原子成功。

处理预算用不可变分配A与已合法解除的未执行量R：`可再分配=Q−Σ(A−R)`。未执行和已执行均占原分配，正常出库不反向锁来源；解除时才核实E并原子写`R=A−E`及终结证据。Q10、分配6、实发2后取消，归还未闭合仍占6；闭合并解除4后占2，可再分配8。销售退货、财务冲回、回执TTL清理不让E回流。精度先核原输入/换算，再以基本量百分量计算，金额精度保持。

| 写入口/锁序 | 首版有限关联契约 |
|---|---|
| 创建：来源→本事务新目标→新关联 | 不锁所有旧目标；原创建一次提交，关联失败整笔回滚 |
| sale update/adjust：原销售头→当前读关联 | 有关联即拒绝删行重建/改量，保留草稿；不取得来源写锁 |
| reserve/release | 保留原预占与释放，固定关联行仓库；不取得来源锁 |
| sale.ship/warehouse.ship、物理归还finalize | 保留原派发、实发、账款及归还；不增加来源锁 |
| sale.cancel/delete | 保留原取消/部分关闭/软删；不立即释放额度；未闭合归还/调整禁止删除，关联历史保留 |
| PR confirm/cancel | 原确认/取消不等于处理完成；准确PR行及实发事实保留；原锁序风险见下 |
| 关联报废 | 原提交/审批/执行；关联后拒绝编辑重建，已批状态3不假造取消出口 |
| 解除：来源→目标头→相关WT按ID→关联记录 | 独立幂等核对写操作；正常操作不反向取得来源写锁 |

解除前员工先走原目标取消；页面显示“已取消，待实物归还/待解除关联”，提供原取消、归还、原结果查询与解除入口。核所有相关任务（含软删历史），取消/调整/容器归还/拆箱未闭合不解除。销售部分关闭只解除未执行部分；PR实发取准确`purchase_return_item_id`的真实出库事实。部分取消后目标行可能被删除，缺行不能自动当E=0；须按准确原关联快照与任务实发历史证明，无法证明保持待核对。Q/A/E/R缺失、负值或不满足`0≤E≤A≤Q、0≤R≤A−E`均fail-closed。解除终结单向且R只按终结事实绝对赋值一次，重放返回原响应、不增量累加或重新开放同关联。头状态、计划量或目标存在不能替代实发/归还证据；不一致保持待核对，不能再建替代目标绕过仍占额度。

进度只读批量推导，保留所有解除历史。TTL仍7天，只有已持久保存原响应的关联操作可长期定位恢复；旧报废state4或缺回执不能状态合成success。本人查询核本人、准确来源/目标归属及当前仓范围，不新增创建/执行/查看权限门；撤写权可核对，不能重试。

**采购退货独立技术验证门：**`cancelPR`先PR→WT；实际出库先WT→库存→PR，存在静态锁序反转风险；锁来源后预算仍普通读也有RR旧快照推断。没有数据库死锁、超退或安全结论。采购退货关联进入开发前需单独审阅准确PR提前锁并重核WT归属、锁后当前预算读取等窄方案，再做隔离并发证伪；不能借R10改全PR主链或凭旧注释称安全。普通销售有限关联与PR候选分别验收。

## 状态呈现、价格、权限与回执

新 `handlingProgress` 独立于旧审批状态：待关联、已关联待执行、部分执行、已完成、目标取消待解除、待核对。“已终止/部分执行后终止”只作为待签认历史动作的预留呈现，授权与技术契约确定前不开放；首版不另增新来源终止动作。改价通过不是完成；缺关联/错身份/未知回执显式待核对。来源销售退货显示逆向事实，不自动释放再分配额度。

- 本单优惠沿现有正常手工成交价、等级价参考、价格事件/低进价预警；这些不是独立优惠审批。如需要额外阈值审批另待决定。
- 采购退货价格只认准确原采购行。已付金额保护、应付锁、对账刷新和打回财务确认保留：如总应付100、已付80，退30在确认预判及实发锁下均被拒，退20可满足该保护（是否实际可退仍依原量/库存等规则）。供应商付款和客户收款核销均只增加已付额，余额调整没有采购关联且不解除保护；不能据此声称供应商退款完成，也不开放负数登记绕过。以上是静态代码结论，无运行验证。
- 销售与退货的创建/占库/确认/执行/改单/取消各走原权限；处置查看不能借关联返回客户价、采购价、应付。摘要/链接后端先核原查看与完整范围。
- 自批继续查 `allow_self_approve`，不按角色1放宽；资金期间与共享/排他账套锁原样保留；存货报废不冒用固定资产 `ASSET_DISPOSAL`。
- 保存原操作者/服务器/来源revision/意图/目标/完整载荷/稳定键。超时、断网、5xx、重挂查原回执；pending/not_found/查询失败保持待核对，原载荷原键重试，不换键、不按当前库存猜成功。
- `operation_requests` 默认7天TTL，长期防双开依赖持久关联。创建指纹允许同键不同载荷不同作用域，故未知结果必须冻结载荷。回执清理后通过持久原身份定位目标。重放/回执查询重新核撤权后的来源、目标范围，需补窄领域guard。

## 可先独立实施的部分与需要决定的部分

可确定的第一段：建议单位成本/参考量文案纠正；新独立单前后端及service只接报废；权限内提供正常业务入口并保护草稿；报废稳定回执；历史分类和拒绝契约。导航交接只称入口，不称持久关联。第二段采用上述有限来源/额度候选，在全部写入口约束、锁序、迁移与并发方案审阅后实施，不提前新增空表或泛化创建核心。

### 独立设计复核后的收窄

- 防止新增旧语义状态3不仅是限制create。`disposal.submit` 与 `approve` 锁整单后核明细，含1/2的旧草稿/待审不能继续提交/批准；旧草稿/待审仍保留原cancel，待审仍可按原自批规则reject。前端必须拆分canApprove/canReject，不能用一个布尔量把合法驳回和取消一起隐藏。
- 已批全报废继续原dispose与新增回执。已批含1/2只明确标待签认，转换授权不开放；“新路径纠偏”与“06b完整闭合”分别报告，不能宣称旧单出口完成。
- 原泛化方案未覆盖普通销售create/update/adjust/reserve/cancel/delete及物理归还finalize。现候选改为固定关联行与禁止重建/增量操作，正常写入口不反向锁来源，独立解除核真实归还；采购来源不借pool读取，销售原提交后通知保持。该限制及所有接点仍须实际代码验收，不是已实现稳定token。
- Q来自明确保存的不可变处理意图；已补创建UUID、持久唯一身份及原响应。同一来源防重复，不同UUID圈选仍不自动防重；不得把“同来源”扩大为“全仓同商品”保证。
- 原多来源同一行的实发分摊问题通过首版“一目标普通单行一来源”排除；取消后的实际E/合法R保留，软删不级联关联历史。任意重绑和多来源分摊后置。
- 参考估值可能从avg_cost/cost_price回退sale_price，应显示依据，不称纯成本。建议数量是扣预占后的参考量，当前总估值是全部ACTIVE库存；修正单位值仍须分别标在库量、参考量及对应估值，历史unit_value/total_value不重算。
- 第一段原回执边界已按`system.routes.js`核实：查询本人原操作不新增查看或执行权限门，但必须核准确处置资源及当前仓范围；写重放、恢复重试仍受原执行权限控制。旧state4或TTL后缺回执不能凭单据状态/金额合成成功，也不能再次执行。
