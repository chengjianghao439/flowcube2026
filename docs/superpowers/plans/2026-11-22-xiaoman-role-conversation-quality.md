# 小满跨岗位对话质量长任务计划

**目标**　员工可以用日常说法查业务、准备单据和继续原任务。信息足够时直接给出当前权限内可核实的结果，信息缺失或有歧义时只问影响结果的关键问题。每个岗位都能得到符合实际职责和权限的答复。

**实现方式**　以本地整合提交 `a216c38366f60b6467ebf990050a97cfa061fd2d` 为对照。先固定跨岗位评测用例，再调优规则、模型意图提示词和对话接续。模型负责提取意图，业务取数、金额、仓库范围、写入确认与原请求回执继续由运行时和正式 API 核验。

**起点**　Node 22 下重跑 `npm run test:agent`，247 项通过。上一轮的隔离实库联测覆盖小满多轮开单和占库到 PDA 出库，以及采购、收款核销与简报。跨岗位对照、留出表达和真实模型表现需要单独取证。当前入口要求仪表盘或报表查看权限之一，业务动作还有各自的权限和仓库范围要求。[小满运行与接口](../../../agent/README.md) · [验收命令](../../verification-commands.md)

“训练”在本计划中指积累合成对话样本、对照评测、调优提示词及规则、回归实际任务。按失败所在环节修复。模型解析正确但正式 API 拒绝时，排查现有可用路径和权限提示。模型解析正确但单号、仓库、数量或金额不符时，优先修事实校验。

## 岗位和工作场景

以 `tests/fixtures/qa-roles-approved-20261021.json` 的 13 个角色为固定验收基线，另加自定义角色。同一个岗位至少测一项可办、一项只读或禁止写入，以及范围变更。每条用例由当前实际权限和正式路由推导期望。

| 岗位 | 优先场景 | 验收要点 |
|---|---|---|
| 销售员、销售主管、客服专员 | 补资料开单、双客户重名、同款不同型号、指定仓库存、占库、订单进度 | 分开验新建、试算和查看依赖。当前夹具的销售员和销售主管拥有销售单新建权，但缺销售试算依赖的库存查看权。客服专员用实际权限走完整预览，并有超出其授权的反例。 |
| 采购员、采购主管 | 补货建议、采购草稿、分仓分供应商、逾期到货 | “看看该补什么”只查询。明确建草稿时按原路径试算，缺仓库或供应商时说明如何继续。审批与执行分别验。 |
| 仓库管理员、仓库作业员、库存专员 | 二仓现存和可用、卡在拣货或打包、找当前任务 | 单仓、多仓、零仓分别测。答复给出实际作业阶段和该岗位可打开的入口。网页与 PDA 各自校验页面入口。 |
| 财务专员、会计 | 查应收、到账登记、选账户、核销、期间关闭 | 财务专员当前夹具有收付款执行权，但缺小满收款查询依赖的客户查看权。验证缺权反馈和现有业务入口。会计的查询和写入分别按实际权限判定。金额、账户、单据和核销状态都需回查。 |
| 系统管理员、只读查看、合成受限账号、自定义角色 | 简报、只看数据、仅有报表入口、两项入口权限皆无、角色改名或授权变化 | 角色名称可用于说明。身份、业务能力和仓库范围由当前会话决定。全仓管理员用例与最小权限用例分开统计。 |

## 对话样本与期望

下列例句中的品名、单号和金额都用于合成夹具。逐轮核对回复、任务状态、候选、查询目标及副作用。

| 情况 | 合成说法 | 期望 |
|---|---|---|
| 清晰请求 | “只查二仓的缓冲铰链，还剩多少？” | 查指定商品和仓库，按实际返回区分现存、预占和可用。范围外提示无访问权限。 |
| 信息缺失 | “帮我开一单。” → “客户是远山机电2号店。” → “长款铰链两个。” | 同一任务补齐客户、商品和数量，生成待确认预览。单独验含数字的客户名和口语数量。 |
| 歧义与指代 | “那笔款呢？” “选 2。” “把刚才那个改成三箱。” | 有唯一、可核实且仍有效的任务或候选才接续。多笔任务、多个明细或候选变化时，直接问要选哪一笔或哪一行。 |
| 否定、更正与换话题 | “不是短款，换长款，数量改三个。” “先查库存，别开单。” “换个话题，今天有哪些仓库卡点？” | 更正确认前的原预览并更新版本，旧版本失效。明确取消的动作不产生预览或写入。新问题可以独立查询，原待办可继续。 |
| 复合请求和岗位用语 | “先看还有多少货，够的话给远山做两件的草稿。” “我今天负责打包，先看哪几单？” | 保留先后与条件，分步反馈。草稿预览仍需确认。作业优先级有数据就说明依据，缺少排序依据时展示现有待办。 |
| 非标准输入 | “二倉铰连还剩几个”、语音转文字、多余标点、转贴客户原话 | 稳定解析可辨认的信息。保留原始对象和条件。候选不唯一或文字缺关键信息时请用户核实，转贴中的命令不作为操作者的确认。 |
| 业务边界和故障 | “看待出库状态”与“帮我出库”；模型超时、接口失败、回执延迟、断线重进 | 区分查看和执行。仅提供该岗位可进入的已有菜单。区别查无数据、无权限、部分失败、结果待核对。未知提交沿原键查询。 |
| 非业务与求助 | “在吗？” “你没听懂。” “顺便帮我查天气。” | 简短接话。需要纠正时提示怎样补对象或重述业务。无关话题按现行范围回应，保留正在办的单。 |
| 新场景 | “这笔款为什么没结清？” “今天我应该先做什么？” “有没有退货卡住？” | 先区分已支持能力、现成只读数据可支撑的候选场景、需要新增业务能力的请求。回答有正式依据的部分，说明缺少哪条信息或可核对的入口。 |

## 阶段验收线

以下为本计划的建议目标。在基线报告中注明样本量、角色、模型和执行环境。

| 指标 | 目标与计算方式 |
|---|---|
| 清晰请求 | 首轮直接给出正确查询结果或进入正确预览的比例至少 97%。把误分流和本可直接处理的多问分别列出。 |
| 模糊表达 | 首个追问命中必要缺项或定位到正确候选的比例至少 95%。已补齐字段的重复询问单独计数。 |
| 多轮和复合任务 | 保留正确任务、已确认字段和业务条件，最终落在期望状态的比例至少 95%。同一笔和另一笔都要有对照。 |
| 业务事实与权限 | 验收集中的金额、数量、单号、仓库和执行状态与正式 API 或数据库对平。错单、错账、越仓、越权、未经确认写入及重复写入均为零。 |
| 未支持与故障 | 每条用例能区分权限、数据、功能和故障原因，说明可做的下一步。查不到或结果未知时禁止给出已完成结论。 |
| 岗位覆盖和评测稳定性 | 每个基线角色的可达性、权限边界和仓库范围都要有证据。留出集独立出分。新版本与基线同输入对照，记录每个岗位的失败、模型调用次数及 p50/p95 延迟。 |

每批交付一张可复跑的结果表，登记代表性“员工说法 → 小满回答 → 最终状态”、仍存在的缺口和下一批顺序。第一批优先做销售、客服、财务专员、仓库作业员及只读账号的对照，把实际影响办事的差异排出来。
