## 2. 始终保留的设计与投入边界

1. 商品编码、供应商型号、型号、名称、颜色保持独立，不能为缩窄表格合并身份列。
2. 库存事实仍来自 ACTIVE 容器余量；缓存经既有引擎同步。拆分、放货和还原整件保持数量守恒及真实来源。
3. 录入单位与基本单位分开，后端负责权威换算；数量两位小数和整数商品政策保留，金额及单价精度不跟着改。
4. 现货、有效预占、预计供应、计划/申请/采购草稿覆盖分开解释。暂定覆盖不能成为客户交付承诺。
5. 分批发货保留已发事实；取消和改单涉及已搬动物料时保持实物归还闭环。
6. 收到钱、核销账款、会计记录、税票分别保持原业务含义；不为减少入口合并资金事实。
7. 业务事务、打印入队、物理打印、承运商取号和实际出库分别表达。补打不能重做库存或账款。
8. 请求键和回执绑定原操作；查不到不等于确定失败，不自动重放关键写入。
9. 保留单体架构与当前框架。不因文件长或技术外观开展全仓重构。
10. 保留现有发布和迁移管理。任何迁移另行明确范围、兼容及回退；首批工作包默认不新增迁移。

**当前不进入开发队列：** 微服务、多租户改造、额外消息平台、通用工作流/仓库路线引擎、离线库存或财务写入、自动采购、自动交期承诺、整体重写，以及尚无实际需求依据的生产/装配系统。

### 三个独立切片

- [x] **A1a 分拣格交接（本地实现与验收）：** 从原任务进入已有分配弹窗/页面，自动定位任务与仓库。有处理权限显示“分配分拣格”；没有权限显示需要主管处理及已有负责人（如果有），不凭空指定某个人。真实员工及生产验收另记。

- [x] **A1c 逆向等待（本地实现与验收）：** 销售取消/改单已要求实物处理时，定位已有逆向任务/卡片；已发货或已搬动的事实不因关闭事项消失。实际 PDA 硬件与员工验收另记。

### 必须保持

不新增通用工单、不改业务状态、不自动占库或采购、不代员工承诺交期、不提高权限。处理期限与业务交期分开，自动刷新不得覆盖人工设置。清单投影不得在 GET 中写事项或产生逐行 N+1 查询。

### 验收情景

1. 同仓待分配任务：主管进入正确任务；普通操作员理解下一步但不能绕过权限分配。
2. 无授权仓库：看不到该仓单据/动作；直接访问目标也被既有后端拒绝。
3. 点入口前任务已分配、取消或进入新阶段：显示最新结果，不执行过时动作。
4. 供应总量够但到货偏晚、到货未知、部分可发：三种解释和动作各自正确。
5. 逆向处理未完成：不能只关闭事项当作货已归还；完成后原单和待办一致。
6. 返回待办保留筛选、滚动和原工作区；别单已有草稿不被覆盖。

收益验证：真实员工能在不追加口头说明的情况下找到准确对象及处理岗位；记录改善前后的查找、求助和完成步骤。

### 恢复契约与步骤

- [x] 首发前记录当前账号归属、原资源 ID、完整 action、稳定 requestKey、创建时间及允许保存的原提交字段。只保存恢复必要信息，不含口令、Token、客户名称、自由备注或整个页面对象。
- [x] 对还原整件试点，保存原 `boxId` 和原数量参数；客户端存储只是恢复线索，不作为权限或库存事实。
- [x] 先完成记录保存再发送。首发前持久化不可用时，明确阻止本试点的新提交；已发请求的保存/清理失败仍保留内存阻断，不伪装已确认。
- [x] 重载后恢复“原操作待确认”，只查询，不自动执行写入或补打。恢复不得套用当前正在查看的盒。
- [x] `success`：呈现原结果，刷新原对象，随后清理记录；`failed`：告知明确失败，再允许新的显式提交；`pending`/`not_found`：保留原身份。
- [x] 原内容完整且权限有效时，显式重试用原键和原内容；原内容缺失或不可信时只提供原回执确认，不能用当前输入重建原请求。
- [x] 退出/换账号后隔离恢复记录。脱敏的未归属身份只可用于受后端权限保护的确认，不把前一用户的数量、标签或内容显示给新用户；不自动认领为新用户。
- [x] 服务端回执不可用或归属不一致时说明原因，禁止本地猜成功/失败。沿用本人回执查询无需业务执行权限的目的；撤权禁止新提交/重试，详情拒绝与服务端已确认结果分别解释。记录清除失败要能再次确认，不换键制造新操作。
- [x] 旧版本存储只能做保守兼容；未知结构不执行重放、不静默移除唯一恢复来源。

### 故障验收矩阵

1. 服务端完成、响应被代理丢弃：页面待确认；刷新后查到原结果，容器数量、库存及打印入队各仅一次。
2. 请求未送达：查不到保持原键；按原内容显式重试只执行一次。
3. 服务端仍处理：查询 pending 或暂时 not_found，不建立新操作。
4. 明确失败：恢复可解释的失败状态，不声称成功；新提交仍经业务校验。
5. 当前查看 B 盒，原提交针对 A 盒：确认结果仅更新 A，不关闭/覆盖 B 的新输入。
6. 退出、换账号、撤销仓库权限、旧异步响应返回：不泄露或恢复到错误账号。
7. 存储写入/读取/清理失败与旧记录：不自动重放、不静默放开新的重复写入。
8. 物理打印结果仍独立：确认业务成功不等于纸张已经打出。

**推广条件：** 首个入口上述矩阵通过且员工能恢复后，逐个评估 PC 收付款、核销等入口；财务字段、补录与期间规则须另写子计划。不能批量替换全部 hook，也不能直接复制 PDA UI。

### C2 成套配件

**状态：用户已决定要做。性质：销售、库存、仓库、售后和金额的业务扩展。**

**目标：** 销售按“一套”选商品和报价；系统保留套组成，仓库按实际组件拣货、分拣、复核、装箱和出库，库存与成本仍来自组件。订单、缺货、采购建议及退货都能追溯到同一套组成。

#### 建议的最小方案与保留边界

1. 首版支持固定套组成：套商品、每套组件与基本单位数量、启用状态、版本。套数默认整数；各组件遵守自己的数量政策。首版禁止循环套件/套中套，避免展开失控。
2. 销售显示套主行和可展开组件；订单保存当时组成与价格分摊快照。套定义后来改价、改组成或停用，不追改已保存订单。
3. 按组件库存执行，不给虚拟套主行造容器或复制一份库存。已经独立存货的成套实物继续是普通 SKU；不能因为名字带“套”就自动转成虚拟套。
4. 可成套数量按同仓全部组件可用量共同约束；相同组件在多个套/普通行重复出现时，先汇总需求再占库。完整组件够几套才显示可发几套，不把单个组件够当整套够。
5. 建议首版按整套分批履约，剩余套待补占；不自动将缺件套拆成部分组件发货。每次出库核对本批套组成闭合，实际拣货仍按组件、批次和容器。装箱保持现有每箱商品约束，不能为套件强制多品混装。
6. 价格主行为一套的成交价；组件分摊用于已发应收、退货、毛利和来源解释。建议按下单时组件参考售价比例分摊；总参考价为零时必须显式配置合法权重。保存依据和结果，按系统现有金额精度处理尾差，组件合计必须等于套主行金额，不同时把父行和子行计两遍。整单折扣/税额继续沿用既有净额规则并核对归属。
7. 成本使用实际组件出库的现有成本快照，不以今日组件价格替代历史成本。采购与补货按组件净需求，不给虚拟套生成一份重复采购需求。
8. 退货支持整套及明确选择组件的部分退货，按原订单组件归属与已发可退量限制；金额按原分摊快照，成本按原组件快照。不能退一个组件却退整套价，或把同商品别套的组件份额算过来。
9. 首版不自动替代组件。调整组成只能通过明确版本/合法改单路径，已发组成与历史金额保留；跨仓凑套、自由拆套发货、自动装配以后单独决定，不随首版引入。
10. 不引入生产工单、工时、制造成本或完整 MRP；只完成经销业务的按套销售和组件履约。

**设计时只需确认会改变结果的业务细节：** 用实际套样例核对以上建议，重点是固定组成、按套报价、缺件时是否只按整套发、组件退货价格及替代件。方向已决定，不再次问是否要做套件。若实际做法不同，应把具体差异写成可审阅规则，再实施。

#### 必须验收

- 一套含多个商品，某组件有包装换算；整数/两位数量政策均按组件检查。
- 两个套与普通商品共享同一组件，不超占、不重复采购；两人并发开单仍只使用真实可用组件量。
- 只够部分完整套、单组件缺货、组件到货日期不同；可发套数及预计完整交付日期准确，未知日期不猜。
- 套组成改版、组件停用、客户改价，不改变旧单快照；普通成套 SKU 和虚拟套不会双计库存。
- 原组成缺件或替代件未确认时拒绝不完整出库；不能用错误任务/套的同商品扫码凑闭合。
- 套价与组件参考价不相等、参考价全零、折扣及分摊尾差；收入、成本、报表不双计。
- 整套退、单组件退、部分退后再退、取消/改单、响应丢失重放；原可退量、原价与原成本可解释。
- 旧订单/旧接口保持原行为；三岗位都能说明“卖了几套、实发哪些件、退回哪些件、金额怎么算”。

### C4 持续收货、边收边上架

**状态：用户已决定要做。性质：现有收货状态、库存兑现、完结与财务边界的变化。**

**目标：** 同一收货单尚在继续收货时，已收到并生成的待上架容器可以扫码上架，成为可用实物；之后仍可继续收其他货，不要求先收齐或短装结案才能上架。

#### 当前事实与建议边界

- 当前 `putaway.from=[3]`，PDA 也按 `status < 3` 阻止上架；这是现行规则，不是本计划已经改掉的行为。
- 当前完结要求收齐或短装关闭、全部实收已上架，随后自动结算；应付只汇总 `audit_status=1` 的实际上架量。
- 当前预计采购按采购量减累计上架量计算，未完结收货的已上架量也会被扣除；新方案必须沿用并验证，不能同时计入 ACTIVE 和预计供应。

**建议首版把仓库效率与财务时点分开：** 收货中允许已收容器上架及使用；整单“收货结束且实收全部上架”才完结并按实收统一结算。每箱上架即时增加应付不作为本次默认方案。如果业务要求逐次确认应付，需要在具体设计里明确期间、付款确认与重复结算政策，不能顺手放开。

#### 状态与员工操作

1. 保留“待收货、收货中、待上架、已完成、已取消”基础状态含义，不新增每一种数量组合的枚举。“收货中”可以同时有已收未上架和已上架数量。
2. 收货中/待上架允许上架**本任务、本仓、有效待上架容器**；不允许凭订单数量直接造库存，不允许未收货上架。待收货阶段仍先登记收货。
3. PDA 收货列表/详情同时给出继续收货与上架已收货入口，按实际待上架量说明；扫码条码、任务归属、库位和设备仓校验保持。当前没有待上架货时显示原因及下一步，不虚构完成。
4. 收货中把本次已收全部上架后，任务仍可继续收货，不自动结案；没有待上架容器不等于整单已完成。
5. 全部计划量收齐时按既有规则结束收货；短装仍由 ERP 显式“结束收货”并记录原因。关闭后不能继续向该收货单登记新到货，剩余采购是否继续收仍按原采购边界处理。
6. 关闭时若此前已把实收全部上架，必须在同一事务检查并立即完结/结算，不能等待下一次不存在的上架动作。关闭时仍有待上架货则完成最后上架后完结。
7. 展示应到、已收、未收、已上架、待上架及“收货未结束/待结算”。已上架可用与应付未生成分别说明，采购、销售和财务不能误认整单已经结束。

#### 事务与上下游

- [ ] 在现有任务锁和权威状态检查中扩大已收容器的上架许可，保留采购→库存维度→容器等既有加锁约束；不只改前端按钮或 `from` 数组。
- [ ] 一次上架在同一事务完成容器状态、库位、明细上架量、库存缓存、预计绑定兑现与原回执，提交后刷新相关履约信息。
- [ ] 同一任务同时收货/上架/关闭时，以当前锁内事实决定动作；关闭不能漏掉正在完成的实收，重复扫码和同键重放不重复加量。
- [ ] 抽取/复用单一完结检查给上架与结束收货入口调用。收货仍开放时不完结；关闭且全部上架时只结算一次，采购退货冲减和已付事实不被覆盖。

- [ ] 应付、采购完成、月结及会计核对继续沿既有结算事实；已上架未结算量在原单可解释。跨期、关闭期间冲突必须按现有财务规则拒绝或进入合法补录，不能静默换日期。
