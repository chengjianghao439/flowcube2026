# 授信审批一致性（待发布）

基线为 `bd011c1db9a9c14a08fc786e7836ed5f68596eac` / `v0.13.6`。本分支仅修复授信申请、审批和消费批准的业务逻辑，不实施角色权限提案，不合并、部署或创建发布标签。用户安排独立验收；作者自测不代表独立验收通过。

## 超额必须审批

占库取消 `confirmCreditOverride` 的授权路径，HTTP 请求带旧标记会被拒绝。管理员及仍存有 `sale.credit.override` 的角色都不能直接放行。出库复用与占库同一 `hasApprovedOverride` 校验，仓管只需原有作业权限和范围，无须旧直放权。旧权限常量/种子保持不变，其业务旁路已移除；角色默认授权的清理仍等用户确认。

申请创建按销售单行锁串行化，排除本单后计算已用授信，避免已预占订单重复计算自身敞口。新增 294 的 `sale_credit_approval_proofs` 冻结客户、订单、折扣/金额、商业版本以及全部明细身份、商品、单位、数量、单价和仓库的 SHA-256。占库、审批和出库均检查当前内容；占库/拣货/部分发运进度不属于商业内容，不使同一批准自动失效。消费批准还核客户、额度、整单净额、获批超额范围、申请/审批终态、销售单状态及可选截止时间。

没有凭空设定统一有效天数：创建 API 可传 `expiresAt`；缺省 NULL 表示未设置固定截止时间，其他所有绑定仍生效。过期、取消、改单或客户/额度变化不匹配的申请不能继续消费。显式取消已批准申请只阻止后续消费，不回滚已发生的库存或资金事实。

294 不回填历史批准的内容证明。缺少原始商业版本证明的旧批准不能被当前内容自动“补证”；原记录保留，可按当前销售单直接重新申请，不要求先取消历史批准。用户独立验收已反馈正式库存在此类旧批准，本轮没有读取正式库或核对数量。本分支没有删除或重写历史业务数据。

## 当前资格、自批与审计

沿用既有业务权限码：授信审批仍要求 `sale.credit.override.apply`、`sale.credit.override.view` 和 `approval.task.view`，再同时要求当前节点快照、有效账号及销售单整单仓库范围。管理员也必须命中授信节点，不能代批或跳级。待办、列表按钮和节点解析使用相同的业务权限、自批与范围条件；过期、无证明或已结束原单不提供审批入口。执行时再次检查内容证明等事务前提，拒绝读取后发生的业务变化。

`allow_self_approve` 保留，修改开关的授权未改。它只解除“申请人与审批人相同”的限制，不授予业务权限、节点资格或仓库范围，也不自动审批。执行时在事务中当前读取并锁定用户设置；待审期间关闭立即阻止后续自批，已完成节点和批准不因此撤销。自行批准/驳回必须说明原因。

每次审批/驳回需 `X-Request-Key` 和 `expectedTaskId`。锁序为销售单→申请→当前操作者→审批实例/节点。定位申请的普通读可能建立旧 RR 视图，因此拿到订单锁后使用 `FOR SHARE` 当前读取实例和节点，再核预期节点。相同请求键回放原结果，不推进下一节点；不同请求键竞争同一节点，后到者收到节点冲突。原请求正文不一致也不能冒充原成功。

`sale_credit_approval_actions` 在同一事务内记录申请、销售单、申请人、实际审批人/姓名、实例、节点、动作、原因、时间、自批标识，以及当时的用户开关、角色授权依据、所需/持有权限、节点和仓库范围。节点唯一索引防止重复业务审计。出库仍使用既有资源回执和库存事务，不重建库存。

出库在销售单锁后、任何 RR 一致读前取得客户锁，避免等待期间其他订单刚提交的授信占用被旧视图漏读。预占、出库、审批取消沿原销售单锁协调，不通过扩大仓管权限解决批准后出库。

## 2026-10-20 独立验收反馈

问题1为缺陷，已批准不等于当前仍有效。创建在销售单行锁内区分草稿/待审批、有效批准和失效批准：前两类继续防重复，失效批准不阻塞新的草稿。有效性共用当前内容、客户、额度、金额/敞口、截止时间、原始证明及审批完成记录；占库/出库失败返回 CREDIT_APPROVAL_INVALID、明确原因和下一步。无批准时仍用 CREDIT_LIMIT_EXCEEDED。列表、详情和导出显示“已批准（已失效）”及原因；状态3仍表示原历史审批成功，未改原单、实例、节点、审核人/理由/时间或逐节点审计。

点击失效行“重新申请”会绑定原销售单，可包含部分占库/执行中单；显示当前金额和客户，填写新原因后创建新草稿，并定位到新单以供用户“提交”。不自动提交或批准。用户仍须原申请权限；审批资格、自批开关、节点与仓范围不变。客户端将该409识别为明确未执行，避免保留未知结果锁；不放宽其它409或网络未知结果。现有草稿或待审批导致的并发冲突仍提示查看原申请，保留填写内容。

新申请是持久的替代事实：较旧批准即使其后条件又匹配，也不能越过更新的申请恢复放行；更新单取消/驳回/软删不复活旧批准。无需改已有迁移或补写旧证明。批准列表补充效力时固定批量读取元数据、订单、明细和按同一A+B来源计算的用信，不按行发SQL；精确四位金额在排除本单后才转为Number。
