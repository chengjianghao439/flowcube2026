## 1. 用户已确认的规则【已确认】

1. **每盒只放一种商品**；**同商品不同批次允许混放**。
2. 散件还原整件时，**由人工填写每箱数量**。
3. **取货标签贴在取出的货上**，并支持后续作业，**不跳过状态与权限**。
4. 放货时把**整件来源的全部实存**放进盒，**不是**按订单量只放 150。
5. **不需要管理保质期**（2026-09-29 确认，**定为正式规则**）：塑料盒范围是**普通散件**——每盒一种商品、同商品可混批、**无效期业务**；因此**不做逻辑 FIFO、不伪造每批剩余**；混合批次标识**不得冒充单一批次**，只提供**来源贡献与可能来源集合**，**不声称取出件的确切批次**。
6. **取货标签第一期下游为「分拣、复核、装箱」三项**（2026-09-29 确认，**定为正式规则**）：三项都必须接**真实状态推进链**与**真实扫码复核**，不跳过状态与权限（具体链条见计划文档 2026-09-29 审查修订 R1/R2）。

## 3. 待设计的能力

### 3.1 放货：扫来源 `I` → 扫指定 `B`，默认**全部**放入

- 交互：扫整件来源码（`I`）→ 扫目标盒码（`B`）→ **默认数量 = 来源当前实存**（不是订单量）。
- 校验：**同商品**；**同仓库**；目标须为 `B` 盒（**不要求空盒**，见 §3.2）。
- **总数守恒**：来源 + 目标合计不变（同一事务内两步更新）。
- **来源留历史、不硬删**：来源容器按现有「扣空转态」处理并保留行与流水，**不做物理删除**。
- **来源可为多件整件【已核对】**：入库建容器**未传 prefix/type**（`backend/src/modules/inbound-tasks/inbound-tasks.command.js:540`），`createContainer` **默认 `I` / `type=1`**（`containerEngine.js:124`）；`isIndividualContainer` **同时**要求 `type=1` **与** `initial_qty=1`（`containerEngine.js:909`）。⇒「一件一码」只针对 `initial_qty=1`，**`I` 且 `initial_qty>1` 可作拆分源**。**先前「未读入库代码、仅按 initial_qty 判定」的失实记录作废。**

### 3.2 混批：**同商品不同批次一律可混**，只按真到期事实设闸

- **放行判定只认真到期事实 `exp_date`**【已核实】：`batch_no` / `mfg_date` **不是保质期依据**，`batch_managed` 也不等同。**两个来源 `batch_no` 不同、且 `exp_date` 均为 `NULL` 时必须允许混放**。
- **设闸的真正理由**【已核实】：一旦盒上 `exp_date` 不再代表整盒，4 处既有逻辑会读错——`containerEngine.js:281-285`、`:367-371`、`warehouse-tasks.pick.js:194-207` 的 FEFO 排序，以及 `inventory.aging.js:122-165` 的效期告警。**所以只对 `exp_date` 设闸，不对批次设闸。**
- **混合标识**【建议】：混批后盒置 `is_mixed_batch=1` 并**清空 `batch_no`/`mfg_date`**——盒上那个批次已不代表整盒，**不得继续冒充单一批次**；原批次靠来源历史查。
- **来源贡献可查、不需要新表**【已核实】：`logContainerSplit`（`containerEngine.js:935`）已把 `log_source_ref_id=来源容器ID` 写进 `inventory_logs`，且 `container_id` 为 target 视角。只需给 `getContainerLogs`（`inventory.service.js:486`）的 `SELECT`/返回**加两个字段**。
- **不按批次伪造剩余**：本范围**无效期业务**，**不做逻辑 FIFO、不按批次分摊「每批还剩多少」**；只提供**来源贡献与可能来源集合**，**不声称取出件的确切批次**。
- **消费者依赖**【已核实】：盘点、调拨、报表、补打、退回**均不读/不校验批次**；只有 `exp_date` 相关路径依赖（详见计划 `docs/superpowers/plans/2026-09-29-plastic-box-workflow.md` §0.1）。

### 3.3 散件还原整件：人工填**每箱数量**与**箱数**，生成**独立整件库存码**

- 交互：在盒上操作「还原整件」→ **人工逐箱填 `qty` 清单**；**箱数作为「同 `qty` 批量」快捷输入**（每箱等量时一次填箱数即可）→ 生成**独立的整件库存码**（`I`）。
- **防合计超盒余量**：填写的各箱合计**不得超过盒内余量**。
- **余量留盒是本方案默认**：只装走填写的量，**剩余留在盒内**（**不再作为待业务确认的问题**，见 §8）。
- 保留**盒内余量**与**来源信息**（至少记录从哪只盒、多少量还原）。
- **单件 `qty=1` 边界（与 §8 一致，收敛）**：**每次取出都出标签**；既有「`I` / `type=1` + `initial_qty=1` 即个体」的限制**保持**（`containerEngine.js:909`），**不因本功能改全局规则**。
- 【建议】生成的整件码写入**来源盒 ID**（`sourceRefType='plastic_box_repack'` + `sourceRefId=盒id`），便于追溯「从哪只盒来的」；**盒为混批（`is_mixed_batch=1`）时新码不带单一批次**（`batch_no`/`mfg_date` 置空），**不冒充单一批次**；盒为单批时才继承。

### 3.4 销售扫 `B` 生成**独立取货标签**（与任务/本次取货绑定）

- 数量按**需求量与盒内可用量**共同确认（取 `min(需求 − 已拣, 盒内可用)`，与现有前端口径一致：`frontend/src/pages/pda/task.tsx:230,243`）。
- 标签内容：**销售单号 / 商品 / 数量 / 条码**；标签**与本次取货（任务）绑定**（同一任务、同一物）。
- **身份分离**（核心）：取出的 150 与盒里剩的 50 **是两笔不同身份**——盒剩 50 仍在 `B` 上；取出的 150 落到与本任务绑定的记录上。

## 4. 推荐模型（第 4 点核心：最小复用 vs 另建份额）

| | **方案 A（推荐）** | 方案 B（不推荐） |
|---|---|---|
| 做法 | 从 `B` **转 150 到本任务锁定的独立库存记录**；`B` 剩 50 | 另建「拣货份额」表记录「从某盒取 150」 |
| 编号 | 【建议】新码**沿用 `I` 前缀**、`container_type=1`；建码 **`sourceType=SOURCE_TYPE.CONTAINER_SPLIT`**（既定同仓守恒来源，已含于 `DIRECT_ACTIVE_SOURCE_TYPES`，`containerEngine.js:33,48-51`），另写 **`sourceRefType='plastic_box_pick'` + `sourceRefId=来源 B 的真实容器 ID`**，并随盒的 **`is_mixed_batch`** 决定是否带单一批次；**原 `B` 码只留来源审计、出库时不再锁它**。**不新增 `DIRECT_ACTIVE` 白名单、不绕「待上架收货」流程**；打印**新「取货标签」用途**，**不得用现有库存标签假充**（现有类型见 `print-jobs.label-command.js:171,251,303,357,428,472`） | 不产生新码，靠分配表关联 |
| 总实存 | **200 不变** | 200 |
| 正式出库 | **扣那 150**（走现有出库扣减） | 需下游全部改造才能扣 |
| 复用度 | **复用现有容器事实源 + 下游扫码 + 任务闭合** | 复核/装箱/出库都要改 |
| 风险 | 需保证转移与锁定在**同事务** | **独立分配表本身可不作为库存事实源**；其额外成本是**更大的出库与闭合适配**（下游要全部认这张表），**并非必然「新增事实源」** |

> **推荐 A 的理由**：**沿用唯一库存事实源**并**复用现有锁定 / 扣减**（`locked_by_task_id` + `deductFromTaskLockedContainers`），下游改动面最小；方案 B 需为出库与任务闭合另做一套适配。

**红线（无论哪个方案）**：

- **不在拣货时直接扣仓库库存 150**（拣货只锁、出库才扣，`scan-logs.service.js:196`）。
- **150 不得同时计在 `B` 与新码上**（会双计）——转移必须**同事务**完成。
- **`scan_logs` 必须记录「新锁定的那条取货记录」**，原 `B` 码**另存为来源审计**；否则任务侧「锁定集合」与「扫码集合」会**失配**（`backend/src/modules/warehouse-tasks/warehouse-tasks.helpers.js:73-92` 处按 `locked_by_task_id` 与 `scan_logs.container_id` **逐一比对**的既有校验会抛错）。**出库时不再锁 `B`**。
- **补打 / 重印同一取货码不新增货**（只重出标签）。
- **取消 / 减量**：按扫码的**实物返还**处理——**先沿用安全库存码 / 同仓库位**的既有流程，**不自动把货加回 `B`**；要回盒必须**指定盒并人工确认**。
- **P4 与 P5 必须是同一个可验收闭环**：不得「先上线新取货标签、以后再补归还路径」。
