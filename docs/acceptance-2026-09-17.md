# 极序 Flow 全系统深度验收（2026-09-17）

验收对象：本地开发环境 `/Users/chengjianghao/flowcube`，分支 `main`（`9daf627`），前端 `0.9.18`。
环境：MySQL 8 开发库 `flowcube_dev8`（127.0.0.1:3307）、后端 3000（development）、ERP 5173、PDA 5174。
方式：真实启动系统后用浏览器真人操作 + 接口直调 + 数据库核对 + 代码交叉验证。

**本文所有数据库异常计数均来自本地开发库。该库长期被 smoke/回归脚本写入，存在大量测试数据；部分异常已能判定是测试污染，部分需要到干净环境复现后才能定性。文中逐项标注了定性程度。**

## 0. 结论摘要

**整体健康度：框架扎实，工程纪律明显高于同类自研 ERP；核心交易链路（建单→占库→出库任务→取消释放）在真实操作下数据一致；权限与幂等实现经得起攻击性测试。主要问题集中在三类：本地/测试数据污染、长期滞留任务与资源锁、以及若干配置与展示层缺陷。**

可以放心的部分

- 库存事实源纪律有效：全库 `ACTIVE 容器 remaining_qty` 合计 98,349 与 `inventory_stock.quantity` 合计 98,349 **完全相等**（1,779 个库存维度无一处漂移）。
- 全库无负库存、无负预占、无超发（`dispatched_qty > quantity` 0 条）、无折扣超过合计。
- 权限拦截有效：只读账号（`codex_ui_test`，role 5）对 12 个不同模块的写接口**全部返回 403**；无 token 返回 401；履约写接口在服务层二次校验同样 403；PDA-only 路由同时挂 `pdaOnly` 与 `pdaSessionRequired`。
- 幂等有效：同一 `X-Request-Key` 串行重放、同键不同报文重放、**并发同键双发**三种情况下都只产生 1 张单，且返回同一单据 ID。
- 我真实创建的销售单全链路数据一致：单据头金额 = 明细合计（380.96），占库写入预占账，发起出库生成仓库任务，取消订单时**订单状态、预占释放、任务取消在同一秒的同一事务内完成**。
- 错误与引导文案质量高：取消订单对话框明确"将同步取消关联仓库任务并释放锁定资源"；PDA 未绑定设备给出明确下一步；占库弹窗展示"现货 / 已占 / 预计到货 / 占后剩余"完整 ATP 口径。

风险最高的部分

- **长期滞留的仓库任务与被锁库存**：1,106 个任务停留在执行态超过 7 天（最久自 2026-04-23），643 个容器、6,230 单位实物被这些任务锁定；分拣格 A01–A03 100% 被 7 月的僵尸任务占用，**Put Wall 完全无法使用**；系统没有任何超时回收/清理机制。
- **本地数据库被 smoke 测试污染到影响使用**：253 个仓库里 248 个是测试仓、74 个客户里 69 个是测试客户、2,637 个商品里 2,631 个是测试商品、57 个用户里绝大多数是 smoke/提权测试账号（含仍启用）。所有下拉、选择器、看板数字都被污染。
- **孤儿数据**：11 个 ACTIVE 容器指向已不存在的商品（5,003 单位），299 条库存预占指向已删除的销售单（其中 106 条仍为有效状态，6,900 单位"幽灵预占"）。
- **单号前缀设置与实际生成不符**：系统设置页显示并允许编辑"销售单号前缀 SO / 采购 PO / 盘点 IC"及示例，实际生成的是 `SL20260917001` / `PC20260917001`（迁移 230/231 已废弃旧键，真正生效的 `code_prefix_*` 不在页面上）。

## 1. 已复现问题

### P1-1 畸形 JSON 请求体返回 500（已复现，稳定）

```
curl -X POST -H 'Content-Type: application/json' -d '{}{}'  /api/auth/login
→ HTTP 500 {"code":"INTERNAL_ERROR","message":"服务器内部错误"}
```

同样对带鉴权的 `/api/products` 发送 `{"a":}` 也是 500。后端日志记录为 `[Unhandled] Unexpected non-whitespace character after JSON at position 2` 并打印完整堆栈。

影响：语义错误（应为 400 客户端错误）；任何客户端 bug、代理截断、脚本错误都会被记成"服务器内部错误"污染错误日志；未鉴权端点也可被用来刷错误日志。
定位：`backend/src/middleware/errorHandler.js` 未识别 body-parser 的 `entity.parse.failed`（代码里只处理了 `MulterError`）。
建议：在 errorHandler 中把 `err.type === 'entity.parse.failed'` 映射为 400 `BAD_REQUEST`，并顺带处理 `entity.too.large`（当前 `express.json({limit:'10mb'})`）。

### P1-2 僵尸任务与被锁库存无人回收（已复现，dev 库规模巨大）

证据：

| 指标 | 数值 |
|---|---|
| 停留在执行态 > 7 天的任务 | 1,106 |
| 其中拣货中(2) | 903（最早 2026-04-23） |
| 被滞留任务锁定的容器 | 643 |
| 被锁定的实物数量 | 6,230 |
| 被**已出库(7)**任务继续锁定的容器 | 3（101 单位，例：`CNT000001` 96 单位） |
| 分拣格占用 | A01/A02/A03 全部占用，空闲 0 |

`sorting_bins` 三条记录 `status=2` 且 `current_task_id` 指向 7 月 19 日的任务 143/145/147（这些任务至今仍是 `status=2` 拣货中），导致 PDA 分拣页"空闲 0"，任何新任务都无法分拣。

代码侧：`backend/src/scheduler.js` 中没有针对滞留仓库任务的超时回收/告警；容器解锁只发生在明确的取消/改单路径（`containerEngine.releaseLockedContainers`、`warehouse-tasks.pick.js`）。**已出库任务仍持有容器锁**这一点在开发库可复现，但无法排除是历史测试脚本中断造成，建议在干净库做一次定向复现后再定性为代码缺陷。

影响：真实仓库若出现"拣到一半撂下""PDA 没电/断网"，库存会被长期锁死且无人察觉；分拣格耗尽后整条出库链停摆。
建议：① 增加"任务停留超时"巡检（告警 + 允许管理员强制释放/归还）；② 分拣格占用增加以任务状态为准的自动回收；③ 出库完成路径显式解锁残余容器锁并加回归断言。

### P1-4 孤儿数据：容器与预占指向已不存在的单据/商品（已复现）

- 11 个 `status=1`（ACTIVE）容器指向不存在的商品，合计 **5,003 单位**（如容器 5984 → 商品 2730，500 单位）。这些量计入全库库存事实总量，但商品主档不存在，按商品聚合的报表/列表无法呈现，PDA 也无法处理。
- 299 条 `stock_reservations` 指向已不存在的销售单，其中 **status=1（有效）106 条、合计 6,900 单位**，会持续压低 ATP。

代码侧已确认 `DELETE /api/sale/:id` 是软删除（`deleted_at=NOW()`）且受状态机限制，不会产生这类记录 —— 这些孤儿来自直接删除的脚本/清理。全库仅 1 个外键约束、4 个触发器，**引用完整性几乎完全依赖应用层**，因此这类脏数据一旦产生无人拦截。
建议：① 把这两类检查加入 `npm run audit:business-consistency`（当前只覆盖预占来源身份，未覆盖容器→商品）；② 生产库执行一次只读核对；③ 明确"禁止对业务表执行物理 DELETE"的操作纪律。

### P2-1 单号前缀设置是"死配置"且示例错误（已复现）

### P2-2 取消订单后明细的已占/已发数量未清理（已复现）

实测：订单 3254（`status=5` 已取消）的明细仍为 `reserved_qty=2.0000`、`dispatched_qty=2.0000`，而对应预占账已 `status=3` 释放、任务已取消。

代码侧：`sale.service.js` 取消分支只在 `status ∈ {2,6}` 时执行 `UPDATE sale_order_items SET reserved_qty = 0`；`status=3`（执行期）分支释放预占后**不回写明细**。

开发库规模：793 张已取消订单中，56 张订单的明细仍带 `reserved_qty>0`（合计 68），628 张带 `dispatched_qty>0`（合计 704，部分属于"部分已发后关闭"的正常保留）。

影响面：ATP/可用量走 `stock_reservations`，**不影响库存判定**；但明细层面的"已占"与预占账不一致，取消单会继续显示占用，任何将来以 `sale_order_items.reserved_qty` 为口径的新功能都会踩坑。
建议：执行期取消且无实物移动时同步清零明细 `reserved_qty/dispatched_qty`；如属有意保留，请在 AGENTS.md 写明并让 UI 区分"历史事实/当前占用"。

### P2-3 大批量列表在前端一次性渲染（已复现）

- 商品选择弹窗：2,637 行一次性渲染，**29,766 个 DOM 节点**，打开时发出 **14 次** `/api/products` 分批请求（单次 12–29ms）。无虚拟滚动。
- 仪表盘：一次加载 **43 个 API 请求**，累计请求耗时约 0.95s，其中 `/api/reports/role-workbench` 被调用 **11 次**。

影响：客户端渲染与内存占用随数据量线性增长；打开弹窗有可感知卡顿，低端设备（PDA/办公旧机）更明显；仪表盘重复请求浪费服务端与网络。
建议：① 弹窗列表改为虚拟滚动或服务端分页；② 排查 role-workbench 的 11 次调用是否可用同一 query key 合并；③ 给"不分页"设计补一条数据量上限与降级策略。

### P2-4 角色冗余列漂移（已复现）

34 个活跃用户中 **29 个** `sys_users.role_name` 与 `sys_roles.name` 不一致（例如 `admin` 冗余列写"管理员"，角色表为"系统管理员"）。登录后 JWT/前端展示的 `roleName` 取自冗余列，因此界面显示的是过期名称。
附带：角色 1（系统管理员）在 `sys_role_permissions` 里只有 2 条记录，但代码把 `roleId=1` 硬编码为超管（`PERMISSION_MIDDLEWARE` 默认 `superAdminRoleIds=[1]`），权限页展示的勾选状态与实际能力不符。

## 4. UI / UX 观察

做得好的

- 占库弹窗与发货弹窗的信息层级专业：完整商品身份（编码/供应商型号/型号/颜色/单位）+ 需求/已占/待占 + 仓库 + ATP 明细，行业里常见的是只给一个"可用量"数字。
- 危险操作有明确后果说明（取消订单对话框）。
- 空态与未就绪态有引导（PDA 未绑定设备、无库位提示）。
- 只读角色确实看不到"新建销售单"等写操作入口（前端也按权限裁剪，不只是后端拦截）。

值得改的

1. **下拉无搜索 + 数据量大**：仓库下拉 251 项、无筛选；商品弹窗虽有关键词搜索，但一次性渲染全量。仓库/客户这类"必须精确选择"的控件应支持输入过滤。
2. **名词与实际不一致**：设置页"销售单号前缀 SO"、示例"SO20260917"，而系统生成 `SL…`。这类"界面在撒谎"的问题比缺功能更伤信任。
3. **PDA 绑定信息过技术化**：`所属仓库 #1`，应展示名称；设备码、仓库、绑定时间建议一并展示，便于仓库主管核对。
4. **PDA 拣货推荐列表缺库位**：本次任务的 12 个候选容器全部显示"无库位"，拣货员只能挨个扫条码，无法按库位找货。库位为空的容器要么禁止参与拣货推荐，要么在界面上明确"需扫码定位"。
5. **数字输入体验**：数量/单价输入框接受科学计数与浮点噪声，`0.00001` 这类值应直接拒绝或规整显示。
6. **弹窗与表格在窄窗口的横向滚动**：商品明细列多，窄窗口下需横向滚动才能看到"金额/删除"，仓库现场的小屏设备更明显。

## 5. 业务与流程设计问题

1. **采购确认后不会自动生成收货订单**（实测：确认 PO 2387 后无任何收货单产生，"待收货"看板 569 条长期堆积）。真实使用中极易出现"采购已确认、仓库不知道要收货"。建议采购确认即生成待收货单（或明确由仓库按 PO 建单，并在采购列表提供入口）。
2. **僵尸任务无兜底**：拣货中/待分拣/待复核/待打包没有任何超时提醒或强制回收，分拣格被占满后整条链停摆。对比之下"打印后未上架超时"已经做了提醒，说明能力具备、只是没覆盖到这条链。
3. **待办数量过大导致待办中心失去意义**：本地看板"我的待办 4,065 条""履约超时 958"。真实经营里几百条以上的待办必须分层（按责任人/仓库/时效），否则等于没有待办。
4. **"不分页"的产品取向需要配套上限**：AGENTS.md 已记录 5,000 行上限，但前端仍一次性渲染；建议上限下移 + 虚拟滚动，否则数据增长后必然回归。
5. **测试/演示数据与业务数据同库**：见 P1-3。开发库应可一键重置为"最小可信数据集"。

## 6. 数据与架构风险（未直接表现为页面 Bug）

1. **引用完整性几乎全靠应用层**：全库仅 1 个外键、4 个触发器。已出现指向不存在商品/单据的孤儿数据。建议至少给"容器→商品/仓库""任务→销售单""预占→单据"加只读巡检 + 定期告警。
2. **冗余字段（`sys_users.role_name`）与角色表漂移不会触发任何错误**，却直接影响 JWT 与界面展示。
3. **`sale_order_items.reserved_qty` 与预占账双轨**，取消/改单路径已出现不一致；任何新功能误用这个字段都会得出错误结论。
4. **测试脚本直连开发库**：污染规模说明存在长期习惯，建议在 `tests/helpers/testEnvironment.js` 之外增加"生产库/开发库指纹"拦截，或在脚本入口强制校验库名白名单。
5. **express.json 10MB + 无限流**：未鉴权接口可提交大报文；结合 P1-1 的 500 会放大日志与 CPU 消耗。
