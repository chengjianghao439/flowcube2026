### R2-01：调拨部分入库提前完成

- 定位：`backend/src/modules/transfer/transfer.service.js:393–404`。
- 复现：一条商品计划 10 件，源仓两箱各 5 件。第一箱扫出、目标仓扫入后立即返回 `completed:true`。SQL 显示订单状态 4，计划 10、已出 5、已收 5；另一箱仍在源仓。随后第二箱扫出返回 400，无法完成剩余计划。
- 根因：完成条件只统计当前在途容器数，没有检查尚未发出的计划量。该问题独立于重复商品行；正常两端分批操作即可触发。
- 前端路径：`pda/transfer.tsx:54–55` 允许首箱发出后的在途单进入收货；`pda/transfer-in.tsx:67,77` 按服务端完成标记显示整单完成。本轮核对代码路径和 HTTP，未执行 PDA 真机交互。
- 修复方向：在同一事务中验证计划、已出和已入数量闭合；若业务允许短调，使用显式结案规则。实物数量并未凭空增加，问题是订单提前关闭和余量无法执行。

### R2-02：旧请求被归到新登录账号

- 定位：`frontend/src/api/client.ts:323–336`，`frontend/src/lib/authSession.ts:24–43`，`frontend/src/hooks/useAuth.ts:35–45`。
- 复现：账号 A 发起销售删除请求但响应延迟；同页面退出并登录 B；旧请求此时才返回 401；拦截器读取 B 的 refresh token，续期后用 B 的新 token 重放原删除。
- 根因：检查的是“开始续期时的会话有没有变化”，没有验证“原业务请求属于哪个会话”。现有测试覆盖续期进行中切换账号，未覆盖首次 401 到来之前已换账号。HashRouter 的同文档 hash `location.replace` 不会销毁全部在途 JavaScript，清除 Query 缓存也不等于取消底层 mutation 请求。
- 主任务独立复核：归档探针使用真实 `client.ts`，通过 adapter 控制响应，以模拟会话对象替代账号；18 项通过，其中 16 项既有测试、2 项新增缺陷探针。没有调用真实销售删除 API。专项复核另以真实登录/退出 hook 和 HashRouter 验证页面可达性；该专项临时组件文件未保留下来，不计入可重跑证据。
- 影响：B 未确认的旧操作以 B 身份提交；服务端仍校验 B 的权限、仓库范围和单据状态，不是服务端权限绕过。
- 修复方向：请求捕获会话代次，退出/登录使代次失效；在续期、重放及迟到结果处理前校验归属。避免只比较 token 字符串，因为同账号正常续期也会换 token。

### R2-03：累计扣除余额丢失

- 定位：`backend/src/modules/hr/hr.tax.js:40–42`，`hr.service.js:208–232`。
- 复现：同一单位持续任职员工，1 月应发 0，2 月应发 10000，无社保及其他扣除。1 月累计所得被保存为 0；2 月计算税额 150、实发 9850。按此代码声明的普通累计预扣口径，两个月收入 10000、基本减除 10000，2 月税额应为 0。
- 根因：把递推使用的累计余额截零后持久化，前月未用扣除无法带入后月。税额不能为负不代表递推信息也可以丢失。
- 修复方向：保留完整累计收入与扣除，或保留足以还原累计净额的台账；计税时再处理非正所得。补零收入、低收入转高收入、跨年度和任职月份边界。

### R2-04：跨月份核算缺少依赖保护

- 定位：`backend/src/modules/hr/hr.service.js:178–232,254–274`。
- 复现：1、2、3 月均录入应发 30000。先核算 2 月、再核算并发放 3 月；之后补算 1 月、重算 2 月全部成功。3 月仍保留税额 1730，正常顺序对照为 2500，差 770；已发放 3 月不能再按正常入口重算，累计台账也未随前月变化修订。发放创建两张系统凭证，本次不涉及真实银行转账或缴税。
- 同根因：只读取紧邻上月台账，缺失直接归零。已有 1 月核算、2 月录入 0 但未核算时，3 月可以直接核算并忘记 1 月累计历史。
- 根因：当前工资单行锁只保护本单，不能保护年度累计链；发放只验证当前单金额和状态，没有校验累计基线是否有效。
- 修复方向：建立员工/账套/年度的核算依赖与并发规则；拒绝无有效前置的核算和发放。前月更正应使后续结果失效或进入显式修订流程，不能静默保留已发放旧结果。

R2-03/04 的税额对照仅验证项目已采用的普通累计法，不判断员工是否符合其他优惠政策。累计减除按在本单位任职月份计算，依据[国家税务总局官方说明](https://neimenggu.chinatax.gov.cn/zcwj/rdwd/201911/t20191111_706924.html)及其中引用的 2018 年第 61 号公告第六条。

### R2-05：重复商品调拨行无法完整扫码

- 定位：`backend/src/modules/transfer/transfer.service.js:91–99,235–248,380–384`。
- 复现：同一商品两行各 5 件，创建、确认成功；首箱扫出成功，第二箱返回 409“剩余可调量 0”。SQL 显示两行已出为 5 / 0。
- 根因：建单保留重复行，确认按商品合并校验可用量，扫码却只取排序第一行并核算该行余量。前端 `transfer/form/index.tsx:101–170` 可以重复选择商品，提交未合并或拒绝。
- 修复方向：统一同商品行契约，创建/编辑时合并，或扫码按明确行归属分配；同时同步扫入。保留现有整箱数量保护。P1 是因为合法 UI 建单可产生无法正常执行的已确认订单。

### R2-06：受限用户可创建两端均无权限的调拨草稿

- 定位：`backend/src/modules/transfer/transfer.controller.js:8`，`transfer.service.js:91–99`。
- 复现：仅可访问仓 A、具备调拨创建权限的用户，向外仓 B → C 创建单据得到 201；同一账号读取、确认新单却返回 403。数据库确有该草稿。
- 根因：创建入口没有传入、验证用户仓库范围；修改和确认已有校验。
- 边界：正常仓库下拉已经过滤，需直接构造 API 参数触发。证明的是无权仓库单据写入，未证明可以实际调动外仓库存。
- 修复方向：在服务端创建事务前校验两端仓库范围，复用现有仓库范围工具并补受限用户 HTTP 回归。

### R2-07：调拨幂等键未绑定单据

- 定位：`backend/src/modules/transfer/transfer.service.js:200–201,315–316`，`backend/src/utils/operationRequest.js:30–34`。
- 复现：A 单扫码成功后，同账号将该键用于 B 单，返回 200 和 A 单回执；B 单实际未执行。扫入同样返回 A 的 `completed:true`，B 仍在途。换新键才能真正完成 B；不存在的单号也能回放 A 的旧成功回执。
- 根因：固定 action `transfer.scanOut` / `transfer.scanIn`，回放发生在目标单据和设备仓检查之前，没有资源匹配。
- 边界：未发现跨用户泄漏或重复加库存。普通 UI 的随机请求键不必然碰撞，本项是客户端错误复用键时的明确服务契约缺陷。
- 修复方向：action 绑定单据 ID，或在重放前验证已存回执资源；同步 PDA `requestAction` 和结果查询契约。扫出、扫入属于同一个根因，合并计数。

### R2-08：创建账套成功后被误报失败

- 定位：`frontend/src/pages/accounting/consolidation/index.tsx:71–80,157`，`frontend/src/store/companyStore.ts:24`，`frontend/src/api/client.ts:243`。
- 复现路径：创建账套请求仍在等待时可以取消弹窗，再切换账套。该页面直接调用 API，不属于 React Query mutation，所以 `isMutating()` 闸门没有拦住切换。服务端已成功提交，迟到的成功响应被账套拦截器取消，页面进入错误提示，成功后的列表刷新也不执行。
- 主任务归档 probe 证明成功写响应会被取消；页面 pending 状态和切换可达性由组件调用链及专项组件探针复核，专项临时组件文件未保留。后端 `companies.service.js:81–82` 明确先提交再返回。
- 影响限于结果丢失、误报失败，未证明发生跨账套写账。
- 修复方向：把直接写 API 纳入统一提交生命周期，创建中禁重复提交并正确处理切换、取消及已提交回执。不要简单移除旧账套响应隔离。
