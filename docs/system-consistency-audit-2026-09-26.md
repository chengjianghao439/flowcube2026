## 1. 系统关系图（简版）

单一后端服务，三类客户端共用同一套 API 与权限体系：

```
PC 网页 / Electron 桌面 / Android PDA
        │
        ├── 销售：草稿→确认→占库(reserved_qty + stock_reservations)→派发(dispatched_qty)
        │        →仓库任务(拣/分拣/复核/打包)→出库→应收 payment_records(type=2)
        │
        ├── 采购：草稿→确认→入库任务→PDA收货(容器 PENDING_PUTAWAY)→上架(容器 ACTIVE)
        │        →应付 payment_records(type=1)→财务确认(confirm_status)→出纳付款
        │
        ├── 库存唯一事实源：ACTIVE 容器 remaining_qty
        │        inventory_stock.quantity 只是缓存，只能由 containerEngine 回写
        │
        ├── 逆向通路：销售取消/改单、采购撤回收货、销售退货、采购退货、调拨、盘点、报废
        │
        └── 会计：finance_account_transactions(资金流水) → 凭证引擎 → 总账
                 凭证来源 SOURCE_TYPES 18 种，期间结账后拒绝写入
```

**关键判断：正向通路本身设计相当扎实。** 库存事实源唯一、引擎不允许自己开事务、
状态机与 CAS 齐全、金额重算走"全量重算 + upsert"幂等模式、
PDA 关键动作统一封装了幂等键 + 离线待确认 + 服务端状态回查。
**问题集中在"防护装了一半"和"逆向不对称"两类，而不是正向流程本身。**

- **静态守卫不是摆设**【守卫验证】：我对 `test:stock-cache-write` 和

  2026-08-21 审计 C.1 的跨账号残留问题已修复在位。

### 2.2 哪些只验证了一部分

- 金额口径：正向（建单/改单/发货/结算）我读到的是自洽的；
  但**"订单总额"与"应收台账"与"会计凭证"三处用的是不同的算术**
  （浮点累加 vs 逐行四舍五入 vs BigInt 定点），分厘级尾差有证据，见 §3.3。
- 权限与仓库范围：绝大多数入口有校验，但**守卫测试对部分文件失守**，见 §3.1.3。
- 前端数据新鲜度：同会话内会失效，**跨设备/跨会话不会**，见 §3.4。

### 2.3 哪些是已确认的问题

按后果从重到轻（详细论证见 §3）：

1. **【已行为复现】已发生的事实可以被单方面抹掉**——退货已入库后取消退货单，库存留着、应收不减；
   采购已付款后撤回收货，应付被清成 0 并显示"已付清"。两条都**在系统内无法自救**。
   （复现见 §0.1-bis；采购侧还额外确证：**从未付款的收货单撤回后同样显示"已付清"**，
   且撤回后按短装重收，多付的钱在账款上完全不可见。）
2. **运费与手工应付根本不进总账**，而系统的勾稽对账**刻意把它们排除**，
   所以对账永远显示"平"。这是"系统自己的对账在说谎"。
3. **会计期间结账后，资金与账款侧仍可写入**，凭证静默跳过，全程无提示。
4. **手动出库是全系统唯一"重复执行不会报错"的库存扣减入口**
   （后端幂等已实现，但前端没发幂等键）。
   *经核实，其提交按钮已有 `disabled={isPending}`，双击被 UI 挡住，因此实际触发概率低，不是高危。*

### 2.4 哪些风险因环境不足无法排除

- 生产库中是否存在历史脏数据（重复明细行、悬挂容器、已取消单的 ACTIVE 容器、

  这是判断"问题是否已经真实发生"的关键缺口。
- 并发竞态：**仍未验证**。已有代码级论证（行锁 + CAS）看起来是自洽的，
  但"看起来"不等于"验证过"。
- 真实金额结果：§3.2 两条已用**测试库真实数据**验证（§0.1-bis）；
  §3.3 的金额类结论仍停留在代码口径比对，没有真实数据支撑。
- GUI / PDA 真机 / 物理打印：本轮全部未做（复现脚本走的是 HTTP 接口层，
  带真实 PDA 会话头，但**这不等于在 PDA 设备上操作过**）。

**不能据此说"系统可以上线"或给出任何完成度百分比。**
本轮证据强度已从"纯静态"提升到"静态 + 两条主链的行为复现"，但仍**不是**全系统验收。

## 3. 关键规则与系统性问题

按**根因**归并，不按模块罗列。一个根因下的多个表现合并陈述。

---

### 3.1 根因一：同一套防护，只装了一半

系统的保护机制（幂等键、期间锁定、仓库范围、守卫测试）都是**逐个入口手工接线**的，
没有"新增入口自动获得保护"的机制。于是每加一个入口，就多一次漏接的机会。

#### 3.1.1 幂等键：前端漏发 → 后端防护形同虚设

**机制**【代码确证】：
`backend/src/utils/operationRequest.js:45`
```js
if (!key) return { enabled: false }   // 没有请求键 → 整套幂等直接放行
```
后端为 15 个 controller 模块实现了幂等，但**请求键必须由前端主动发送**。

**已确认的两个漏发点**【代码确证】：

| 入口 | 前端 | 后端 |
|---|---|---|
| 手动出库 | `frontend/src/api/inventory.ts:12` `outboundApi` 无 key 参数；`hooks/useInventory.ts:17` `useOutbound` 无 keyRef | `inventory.service.js:209-217` 已实现幂等，收 `requestKey` |
| 退款执行 | `frontend/src/api/refund.ts:17` `executeRefundApi` 无 key | `refund-orders.service.js` 用 `beginResourceOperationRequest`，注释明言"连点两次会重复退钱" |

对照：销售（`hooks/useSale.ts`）、采购、入库任务、退货表单、收付款弹窗、
**以及全部 PDA 页面**都正确发了 key。

**为什么现有防护没覆盖**：
- 出库按钮有 `pages/inventory/index.tsx:411` `disabled={isPending}`，双击被 UI 挡住；
  前端 mutation `retry: 0`，不会自动重试。
- 于是只剩三种触发：请求超时/断网后用户关弹窗**重新操作**（前一次可能已成功）、
  多标签页并行操作、用户主动重试。
- **手动出库是唯一"没有状态机兜底"的库存扣减入口**：
  它走 `adjustContainerStock` FIFO 扣减，每次调用在业务上都是合法的，
  没有任何状态检查能挡住第二次。其余入口（如盘点提交、任务操作）都有状态机。

**业务后果**：库存被重复扣减后，系统里没有任何标记表明"这是重复的"。
员工只会看到一个变小的数，只能手工调回——正是"被迫在系统外补账"。

**最小修复**：照 `useSale.ts` 的 `keyRef` 模式给 `useOutbound` 加稳定请求键，
`outboundApi` 加第三参数。**后端零改动**（防护已就绪）。

**回归范围与验收**：出库成功后 key 轮换；相同 key 重发返回首次回执且不重复扣减；
库存流水只产生一条。

#### 3.1.2 会计期间锁定：只锁了凭证侧，没锁资金侧

**机制**【代码确证】：
`assertPeriodOpen` 的调用点全部集中在会计域——
`accounting.period.service.js`、`accounting.voucher.service.js`(99/138/200/227)、
`voucher-engine.js`(136/137)、`voucher-source-revisions.js`(28-30)、
`fixed-assets.service.js`(197/232)。

**而以下"改钱"的入口一个都没有调用它**：
`payments.service.js`（含 `recordPayment`）、`payment-receipts`、
`returns.helpers.adjustPaymentRecordForReturn`、`refund-orders.service.js`、
`logistics.freight.js`、`finance-accounts.recordTransaction`。

更关键的是 `voucher-engine.js` 里**两处**遇到已结账期间的处理：

```js
// :510-511 —— 主路径：业务日期落在已结账期间，静默跳过
if ((closedPeriods && closedPeriods.has(periodOf(dateStr)))
  || (SALE_TYPES.includes(spec.sourceType) && allClosed.has(periodOf(dateStr)))) { stats.skippedClosed += 1; continue }

// :516 —— upsert 抛错时的兜底，同样静默跳过
if (!period && e.code === 'ACCT_PERIOD_CLOSED') { stats.skippedClosed += 1; continue }
```
两处都只累加一个计数器。

**同一文件内的对照（同一作者、同一时期）**：紧邻的 `:503-505` 对
"缺少业务发生日期"的跳过**加了逐条 `logger.warn`**，
注释明说"不能退回静默 continue……必须计数 + 逐条告警，让漏记可被发现"
（2026-09-18 审计的修复）。**而已结账跳过这一条至今没有逐条告警**——
同一个"不能静默丢凭证"的原则，只落实在了一半的跳过路径上。
这是 §3.1 根因一（同一防护只装了一半）在本模块内的又一次重演。

**触发条件**：付款/收款/退货/退款/资金流水的业务日期落在**已结账**的会计期间
（典型场景：9 月初补录 8 月的付款，而 8 月已在 8 月底结账）。

**实际行为**：资金/账款已改 + 凭证永不生成 + 界面无任何提示。
**预期行为**：要么拒绝写入，要么明确告知"该期间已结账，此笔不会生成凭证"。

**业务后果**：已结账期间的总账被冻结，但资金流水与应付/应收台账被改动，
两者永久分离。财务在下期对账时会发现勾稽不符，但**没有任何线索指向原因**。

**修复方式（业务方已拍板，2026-09-26）——「允许补录，但必须人工审批留痕」，三层缺一不可**：

1. **默认拒绝**：资金/账款侧写入口遇到业务日期落在已结账期间 → 409 拒绝，
   **不再默认放行**。
2. **特权通道 + 留痕**：另开"跨期补录"路径，需专门权限
   （如 `finance.period.backfill`），写入时留下"跨期补录"显式标记（谁 / 何时 / 哪张单）。
3. **放行就必须真的记账**：走审批放行后**凭证必须生成**，
   不能再落进 `voucher-engine.js:510-511` 的静默 `continue`；
   同时把 `skippedClosed` 的静默跳过改为显式返回或逐条告警。

（排期见 §5 第 3 位。）

**影响面检测（2026-09-26 续）**——业务方要求先查清影响面再决策。
以下三条**只读**查询已在本轮验证语法可执行（`acct_periods.status = 2` 即「已结账」，
见 `194_accounting_period_close.sql:4`），**可在生产库只读跑，不改任何数据**：

```sql
-- ① 落在已结账期间的付款明细（有多少笔、多少钱）
SELECT p.period, COUNT(*) AS 笔数, SUM(e.amount) AS 金额
FROM payment_entries e
JOIN acct_periods p ON p.period = DATE_FORMAT(e.payment_date,'%Y%m') AND p.status = 2
GROUP BY p.period ORDER BY p.period;

-- ② 落在已结账期间的收付款单
SELECT p.period, COUNT(*) AS 笔数, SUM(r.amount) AS 金额
FROM payment_receipts r
JOIN acct_periods p ON p.period = DATE_FORMAT(r.payment_date,'%Y%m') AND p.status = 2
WHERE r.deleted_at IS NULL
GROUP BY p.period ORDER BY p.period;

-- ③ 其中有多少笔「改了钱但没生成凭证」（skippedClosed 的实际落点）
SELECT COUNT(*) AS 无凭证笔数
FROM payment_entries e
JOIN acct_periods p ON p.period = DATE_FORMAT(e.payment_date,'%Y%m') AND p.status = 2
WHERE NOT EXISTS (
  SELECT 1 FROM acct_vouchers v
  WHERE v.source_type = 'payment_out' AND v.source_id = e.id
);
```

**测试库实测结果**（⚠ **测试库数据是测试产生的，不代表生产，仅证明机制会这样表现**）：

| 查询 | 结果 |
|---|---|
| ① 付款落在已结账期间 | 期间 `202609`：**1094 笔，¥196,897.20** |
| ② 收付款单落在已结账期间 | 期间 `202609`：464 笔，¥157,800.00 |

### 3.2 根因二：逆向路径与正向路径不对称

正向做了一件事，逆向没有对称地撤销它。
**这类问题的共同特征是：触发后系统内没有任何操作能恢复，员工只能手工改数据。**

#### 3.2.1 销售退货：部分上架后取消 → 库存留着、应收不减、文案失真

> **订正（2026-09-26 落地后回填，先读这段）**：本节对**事实**的认定成立，对**预期**的认定不成立，
> 已按下述修正；实施结果与依据见 `docs/sale-return-reverse-flow-2026-09-26.md`。
>
> - ✅ **仍成立**：取消路径确实不冲应收；ACTIVE 容器会留在已取消的单据上、追溯链断裂；
>   「未执行退货入库」的事件文案与实际不符。
> - ❌ **不成立**：「取消时应按已入库合格量**对称冲减应收**」。退货单**只有推进到状态 3（已执行）**
>   才冲应收（`tryFinishReturnTaskPutaway` 待上架量归零 → 状态 3 → `syncSaleReturnCompleted`；
>   凭证引擎取数条件同样是 `sr.status = 3`）。可取消的状态只有 1/2，此时应收**从未冲减过**，
>   所以没有"冲减"可撤销——**不存在"恢复应收"这件事**。若按本节的"对称冲减"再冲一次，
>   等于「货已经退还给客户了、还把应收再减一次」：客户被**少收**一次钱、收入虚减，
>   比不改更糟。
>   本节把「库存增了、应收没减」读成账实不符，但这是**一致的**：货在库里，客户本就该继续欠全款。
> - 实际采纳的修复：**拒绝直接取消**（本节"选项 A"方向）**+ 生成一张独立的退货返货出库单**
>   （`warehouse_tasks.task_type='sale_return_out'`），仓库出库完成后退货单才转为已取消；
>   全程**不碰 `payment_records`、不生成任何凭证**、不新增销售单。**选项 B（对称冲减）未采用。**
> - 故标题里的"应收不减"**不是缺陷**，正文"业务后果：客户还欠全款"**是应有的结果**——
>   真正的缺陷是"货与单据脱钩"和"文案失真"，两者都已修复。

**这是本轮最值得优先处理的一条。** 触发链路完整确证：

1. 退货单状态规则 `documentStatusRules.js:117-125`：
   `cancel: { from: [1, 2], to: 4 }` —— **状态 2（已确认）可取消**。
2. 退货单仅在「待上架量归零」时才推进到 3（已执行）：
   `return-tasks.service.js:344-354` 用
   `SUM(checked_qty - rejected_qty - putaway_qty) > 0` 判断并提前返回。
   **因此在"部分明细已上架、部分还没上架"的中间态，退货单仍是状态 2。**
3. 此时取消退货单 → `returns-sale.service.js:369-395` `cancelSR`
   → 联动 `return-tasks.service.js:548-577` 取消任务。
4. 任务取消只作废**未上架**的容器（`return-tasks.service.js:567-571`）：
```sql
UPDATE inventory_containers SET status = 3
WHERE source_ref_type = 'sale_return' AND source_ref_id = ?
  AND status IN (PENDING_QA, PENDING_PUTAWAY)
```
   **已经 ACTIVE（已入库）的合格容器不在作废范围内，保留且已计入库存。**
5. 应收冲减只在整单完成时触发（`return-tasks.service.js:353`
   → `returns-sale.service.js:423-448` `syncSaleReturnCompleted`），
   **取消路径完全不调用它**。

**实际行为**：库存已增加（实物确实在库）、应收**不冲减**（客户欠款仍按全额算）、
退货单显示「已取消」，事件文案写「未执行退货入库」——与实际不符。
ACTIVE 容器的 `source_ref_id` 仍指向一张已取消的单据，追溯链断裂。

**预期行为**：取消时应按已入库合格量对称冲减应收；或直接**拒绝取消**
含已入库容器的退货单，要求走反向出库。

**为什么现有防护没覆盖**：正向（上架增库存）与逆向（取消）由不同代码路径实现，
取消路径的作者只考虑了"容器还没入库"的情形，漏了"部分已入库"这个中间态。

**业务后果**：客户退了货、货在库里，但系统说客户还欠全款。
财务对不上账，且**没有任何操作能把这两者重新拉平**。

**修复选项（需业务决策）**：
- 选项 A（保守）：取消前检查是否存在该退货单的 ACTIVE 容器，有则 409 拒绝，
  提示"已有 N 件合格入库，请先做反向出库或走退货完成"。
- 选项 B（对称）：取消时按已 ACTIVE 合格量调用一次应收冲减，再作废任务。
- **代价对比**：A 改动小、语义清晰、把选择权交回业务；B 更"自动"但会让
  ACTIVE 容器挂在已取消单上，追溯更乱。**我倾向 A。**

**回归范围与验收**：构造"部分上架 + 取消"用例；
验收标准是**取消后库存与应收保持业务上可解释的关系**，
且事件文案与真实发生的事一致。

**行为复现（2026-09-26 续，`tests/repro-20260926-return-cancel.js`，6/6 通过）**——
在测试库走完整真实链路：销售出库 10 件 → 建退货单 10 件 → 收货分 2 箱 → 质检全合格
→ 只上架第 1 箱（5 件）→ 在中间态取消退货单，逐项读库得到：

| 观测点 | 实测值 | 说明 |
|---|---|---|

| 库存 | 95.00 → 95.00 | 已入库的 5 件**保留**，未回退 |
| 应收 | 150.00 → 150.00 | **未按已入库合格量冲减** |

即：初稿的代码推断被真实行为逐条证实，无一项被推翻。

**销售单取消的机制**（触发在 `warehouse-tasks.command.js:178-229`，
配套实现独立成文件 `warehouse-tasks.cancel-return.js`，已读全文核实）——
销售出库单在「已拣出货架、货还没归位」时被取消，系统**不做后台直接解锁**，
而是把取消改成一次待办任务：

```js
const needsReverseReturn =
  lockedContainers.length > 0 &&
  [PICKING, SORTING, CHECKING, PACKING, SHIPPING].includes(status)
```
- 走逆向归还：`UPDATE warehouse_tasks SET cancel_requested_at = NOW()`，
  记 `WT_EVENT.CANCEL_REQUESTED` 事件，事件里带 `containersToReturn`
  （含 locationCode / zone / aisle / rack / level / position）与 `packagesToUnpack`
- 再次请求取消会被挡：`if (taskRow.cancel_requested_at) throw new AppError(
  '任务已在拣货退回中，请等待逆向归还完成', 409)`
- **代码原注释**（作者当时的判断，与本轮结论同向）：
  > "已经拣出货架、还没归位的容器不能批量后台解锁……改走逆向归还流程：
  > 逐容器扫码确认放回位置，全部归位后才真正完成取消"

**为什么退货侧不能照搬**——两者"货的状态"根本不同：

| | 销售单取消 | 退货单取消（部分上架后） |
|---|---|---|
| 待处理容器状态 | `status=4`（待上架，**没入库**） | `status=1`（ACTIVE，**已入库**） |
| 有无 `location_id` | 无 | **有**（已上架到具体库位） |
| 有无 `locked_by_task_id` | **有**（被任务锁着） | 无 |
| 语义 | "货还在手上，请放回去" | "货已经进库了" |

`return-tasks.service.js:504-509` 的 `putaway` 把容器置为
`status = 1, location_id = ?`（`WHERE source_ref_type='sale_return'`）；
且 `grep locked_by_task_id return-tasks.service.js` → **零命中**，
退货侧从不设置该字段（销售侧则全靠它驱动归还，见 `warehouse-tasks.cancel-return.js:60`）。
`return-tasks.service.js` 的完整函数清单里也**没有任何反向出库/下架函数**
（assertPdaWarehouse / genTaskNo / isValidTransition / findPdaTasks / findById /
create / submitWithinTransaction / submit / receive / allocateQaContainers /
fmtSqlDate / tryFinishReturnTaskPutaway / check / putaway / cancel /
fmt / fmtItem / findPutawayTask / findPutawayContainer / findPutawayLocation）。

#### 退货侧到底有没有出口——「反向出库没有入口」核查（2026-09-26 续）

业务方说"反向出库目前没有入口"。**查证结论：这句话精确成立，且比表面更彻底。**

**① 系统里能减少库存的现成入口有 4 类，但只有 1 类能精确指定"哪一批货"：**

| 入口 | 后端路径 | 能不能指定"就是这批退货货" |
|---|---|---|
| 手动出库 | `POST /api/inventory/outbound` → `adjustContainerStock(-qty)` | **不能**——按 商品+仓库 **FIFO 扣减**，扣到哪个容器不由人决定 |
| 报废 / 处置 | `disposal.service.js:427` → 同样走 `adjustContainerStock(-qty)` | **不能**——同样是 FIFO，且语义是报废 |
| 盘点盘亏 | `stockcheck.service.js:511-558` | **不能**——改的是数量，不是这一批 |
| 销售出库拣货 | `warehouse-tasks.ship.js:144` ← 扫码 `scan-logs.service.js:194` | **能**（按条码精确认容器），但语义是"卖给客户" |

**所以：没有任何现成入口能做到"把退回来的这一批货精确出库"。**
业务方的判断是对的——不是"缺一个按钮"，而是**四种业务含义里有三种在系统里根本没有对应动作**。

**② 一个好消息（避免误判）**：退货容器**没有被锁死**。
`deductFromContainers`（`containerEngine.js:260-343`）的筛选条件只有
商品 / 仓库 / `status=ACTIVE` / 未删除 / 未被任务锁定，**不筛 `source_ref_type`**。
退货已入库的货就是"正常库存"，能正常参与拣货、出库、盘点，不会被卡住。

**③ 销售侧能"扫码归还"的前提，正是退货侧不具备的**：
归还动作本身（`scan-logs.service.js:466-471`）**只清 `locked_by_task_id`、写回 `location_id`，
不改数量、不改 `status`**——因为货只是"放回原位"。
而退货容器**已经上架、位置已知、没有被任何任务锁定**，没有"归还"这个动作可做。
`return-tasks.service.js:567-571` 的取消只能作废 `PENDING_QA(5)`/`PENDING_PUTAWAY(4)` 容器，
**明确不含 `ACTIVE(1)`**。

**④ 因此"反向"的真正难点不是搬货，是定性质**——
这批货已经实实在在进库了。要"反向"，必须先回答一个**业务问题**：
**这批已入库的货，取消时要变成什么？** 四种可能，系统现状各不相同：

| 业务含义 | 对应动作 | 系统现状 |
|---|---|---|
| 退回给客户 | 一次真实的出库发货 | **无入口**（没有"退货货退回客户"流程） |
| 货留下、只取消这笔退货（转普通库存） | 解绑退货单 + 不冲减应收 | 无入口；**与当前实际效果最接近**（货留、应收不冲） |
| 货留下、作为报废或其它处置 | 报废 / 处置单 | **有入口**，但只能按商品 FIFO 扣，**指不到这批** |
| 货作废、不计库存（实物另行处理） | 容器置 `VOID(3)` + 同步库存 | **无入口**（现有 VOID 只处理 待上架/待质检） |

**⑤ 结论与成本**：
业务方要的"和销售拣货取消一样的反向引导"，**必须新做**，不能靠指向现有入口实现。
参照销售侧形态，最小可行设计是：

1. 取消退货单且有 ACTIVE 容器时 → **不直接取消**，进入"待反向处理"（对应销售侧 `cancel_requested_at`）
2. 给出待办清单：这批退货的每个容器（条码 / 库位 / 数量）
3. 员工确认每个容器的处理方式（**业务方已选定「退回给客户」**，见下）
4. 全部处理完 → 真正取消

**成本提示**：这需要新增"按条码精确处置容器"的能力 + 一个新状态 + 一个引导界面，
**不是小改动**（销售侧那一套是一个独立文件 `warehouse-tasks.cancel-return.js` + PDA 扫码流程）。

**⑥ 分期建议（建议业务方采纳）**：

> **订正（2026-09-26 落地后回填）——两期均已实施，本节以下文字为历史方案。**
> 第一期止血 409 已被第二期**取代**：有 ACTIVE 容器时**不再 409**，而是生成**独立的返货出库任务**
> （`task_type='sale_return_out'`）交仓库出库，出库完成才真正取消。
> 本文下方"第一期返回 409 / 第二期另起一张发货单 / 恢复应收"等表述均不再代表实现。
> 实际实现见 `docs/sale-return-reverse-flow-2026-09-26.md`。
- **第一期（小、可立即做，且必须先做）**：把"静默取消"改成**显式阻断**——
  有 ACTIVE 容器时返回 409。提示语**不再指向不存在的入口**，
  如实说明"已有 N 件入库，取消流程尚未完成，请先联系仓库/管理员"。
  这一期的价值不是"解决问题"，而是**止血**：把"静默产生的错误状态"变成"看得见的阻断"。
- **第二期（大）**：实现上面第 ⑤ 条的完整反向引导流程。**业务方已选定「退回给客户」**，
  落地代价见下。

**业务方已拍板（2026-09-26）：取消退货单时，已入库的这批货「退回给客户」**——
即要**真的把货发回去**。

> **这个选项是四选里最重的**，且有两笔实打实的代价，实施前必须知道：

**代价一：不能复用原销售单发货，必须另起一张单。**

- 客户能退货，说明货早就发出去了。原销售单此时必然已是**已出库(4)**，
  而 4 是**终态**：`saleOrderStatus.js:52-55`
  `SALE_STATUS_TERMINAL = [SHIPPED(4), CANCELLED(5)]`。
- 出库路径本身也会拦：`warehouse-tasks.ship.js:120-122`
  → `"关联销售单 {order_no} 已完成出库，请勿重复操作"`。
- 所以这次"退回客户"的发货**无法像销售侧那样在原单上继续走**，
  只能**新建一张单**（新销售单，或专门设计一条"退货返货出库"）。
  这是设计上最大的一个岔口，**建议实施方先出方案再动手**。

**代价二：应收必须加回去，否则等于白送。**（**订正：此"代价"不存在，见下**）

> **订正（2026-09-26 落地后回填）——"代价二"的前提不成立，不需要也不应该恢复应收。**
> 本节假设"退货入库完成时 `syncSaleReturnCompleted` 已经把应收冲减了"，但**本场景的退货单只是状态 2
> （部分上架）**，根本没走到状态 3，`syncSaleReturnCompleted` 从未被调用——应收**一直是全额 10000，
> 从未冲减过**。
> 所以下方 `line 535-538` 的代入是错的：不存在"货发出去 2000 却少收 2000"的窟窿，
> 也不存在"比什么都不做还亏"。取消退货并把货退还给客户后，客户继续欠全款，账实自洽。
> **照本节去做这个动作，方向一定是错的——"加"和"减"在本场景都会算歪**：
> 应收当前是**未冲减的全额 10000**，正确处理是**一分不动**（客户本应继续欠全款）。
> · 照字面**把应收"加回去"**（+2000）→ 12000：**多收客户 2000、6001 收入虚增**；
> · 若有人把它理解成**再"冲减"一次**（−2000，照抄 `adjustPaymentRecordForReturn`）→ 8000：
>   **少收客户 2000、收入虚减**。
> **本实现两个动作都不做**（应收保持未冲减的全额）。
> 另外，下方"出库路径本身会重算应收"（`ship.js:162-168`）**不适用于返货**：返货任务的
> `sale_order_id` 为 NULL，`ship.js` 里显式跳过应收重算与销售单校验。

- 退货入库完成时，`syncSaleReturnCompleted`（`returns-sale.service.js:445-455`）
  调用 `adjustPaymentRecordForReturn` 把该客户应收**冲减**了：
  `returns.helpers.js:47` — `newTotal = currentTotal - amount`。
- 而当前的 `cancelSR`（`returns-sale.service.js:357-417`）**完全不碰 `payment_records`**。
- 代入：客户买 10000、退货 2000，退货入库后应收变 8000。
  现在取消退货、把 2000 的货发回客户 —— 客户理应继续付这 2000。
  **若只发货不恢复应收**：货送出去了、钱也不收了，
  **比现在什么都不做还亏**（现状至少货还压在自己仓库里）。
- 恢复的正确时机与口径：出库路径本身会重算应收
  （`warehouse-tasks.ship.js:162-168` 的 `syncShippedByWarehouseTaskWithinTransaction`），
  但必须保证重算能吃回退货时冲减的那一笔（`(checked_qty − rejected_qty) × unit_price`，
  见 `returns-sale.service.js:438-444`）。
  恢复后同样要把 `confirm_status` 打回**待确认(0)**（既有口径见 `returns.helpers.js:59-60`）。

> **订正（2026-09-26）——上面这两条（"若只发货不恢复应收…比什么都不做还亏"与"恢复的时机会重算应收"）**
> **的前提都不成立**：本场景（退货单状态 1/2）应收**从未被冲减**，没有"可恢复的量"；
> 且 `ship.js` 的应收重算由 `sale_order_id` 驱动，返货任务该字段为 NULL，**天然不会进入**。
> **本实现既不冲减、也不加回**——应收保持未冲减的全额，两个方向都不动会计。
> 故本条整体作废，见上方"代价二"订正块。

**由此得到第二期的完整动作清单（订正后：只剩一个动作）**：

1. **把货发回客户**（按条码精确指定这批容器 → 出库）。**复用既有 `warehouse_tasks`**
   （新增 `task_type='sale_return_out'`），**不是"挂新单据"**——原文这一表述已按实施结果订正。
2. ~~**把退货时冲减的应收加回去**（并打回财务确认）~~ —— **不做**；
   同时也**不做**"再冲减一次"。见上方"代价二"的订正：本场景应收**从未冲减**（仍是全额），
   既没有"可恢复的量"、也没有"要再减的量"。**两个方向都不动会计**，这是本实现的明确选择。

**实施前需业务方+实施方共同敲定**：退回客户的这次发货，
是**新建一张销售单**，还是走一条**独立的"退货返货"出库流程**？
这决定界面、权限与对账口径怎么设计。
> **已敲定（2026-09-26）**：走**独立的退货返货出库流程**，不新建销售单；
> 全程不动会计。见 `docs/sale-return-reverse-flow-2026-09-26.md`。

#### 3.2.2 采购收货：已付款后仍可撤回 → 应付被抹成 0 并判为「已付清」

**已确证**：

1. `inbound-tasks.void.js` 的守卫列表（行 61/74/81/102）覆盖了拣货锁定、
   调拨在途、单据被动过、销售预占——
   **全文没有任何 `paid_amount` / `confirm_status` 检查**
   （`grep paid_amount backend/src/modules/inbound-tasks/*.js` 只命中 `settle.js`）。
2. 撤回后触发的应付重算 `inbound-tasks.settle.js:81-86` 是 upsert：
```sql
balance = GREATEST(0, VALUES(total_amount) - paid_amount),
status  = CASE WHEN paid_amount >= VALUES(total_amount) THEN 3
               WHEN paid_amount > 0 THEN 2 ELSE 1 END
```
3. 撤回收货会把 `total_amount` 重算为 0（若无其他有效收货）。

**代入**：`paid_amount = 5000`、`total_amount = 0`
→ `balance = GREATEST(0, -5000) = 0`
→ `status = CASE WHEN 5000 >= 0 THEN 3` = **3（已付清）**。

**实际行为**：应付台账显示 total=0、balance=0、状态"已付清"，
但 `paid_amount` 仍是 5000——**这 5000 是真实付出去的钱，对应的负债凭据被抹掉了**。

> **更正（2026-09-26 续，实测）**：初稿此处写"`confirm_status` 同样不会因撤回而复位"，
> **与代码不符**。`settle.js:82` 的 `confirm_status = CASE WHEN total_amount <> VALUES(total_amount)
> THEN 0 ELSE confirm_status END` 会在金额变化时把确认状态**重置为 0**（金额未变则保持）。
> 实测撤回后 `confirm_status` 由 1 → 0。这不改变本条缺陷的性质，但说明
> **"已付款的账款被撤回后反而退回'待财务确认'"**——付款都发生了还要求重新确认，
> 语义同样错乱（且为"重新确认→再登记一次付款"留下了路径）。

**预期行为**：已登记付款（`paid_amount > 0` 或 `confirm_status` 已确认）的收货不应被撤回；
或撤回时必须先冲销付款。

**为什么现有防护没覆盖**：撤回守卫是按"实物是否被后续动作占用"设计的
（拣货、调拨、预占），**没有考虑"钱已经付了"这个维度**。

**业务后果**：财务账面显示这单没有任何应付、也没有欠款，
但那笔钱确实付出去了。对账时付款记录挂着、账单却消失了。

**最小修复（分层，缺一不可）**：

- **层 1 · 重算逻辑（根治，必做）**：`settle.js:85-86` 的
  `WHEN paid_amount >= VALUES(total_amount) THEN 3` 在 `total_amount = 0` 时恒真，
  把"从未收到货"误判成"已付清"。应加 `VALUES(total_amount) > 0` 前置条件，
  否则**任何**撤回收货都会污染账款状态，与是否付款无关。
  **注意这份判式在系统里有 4 处拷贝**（见 §3.3.1 末表），
  修复时要一并检查 `sale.service.js:371` / `logistics.freight.js:207` /
  迁移 `130_*.sql:80`，只改 `settle.js` 会留下同类缺口。
- **层 2 · 撤回守卫（业务闸门）**：`void` 守卫链中加入
  `paid_amount > 0 || confirm_status > 0` → 409，
  提示"该收货单已登记付款/已确认，请先冲销付款后再撤回"。
  这一层管的是**业务决策**（钱货不能单方面脱钩），不是数值 bug。

> 初稿只写了层 2。行为复现的 §C 证明层 2 单独上线**不足以**修好这条——
> 未付款的普通撤回仍会留下 `total=0 / status=3(已付清)` 的脏记录。
> 两层必须一起改，或用层 1 兜底并明确层 2 的业务口径。

**回归范围与验收**：付款后撤回被拒绝；未付款撤回不受影响；
已存在的历史异常数据另行处理（不要用代码自动修复历史）。

**行为复现（2026-09-26 续，`tests/repro-20260926-payable-void.js`，11/11 通过）**——
三段场景全部走真实 HTTP 链路（建采购单 → 收货 → 上架自动结算 → 财务确认 → 登记付款 → 撤回）：

| 阶段 | 应付台账实测 |
|---|---|
| 上架自动结算后 | 总额 ¥5000.00 / 已付 ¥0.00 / 余额 ¥5000.00 / 待付款(1) / 财务确认 0 |
| 财务确认 + 全额付款后 | 总额 ¥5000.00 / 已付 ¥5000.00 / 余额 ¥0.00 / 已付清(3) / 财务确认 1 |
| **撤回收货后** | **总额 ¥0.00 / 已付 ¥5000.00 / 余额 ¥0.00 / 已付清(3) / 财务确认 0** |

撤回请求 HTTP 200，守卫链**无任何拦截**；付款明细（`payment_entries`）**不随撤回回滚**，
钱已出账、只有主记录被抹平。

**§B 危害放大（初稿未涵盖）**：撤回后按短装重新收货，实收 4 件 = 应付 ¥2000，
但已付仍是 ¥5000，`balance` 仍算 0、状态仍"已付清"——
**多付的 ¥3000 在账款上完全不可见**（实测 `total=2000 / paid=5000 / balance=0 / status=3`）。

**§C 触发面扩大（初稿未涵盖）**：一张**从未付过一分钱**的收货单，撤回收货后
应付记录同样变成 `总额 ¥0.00 / 余额 ¥0.00 / 状态 3(已付清)`——
根因是 `paid_amount >= VALUES(total_amount)` 在 `total=0` 时**恒真**，
与是否真的付过款无关。因此**不能把守卫条件只写成"已付款"**，
它同样污染了普通的收货撤回路径。

#### 3.2.3 同类（待核实）：销售退货可退量口径、分仓退错仓、取消后退回期间可用量虚高

来自并行审查，我只核对了机制未走通全链：
- 可退量 `shipped_qty` 按 `product_id + 仓库` 聚合，而 `returned_qty` 按 `sale_item_id`：

  而预占用的 `getStockProjection` 不排除锁定容器 → 短时间内可用量虚高。

**这三条都依赖生产数据才能定性。本环境无法核对。**

### 3.3 根因三：总账覆盖不全，且勾稽口径被窄化以维持「平」

#### 3.3.1 运费与手工应付根本不进总账，对账却显示平

**已确证**：

1. `backend/src/constants/voucherSource.js` 的 `SOURCE_TYPES` 共 18 种
   ——**没有运费应付，也没有手工台账**；`ACCOUNT_MAPPING` 同样没有。
2. `grep -iE "freight|logistics|运费|carrier" backend/src/modules/accounting/`
   → **零命中**。整个会计模块不知道运费的存在。
3. 运费应付的落库方式 `logistics/logistics.freight.js:217`：
   直接 `INSERT INTO payment_records (type=1, order_id=NULL)`，
   且注释说明 `order_id` **必须为 NULL** 以免与采购应付在
   `UNIQUE(type, order_id)` 上冲突。
4. 系统自己的勾稽查询 `accounting.voucher.service.js:306/319`：
```sql
WHERE type=1 AND order_id IS NOT NULL   -- 应付
WHERE type=2 AND order_id IS NOT NULL   -- 应收
```
   **主动排除 order_id 为 NULL 的记录**，即排除运费与手工台账。

**实际行为**：承运商运费结算后——
- 费用科目不增加（利润虚高）
- 应付账款 2202 不增加（负债漏记）
- 而勾稽查询对比的是"采购结算凭证"与"采购应付台账"，两边都排除了运费，
  于是**永远显示平衡**。

**预期行为**：运费是真实的费用与负债，应进入总账；
若业务上决定不进总账，勾稽也应显式声明"此口径不含运费"而不是默默排除。

**为什么现有防护没覆盖**：运费是后加的业务模块，
它的作者正确地避开了 `UNIQUE` 约束冲突，但**没有接入凭证体系**。
勾稽查询作者为了让对账"平"，加了 `order_id IS NOT NULL` 的过滤——
这在当时是合理的（避免把无凭证的台账算进来），
但结果是**掩盖了台账与总账的真实缺口**。

**业务后果**：这是**每月必然发生**的问题（月结运费是常态业务），
且**累积不可逆**。若无人工凭证补救，利润表与资产负债表长期失真，涉及纳税口径。

**最小修复（较大）**：为运费增加 `SOURCE_TYPE` 与 `ACCOUNT_MAPPING`，
在结算时生成凭证（借费用 / 贷 2202）；
勾稽查询改为显式列出包含/排除的来源并展示差异。
**历史数据需人工凭证或专项修复，不要写自动回填脚本。**

**这条的严重性取决于"运费结算功能是否已在实际使用"——需主负责人确认。**

**业务方澄清（2026-09-26）：「运费对账是和快递自动下单绑定的。」**
这句话修正了上面"孤儿半成品"的判断，我据此重查了代码与历史文档，结论如下：

**① 它确实是同一个功能包（06 电子面单）的一部分**——
2026-07-31 同一批 WIP 快照进入仓库、共用承运商与运单数据、外包商权限体系。
所以它**不是被遗弃的孤儿**，而是**一条尚在推进中的功能链的尾端**。
这一点很重要：不要按"清理死代码"处理它。

**② 但"绑定"只到数据层，流程上是断的**——这是必须说清的关键点：

| | 实际情况 |
|---|---|
| 自动下单时系统拿到运费了吗 | **拿到了**。`logistics.worker.js:113` 把平台返回的 `res.freight` 写进 `logistics_waybills.est_freight`（"平台预估运费"），前端物流列表/详情**能看到** |
| 这个预估运费会自动变成运费账单吗 | **不会。** `logistics_freight_bills` 的唯一写入点是 `logistics.freight.js:112`，只被手工录入接口调用 |
| 那运费账单怎么来 | **只能逐单手工录**：页面要求选承运商、填快递单号、填金额、填账期，一次一单 |
| 有批量导入吗 | **没有**。全模块只有 4 条路由（`logistics.routes.js:42-45`），录入接口一次只收一单 |
| 那"绑定"体现在哪 | 仅在于**单号匹配**：录入的快递单号会去 `logistics_waybills` 找运单，从而知道这单是寄付还是到付，决定是否计入应付（`logistics.freight.js:97-104`） |

设计文档也印证这是**有意为之**：`docs/direct-express-2026-09-06.md:56` 明确写
"最终实重由快递员称重确认，**不写入实际重量或运费账单**"——
即系统从一开始就打算让人工把承运商月结账单录进来（`docs/direct-express-2026-09-06.md:5`：
"用户已有两家月结账号……运费仍按已有月结合同结算"）。

> **页面存在一处对用户的虚假承诺**：运费账单空列表时的提示是
> "暂无运费账单（点「录入账单」添加，**或对接平台回传**）"——
> "对接平台回传"这条路径**代码里不存在**（没有任何导入接口）。
> 属于文案承诺了未实现的能力。

**③ 使用状态：整条链的头（自动下单）至今仍暂停，从未投产。**
历史文档的最后记录（2026-09-09，`docs/direct-express-2026-09-06.md:176`）明确：
"常用服务尚未选择、**已验收清单为空、自动下单仍暂停**"；
生产核对同时记载"**当前没有顺丰运单**"、"德邦仍未配置"
（`docs/carrier-production-setup-2026-09-08.md:36`、`:14`）。
此后至今（2026-09-26）**没有找到任何"已启用"的记录**。

**由此得到的判断（证据强度：文档确证 + 代码确证）**：
既然自动下单没启用、生产里也没有运单，那么运费对账**没有可供匹配的运单对象**，
**大概率同样没有在跑**。两个功能是"头还没通、尾在里面等着"的状态。

**⚠ 这反而把优先级问题问对了**：真正决定这条何时必须修的不是
"运费页有没有人在用"，而是——**「快递自动下单打算什么时候启用？」**
因为一旦自动下单开闸，运单开始批量产生，运费对账立刻变得可用、可用就会被用，
**那一刻起产生的应付就全部不进总账**，且逐月累积。
**修复应当赶在自动下单启用之前落地**，而不是等出账再补。

**业务方已答复（2026-09-26）：快递自动下单「还没定 / 更远」。**

**据此的落地判断**：

- 运费对账本任务**不挤当前修复窗口**，排在任务 1、2 之后即可。
- 但这个判断的**有效期 = 自动下单尚未启用的期间**。
  答复是"还没定"，**不是"不启用"**——链子头一开，运单批量产生，
  运费对账立刻可用、可用就会被用，**那一刻起产生的应付就全部不进总账**，且逐月累积。
- 因此必须给这条任务挂一个**前置触发条件**（已写入任务卡）：
  **一旦快递自动下单的启用排期确定，本任务立即提为与它同批上线，不得拖后。**
  这也是本任务被保留在清单里、而不是"关掉不做"的理由。

**顺带发现（同一规则的第 4 处实现）**：`logistics.freight.js:207` 重算运费应付时
也用了 `status = CASE WHEN paid_amount >= ? THEN 3 ...`——
即 §3.2.2 那条"`total=0` 时被误判已付清"的**同一判式在系统里有 4 份拷贝**：

| # | 位置 | 侧 |
|---|---|---|
| 1 | `inbound-tasks.settle.js:85` | 应付（采购收货） |
| 2 | `sale.service.js:371` | 应收（销售出库） |
| 3 | `logistics.freight.js:207` | 应付（承运商运费） |
| 4 | `database/130_fix_sale_order_items_warehouse_after_adjust.sql:80` | 历史补丁 |

**修复时必须 4 处一起看**，只改 `settle.js` 会留下另外 3 个同类缺口——
这正是 §3.1 根因一（同一规则多处实现、只修一处）在本议题上的重演。
（应收侧 `sale.service.js:344-348` 已有 `total <= 0` 的处理分支，
比应付侧严谨，但判式本身仍是同一份。）

#### 3.3.2 金额三套算术（尾差）【待核实】

同一个"应收金额"在三个地方用不同方式算出：
- 订单总额：按**录入单位**逐行 `round2(entryQty × entryUnitPrice)`
- 应收台账 `sale.service.js:311-312`：`SUM(shipped_qty × unit_price)` **不逐行四舍五入**
- 会计凭证：BigInt 定点，先 `halfUp` 到分再分摊

**触发**：多行 + 单位换算率 ≠ 1 + 分批出库 + 整单折扣。
**后果**：`sale_orders.total_amount` 与 `payment_records.total_amount` 可差 1 分，
折扣再按比例二次分摊会放大偏差。**分厘级，不影响业务决策，但会让对账出现无法解释的尾差。**

#### 3.3.3 同类（待核实）

- **成本快照为空记 0**【待核实】：`cost_snapshot ?? 0`，
  报表侧却用 `COALESCE(cost_snapshot, cost_price, sale_price, 0)` 兜底
  → **报表毛利与凭证毛利口径分叉**，无告警。
- **对账单导出丢筛选**【待核实】：`export.service.js:545-549` 只透传
  type/status/keyword，丢弃单据号/往来方/日期/金额区间。
- **reprint 打印 VOID 容器**【待核实】：三种模式的容器查询只过滤 `deleted_at`，
  无状态过滤 → 撤回后补打会把 `remaining_qty=0` 的已作废容器当真标签打印。

### 3.4 根因四：数据新鲜度只在"本会话"内维护

**机制**【代码确证】：`frontend/src/lib/queryClient.ts:13-16`
```ts
retry: 1,
staleTime: 1000 * 60 * 5,
refetchOnWindowFocus: false,
```
`useInvalidate`（`hooks/useInvalidate.ts`）维护了一张"业务事件 → 失效的 queryKey"映射表，
在 mutation 成功后调用。**它只影响执行操作的那个会话。**
商品查找器 `hooks/useProducts.ts:11-12` 未设 per-query `staleTime`，继承全局 5 分钟。

**触发条件**：员工 A 在 PC 打开销售开单页（查找器显示可用量），
员工 B 在 PDA 上出库了同一商品。A 的页面收不到任何失效信号。
`refetchOnWindowFocus: false` 意味着 A 切走浏览器再切回来**也不会刷新**。
（`useVisibleQuery` 在 Tab 隐藏/显示时会重新订阅，可缓解应用内切 Tab 的情况，
但查找器用的是普通 `useQuery`。）

**实际行为**：A 看到的是最多 5 分钟前的可用量。
**重要边界**：**这不导致超卖。** 提交时后端仍会做预占校验与容器锁，
A 会被拒绝并看到错误。所以这是**"看到能做、点了才说不能"的体验问题**，
不是数据被写坏。

**为什么现有防护没覆盖**：`useInvalidate` 的设计前提是"操作者自己需要刷新"，
没有考虑"别人操作了、我需要知道"。项目自己的
`docs/system-deep-acceptance-2026-09-24.md` §7 已把查找器 5 分钟陈旧缓存
标为"已复现正确性问题"，本轮确认根因仍在。

**附带发现**：`hooks/useInvalidate.stock.test.tsx` 是**同义反复测试**——
它的 `affecting` 数组（第 20-24 行）是**从实现的 `FINDER_STOCK_EVENTS` 集合抄过来的**
同一份清单。实现漏配一个事件，这个测试也会同步漏测。
它只能证明"实现和它自己一致"，**不能发现漏配**。

**最小修复**：查找器加独立且更短的 `staleTime`；或对
`refetchOnWindowFocus` 按页面类型放开；
或把 `FINDER_STOCK_EVENTS` 改为从业务事件定义派生而非手写两份。
**这是体验优化，不是正确性缺陷，优先级低于 §3.2。**

### 8.3 已定产品决策：补录之后，凭证落在哪一期？

**报告 §5 第 3 位原写"走审批放行后凭证必须生成"——实现已做到，但落点与原设想不同，
必须说清楚，否则会与 `finance-backfill-approval` §F 正例的断言对不上**：

- 期间已结账（`acct_periods.status=2`）是**有意的会计约束**，凭证引擎在已结账期间
  拒绝写入是正确的。**补录不撬开已封的期间**：业务数据（`payment_entries`、账款余额、
  资金账户流水）按业务日期落库，**资金流水的 `happened_at` 保持业务日期不变**；
  凭证则**不落在那个已结账期间**。
- **已定（2026-09-26）：凭证落在「执行审批当天所属的期间」**。
  落期由 `voucherDateOverride = beijingTodayYmd()` 写入
  `finance_account_transactions.voucher_date_override`，凭证引擎取
  `r.vdate_override || r.vdate`，最终体现在 `acct_vouchers.voucher_date`。
  这样"业务事实留在原始业务日期、会计调整落在发现它的当期"，是标准的追溯调整口径。
- **生成时机是"业务提交后立即"，不是"等 regenerate 补齐"**：`execute` 在业务事务
  **提交之后**调 `settleVouchersFor` → `generatePeriodVouchers` + 逐笔核对
  （每条流水的有效凭证、期间、借贷金额、分录数）。核对通过置
  `voucher_generated_at`；**核对不过才**写 `voucher_generate_error` 停在待生成，
  由页面「重新生成凭证」（`regenerateVoucher`）与定时 `retryPendingVoucherGeneration` 重试。
  两段事务不能合并的原因见 `finance-backfills.service.js` `execute` 注释
  （凭证生成是独立全量重算，读的是已落库数据；塞进业务事务会读不到自己未提交的写入，
  把刚补好的凭证判成缺失）。
- **补录当期也已结账时会被明确拒绝，不会"钱先动、凭证补不上"**：
