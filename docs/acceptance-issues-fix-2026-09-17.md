## 一、错误码保真（ISSUE-003 / 015 / 016 根因，影响面最大）

- **问题**：后端对未带业务码的 4xx 兜底成 `CONFLICT` 等通用码，前端优先用通用码渲染，
  把「箱贴仍待确认：箱号 L000493 尚未打印完成，请先收口打印任务」「该容器 5 件超出调拨单
  剩余可调量 1 件」这类**唯一可操作的提示**替换成「状态已变化，请刷新后重试」，现场反复刷新
  永远无效（打包、调拨、上架都会中招）。
- **修复**：
  1. `backend/src/middleware/errorHandler.js`：`AppError` 只在**显式带 code** 时才输出 code，
     不再编造通用码，后端中文原因原样下发。
  2. `frontend/src/utils/displayFormatters.ts` 新增 `resolveApiErrorMessage()`：通用码
     （CONFLICT / BUSINESS_ERROR / INTERNAL_ERROR / ERROR / UNKNOWN）一律以后端中文原文优先；
     具体业务码仍按既有映射展示。`frontend/src/api/client.ts` 改用它。
- **验证**：`tests/acceptance-fixes-2026-09-17.test.js`（未带码的 AppError → `code: null` 且原因保留；
  显式码保留）、`frontend/src/utils/displayFormatters.apiError.test.ts`（通用码不覆盖中文原因）。
  GUI 回归：PDA 打包页现在直接弹出「箱贴打印失败：箱号 L000493，no printer available」；
  调拨调出页弹出「该容器不在本调拨单的调出仓库」。

## 二、打包环节（ISSUE-003 / 015）

- **修复**：`backend/src/modules/packages/packages.service.js` 的箱列表返回最新箱贴打印状态
  （`printStatus: {key,label,errorMessage}`）；PDA 打包页显示每箱「箱贴：待派发/已打印/打印失败」，
  并在完成打包按钮上方常驻告警块，列出待处理箱与三条出路（重新入队打印、ERP「条码打印查询 →
  出库条码」重新打印、启动绑定打印机的桌面客户端）。
- **保留的业务规则**：「箱贴未打印成功不得进入待出库」是服务端强制的前置校验，本轮**不改规则**，
  只让现场能看懂原因并知道去哪里收口（原问题是无提示 + 提示错误，不是规则本身）。

## 三、调拨（ISSUE-016 / 018）

- **修复**：PDA 调出页显示每个商品的「剩余可调 X」并说明"容器数量需不超过剩余可调量"；
  调出/调入第三步不再用 `R<数字>`/`LOC-*` 前缀卡库位格式，改为把扫描值交给后端按
  「编码或条码」解析（`frontend/src/flows/putawayFlow.ts`、`frontend/src/pages/pda/transfer-in.tsx`），
  归属仓/库位状态仍由服务端校验。
- **迁移**：`245_backfill_location_barcode.sql` 回填历史库位的 `barcode`（`R+6位ID`），
  与新建库位的生成规则一致，避免"库位没有条码扫不了"。
- **验证**：PDA 扫 `SH-A01`（库位编码）现在能被服务端受理，并如实返回
  「设备绑定仓库与调拨目标仓不一致，无法扫入」——证明前端不再误拦、服务端闸门仍在。

## 四、盘点（ISSUE-009）

## 十、续测新增（2026-09-17 晚，补齐调拨调入与盘点闭环时发现）

### ISSUE-019（P1）纯 PDA 扫码完成的盘点单在 ERP 提交不了

- 现象：盘点单全部明细都由 PDA 扫码完成（`scanDriven`）时，ERP「提交盘点」只弹
  「请至少填写一行实盘数量后再保存」，单据永远停在「进行中」——盘点链断在最后一步，
  库存无法按实盘调整。
- 原因：`CheckDetailDialog.validateActuals()` 先过滤掉扫码行，再要求"至少有一行手工填写"；
  G-13 修复（空输入不能当 0）之后这条规则没有为"全部扫码行"留出口。
- 修复：存在已扫码且实盘非空的明细时，允许"无手工行"提交（`items` 为空数组，后端按扫码集合派生实盘）。
- 验证：北京主仓全盘单 SC20260917006（2 行明细、8 个容器）经 PDA 扫码后，ERP 提交成功转为
  **已完成**；明细 账面 100/实盘 100/差异 0、账面 50/实盘 50/差异 0，库存保持 100/50 未被改写，
  扫码明细（I005336=100、B000564=0、I005337=50）留痕正确。

### ISSUE-020（自查）引入并修复：SQL 文本里的 `--` 行内注释导致语法错误

- 本轮给 `listPendingScanChecks` 加 LEFT JOIN 时把说明写成了 SQL `--` 注释，注释后紧跟全角
  括号，MySQL 不认为它是注释，`GET /api/stockcheck/scan/pending` 直接 `ER_PARSE_ERROR` → 500，
  PDA 扫码盘点列表全空。
- 修复：说明移到 JS 注释；`pendingCount` 同时改为只统计真实存在的明细行
  （`ici.id IS NOT NULL AND ici.actual_qty IS NULL`），空单显示 0/0。
- 验证：服务函数直调返回两单；HTTP `GET /api/stockcheck/scan/pending` 由 500 恢复 200，
  PDA 列表正常显示「SC20260917005 无盘点明细，请在 ERP 取消后重建」与「SC20260917006 待盘 2/2」。

## 十一、发版 CI 连带修正（v0.9.20，2026-09-18）

本批改动推上 main 后，Tests 有两个旧断言与本次有意的行为变更冲突，已随发版修正：

| 失败项 | 原因 | 处理 |
|---|---|---|
| `smoke:warehouse-assets-waves`：`待归还成员沿用业务错误` `["CONFLICT", …] != [null, …]` | 断言的正是**被本次移除的通用码兜底**：波次完成遇待归还/待改单成员时后端抛的是不带 code 的 `AppError`，现在按「错误码保真」下发 `code: null` + 中文原文 | 断言改为 `[null, message]`（同时钉住中文原文），并更新 `docs/warehouse-assets-waves-regression-2026-09-13.md` 的表述 |
| `smoke:warehouse-scope`：`别人仓的盘点单详情被拒 — status=500` | 新规则「仓库没有在库商品时不允许创建盘点单」让该用例在空仓建单失败，拿到 `NaN` 再去请求 `/api/stockcheck/NaN` 才报 500（**不是权限回归**） | 场景内先 `createProduct` + `seedStock` 给目标仓铺底一箱在库商品再建单；仓库范围隔离断言本身未放宽 |

「未带业务码 4xx」的旧期望，以及空仓夹具的铺底方式。
