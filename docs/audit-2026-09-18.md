## 二、P0：已由本人逐行复核确认（5 条）

这 5 条是**两轮独立扫描各自命中、且我已亲自读代码确认**的问题。共同特征是「静默出错」——界面正常、数字悄悄不对，或货在系统里消失。

### P0-1 盘点扫码把「已被拣货任务锁定」的容器当未扫到清零

- **位置**：`backend/src/modules/stockcheck/stockcheck.service.js:440-443`
- **复核结论**：**成立**。账面容器查询为
  `SELECT id, barcode, remaining_qty FROM inventory_containers WHERE product_id=? AND warehouse_id=? AND status=? AND deleted_at IS NULL ORDER BY id ASC FOR UPDATE`
  —— **无 `locked_by_task_id` 条件**；紧随其后的 `:447` 是 `const counted = scannedMap.get(Number(bc.id)) ?? 0`，即「没扫到 = 全亏」。
- **为什么既有修复没挡住**：库存引擎侧有明确防线（`containerEngine.js:269-279`，注释写着「必须排除已被拣货任务锁定的容器……否则持锁任务出库时会永久卡在待出库」），但那道防线在 `deductFromContainers` 里。**PDA 扫码盘点是后来新增的分支，自拼批量 UPDATE，绕开了引擎闸门** —— 典型的「修复漏了调用点」。
- **后果**：拣货中的货物理上在料箱/分拣区，盘点员扫不到 → `counted=0` → `remaining_qty` 归零并置 `EMPTY`，缓存同步下调。随后该任务出库时 `deductFromTaskLockedContainers` 找不到可用锁定容器 → 400 永久卡在待出库，现场无自助解法。账面漂移校验拦不住：拣货锁定**不改** `remaining_qty`，所以不构成「漂移」。
- **改法**：账面容器查询补 `AND locked_by_task_id IS NULL`（与引擎同口径）；或盘点前显式 409 提示「有 N 只容器正被拣货任务锁定」。长期应收敛进引擎出口函数，禁止模块层再自拼容器扣减 SQL。

### P0-2 库存容器写接口缺仓库范围校验，移库还不校验库位与容器同仓

- **位置**：`inventory.routes.js:58-62`（移库）、`:63-70`（拆分）；`inventory.controller.js:172-194`
- **复核结论**：**成立**。两个 handler 分别是
  `svc.assignContainerLocation(containerId, locationId)` —— **完全不传 `scopeWarehouseIds`**；
  `svc.splitContainerOp(id, { qty, remark, printLabel, targetContainerId, userId, userName })` —— 同样不传仓库范围。
  对照同文件其它 handler（`:46/57/72/134/152/166/206/236/247/261`）都传了 `req.user?.warehouseIds ?? null`，说明这是遗漏而非设计。
- **附带问题**：`inventory.service.js:1064` 取容器时 `SELECT id, barcode, status ... FOR UPDATE` **不取 `warehouse_id`**，`:1075` 取库位时只 `SELECT id, code`，因此**移库不校验目标库位与容器是否同仓**。
- **后果**：① 限仓用户可把别仓 ACTIVE 容器改到任意库位（包括指向自己仓的库位编码），该容器从此带错误位置在册，拣货路由、盘点、追溯全部按错位置取数；② 可对别仓容器执行拆分（扣余量、建新盒、写流水、入队标签）。
- **改法**：两个 handler 补 `scopeWarehouseIds`；service 在 `FOR UPDATE` 取到容器后立即 `assertInScope(..., container.warehouse_id)`；移库同时校验目标库位 `warehouse_id` 与容器一致。

### P0-3 销售出库收入凭证按**毛额**入账，与应收/报表的**折后净额**口径不一致

- **位置**：`backend/src/modules/accounting/voucher-engine.js:218-240`（`buildSaleRevenue`）
- **复核结论**：**成立**。凭证侧：
  `COALESCE((SELECT SUM(shipped_qty * unit_price) FROM sale_order_items WHERE order_id = pr.order_id), 0) AS gross`，随后 `1122 应收账款` 借方 = `gross`、`6001 主营业务收入` 贷方 = `gross - tax`。
  账款侧（`sale.service.js:342-343`）：
  `const total = Math.max(0, grossTotal - (Number(returnedAmount) || 0) - discountApplied)` —— **扣了整单折扣**。
- **后果**：只要有整单折扣，总账 `1122` 比子账应收多出 Σ折扣，勾稽长期对不上；收入与利润虚增 Σ折扣。两个账各自内部自洽，因此不会互相报警。
- **改法**：`buildSaleRevenue` 复用 `calculateDiscountApplied` / `getNetOrderAmount` 的同一口径（按已发原值比例分摊折扣），使凭证净额与 `payment_records` 一致。

### P0-4 补占时更换发货仓库不迁移旧仓预占 → 孤儿预占 + 静默释放他人预占

- **位置**：`backend/src/modules/sale/sale.service.js:1389-1395`（`reserveStock`）
- **复核结论**：**成立**。该处无条件下发
  `UPDATE sale_order_items SET warehouse_id = ?, warehouse_name = ? WHERE id = ? AND order_id = ?`
  —— 全函数**没有任何旧仓预占释放或换仓一致性校验**；`:1363-1371` 的占库量校验只按 `row.quantity - row.reserved_qty`，**不区分仓库**；`assertInScope` 只校验新仓在范围内。
- **机制确证**：`inventoryEngine.js:194-203` 出库释放预占时用
  `UPDATE inventory_stock SET reserved=GREATEST(0, reserved-?) ...`，
  且引擎注释自己写明这个风险：「会把同商品同仓下其它销售单的预占凭空释放掉：可用量虚高 → 别的订单占走同一批货 → 原订单拣货时货已不在 → **超卖**」，并在 `reserved < absQty` 时打 `[GUARD]` 日志。
- **后果**：行在 A 仓已占 60，补占时切到 B 仓再占 40 → 明细 `warehouse_id=B, reserved_qty=100`，而预占账是 A:60 + B:40。出库按行仓库 B 整量履约 `moveStock(100)`：B 的 reserved 若含他单预占会被 `GREATEST` 一并截掉（超卖）；A 的 60 成为**永不释放的孤儿预占**，A 仓可用量永久虚低。
- **改法**：写回行仓库前，若该行已有有效预占且仓库变化，先按 `(product, warehouse)` 释放旧仓该行 `reserved_qty`；或在 `reserved_qty > 0` 时禁止换仓并返回 400。

### P0-5 撤回收货吞掉**在途调拨**容器：货从账上消失 + 调拨单永久卡在在途

- **位置**：`backend/src/modules/inbound-tasks/inbound-tasks.void.js:51-70`
- **复核结论**：**成立**，且机制比原报告更直接。
  - 候选容器集：`WHERE inbound_task_id = ? AND deleted_at IS NULL AND status IN (ACTIVE, PENDING_PUTAWAY, EMPTY)` —— **全文没有任何 `transfer_order_id` 引用**。
  - 两道守卫：`locked_by_task_id != null` → 拒绝；`remaining_qty != initial_qty` → 拒绝。
  - 而**整箱调拨复用同一容器行**（`transfer.service.js:294`）：
    `UPDATE inventory_containers SET warehouse_id = ?, status = ?, location_id = NULL, transfer_order_id = ? WHERE id = ?`
    —— 只改 `warehouse_id / status / transfer_order_id`，**数量一字未动**，因此 `remaining_qty == initial_qty` 恒成立；`locked_by_task_id` 也为空。
  - 于是两道守卫**全部放行**，容器被置 VOID / `remaining_qty=0`，且不写任何 `inventory_logs`（`void.js` 自述的安全边界形同虚设，注释却把「已被调拨动过」列为应拦截对象）。
- **后果**：货在运输途中从账面消失（源仓已减、目的仓未入，中间态被抹掉）；`transfer_order_id` 仍指向该 VOID 容器 → 目标仓 `scanIn` 失败 → **调拨单永久卡在在途**，只能走 force-close 了结。旁证：`transfer.service.js:485` 注释明确「在途容器源仓/目的仓的盘点都覆盖不到」，说明系统本来承认在途是可见性盲区，撤回收货却直接把它删了。
- **改法**：`void.js` 的候选查询与 `touched` 判定都纳入 `transfer_order_id`；非空即 409「存在 N 个条码正在调拨在途，请先在调拨单扫入或异常了结后再撤回收货」。

## 五、审计边界与建议

1. **两轮扫描的 P0 集合不重合**（第一轮 3 条、第二轮 2 条，合计 5 条且互补）。这说明**单轮扫描并不穷尽**，本轮结论应视为「高置信抽样」而非「完备证明」。建议按季度做一次同类扫描，并逐步把不变量的守卫做成**静态契约测试**（见 F-4）而不是依赖人工审计。
2. **最高杠杆的修复顺序**：
   - 先修 **P0-5（撤回收货吞调拨在途）** 与 **P0-1（盘点核销拣货锁定容器）** —— 两者都会让货物从账上消失且不可自愈；共同根因是「模块层自拼容器写 SQL，绕开引擎闸门」，建议一并收敛。
