## 1. 背景与现状

### 1.1 现状：完全没有预测

`grep -rni "forecast|需求预测|mrp|purchase_plan|采购计划|请购"` 在 `backend/src` 与 `frontend/src` **全部为空**。系统对"未来要卖多少、该提前买多少"没有任何机制，采购时点和数量全靠采购员经验。

### 1.2 与文档 01 的关系（务必分清）

文档 01 和本文都是"告诉运营该补货"，但**触发逻辑根本不同**，是两层能力：

| 维度 | 文档 01 · 补货建议 | 文档 11 · 需求预测与采购计划（本文） |
|---|---|---|
| 触发方式 | **被动**：库存跌破补货点才提醒 | **主动**：预测未来 N 天要卖多少，提前规划 |
| 数量依据 | 静态基准 `target_stock`（人工设的目标库存） | **历史出库趋势** → 预测未来需求 |
| 看的时间轴 | 只看"现在"（当前可用 vs 补货点） | 看"未来"（提前期 + 覆盖周期内的净需求） |
| 提前期 | 不考虑（Phase 2 才提） | **核心输入**：提前期决定"现在就得下单"还是"还能等" |
| 产物 | 补货建议列表（补到目标库存） | **采购计划**（可按供应商/到货周期分批，可调整，可转采购单） |

一句话：**01 回答"哪些商品该补、补到多少"，11 回答"根据卖货趋势，未来一段时间总共要买多少、什么时候下单、向谁买"**。11 是 01 的进阶延伸，两者共用同一套安全库存基准（`product_stock_policies`）和同一套库存/在途口径，不冲突、不重复。

### 1.3 为什么是"轻量版 MRP"

标准 MRP（物料需求计划）是多级 BOM 展开 + 时段化净需求（time-phased netting）+ 能力约束的重型系统。本文**刻意只取其最有价值的骨架**：

- **只做单级**：flowcube 是贸易/仓储型 ERP，商品即采购件，没有 BOM 多级展开。
- **只做需求侧预测 + 净需求计算**：预测未来需求 → 扣掉现有和在途 → 得出该买多少。
- **不做时段化排程、不做产能约束、不做自动下单**。产物是**建议**，最终决策权在采购员（见第 2 节非目标与第 5.4 节）。

这样落地风险可控，且和系统"仓库/现场只执行不决策；办公端可给建议"的取向一致——采购计划是办公端功能，给建议合理，但不越权替采购员下单。

## 2. 目标 / 非目标

**目标**
- 基于历史出库趋势，按 **商品 × 仓库** 粒度预测未来 N 天的需求（Phase 1 用简单移动平均）。
- 引入**供应商采购提前期** `lead_time_days`（文档 01 Phase 2 提到、本文正式设计）。
- 用 MRP 净需求公式算出**采购计划建议**：`净需求 = 预测毛需求 + 安全库存 − 可用 − 在途`。
- 一个"采购计划"页：生成一批计划建议 → 采购员可逐行调整数量/供应商/到货日 → 勾选转采购单草稿。
- 建议可**按供应商分组、按到货周期分批**呈现。

**非目标（本期不做，留后续或 Phase 2/3）**
- 多级 BOM 展开、时段化排程、产能约束（标准 MRP 的重型部分，本系统无此需求）。
- **自动下单 / 自动审批采购单**：本文只产出建议草稿，采购员必须人工确认（硬约束，见第 5.4、第 11 节）。
- 加权移动平均、季节性因子（Phase 2）；预测准确度回溯看板（Phase 3，见第 4.4 节 `demand_forecasts` 表）。
- 商品默认供应商主数据（本文用"计划页选供应商 + 最近采购供应商兜底"，见第 11 节待确认）。

## 5. 核心算法与流程

### 5.1 预测算法：先做简单移动平均（SMA）

**Phase 1 只做简单移动平均**，别过度工程化：

```
预测日均需求 ADU = Σ(最近 N 天 sale_out 已出库 picked_qty) / N        [按 商品 × 仓库]
```

- `N` = `forecast_window`（默认 30 天），是滑动取样窗口。
- 分母固定用 `N`（自然日）而非"有出库的天数"——把没卖的日子算进去才是真实日均，否则会系统性高估。
- 数据源严格按第 3.1 节口径：`warehouse_tasks.task_type='sale_out' AND status=7`，用 `shipped_at` 落在 `[今天-N, 今天)` 的任务，取 `warehouse_task_items.picked_qty` 按 `(warehouse_id, product_id)` GROUP BY 求和。

**Phase 2 增强（不在本期）**：
- 加权移动平均 WMA：近期权重高，`ADU = Σ(qty_i × w_i) / Σw_i`，如最近一周权重 3、上上周 1。
- 季节性因子：用去年同期 / 上月同期的同比系数放大缩小 ADU（需至少一年历史，冷启动前无意义）。

### 5.2 需求覆盖周期与毛需求

要覆盖的时间轴 = **提前期 + 补货覆盖周期**（下单后到货要 `lead_time` 天，到货后这批货还要撑 `horizon` 天到下一次补货到货）：

```
毛需求 GR = ADU × (lead_time_days + horizon_days)
```

- `lead_time_days`：本行提前期（供应商.lead_time_days，未设则回退计划头 `default_lead_time`）。
- `horizon_days`：计划覆盖周期 `P`（默认 30，即"这批货要撑一个月"）。

### 5.3 MRP 净需求（建议采购量）

这是"轻量 MRP"的核心一步——**需求 − 供给 + 安全垫**：

```
安全库存 SS = COALESCE(本仓 policy, warehouse_id=0 默认, 0)          [复用文档 01 基准]
可用量 AV   = GREATEST(0, inventory_stock.quantity − reserved)      [复用文档 01 口径]
在途采购 IT = Σ(已提交PO下单量) − Σ(已上架 putaway_qty)            [复用文档 01 口径]

净需求（系统建议采购量）
  suggested_qty = GREATEST(0, GR + SS − AV − IT)
```

**两个容易算错的点（沿用文档 01 的踩坑记录）**：
1. **可用量已扣过预占 `reserved`，公式里不再 `+ 已占用`。** 用"可用量"当基数就是已经扣干净的口径，再补回预占是重复扣、建议量虚高。
2. **在途减 `putaway_qty`（已上架）而非 `received_qty`（已收未上架）**，与"可用量=已上架容器"首尾衔接，"已收未上架"仍算在途、不留空档不漏计。

**建议到货日** `expected_arrival = 今天 + lead_time_days`，用于按到货周期分批展示。

### 5.4 端到端流程（决策支持，不自动下单）

```
采购员在"采购计划"页
  → 设参数（预测窗口 N、覆盖周期 P、目标仓库范围）→ 点"生成计划"
后端 POST /procurement/plans（一次只读计算，不碰任何库存写）
  ① 拉最近 N 天 sale_out 出库 → 算 ADU（商品×仓库）
  ② 拉 product_stock_policies（安全库存基准，复用 01）
  ③ 拉可用量投影 + 在途采购（复用 01 口径，只读缓存）
  ④ 逐行算 GR / suggested_qty / expected_arrival
  ⑤ 只保留 suggested_qty > 0 的行，落 procurement_plans + _items（全快照）
采购员逐行审阅
  → 可改 adjusted_qty（默认=suggested）、补选 supplier_id、忽略某些行(status=3)
  → 勾选若干行 → POST /procurement/plans/:id/convert
      target=purchase：按 supplier_id 分组，每组生成一张采购单草稿(status=1)
      target=requisition：生成请购单（文档 02 落地后）
  → 回填 plan_item.purchase_order_id、item.status=2、必要时 plan.status=2/3
最终确认采购单(→2 已提交)仍是采购员的人工动作，本流程绝不自动推进
```

**硬约束贯穿全程**：本流程**只读库存/在途/出库缓存**，`POST /procurement/plans` 不做任何 `inventory_*` / 容器 / 预占写入；转采购生成的是**草稿**，需人工确认。采购计划是办公端的**决策支持**，与"仓库/现场只执行不决策"不矛盾——它给采购员建议，不替采购员拍板。

**生成计划主查询骨架**（`procurement.service.js`，实现时精修表名/列名，`sold` 与 `pt`/`ip` 三个子查询都下推仓库范围与时间窗）：

```sql
SELECT p.id AS product_id, p.code, p.name, p.unit, ip.warehouse_id,
       COALESCE(sold.total_sold, 0) / :N                         AS adu,
       GREATEST(0, ip.quantity - ip.reserved)                    AS available,
       COALESCE(pt.in_transit, 0)                                AS in_transit,
       COALESCE(sp_wh.safety_stock, sp_def.safety_stock, 0)      AS safety_stock,
       COALESCE(sup.lead_time_days, :defaultLeadTime)            AS lead_time_days
FROM (SELECT product_id, warehouse_id, quantity, reserved FROM inventory_stock) ip
JOIN product_items p        ON p.id = ip.product_id AND p.deleted_at IS NULL AND p.is_active = 1
JOIN inventory_warehouses w ON w.id = ip.warehouse_id            -- 表名以 warehouses 模块实际为准
LEFT JOIN product_stock_policies sp_wh  ON sp_wh.product_id=ip.product_id AND sp_wh.warehouse_id=ip.warehouse_id
LEFT JOIN product_stock_policies sp_def ON sp_def.product_id=ip.product_id AND sp_def.warehouse_id=0
LEFT JOIN (   -- 最近 N 天真实出库：口径见 3.1
  SELECT wt.warehouse_id, wti.product_id, SUM(wti.picked_qty) AS total_sold
  FROM warehouse_tasks wt
  JOIN warehouse_task_items wti ON wti.task_id = wt.id
  WHERE wt.task_type='sale_out' AND wt.status=7
    AND wt.shipped_at >= DATE_SUB(CURDATE(), INTERVAL :N DAY)
  GROUP BY wt.warehouse_id, wti.product_id
) sold ON sold.warehouse_id=ip.warehouse_id AND sold.product_id=ip.product_id
LEFT JOIN (   -- 在途采购：口径见 3.1（purchase_orders.warehouse_id 在单头）
  SELECT po.warehouse_id, poi.product_id,
         SUM(poi.quantity) - COALESCE(SUM(done.putaway),0) AS in_transit
  FROM purchase_orders po
  JOIN purchase_order_items poi ON poi.purchase_order_id = po.id
  LEFT JOIN ( /* 每 PO×商品 已上架 putaway_qty，audit_status=1，见 purchase.service.js */ ) done
         ON done.purchase_order_id=po.id AND done.product_id=poi.product_id
  WHERE po.status=2 AND po.deleted_at IS NULL
  GROUP BY po.warehouse_id, poi.product_id
) pt ON pt.warehouse_id=ip.warehouse_id AND pt.product_id=ip.product_id
LEFT JOIN supply_suppliers sup ON sup.id = :chosenSupplierId     -- 供应商提前期，MVP 可后置到应用层取
WHERE p.deleted_at IS NULL ${scope.sql}                          -- scopeFilter(ids,'ip.warehouse_id')
```

毛需求与建议量在应用层算（避免 SQL 里堆表达式）：
`GR = adu × (lead_time_days + horizon)`；`suggested_qty = GREATEST(0, GR + safety_stock − available − in_transit)`；只落 `suggested_qty > 0` 的行。

**并发/幂等**：`POST /procurement/plans` 和 `/convert` 都接 `X-Request-Key`（`beginOperationRequest/completeOperationRequest`），防采购员连点生成重复计划或重复转采购。转采购在事务内：锁计划头 `lockStatusRow` → 校验行 status=1 → 建采购草稿 → CAS 回写 item.status=2 + `purchase_order_id`。

## 11. 风险与待确认

- **别过度自动化（最高优先级）**：本文严守"建议不下单"。任何"定时自动生成计划 + 自动转采购 + 自动提交"的诉求都要单独评审——一旦预测偏差被自动放大成真实采购，就是静默的资金/库存损失。采购员的人工确认环节**不可省**。
- **预测准确度 / 冷启动**：SMA 对新品（无历史）、促销/大客户一次性大单、季节性商品都会失真。缓解：① 新品无出库时 ADU=0、不进计划（靠文档 01 的静态补货点兜底）；② 页面明确标注"基于历史趋势，供参考"；③ Phase 2 才上季节性，且需至少一年历史，冷启动期不启用。
- **一次性大单污染日均**：某天一张超大出库会把 ADU 顶高。Phase 2 可考虑剔除离群值或改用中位数/加权；Phase 1 先接受，靠采购员在明细页人工下调 `adjusted_qty` 兜底。
- **商品→供应商映射缺失**：系统当前无"商品默认供应商"主数据。MVP 让采购员在计划明细页手动选供应商；可用"该商品最近一次采购的供应商"做默认建议。是否引入商品默认供应商字段，待确认（会影响提前期取值与转采购分组）。
- **提前期粒度**：MVP 供应商级。若同一供应商不同品类到货差异大，Phase 2 再细化到"商品×供应商"。全局默认提前期（计划头 `default_lead_time`，默认 7）是供应商未设时的兜底，不是精确值。
- **依赖文档 01 未落地**：`product_stock_policies` 是 01 的产物、当前仓库尚无此表。11 实现前需确认 01 的迁移 151 已落地，或把等价 DDL 一并带上（见 3.1）。安全库存取不到时 `SS` 回落到 0，建议量会偏低但不会出错。
- **在途/出库口径边界**（沿用文档 01）：在途只算 `status=2` 的开口采购单；短装结案(→3)的未收部分不再计入在途（符合预期）。出库只算 `task_type='sale_out' AND status=7`，采购退货出库不计入需求。
- **`inventory_stock` 缓存漂移**：预测的"可用量"读缓存，若缓存与容器漂移会让净需求略偏。本功能不写库存、不引入新漂移；展示层已声明"基于库存缓存"。
- **性能**：生成计划主查询有出库、在途两个聚合子查询 JOIN，商品×仓库量大时关注执行计划；两个子查询都要下推时间窗（近 N 天）与仓库范围，必要时限制单次计划的仓库/品类范围。
- **迁移编号**：本文用 `15X` 占位，**不写死编号**。落地前用 `ls backend/src/database/*.sql | grep -oE '^[0-9]+' | sort -n | tail -1` 取当前最大值，连续 +1，注意与文档 01 的 151 及其它并行分支不撞号。
