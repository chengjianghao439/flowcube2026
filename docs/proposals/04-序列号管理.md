# 设计文档 04 · 序列号管理

> 状态：**设计草案，待评审**
> 核心方向已确认：**库存事实源仍是容器（数量制），序列号是叠加在容器之上的个体制账**。
> 本文所有"可机械验证的声明"均对着 2026-07-29 的当前代码核实过；实现时若发现代码已变，以代码为准并回来订正本文。
> 新迁移编号在本文里一律写作"迁移 N"占位，**实现合并时取当时最大编号 +1**，不写死具体数字（当前最大 `150_create_customer_addresses.sql`，仅供参考）。

---

## 1. 背景与现状

系统目前**只有批次/效期管理，完全没有序列号（SN / IMEI）能力**。

现状的个体化管理止步于"批次"这一粒度：

- 商品主表开关：`product_items.batch_managed`（迁移 `121_product_batch_managed.sql:6-8`），`=1` 时收货强制录入批次号与效期。
- 库存事实以**容器**为单位记数：`inventory_containers` 的 `remaining_qty` 是真实数量，同容器只带一组 `batch_no / mfg_date / exp_date`（`backend/src/engine/containerEngine.js:161-171` 建容器写入这三列）。
- 出库排序是 **FEFO**（先到期先出，无效期回退 FIFO）：`containerEngine.js:265-269`、`349-353` 的 `ORDER BY (exp_date IS NULL) ASC, exp_date ASC, created_at ASC, id ASC`。

也就是说：一个批次商品的容器 `remaining_qty=100`，系统知道"这 100 件是同一批、同一效期"，但**无法区分其中的每一件**。一旦客户按机身码保修、或需要"这台设备卖给了谁、从哪张采购单进的"这类个体追溯，现有模型无法回答。

序列号管理要补的正是这个粒度：让 `remaining_qty=N` 的容器**对应 N 个被逐一登记的序列号个体**，全链路（收货→上架→出库→退货）逐台扫码，并支持"某序列号的一生"追溯查询。

## 2. 目标 / 非目标

**目标**
- 商品级开关 `serial_managed`（仿 `batch_managed`），`=1` 的商品进入"个体制"：收货逐台登记序列号、出库逐台核销序列号。
- 序列号是**容器的下挂个体**：容器仍是库存事实源与数量载体，序列号只回答"这 N 件具体是哪 N 个"。**数量与在库序列号数强一致**。
- 全链路 PDA 扫码：收货登记 → 上架（随容器走）→ 出库核销 → 退货入库重新登记。
- **序列号状态机**：在库 / 已出库 / 已退货，每次流转写事件流水。
- **追溯查询**：输入一个序列号，返回它的全链路事件（哪张采购单进、哪个容器、哪张销售单出、卖给谁、是否退回）。

**非目标（本期不做）**
- 序列号 + 批次 + 效期三者叠加的复杂组合管控（本期 `serial_managed` 与 `batch_managed` 可共存但互不依赖；效期仍走容器批次那套）。
- 保修期 / 保修工单 / 售后履历（属于售后模块，另立文档）。
- 序列号在盘点单里的逐台核对（Phase 2，见第 9 节）。
- 调拨的逐台扫码核销（Phase 2；本期调拨随容器整体迁移，序列号跟随容器改仓，不逐台扫）。
- 从外部系统批量导入历史序列号（Phase 2）。

## 3. 与现有系统的关系（重点）

这是本设计最关键的一节：**序列号绝不取代容器，也绝不成为第二个"库存事实源"**，否则会踩穿第 9 节的全部库存不变量。

| 维度 | 容器（现状，不变） | 序列号（新增，叠加） |
|---|---|---|
| 角色 | **库存唯一事实源**（`CLAUDE.md` §9.1） | 容器下挂的个体登记，**从属账** |
| 计数 | `remaining_qty`（DECIMAL 数量） | 个体行数（每台一行） |
| 可用库存判定 | `getAvailableStockForDecision()`（ACTIVE 容器合计 − reserved） | **不参与**可用量判定，只做个体归属 |
| 扣减权威 | FEFO / 本任务锁定容器（`deductFromTaskLockedContainers`） | 跟随容器扣减，**同一事务内**把对应序列号核销 |
| 状态 | `CONTAINER_STATUS`（ACTIVE1/EMPTY2/VOID3/PENDING_PUTAWAY4/PENDING_QA5/REJECTED6，`containerEngine.js:21-27`） | 序列号自己的三态（在库/已出/已退） |

**几条硬边界（对着不变量核过）：**

1. **数量仍以容器为准，序列号数是它的镜像。** 对 `serial_managed` 商品，任何时刻**某容器的 `remaining_qty` 必须等于挂在该容器上、状态=在库的序列号行数**。这是本设计的核心不变量（详见第 4/10 节的一致性校验）。绝不允许"序列号说有 5 个、容器 `remaining_qty=4`"。

2. **绝不新增直接写 `inventory_stock` 或裸建 ACTIVE 容器的路径。** 序列号登记必须**搭在现有建容器/扣减容器的事务里**，不另开库存写入口。建容器仍只经 `containerEngine.createContainer`（`containerEngine.js:130`，收货来源强制先 `PENDING_PUTAWAY(4)` 再 promote，见 `:142-150`），序列号登记是这条链路里追加的一步，不是旁路。

3. **序列号核销与数量扣减必须同一事务。** 出库扣容器（`deductFromTaskLockedContainers`）与把对应序列号置"已出库"必须在**调用方开启的同一 `conn`** 上完成，任一失败整体回滚。绝不允许"库存扣了但序列号还挂在库"或反之。

4. **与批次/FEFO 并存、不冲突。** `serial_managed` 与 `batch_managed` 相互独立：一个商品可以同时是批次+序列号管控（同容器一批、批内每台一个 SN），也可以只开其一。出库排序仍走容器层 FEFO，序列号不改变"先出哪个容器"的决策，只决定"这个容器出库时核销哪几台 SN"。

5. **容器合并/拆分要带着序列号走。** 现有 `container_split`（`DIRECT_ACTIVE_SOURCE_TYPES`，`containerEngine.js:45`）拆容器时，`serial_managed` 商品必须把被拆出的序列号改挂到新容器，保持"容器↔在库序列号"一致。**这是本设计对 containerEngine 影响最大的一处，实现时须逐调用点核对**（见第 6 节与第 11 节）。

## 4. 数据模型

新增两张表：**序列号主表**（个体当前状态）+ **序列号事件流水**（追溯）；商品主表加一个开关列。

### 4.1 商品开关（迁移 N，仿迁移 121）

```sql
ALTER TABLE `product_items`
  ADD COLUMN `serial_managed` TINYINT NOT NULL DEFAULT 0
    COMMENT '1=收货逐台登记序列号、出库逐台核销；个体制' AFTER `shelf_life_days`;
```

### 4.2 序列号主表 `product_serials`（迁移 N）

每一台一行，记录它**当前**的归属与状态；历史流转看事件表。

```sql
CREATE TABLE `product_serials` (
  `id`              BIGINT NOT NULL AUTO_INCREMENT,
  `product_id`      BIGINT NOT NULL,
  `serial_no`       VARCHAR(64) NOT NULL COMMENT '序列号/机身码/IMEI，扫码原文',
  `warehouse_id`    BIGINT NOT NULL DEFAULT 0 COMMENT '当前所在仓；已出库时保留最后所在仓',
  `container_id`    BIGINT NULL COMMENT '当前所在容器；已出库/已退待处理时为 NULL',
  `status`          TINYINT NOT NULL DEFAULT 1 COMMENT '1在库 2已出库 3已退货(待处理)',
  -- 来源（收货登记）
  `inbound_task_id`      BIGINT NULL COMMENT '登记时所在收货订单',
  `inbound_task_item_id` BIGINT NULL COMMENT '归属收货明细行（对齐容器 inbound_task_item_id）',
  `purchase_order_id`    BIGINT NULL COMMENT '溯源采购单',
  -- 出库（核销时回写）
  `warehouse_task_id`    BIGINT NULL COMMENT '出库任务',
  `sale_order_id`        BIGINT NULL COMMENT '销售单',
  `shipped_at`           DATETIME NULL,
  -- 退货
  `return_ref_type`      VARCHAR(32) NULL COMMENT 'sale_return / purchase_return',
  `return_ref_id`        BIGINT NULL,
  `created_at`      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_product_serial` (`product_id`,`serial_no`),
  KEY `idx_serial_no` (`serial_no`),
  KEY `idx_container` (`container_id`),
  KEY `idx_status_wh` (`status`,`warehouse_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='序列号个体主表（容器下挂个体，数量以容器为准）';
```

**设计要点：**

1. **唯一键是 `(product_id, serial_no)` 而非全局 `serial_no`。** 同一物理序列号可能在不同商品间重复（不同厂商编码空间独立）；但同一商品同一序列号**不能同时存在两台在库**。是否允许"同一序列号先出库、退货再入库、再次出库"复用同一行 → **允许**（复用同一行改状态，见第 5 节），故不能用"含历史"的更强唯一约束。**待确认**：极少数场景需要"一个 SN 一辈子只能出现一次" ——若业务要求，改用一致性检查而非唯一键实现。
2. **不设 `deleted_at`。** 序列号是账实记录，退役走状态（可加 `4作废` 态，本期先不加），不软删。
3. **`status` 三态**：`1在库`（挂在某 ACTIVE/PENDING_PUTAWAY/PENDING_QA 容器上）、`2已出库`（`container_id=NULL`，带出库单据）、`3已退货`（销售退货已收但可能待质检/待上架，`container_id` 视阶段可空）。**在库态的行数必须等于对应容器 `remaining_qty`**（核心不变量）。
4. **`container_id` 是与容器的关联锚点**：上架、拆分、出库都要维护它。容器进入 EMPTY/VOID 时，其下不应再有在库序列号（出库核销时已把它们置已出库 / 拆分时已改挂）。

### 4.3 序列号事件流水 `serial_events`（迁移 N）

仿 `inventory_logs` 的"每次动作一条"，是追溯查询的数据源。

```sql
CREATE TABLE `serial_events` (
  `id`           BIGINT NOT NULL AUTO_INCREMENT,
  `serial_id`    BIGINT NOT NULL COMMENT 'product_serials.id',
  `event_type`   VARCHAR(32) NOT NULL COMMENT 'register/putaway/pick/ship/return_in/qa/transfer/void',
  `from_status`  TINYINT NULL,
  `to_status`    TINYINT NULL,
  `container_id` BIGINT NULL,
  `warehouse_id` BIGINT NULL,
  `ref_type`     VARCHAR(32) NULL COMMENT 'inbound_task / warehouse_task / sale_order / *_return',
  `ref_id`       BIGINT NULL,
  `operator_id`  BIGINT NULL,
  `remark`       VARCHAR(255) NULL,
  `created_at`   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_serial` (`serial_id`,`created_at`),
  KEY `idx_ref` (`ref_type`,`ref_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='序列号全链路事件流水（追溯用）';
```

**每次改 `product_serials.status` 或 `container_id` 必须同一事务追加一条 `serial_events`**（与库存动作写 `inventory_logs` 同理）。

## 5. 核心流程（标 PDA 扫码点）

序列号只在 `serial_managed=1` 的商品上触发；其余商品链路完全不变。

### 5.1 收货登记（PDA 扫码点①：逐台扫序列号）

现有收货：PDA 逐箱扫码建容器（`PENDING_PUTAWAY`），累加 `received_qty`（`inbound-tasks.command.js`）。

序列号叠加：**收货这箱货时，除扫容器/录数量外，逐台扫每个序列号**。

```
PDA 收货界面（serial_managed 商品）：
  扫码建容器(status=4 待上架) → 对本容器逐台扫 SN（扫 N 台）
  → 提交时校验：本次 SN 数量 == 本容器 received_qty（数量与序列号数一致，否则拒绝）
  → 同一事务：createContainer + 批量 INSERT product_serials(status=1在库, container_id=新容器)
             + 每台一条 serial_events(event_type='register')
```

- 校验：同商品已存在**在库态**的相同 `serial_no` → 拒绝（重复入库）。存在**已出库/已退**态的相同 SN → 复用该行、状态改回在库（二次入库合法）。
- 幂等：收货已走 `X-Request-Key`（`inbound.receive`），序列号批量登记**搭同一 `beginOperationRequest/completeOperationRequest`**，断网重试命中回执直接返回原结果，**不重复插序列号**。

### 5.2 上架（PDA 扫码点②：扫容器，序列号随容器走）

现有上架：扫容器 → 扫库位，容器 `4→1 ACTIVE`（`inbound-tasks.putaway.js`）。

序列号叠加：**上架不逐台扫**（个体已在收货登记好，且整箱移动）。上架事务里：

```
promote 容器 4→1 → 同一事务把该容器下 status=1 的序列号写 serial_events(event_type='putaway')
                （warehouse_id / container_id 不变，只留痕；如需可回写 location）
```

### 5.3 出库核销（PDA 扫码点③：逐台扫序列号核销）

现有出库：拣货（扫容器）→ 分拣 → 复核 → 打包 → 出库确认，FIFO 从**本任务锁定容器**扣减（`warehouse-tasks.ship.js` 的 `deductFromTaskLockedContainers`）。

序列号叠加：**出库确认时逐台扫要发出的序列号核销**。放在出库确认（ship）这一步最稳妥——此时数量扣减真正发生。

```
PDA 出库确认（serial_managed 商品）：扫箱码 → 对将发出的每台扫 SN
  → 同一事务（承接 ship 的 conn）：
      deductFromTaskLockedContainers 扣容器 remaining_qty
      + 逐台把 product_serials 置 status=2已出库、container_id=NULL、回写 warehouse_task_id/sale_order_id/shipped_at
      + 每台一条 serial_events(event_type='ship')
  → 事务内强校验：本次核销的 SN 必须都挂在本任务锁定的容器上、且数量 == 该容器扣减量
    （防串号：不能核销不属于本任务/本容器的序列号）
```

**核销与扣减同一事务**是硬约束（第 3 节边界 3）：ship 已在事务里，序列号核销是其中追加的写操作，任一失败整体回滚。

> **待确认**：逐台扫 SN 放在 ship（出库确认）还是 pick（拣货）？放 ship 与数量扣减天然同事务、最安全；放 pick 更早发现串号但那时数量尚未扣减，需要额外"预核销"态。**本文按放 ship 设计**，评审时定夺。

### 5.4 退货（PDA 扫码点④：逐台扫序列号重新入库）

**销售退货（库存流入）**：现有 PDA `receive`（建 `PENDING_QA` 容器）→ `check` 质检 → `putaway`。序列号叠加：

```
sale-return receive：逐台扫退回的 SN
  → 找到该 SN 已出库行 → 置 status=3已退货、挂到新建 PENDING_QA 容器
  → serial_events(event_type='return_in')；质检不合格计 rejected 的台不改回在库
  → 上架完成时随容器 promote，序列号 status 3→1在库（serial_events event_type='qa'/'putaway'）
```

**采购退货（库存流出）**：走标准出库流程（`task_type='purchase_return'`），出库时**逐台扫要退给供应商的 SN**，核销同 5.3（置已出库，`return_ref_type='purchase_return'`）。

### 5.5 追溯查询（无扫码，纯查询）

```
GET /serials/trace?serialNo=xxx[&productId=xx]
  → product_serials 主行（当前状态/所在容器/所在仓）
  + serial_events 全部事件按时间正序（register→putaway→ship→return_in→…）
  + JOIN 出单号/客户名/供应商名，拼成"一生时间线"
```

## 11. 风险与待确认

1. **核心不变量维护成本**："容器 `remaining_qty` == 在库序列号数"必须在**每一处**改动容器数量或序列号状态的地方同步维护：收货、上架、拣货、出库、退货、**拆分/合并**、盘点调账、撤回收货、销售单执行期改单（减量拆箱）。**漏一处就静默不一致**。对策：所有序列号写入收口到 `serialEngine`，并在每个事务尾部调 `assertSerialCountMatchesContainer`（类比库存 `assertNonNegativeQty`）。**这是本设计最大风险点。**
2. **撤回收货 / 执行期改单 / 取消归还 的序列号回冲**：`inbound-tasks.void.js`（撤回收货反冲库存）、`warehouse-tasks.adjust.js`（改单减量拆箱）、`cancel-return`（逆向归还）都会反向动容器数量。`serial_managed` 商品在这些逆向路径上必须同步回冲序列号状态。**Phase 1 若不覆盖，须在这些路径上显式挡住 `serial_managed` 商品（报错"该商品序列号管控，暂不支持此操作"）而不是放任不一致**——待确认取哪种。
3. **`container_split` 带序列号迁移**是对 `containerEngine` 侵入最大的改动，且拆分决定"哪几台去新容器"需要业务规则（默认按登记顺序？还是让 PDA 指定？）。**待确认**；Phase 1 建议先对 `serial_managed` 商品禁用拆分。
4. **出库放 pick 还是 ship 扫 SN**（第 5.3 节）：本文按 ship 设计（与扣减同事务最稳）。若现场要求拣货时即校验串号，需引入"预锁定"态，复杂度上升。**待评审定夺。**
5. **序列号唯一性口径**（第 4.2 节要点 1）：允许同 SN 出库-退货-再出库复用同一行；是否要"一个 SN 全局仅一次"由业务定。**待确认。**
6. **同一物理码在不同商品重复**：唯一键定为 `(product_id, serial_no)`。若扫码只扫到 SN 不带商品上下文，收货/出库时需先按当前单据行确定 `product_id` 再定位——收货有采购明细行、出库有任务明细行，均可确定，**但纯追溯查询按裸 SN 搜可能命中多商品**，前端需让用户选商品或全列出。
7. **性能**：追溯查询 JOIN 多单据表，`serial_events` 会随出入库线性增长；`idx_serial` 已按 `(serial_id, created_at)` 建，单序列号追溯走索引无压力；台账列表大范围扫描时注意分页 + 仓库范围下推。
8. **与 `avg_cost` / 成本快照无关**：序列号不改成本口径，`sale_order_items.cost_snapshot` 仍按容器移动加权（`CLAUDE.md` §20.9），不要"顺手"给序列号加单件成本，那是另一个议题。
9. 生产 schema 漂移史（`CLAUDE.md` §20.8）：三张新表上线走标准部署迁移链路，依赖新列的逻辑上线前确认生产已跑过对应迁移。
