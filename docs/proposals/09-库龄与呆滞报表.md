# 设计文档 09 · 库龄与呆滞报表（按天龄分布 + 呆滞识别）

> 状态：**设计定稿，待实现**

> 本文所有"可机械验证的声明"均对着 2026-07-29 的当前代码核实过；实现时若发现代码已变，以代码为准并回来订正本文。

## 1. 背景与现状问题

系统能算"现在有多少货、值多少钱"，但**不告诉运营这些货在仓里躺了多久、哪些已经卖不动**。库存积压、临期报废这类风险，目前只能靠人去翻单子。

现状里唯一沾边的，是利润分析报表里塞着的一段"滞销库存"：

```js
// backend/src/modules/reports/reports.query.js:783-815  fetchProfitAnalysisRows() 的 slowRows
//   WHERE ... (lo.last_outbound_at IS NULL OR lo.last_outbound_at < DATE_SUB(CURDATE(), INTERVAL 90 DAY))
```

它的问题（逐条对代码核过）：

- **只有一个写死的 90 天阈值**（`reports.query.js:805`、`:812`），不可配置。
- **只按商品维度、不分仓**：用 `getProductInventoryProjectionSql()`（`inventoryProjection.js:23-32`，按 `product_id` 汇总所有仓）和 `inventory_logs` 按 `product_id` 聚合（`reports.query.js:801-809`），单仓积压被跨仓合计掩盖。
- **不接数据权限**：整个 reports 模块的 controller 都不传 `req.user`（`reports.controller.js:21-31`），service 也不用 `scopeFilter`，是全局管理员口径。分仓管理员看到的是全公司数据。
- **没有"躺了多久"的分布**：只给一个"90 天没动"的布尔判定，没有 0–30 / 30–60 / 60–90 / 90+ 的天龄分桶，无法回答"积压主要卡在哪个龄段""金额怎么分布"。
- **金额口径用 `cost_price`**（`reports.query.js:797`），不是移动加权成本 `avg_cost`。
- **不覆盖效期**：批次商品的 `exp_date` 临期/过期风险完全没有。

所以本功能不是从零新增一个"滞销"，而是把这段藏在利润报表里、拍脑袋的滞销判定，**升级成一张独立的、按仓、按天龄分布、带效期维度、接数据权限的库龄与呆滞报表**。

## 2. 目标 / 非目标

**目标**

- **库龄天龄分布**：按容器创建日算库龄，分 0–30 / 30–60 / 60–90 / 90+ 天四桶，按商品 / 仓库汇总数量与金额（`remaining_qty × avg_cost`）。
- **呆滞识别**：某商品在某仓超过 N 天（可配置，默认 90）无出库动作且仍有库存 → 标记呆滞，给出最后出库日与积压金额。
- **效期维度**：批次商品（`batch_managed=1`）按容器 `exp_date` 给临期（距到期 < 预警天数）与已过期预警。
- 一个"库龄与呆滞"报表页（概览分桶 + 明细列表），可选一个仪表盘小组件。
- **全程接仓库数据权限**，分仓管理员只看自己仓。

**非目标（本期不做）**

- 不做"库龄→自动清库/促销/调价"的执行动作，只做识别与预警（清库动作钩子留 Phase 2，见第 9 节）。
- 不重构、不替换利润分析里现有的 `slowRows`；本报表上线后它可择机下线或改为跳转本页（Phase 2 决定），本期两者并存但**新报表是唯一权威口径**。
- 不改库存写入路径、不建库存缓存以外的物化表（除非命中第 4 节的性能兜底才加索引）。
- 库龄基准不引入"批次入库日"这类需要改写收货/调拨业务代码才能拿到的新时间字段（见第 5 节决策）。

## 3. 与现有系统的关系（复用什么、为什么这样接）

- **库龄必须下钻到容器事实表 `inventory_containers`，不能只读缓存投影。** `getInventoryDisplayProjectionSql()`（`inventoryProjection.js:16-21`）只按 `product_id, warehouse_id` 聚合 `inventory_stock` 缓存，**没有容器粒度的 `created_at`**，算不出天龄。库龄天生要读容器表的 `created_at / remaining_qty / exp_date`。但这仍是**纯 `SELECT`**：不写、不 `FOR UPDATE`、不碰任何库存扣减判定，符合"只读缓存/事实、不碰库存写"的硬约束。只统计 `status = 1 (ACTIVE)` 的容器（`containerEngine.js:21-25` 的 `CONTAINER_STATUS.ACTIVE`），待上架(4)/质检(5)/作废(3)/清空(2)容器不计入（与"待上架容器不计入账面"的不变量 5 一致）。

- **数据权限照 `inventory` 模块写，不要照 `reports` 模块写。** 这是文档 01 已经踩过的坑，本报表同样适用：
  - reports 模块整体不接数据权限（`reports.controller.js:21-31` 全部不传 `req.user`），若把库龄接口挂进 reports 又不动 controller，就会**越权跨仓**。
  - 正确范式在 inventory 模块：controller 传 `scopeWarehouseIds: req.user?.warehouseIds ?? null`（`inventory.controller.js:42`、`:110`），service 用 `scopeFilter(scopeWarehouseIds, '<仓库列>')`（`inventory.service.js:298`）。
  - **本报表后端接口挂在 `inventory` 模块**（`GET /inventory/aging`、`GET /inventory/aging/expiry`），天然带 `req.user.warehouseIds` 传递，无需给 reports 开数据权限的先例。前端页仍归到"报表"导航分组（用途是报表），二者不矛盾。
  - 备选（不推荐）：若坚持挂 reports 模块，**必须**同步改造 controller 传 `req.user.warehouseIds`、service 全部查询过 `scopeFilter`，并把现有 `slowRows` 一起补数据权限，否则新旧口径不一致、老接口继续越权。成本更高，故选挂 inventory。

- **结构/前端复用现成范本**：后端明细列表照 `inventory.service.getOverview`（`inventory.service.js:251`）的"过滤 + scopeFilter + 分页"三段式；前端页照 `pages/reports/profit-analysis.tsx`（Header + 筛选 + `useQuery` + `DataTable`）；仪表盘组件照 `components/dashboard/registry.ts` 里已有的 `chart-aging`（`registry.ts:62`，应收应付账龄桶）与 `list-low-stock`（`registry.ts:67`）。

## 4. 数据模型（无重表）

**本报表主体不需要新表、不加列、不写迁移。** 它完全建立在已有事实表上：

| 数据 | 来源 表.列 | 备注 |
|---|---|---|
| 库龄基准时刻 | `inventory_containers.created_at`（`016_create_inventory_containers.sql:39`） | 容器首次落库时刻（收货逐箱建 `PENDING_PUTAWAY(4)` 容器的时刻；`promote`→ACTIVE 只改 status 不改 created_at） |
| 在库数量 | `inventory_containers.remaining_qty`（`017_alter_inventory_containers.sql:31`） | 唯一真实库存源；只取 `status=1 ACTIVE` |
| 持有成本 | `product_items.avg_cost`（`119_avg_cost_and_cost_snapshot.sql:9-12`） | 移动加权，`DEFAULT NULL`，只正向移动（见第 5 节金额口径） |
| 批次/效期 | `inventory_containers.exp_date / batch_no`（`016:20-22`）+ `product_items.batch_managed`（`121_product_batch_managed.sql:6`） | 效期维度用 |
| 最后出库时间 | `inventory_logs`（`type=2` 出库，带 `warehouse_id / product_id / created_at / quantity`；`006` + `054:62/88` + `038:87`） | 呆滞判定用，能按仓聚合 |
| 数据权限 | `req.user.warehouseIds` → `scopeFilter(ids, 'c.warehouse_id')`（`warehouseScope.js:39-43`） | 必接 |

**性能兜底（只有必要时才动，届时才写一个新迁移，编号取当前最大 +1，不在本文写死）**：

- 库龄主查询按 `inventory_containers(warehouse_id, product_id, status, created_at)` 过滤聚合；现有索引有 `idx_product_wh(product_id, warehouse_id)`、`idx_status(status)`、`idx_exp_date(exp_date)`（`016:46-51`）。容器量大且执行计划不理想时，可加一条覆盖索引 `(status, warehouse_id, product_id, created_at)`；效期查询可依赖已有 `idx_exp_date`。
- 呆滞子查询按 `inventory_logs(product_id, warehouse_id, type, created_at)` 聚合；现有 `idx_inventory_logs_product_wh(product_id, warehouse_id)`（`006:17`）已覆盖前两列，必要时补 `type` 与 `created_at`。
- **先不预建物化/缓存表**。库龄是低频报表读，容器与流水都是既有索引可支撑的聚合；确有性能问题再评估物化，避免引入"又一张会漂移的缓存表"。

## 5. 核心口径（分桶 SQL 骨架、呆滞判定、金额口径）

### 5.1 库龄基准 —— 取容器创建日（已决策）

- **库龄 = `NOW() − inventory_containers.created_at`**，`created_at` 就是该容器落库的时刻，简单、可靠、按容器精确。
- **不取"批次入库日"**：`batch_no` 只标识批次，`mfg_date` 是生产日期（`016:21`）而非入库日，系统里**没有独立的"批次入库日"字段**；要拿到它得改写收货/调拨业务代码，超出本报表只读范围。批次信息只用于效期维度（5.4）。
- **已知偏差（写进第 11 节风险）**：调拨入库（`transfer`）与容器拆分（`container_split`）会**新建**容器，新容器 `created_at` 是调拨/拆分时刻，会让这部分库存的库龄"从头计"。这是容器模型的固有特性，本报表不修正（修正要改业务写入路径）。报表页需注明"库龄自本仓落库起算"。

### 5.2 天龄分桶（库龄分布）

分桶边界 0–30 / 30–60 / 60–90 / 90+（天数阈值做成常量，便于将来配置）。两种输出形态：

**（A）概览分桶汇总**（喂仪表盘/页头卡片）——每个龄段的 SKU 数、数量、金额：

```sql
-- 骨架，实现时精修表名/别名；:asOf 通常取 NOW()
SELECT
  CASE
    WHEN DATEDIFF(NOW(), c.created_at) < 30  THEN '0-30'
    WHEN DATEDIFF(NOW(), c.created_at) < 60  THEN '30-60'
    WHEN DATEDIFF(NOW(), c.created_at) < 90  THEN '60-90'
    ELSE '90+'
  END                                                       AS age_bucket,
  COUNT(DISTINCT c.product_id)                              AS sku_count,
  SUM(c.remaining_qty)                                      AS total_qty,
  SUM(c.remaining_qty * COALESCE(NULLIF(p.avg_cost,0),
                                 NULLIF(p.cost_price,0),
                                 p.sale_price, 0))           AS total_value
FROM inventory_containers c
JOIN product_items p        ON p.id = c.product_id AND p.deleted_at IS NULL
JOIN inventory_warehouses w ON w.id = c.warehouse_id AND w.deleted_at IS NULL
WHERE c.status = 1                       -- 只统计 ACTIVE 在库容器
  AND c.remaining_qty > 0
  AND c.deleted_at IS NULL
  /* + warehouseId 过滤 */ ${scope.sql}  -- scopeFilter(ids, 'c.warehouse_id')
GROUP BY age_bucket
```

**（B）明细列表**（分页 + scopeFilter）——每个「商品 × 仓库」一行，把四个龄段的数量摊平成列，附总量、加权平均库龄、金额、呆滞标记：

```sql
SELECT
  c.product_id, p.code, p.name, p.unit,
  c.warehouse_id, w.name AS warehouse_name,
  SUM(CASE WHEN DATEDIFF(NOW(),c.created_at) < 30 THEN c.remaining_qty ELSE 0 END) AS qty_0_30,
  SUM(CASE WHEN DATEDIFF(NOW(),c.created_at) BETWEEN 30 AND 59 THEN c.remaining_qty ELSE 0 END) AS qty_30_60,
  SUM(CASE WHEN DATEDIFF(NOW(),c.created_at) BETWEEN 60 AND 89 THEN c.remaining_qty ELSE 0 END) AS qty_60_90,
  SUM(CASE WHEN DATEDIFF(NOW(),c.created_at) >= 90 THEN c.remaining_qty ELSE 0 END) AS qty_90p,
  SUM(c.remaining_qty)                                                              AS total_qty,
  -- 数量加权平均库龄（天）
  ROUND(SUM(c.remaining_qty * DATEDIFF(NOW(),c.created_at)) / NULLIF(SUM(c.remaining_qty),0), 1) AS avg_age_days,
  MAX(DATEDIFF(NOW(),c.created_at))                                                 AS max_age_days,
  SUM(c.remaining_qty * COALESCE(NULLIF(p.avg_cost,0),NULLIF(p.cost_price,0),p.sale_price,0)) AS total_value,
  lo.last_outbound_at
FROM inventory_containers c
JOIN product_items p        ON p.id = c.product_id AND p.deleted_at IS NULL
JOIN inventory_warehouses w ON w.id = c.warehouse_id AND w.deleted_at IS NULL
LEFT JOIN (
  SELECT product_id, warehouse_id, MAX(created_at) AS last_outbound_at
  FROM inventory_logs
  WHERE type = 2                          -- 出库
  GROUP BY product_id, warehouse_id       -- 关键：按仓，不再像旧 slowRows 只按 product
) lo ON lo.product_id = c.product_id AND lo.warehouse_id = c.warehouse_id
WHERE c.status = 1 AND c.remaining_qty > 0 AND c.deleted_at IS NULL
  /* + keyword / warehouseId 过滤 */ ${scope.sql}
GROUP BY c.product_id, p.code, p.name, p.unit, c.warehouse_id, w.name, lo.last_outbound_at
ORDER BY total_value DESC     -- 或按 avg_age_days DESC，页面可切
LIMIT ? OFFSET ?
```

### 5.3 呆滞判定

```
呆滞(某商品×某仓) =  该仓仍有在库库存（Σ ACTIVE 容器 remaining_qty > 0）
                  AND  该仓最后一次出库距今 > staleDays（默认 90，接口参数可配）
```

- 最后出库时间用 `inventory_logs` `type=2`（出库）**按 `product_id + warehouse_id` 聚合**（`inventory_logs.warehouse_id` 存在，`006:7`），比旧 `slowRows` 只按 `product_id`（`reports.query.js:803`）更精确，能识别"整体在动、但某个仓压着不动"。
- `staleDays` 做成查询参数（`?staleDays=90`），**不建配置表**；页面给 60/90/120 快捷切换即可。
- 明细列表里加 `is_stale`（应用层比对 `last_outbound_at`）与 `days_since_outbound`，前端用 `StatusBadge`（tone `danger`/`warning`）标注。
- **口径决策（写进第 11 节待确认）**：`inventory_logs.type=2` 涵盖**所有**减少动作（销售出库、采购退货出库、手动出库、调拨扣减）。MVP 采用"任何出库都算动过"（与旧 `slowRows` 一致，最简单）。进阶可用 `move_type`（`054:49`）细分，只认真正的销售出库，避免调拨/退货把呆滞商品"洗白"——列为可选增强，不在 MVP。

### 5.4 效期维度（批次商品）

对 `batch_managed = 1` 的商品，容器 `exp_date` 非空时给临期与过期预警：

```sql
SELECT c.product_id, p.code, p.name, c.warehouse_id, w.name AS warehouse_name,
       c.batch_no, c.exp_date, c.remaining_qty,
       DATEDIFF(c.exp_date, NOW()) AS days_to_expiry,
       CASE WHEN c.exp_date < NOW() THEN 'expired'
            WHEN DATEDIFF(c.exp_date, NOW()) <= :warnDays THEN 'near_expiry'
            ELSE 'ok' END AS expiry_state
FROM inventory_containers c
JOIN product_items p        ON p.id = c.product_id AND p.batch_managed = 1 AND p.deleted_at IS NULL
JOIN inventory_warehouses w ON w.id = c.warehouse_id AND w.deleted_at IS NULL
WHERE c.status = 1 AND c.remaining_qty > 0 AND c.deleted_at IS NULL
  AND c.exp_date IS NOT NULL
  AND c.exp_date <= DATE_ADD(NOW(), INTERVAL :warnDays DAY)   -- 只列临期/过期
  ${scope.sql}                                                -- scopeFilter(ids, 'c.warehouse_id')
ORDER BY c.exp_date ASC
```

`warnDays` 同样做接口参数（默认 30）。此维度天然是容器/批次粒度（同一 SKU 多批不同效期），不聚合到 SKU。

### 5.5 金额口径（重要）

- **金额 = `remaining_qty × avg_cost`**，回落链 `COALESCE(NULLIF(avg_cost,0), NULLIF(cost_price,0), sale_price, 0)`。选 `avg_cost`（移动加权，更贴近真实持有成本），而非旧 `slowRows` 用的 `cost_price`（`reports.query.js:797`）。
- **必须在页面注明口径偏差**：`avg_cost` **只随入库正向移动，退货/撤回不反冲**（`119:5`，CLAUDE.md 第 20 节第 9 条刻意简化）。因此库龄金额是"按最近加权成本估的持有金额"，不是精确到每个容器批次进价的账面值——这与利润分析用 `cost_snapshot` 的口径不同，是**估值展示**，不作账。`avg_cost` 为空的老商品按回落链取 `cost_price`/`sale_price`。

## 8. 权限

**复用现有 `PERMISSIONS.REPORT_VIEW`（`report.view`），不新增权限码。** 库龄本就是报表类。复用可省掉"后端常量 + 前端常量 + seed 迁移"三处手工同步与 `test:permissions` 成本（CLAUDE.md 第 12 节）。虽然接口物理上挂在 inventory 模块的路由文件，但用 `requirePermission(PERMISSIONS.REPORT_VIEW)` 守，与前端页 `permission: REPORT_VIEW` 对齐即可。

## 11. 风险与待确认

- **表名核对**：仓库主表在 SQL 里写作 `inventory_warehouses`（与 reports/inventory 现有查询一致，如 `inventory.service.js:310`），实现前再确认。
- **库龄基准的调拨/拆分重置偏差**：调拨入库、容器拆分会新建容器，新容器 `created_at` 是本次动作时刻，导致这部分库存库龄"从头算"（5.1）。这是容器模型固有特性，本报表不修正；报表页注明"库龄自本仓落库起算"。若业务确需"原始入库龄"，需另立文档改写 `containerEngine.transferContainers` / 拆分逻辑传递原始 `created_at`——超出本报表范围。
- **呆滞口径的出库类型（待确认）**：MVP 用 `inventory_logs.type=2` 全部出库动作判定动销；是否要用 `move_type` 剔除调拨/退货出库，让"仅调拨走一圈"的商品仍算呆滞——需业务确认。默认 MVP 简单口径。
- **`avg_cost` 估值偏差**：金额用只正向移动、不反冲的 `avg_cost`（`119:5`），是估值展示不作账（5.5），页面须注明。`avg_cost` 为空的老商品走 `cost_price`/`sale_price` 回落。
- **`inventory_stock` 缓存 vs 容器事实**：本报表直接读容器 `remaining_qty`（事实源），**不读 `inventory_stock` 缓存**，故不受缓存漂移影响，也不引入新漂移。
- **性能**：明细查询含一个 `inventory_logs` 出库聚合子查询 JOIN，容器/流水量大时关注执行计划；必要时按第 4 节补索引，或给出库子查询限定时间窗（只需最近一次出库时间，可加 `created_at >= DATE_SUB(NOW(), INTERVAL 400 DAY)` 之类的下推，但要保证"从没出过库"的商品仍被 LEFT JOIN 到 NULL 而识别为呆滞）。
- **与旧 `slowRows` 并存期**：Phase 1 上线后利润分析里的旧滞销仍在（不分仓、90 天固定、`cost_price` 口径），两者数字会不同。以本报表为权威口径，Phase 2 统一。
