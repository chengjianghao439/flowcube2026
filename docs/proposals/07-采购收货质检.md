## 1. 背景与现状

采购收货链路目前**没有任何质量检验环节**：货一收进来，扫码上架就直接变成可售的正式库存，来料不良无处拦截。

现状收货—上架—结算三段，对着代码是这样的：

- **收货**（`inbound-tasks.command.js:523-547`）：逐箱 `createContainer(... containerStatus: CONTAINER_STATUS.PENDING_PUTAWAY)`，容器直接落 `status=4 待上架`。
- **上架**（`inbound-tasks.putaway.js:166-172`）：扫容器→扫库位，容器 `4→1 ACTIVE`，`syncStockFromContainers` 刷新缓存、更新移动加权成本 `avg_cost`、按归属明细回写 `putaway_qty`。
- **结算**（`inbound-tasks.putaway.js:13-80` 的 `tryFinishTask` → `inbound-tasks.settle.js:140` 的 `settlePurchaseOnAudit`）：全部上架完，任务 `3→4 已完成`、`audit_status 0→1`，按 `SUM(iti.putaway_qty × poi.unit_price)` 全量重算应付（`inbound-tasks.settle.js:36-45`）。**没有人工审核环节**（v0.4.22 起移除）。

来料不良目前只被两道**数量层面**的闸门"顺带"沾到，但它们都不检查质量：

- **超收确认**（`inbound-tasks.command.js:255-300` 的 `evaluateOverReceive`）：超收比例 > 20% 或金额 > `OVER_RECEIVE_CONFIRM_AMOUNT`（默认 500 元）需前端带 `confirmOverReceive`。
- **疑似重复扫码**（`inbound-tasks.command.js:314-339` 的 `detectDuplicateScan`）：30 秒内同商品同箱数同总量需 `confirmDuplicate`。

**结果**：破损、错版、色差、过期、以次充好的来料，和合格品一样一路上架成 ACTIVE、更新 `avg_cost`、并被 `SUM(putaway_qty × 单价)` 结算进应付——**钱照付，货照卖**。质量问题只能等销售端客诉或盘点时才暴露，追溯成本极高。

本功能给收货链路补上"先检后入"的闸门，把不合格量挡在可用库存和应付账款之外。

## 2. 目标 / 非目标

**目标**
- 采购收货后，**质检管控**的商品先进"待质检"容器（`PENDING_QA(5)`），质检判定后合格量才 promote 到待上架/上架，拒收量转 `REJECTED(6)`，**不进可用库存、不结算应付**。
- 质检是**开关**：按商品、按供应商（免检供应商）配置，参照 `product_items.batch_managed`（迁移 121）的做法。免检商品/供应商走原有"收货即待上架"路径，零行为变化。
- 支持三种质检处置：**合格放行**、**让步接收**（不良但协商后接收入库，计入结算）、**拒收**（退供应商 / 报废，不入库不结算）。
- 结算口径保持"实收上架量 × 单价"不变——**不合格拒收量天然不进 `putaway_qty`，自然不结算**（第 5.4 节论证）。
- PDA 新增/改造采购质检作业页，与销售退货 `check` 同构。

**非目标（本期不做，留后续文档或 Phase 2）**
- 抽样方案 / AQL 抽检标准库（本期只做全检或按量整批判定，不做统计抽样）。
- 质检不合格自动生成采购退货单 / 报废单的联动（Phase 2；本期 REJECTED 容器留存并留痕，由现有采购退货或人工报废后续处理）。
- 质检项模板（外观 / 尺寸 / 功能等多维检验记录表）。本期只记合格量 / 不合格量 / 处置 / 原因，不做逐检验项打分。
- 质检报告打印、质检工时统计。

## 3. 与现有系统的关系（复用退货质检范式）

**销售退货已有一套完整的收货—质检—上架流程，本功能直接照它建模**，这是落地风险小的根本原因：

| 能力 | 退货已有（范本） | 采购收货质检（本功能） |
|---|---|---|
| 待质检容器状态 | `PENDING_QA=5`（`containerEngine.js:26`，迁移 085 定义） | **复用同一状态**，无需新造 |
| 不合格容器状态 | `REJECTED=6`（`containerEngine.js:27`，迁移 100 定义） | **复用同一状态** |
| 收货建待质检容器 | `return-tasks.service.js:187-203`（`containerStatus: PENDING_QA`） | 同法，仅 `sourceType` 由 `RETURN` 换 `INBOUND_TASK` |
| 质检分流合格/不合格 | `return-tasks.service.js:235-296` 的 `allocateQaContainers`（跨界就地拆容器：合格部分转 `PENDING_PUTAWAY`，不合格部分拆成新 `REJECTED` 容器） | **算法可整体照搬** |
| 三段量记账 | `return_task_items`：`received_qty / checked_qty / rejected_qty / putaway_qty`（迁移 085 + 100） | `inbound_task_items` 增同名列 |
| 可上架量口径 | `checked_qty − rejected_qty − putaway_qty`（`return-tasks.service.js:476`） | 同口径 |
| 完成判定 | `SUM(checked_qty − rejected_qty − putaway_qty)=0`（`return-tasks.service.js:309-315`） | 同口径（**这是必须改 `tryFinishTask` 的核心点**，第 6 节） |
| PDA 质检接口 | `POST /return-tasks/:id/check`（`return-tasks.routes.js:70-76`） | 新增 `POST /inbound-tasks/:id/check` |

**关键：容器引擎无需改动。** `createContainer` 只对"直接建 ACTIVE"做了来源白名单限制（`containerEngine.js:142-150`：非调拨/拆分不得直建 ACTIVE，且 `INBOUND_TASK` 来源禁止直建 ACTIVE）。建 `PENDING_QA(5)` 容器不触发任何拒绝分支，`sourceType=INBOUND_TASK` 完全允许——退货侧已经用 `PENDING_QA` 建过容器验证了这条路。`syncStockFromContainers` 只汇总 `status=1 ACTIVE`（`containerEngine.js:425-431`），`PENDING_QA(5)` 与 `REJECTED(6)` 天然不计入库存缓存、不计入可用库存判定，**满足库存不变量第 5 条（待上架/待质检容器不计入账面、不可被销售占用）**。

**与退货的一个差异**：退货是独立的 `return_tasks` 表 + 内联状态机（不在 `documentStatusRules.js` 里）；采购收货是 `inbound_tasks` 表，状态走全局 `documentStatusRules.js` 的 `inboundTask` 机器。因此"待质检"这一步怎么表达，需要在"改动全局状态机"与"仅用容器状态驱动"之间做选择（第 5.2 节）。

## 4. 数据模型

### 4.1 质检开关（迁移 N1，编号取实现时当前最大值 +1，勿照抄）

参照 `batch_managed`（迁移 121，`product_items` 加 `TINYINT DEFAULT 0` 开关列）的做法，商品与供应商各加一个开关：

```sql
-- 商品级：该商品收货是否需要来料质检
ALTER TABLE `product_items`
  ADD COLUMN `qa_required` TINYINT NOT NULL DEFAULT 0
  COMMENT '1=采购收货需先质检（PENDING_QA）合格才可上架' AFTER `batch_managed`;

-- 供应商级：0=跟随商品；1=该供应商所有来料强制质检；2=该供应商免检（信任供应商，直接待上架）
ALTER TABLE `supply_suppliers`
  ADD COLUMN `qa_policy` TINYINT NOT NULL DEFAULT 0
  COMMENT '来料质检策略：0=按商品 qa_required 决定；1=强制质检；2=免检' AFTER `is_active`;
```

**开关取值规则（收货建单时求值一次并固化，见 4.2）**：

```
需质检 = (supplier.qa_policy == 1)                      -- 供应商强制质检，最高优先
      OR (supplier.qa_policy != 2 AND product.qa_required == 1)  -- 免检供应商(2)直接跳过
```

> 为什么供应商可以"免检覆盖商品开关"：现实里同一件商品，A 供应商是长期信任的免检户、B 供应商是新户要检。开关维度定为"供应商优先、商品兜底"，比只做商品级更贴合采购现实。**这条 or/优先级规则是本设计的待确认决策之一**（第 11 节），也可简化为"商品级单开关 + 供应商级免检名单"。

### 4.2 收货明细增列（迁移 N2）

`inbound_task_items` 现有三段量 `ordered_qty / received_qty / putaway_qty`（迁移 024）。增列对齐退货：

```sql
ALTER TABLE `inbound_task_items`
  ADD COLUMN `qa_required`  TINYINT NOT NULL DEFAULT 0
    COMMENT '本行是否需质检（建单时按商品/供应商开关固化的快照）' AFTER `putaway_qty`,
  ADD COLUMN `checked_qty`  DECIMAL(12,4) NOT NULL DEFAULT 0
    COMMENT '已质检处理量（合格+让步接收+拒收）' AFTER `qa_required`,
  ADD COLUMN `rejected_qty` DECIMAL(12,4) NOT NULL DEFAULT 0
    COMMENT '质检拒收量（不入库、不结算，转 REJECTED 容器）' AFTER `checked_qty`;
```

- **`qa_required` 必须是建单时的快照，不是实时读商品/供应商开关。** 与 `payment_records.settlement_type / cost_snapshot` 同理（CLAUDE.md 第 7.1 节）：在途单据的处置规则应由下单/建单当时的配置决定，之后把商品改成免检不能让已经在检的单据凭空放行、也不能让已放行的单据倒回去检。建单（`createFromPoId` / `createManualTask`，`inbound-tasks.command.js:67-73 / 154-173`）时对每行求值一次写死。
- **让步接收不单独占列**：质检时判为"合格放行"，数量归入合格量→走 `putaway`→计入结算，仅在事件流水与（可选）`concession_qty` 旁路列上留痕区分（旁路统计列列为 Phase 2 增强，不影响主数量流）。这样主数量语义与退货完全同构，改动最小。

### 4.3 收货任务旁路质检标记（迁移 N2，随 4.2 一起，可选但推荐）

为让 ERP 列表能筛"待质检"、PDA 能拉"待质检任务"，给任务头加一个**旁路标志**（不动主 `status`，类比 `audit_status` 的做法，`inbound-tasks.putaway.js:63-69`）：

```sql
ALTER TABLE `inbound_tasks`
  ADD COLUMN `qa_status` TINYINT NOT NULL DEFAULT 0
  COMMENT '0=无需质检/无待质检容器 1=有待质检容器待处理 2=质检已全部完成' AFTER `status`;
```

由收货 / 质检动作在同一事务内维护（收货建 `PENDING_QA` 容器置 1，全部质检完置 2）。**它只是展示/筛选投影，权威事实仍是容器状态与明细数量**，任何流转判定不得只信这个字段（同"状态语义以容器/明细为准"的一贯原则）。

### 4.4 库存不变量对照（无新增违规）

| 不变量（CLAUDE.md 第 9 节） | 本设计如何满足 |
|---|---|
| 5. 待上架容器不计入账面、不可占用 | `PENDING_QA(5)` / `REJECTED(6)` 同样 `status≠1`，`syncStockFromContainers` 不汇总（`containerEngine.js:428`） |
| 2. 只能经 `syncStockFromContainers` 写缓存 | 质检只改容器 `status`（5→4 或 5→6），合格量真正进缓存仍在上架时经 `syncStockFromContainers`（`inbound-tasks.putaway.js:175`） |
| 12. 建容器只经 `containerEngine.createContainer` | 收货建 QA 容器、质检拆不合格容器都走 `createContainer`（复用退货 `allocateQaContainers` 写法） |
| 9. 上架先 `lockStockDimension` 再锁容器 | 上架路径不变，仍是现有 `inbound-tasks.putaway.js:119-137` 的加锁顺序 |

## 5. 核心流程与状态

### 5.1 端到端流程

```
ERP  采购单→收货订单（建单时按商品/供应商开关固化每行 qa_required）→提交到 PDA
PDA  收货（逐箱扫码）
       ├─ qa_required=0 的行：建 PENDING_PUTAWAY(4) 容器      ← 原路径，零变化
       └─ qa_required=1 的行：建 PENDING_QA(5) 容器           ← 新增
     收满 → 待上架(3)，任务 qa_status 置 1（若有 QA 容器）
     质检（新增 check 动作，仅对本任务 PENDING_QA 容器）
       输入每商品 { passedQty(含让步接收), rejectedQty, 处置原因 }
       ├─ 合格/让步：容器 PENDING_QA(5) → PENDING_PUTAWAY(4)   ← 可上架
       └─ 拒收：      容器 PENDING_QA(5) → REJECTED(6)          ← 不入库不结算
       跨界容器就地拆分（照搬 allocateQaContainers）
       全部质检完 → qa_status 置 2
     上架（扫容器→扫库位，仅 PENDING_PUTAWAY 容器）→ ACTIVE(1)  ← 原路径
     可上架量全部上架完 ⇒ tryFinishTask：任务→已完成(4)、audit_status 0→1
        ⇒ settlePurchaseOnAudit：SUM(putaway_qty × 单价) 结算应付（不含拒收量）
```

数量语义（对齐退货，逐行守恒）：

```
received_qty  实收量（合格+不合格都先收进来）
checked_qty   已质检量 = 合格 + 让步接收 + 拒收
rejected_qty  拒收量（转 REJECTED，不上架不结算）
putaway_qty   已上架量 = 合格 + 让步接收（进 ACTIVE，结算基数）

待质检量 = received_qty − checked_qty
可上架量 = checked_qty − rejected_qty − putaway_qty
```

### 5.2 "待质检"如何在订单级表达（待确认，给两方案）

**方案 A（推荐，最小侵入）——容器状态 + `qa_status` 旁路标志驱动，不改 `documentStatusRules`。**
收货完成后订单仍进"待上架(3)"，质检是"待上架阶段内先把 `PENDING_QA` 容器分流成 `PENDING_PUTAWAY/REJECTED`"的前置动作。PDA 待上架任务里，只要还有 `PENDING_QA` 容器就先要求质检，质检通过的容器才允许扫码上架。ERP 用 `qa_status` 展示/筛选"待质检"。
优点：不动全局状态机（`inboundTask` 机器牵连收货/上架/撤回收货等大量代码），迁移与回归面小。缺点：ERP 单据状态列仍显示"待上架"，"待质检"只体现在旁路标记与容器上，语义不如独立状态直观。

**方案 B——给 `inboundTask` 状态机新增"待质检"态**，插在 `receiveComplete` 与 `putaway` 之间。
优点：与退货内联状态机的"3待质检"完全对齐，ERP 状态列直观。缺点：现有 `status=3` 恒等于"待上架"的语义被打破，`documentStatusRules.js:143-188` 的 `inboundTask` 机器、`generated/status.ts`、前端徽章、撤回收货 `voidReceipt` 的 `from:[2,3,4]` 等全部要重排，改动面与回归成本显著更大，且要新造 seed/前端状态常量。

> **建议采用方案 A**，把订单状态机的稳定性放在"状态列好不好看"之上；用 `qa_status` + 容器状态承载质检语义。本文后续 6/7 节按方案 A 写。方案选择请在评审时定档。

### 5.3 免检路径零变化（关键安全边界）

`qa_required=0` 的行，收货照旧建 `PENDING_PUTAWAY(4)`（`inbound-tasks.command.js:535` 一字不改），后续上架、结算、`avg_cost` 更新全部走现有代码。**质检开关默认 0**，意味着上线后存量商品/供应商行为完全不变，功能是纯增量、可灰度（先对个别商品/新供应商打开）。

### 5.4 对结算的影响（核心论证：结算公式不用改）

结算基数是 `SUM(iti.putaway_qty × poi.unit_price)`（`inbound-tasks.settle.js:36-45`），而 `putaway_qty` 只在**上架**时累加（`inbound-tasks.putaway.js:255`）。只要保证**拒收量永不 `putaway`**，拒收量就天然不进结算基数——不必给结算加任何"扣质检不合格"的特殊逻辑。

- **拒收量（rejected_qty）**：容器进 `REJECTED(6)`，永远不会被扫码上架，`putaway_qty` 不含它 → 不结算、不进 `avg_cost`（`avg_cost` 也只随上架正向移动，`inbound-tasks.putaway.js:203-223`）。✓
- **让步接收量**：判为合格放行→上架→`putaway_qty` 含它→结算。✓（货确实收下并入库，按合同价付款合理。）
- **必须改的两处判定（否则任务永远无法完成）**：
  1. `tryFinishTask` 的 `allPutaway = every(putaway_qty >= received_qty)`（`inbound-tasks.putaway.js:36`）。有拒收量时 `putaway_qty < received_qty` 恒成立，任务永远完成不了。改为**扣除拒收量**：`every(checked_qty − rejected_qty ≤ putaway_qty)` 且 `every(received_qty ≤ checked_qty)`（全部收货已质检、全部合格已上架）。这正是退货 `tryFinishReturnTaskPutaway` 用 `SUM(checked_qty − rejected_qty − putaway_qty)=0` 的同款口径（`return-tasks.service.js:309-315`）。
  2. `isPurchaseFullyReceivedAndAudited`（`inbound-tasks.settle.js:93-116`）判采购单是否收齐用 `putaway_qty >= poi.quantity`。有拒收量时该采购单会被判为**未收齐（短装）**，不自动完成——**这是正确语义**：来料被拒收，等于这批没到齐，采购员应走 `POST /purchase/:id/close`（短装结案，`inbound-tasks.command.js:833` 的 `closeReceiving` 链路）或重新催货补发。文档要在采购单页把"因质检拒收导致的短装"提示清楚，避免采购员困惑"我明明收货了为什么没完成"。

- **短装闸门叠加**：短装结案（`closed_reason='short_close'`）后 `tryFinishTask` 用 `shortClosed` 放宽收满校验（`inbound-tasks.putaway.js:31-35`），此时仍要求"已质检的合格量全部上架"才完结；结算按 `putaway_qty` 全量重算天然等于实际入库合格量，无需额外处理。

## 8. 权限

**优先复用现有收货执行权限，避免三处手工同步成本。** 退货侧的先例很直接：退货 receive/check/putaway **三个 PDA 接口全部复用同一个 `RETURN_ORDER_EXECUTE`**（`return-tasks.routes.js:63,72,81`），质检没有独立权限码。

采购收货同理，两个选项：

- **选项一（推荐）**：质检 `check` 复用 `INBOUND_RECEIVE_EXECUTE: 'inbound.receive.execute'`（`permissions.js:65`）——把"现场收货 + 质检"视作同一岗位（收货员即初检员），零新增权限码、零 seed 迁移、不动 `test:permissions`。
- **选项二**：若需按岗位分离质检权（质检员 ≠ 收货员），新增 `INBOUND_QA_EXECUTE: 'inbound.qa.execute'`，则要**三处同步**（后端 `permissions.js`、前端 `permission-codes.ts`、seed 迁移授予相应角色），并跑 `npm run test:permissions`（双向 diff，已进 CI）。商品/供应商开关维护复用现有 `product.manage` / `supplier.manage` 一类权限（实现时对齐 `permissions.js` 现有码）。

> 无论选哪个，`POST /:id/check` 必须挂 `pdaOnly` + `pdaSessionRequired()`（仓库现场作业接口，硬约束 8：ERP 端不得绕过 `pdaOnly` 直接改任务/容器状态）。

- `GET /inventory/check-consistency` 或 `resync:inventory-stock`：确认 `PENDING_QA` / `REJECTED` 容器不污染 `inventory_stock` 缓存（应无影响，作兜底）。

  1. 商品 A 设 `qa_required=1`，供应商免检(2) → 收货应直接 `PENDING_PUTAWAY`（免检覆盖生效）。
  2. 商品 A `qa_required=1`，供应商按商品(0) → 收货落 `PENDING_QA`，未质检扫码上架应被拒；质检合格 60 / 拒收 40 → 只有 60 可上架，应付 = 60×单价，采购单判为短装不自动完成。

## 11. 风险与待确认

- **状态表达方案（5.2）**：方案 A（容器 + `qa_status` 驱动，不改状态机，推荐）vs 方案 B（新增订单级"待质检"态）。评审定档——牵动前端状态常量与回归面。
- **质检开关维度（4.1）**：商品级、供应商级、还是"供应商优先 + 商品兜底"（本文默认）。也可简化为单商品开关 + 供应商免检名单。需产品确认采购现实。
- **拒收后的账实处理边界**：本期 REJECTED 容器只"留存 + 留痕"，不自动生成退供应商单据。拒收量在采购单上表现为短装，需人工 `close` 结案或催补；**要在采购单/收货详情把这个因果讲清楚**，否则采购员会困惑。Phase 2 再做联动。
- **`avg_cost` 口径**：拒收量不上架、不进均价（`avg_cost` 只随上架正向移动，`inbound-tasks.putaway.js:203-223`，刻意简化，CLAUDE.md 第 20 节第 9 条）——不要"顺手"给拒收量反冲或补算。让步接收量按合同价进均价，符合"实际入库成本"。
- **`voidReceipt` 反冲的完整性**：撤回收货必须覆盖 `PENDING_QA(5)` / `REJECTED(6)` 两种新容器，否则撤回后遗留孤儿容器。**改前必读 `inbound-tasks.void.js` 全文**（硬约束 12：不读完整调用链不改反冲）。
- **REJECTED 容器的物理去向**：系统里标 `REJECTED`，物理上仍占货架。是否要求 PDA 扫码把不合格品移到"隔离区/待处理库位"？本期可只记状态不强制移位，Phase 2 再评估隔离库位流程（属于"仓库端只执行不决策"范畴，若做需系统指定隔离位而非让操作员自选，CLAUDE.md 第 1 节）。
- **迁移编号**：本文用 `N1/N2` 占位，实现时取当时 `backend/src/database/` 最大编号 +1（当前最大 150），**勿照抄本文数字**（存在重复/缺号，靠文件名排序执行，CLAUDE.md 第 8 节）。
- **免检行的完成判定**：`tryFinishTask` 改造要保证 `qa_required=0` 的行不因"未质检"卡住（其 `checked_qty` 恒为 0）——须在判定里对免检行用 `received_qty` 而非 `checked_qty`，实现时务必覆盖"同一收货单混合质检行与免检行"的用例。
