# 设计文档 02 · 采购请购与审批流（PR → 审批 → 采购单）

## 1. 背景与现状问题

采购链路目前**没有任何"申请—审批"环节**，任何持 `purchase.order.create` 的用户建单后，直接 `confirm` 就成了对供应商的正式采购承诺：

- 采购状态机只有四态四路径，无"待审批"中间态：
  `constants/documentStatusRules.js:4-28` 的 `purchase`：`1草稿 2已提交 3已完成 4已取消`，动作 `edit / confirm(1→2) / withdrawConfirm(2→1) / createInboundTask / complete / close / cancel / reopen`。
- 提交就是"确认下单"，`purchase.service.js:286-307` `confirm()` 只做 `lockStatusRow → assertStatusAction('purchase','confirm') → compareAndSetStatus(1→2)`，**中间没有任何人复核**。
- 路由 `purchase.routes.js:26` `POST /:id/confirm` 只校验 `PURCHASE_ORDER_CONFIRM`，而该权限在 `071_seed_role_permissions_v2.sql:59-62` 与建单权限一起整包发给了"采购与销售"角色（role_id=3）——**建单人自己就能确认**。
- 收货侧原有的人工审核闸门已在 v0.4.22 移除（`documentStatusRules.js:189-200`：`inboundTaskAudit` 的 `audit_status` 恒为 `0→1` 自动结算），采购全链路自此**无任何审批控制点**。

问题：
- **无预算/需求管控**：谁想买就能建单确认，采购金额无人事前把关。
- **无"需求 → 采购"的分离**：一线（仓库、门店）想补货只能口头告知采购，或直接拿到建单权自行下单，职责不分离。
- **与补货建议脱节**：设计文档 01（安全库存与补货建议）Phase 2 设想"补货建议一键生成采购单草稿"，但直接生成 PO 会绕过任何审批，等于把"系统算的建议"直接变成"对外承诺"，风险大。

本功能补上采购链路缺失的前置环节：**请购单（Purchase Requisition, PR）→ 审批 → 转生成采购单（PO）**。系统里**已有一套现成、经生产验证的一级审批实现——费用报销 `expenseClaim`**，本设计照它的状态机与加锁写法落地，不另造轮子。

## 2. 目标 / 非目标

**目标**
- 新增"采购请购单"单据：一线/采购发起需求 → 提交审批 → 审批人批准/驳回。
- 请购与采购职责分离：发起请购、审批请购、转生成采购单是三道独立授权。
- 已批准的请购单可**转生成采购单**，支持**一张请购转多张 PO（按供应商拆分）**、**分批转单**（部分明细先转、剩余后转）。
- 审批范式、状态机、加锁写法**完全复用 `expenseClaim`**，把落地风险与心智负担降到最低。
- 与补货建议衔接：补货建议页可勾选 →**生成请购单草稿**（而非直接生成 PO），让"系统建议"先过审批再成为对外承诺。

**非目标（本期不做，留后续）**
- 多级审批 / 按金额分级审批流（本期照 `expenseClaim` 只做**一级审批**；多级留 Phase 2）。
- 预算科目、预算占用与扣减（另立文档）。
- 请购询价、比价、供应商竞价（本期请购明细只带"建议供应商"，实际供应商在转单时定）。
- 请购单本身的库存/账款副作用（请购是纯需求单据，**不碰库存、不碰 `payment_records`**，与报销同理）。

## 5. 状态机（照 `documentStatusRules.js` 风格）

在 `constants/documentStatusRules.js` 的 `DOCUMENT_STATUS_RULES` 内**新增一台机器** `purchaseRequisition`，结构照 `expenseClaim`（`:104-125`）：

| 机器 | 状态 | 动作（from→to） |
|------|------|------------------|
| `purchaseRequisition` | 1草稿 2待审批 3已批准 4已驳回 5已取消 6已转采购 | `edit(from[1])`、`submit(1→2)`、`withdraw(2→1，本人撤回)`、`approve(2→3，审批人≠申请人)`、`reject(2→4)`、`convert(from[3]，转采购单)`、`complete(3→6，全部明细转完自动)`、`cancel(1/2/4→5)` |

关键规则（与 `expenseClaim` 对应）：
- `withdraw`：提交后发现填错，本人撤回改单，比走一遍驳回顺手（照 `documentStatusRules.js:110` 注释）。
- `approve/reject`：仅 `待审批(2)` 可操作；`approve` 服务层再加"审批人不能是申请人本人"硬校验（照 `expense-claims.service.js:176-178`）。
- `convert`：仅 `已批准(3)` 可转；**转单本身不改单头状态**（部分转单时请购仍停在已批准），只回写明细 `converted_qty`；当**全部明细 `converted_qty` 达到 `quantity`** 时，同事务内 `complete` 把 `3→6`（终态）。这套"分批 + 全部完成才结案"的语义对齐 `sale_order_items.dispatched` 分批发货（CLAUDE.md 7.2）与采购短装 `close`。
- `cancel`：`草稿/待审批/已驳回` 可取消；**已批准(3)**若已有转单记录不允许直接取消（`blocked` 提示"已批准并部分转采购的请购不能取消，请处理已生成的采购单"），照 `expenseClaim.cancel` 的 `blocked` 写法（`:120-123`）。

状态写入**一律走 `assertStatusAction('purchaseRequisition', action, status)` + `compareAndSetStatus`**，禁止裸 `UPDATE ... SET status=`（CLAUDE.md 硬约束 17.1）。`STATUS_TONE` 建议：`1 draft / 2 warning / 3 active / 4 danger / 5 draft / 6 success`。

**状态推进公共骨架（照 `expense-claims.service.js:122-143`，几乎照抄）**

```js
async function transition(id, action, extraSql = null, extraParams = []) {
  const conn = await pool.getConnection()
  try {
    await conn.beginTransaction()
    const row = await lockStatusRow(conn, {
      table: 'purchase_requisitions', id,
      columns: 'id, requisition_no, status, applicant_id, warehouse_id', entityName: '请购单',
    })
    const rule = assertStatusAction('purchaseRequisition', action, row.status)
    await compareAndSetStatus(conn, {
      table: 'purchase_requisitions', id,
      fromStatus: rule.from, toStatus: rule.to, entityName: '请购单',
    })
    if (extraSql) await conn.query(extraSql, [...extraParams, id])
    await conn.commit()
    return { id: Number(id), status: rule.to, requisitionNo: row.requisition_no }
  } catch (e) { await conn.rollback(); throw e } finally { conn.release() }
}
// approve/reject 前另查 applicant_id，若 === operator.operatorId 则 403（照 expense-claims:176-178）
```

**转采购单 `convert()`（请购特有，最关键、最高危）——SQL 骨架**

要点：① 幂等（连点两次不能生成两张 PO）② 事务 + 单头行锁 ③ 按供应商分组一转多 ④ 回写 `converted_qty` ⑤ 全部转完 CAS `3→6`。

```js
// body: { lines: [{ requisitionItemId, quantity, supplierId, supplierName, unitPrice }], requestKey }
async function convert(id, { lines, requestKey }, operator, scopeWarehouseIds = null) {
  const conn = await pool.getConnection()
  try {
    await conn.beginTransaction()
    // (1) 幂等回执：照 purchase.service.js:184-192 的 beginOperationRequest
    const st = await beginOperationRequest(conn, { requestKey, action: 'purchase.requisition.convert', userId: operator?.userId ?? null })
    if (st.replay) { await conn.rollback(); return st.responseData }

    // (2) 锁请购头 + 校验已批准(3) + 数据权限
    const head = await lockStatusRow(conn, { table: 'purchase_requisitions', id,
      columns: 'id, requisition_no, status, warehouse_id, warehouse_name, expected_date', entityName: '请购单' })
    assertInScope(scopeWarehouseIds, head.warehouse_id, '请购单')
    assertStatusAction('purchaseRequisition', 'convert', head.status)   // from[3]

    // (3) 逐行锁请购明细，校验 本次转量 ≤ (quantity - converted_qty)
    //     SELECT ... FROM purchase_requisition_items WHERE id IN (?) AND requisition_id=? FOR UPDATE
    //     供应商缺失（既未在明细带建议供应商、本次也未指定）→ 400 拒绝

    // (4) 按 supplierId 分组，每组复用 purchase.service.create 的建 PO 骨架（:200-212）：
    //     genOrderNo → INSERT purchase_orders(warehouse=head.warehouse, expected_date=head.expected_date, source_requisition_id=id)
    //     → 逐行 INSERT purchase_order_items（用本次 unitPrice/quantity）
    //     → INSERT purchase_requisition_conversions(requisition_item_id, purchase_order_id, quantity)
    //     → UPDATE purchase_requisition_items SET converted_qty = converted_qty + ? WHERE id=?

    // (5) 全部明细 converted_qty >= quantity ⇒ complete：assertStatusAction('purchaseRequisition','complete',3) + CAS 3→6
    const [[{ pending }]] = await conn.query(
      `SELECT COUNT(*) AS pending FROM purchase_requisition_items
       WHERE requisition_id=? AND converted_qty < quantity`, [id])
    if (Number(pending) === 0) {
      const rule = assertStatusAction('purchaseRequisition', 'complete', 3)
      await compareAndSetStatus(conn, { table: 'purchase_requisitions', id,
        fromStatus: rule.from, toStatus: rule.to, entityName: '请购单' })
    }

    const result = { requisitionId: Number(id), createdOrders: [/* {id, orderNo, supplierName} */] }
    await completeOperationRequest(conn, st, { data: result, message: '转采购单成功', resourceType: 'purchase_requisition', resourceId: Number(id) })
    await conn.commit()
    return result
  } catch (e) { await conn.rollback(); throw e } finally { conn.release() }
}
```

> **不要**在 `convert` 里 HTTP 调用采购模块的 create 接口，而是**在同一事务连接 `conn` 上直接执行建 PO 的 SQL**（CLAUDE.md 11："事务内禁止外部 I/O"；且跨事务无法保证请购状态与 PO 生成原子）。可把 `purchase.service.create` 里"建 PO 头 + 明细"那段抽成一个接受 `conn` 的内部函数 `insertPurchaseOrder(conn, {...})` 供两处复用（**这是唯一需要动到现有采购模块的地方，属新增可复用函数，不改现有行为**）。

**列表查询**：照 `expense-claims.service.js:244-285` 的三段式（过滤 + 分页 + 汇总），**并加仓库数据权限** `scopeFilter(scopeWarehouseIds, 'r.warehouse_id')`（请购带仓，照 `purchase.service.js:93-97`）；详情 `findById` 用 `assertInScope`（照 `purchase.service.js:145`）。

## 11. 风险与待确认

- **转单幂等是头号风险**：`convert` 是"点一下生成对外采购单"的高危写接口，必须走 `beginOperationRequest('purchase.requisition.convert')`（照 `purchase.create`），否则用户连点或 PDA/网络重试会生成重复 PO。前端 `convert` 必须带 `X-Request-Key`。
- **供应商来源待确认**：请购明细的"建议供应商"可空——若发起人不填、转单时也不指定供应商，`convert` 必须 400 拒绝（PO 头强依赖 `supplier_id`，见 `purchase_orders` NOT NULL 与 `purchase.service.create:194-199` 的供应商启用校验）。转单入口需强制每个待转行有确定供应商。
- **期望入库仓单仓约束**：`purchase_orders` 头是单仓（`warehouse_id` 在头），故请购头也设单一 `warehouse_id`，一张请购内所有商品同一期望入库仓；跨仓需求请开多张请购。若未来要一张请购跨仓转多仓 PO，需把仓库下移到请购明细并按 (supplier, warehouse) 双维度分组（本期不做）。
- **"已批准可否取消/改单"边界**：已批准(3)但尚未转单时，业务上可能想撤销。本期设计 `cancel` 不含 from[3]（已批准需先有转单则 blocked）；若产品要"已批准可作废未转部分"，需补一条 `void`/`reject`-back 边，实现时确认。
- **分批转单的剩余处理**：一张请购分批转单，若剩余部分不再采购，请购会永远停在"已批准(3)未结案"。可参照采购短装 `close`（`purchase.service.js:254-284`）补一个"关闭剩余请购"动作把它推到终态；本期先不做，列为待确认。
- **多份文档并行抢迁移号**：本文档与文档 01 都要新增迁移，编号**实现时取当前最大 +1**，勿写死（CLAUDE.md 硬约束：只能新增迁移文件、编号取当前最大值 +1）。
- **审批范式若未来升级为多级**：本期一级审批的字段（`approved_by/at`、`reject_reason`）是单节点快照，升多级需引入审批流水表，届时这几列语义需重新定义——与 `expenseClaim` 会同时面临同一问题，建议两者一起演进。
- `docs/` 历史文档可能滞后，任何冲突以代码为准（同文档 01 第 11 节）。
