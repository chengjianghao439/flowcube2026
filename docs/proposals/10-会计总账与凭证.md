## 1. 背景与现状

### 1.1 系统现在有的是「业务财务」，不是「会计财务」

flowcube 已经把**钱的业务事实**记得相当完整，但完全没有**会计核算层**（科目、凭证、总账、报表）。两者的差别是本文的出发点：

| 维度 | 业务财务（现有） | 会计财务（本文主题，缺失） |
|---|---|---|
| 记录什么 | 「谁欠我多少 / 我欠谁多少 / 哪个账户进出了多少」 | 「每一笔经济业务对应哪些会计科目的借贷」 |
| 数据形态 | 往来账款、收付款、资金流水、费用报销 | 记账凭证 → 明细账 → 总账 → 试算平衡表 → 三大报表 |
| 服务对象 | 业务/运营/出纳 | 会计、税务、审计、老板看经营全貌 |
| 现状 | ✅ 已具备 | ❌ 完全空白 |

**「会计要素完全空白」是逐项 grep 确认过的，不是推测：**

- `grep -rniE "凭证|总账|科目|voucher|ledger|会计|记账"` 在 `backend/src` / `frontend/src` 全仓命中 6 处，**逐条都是无关词**：`loadRolePermissions.js:11` 的「无效凭证」是 JWT 报错文案；`returns.helpers.js:52/124` 的「退款凭证」是提示文案；`usePaymentActions.tsx:82` / `payments.ts:15` 的「记账」指手工登记收付款；`pda/index.tsx:96` 的「设备凭证」指 PDA 会话 token。**没有任何一处是会计意义上的凭证/科目/总账。**
- `grep -rniE "税额|税率|价税|进项|销项|发票|invoice|tax"` 在 `backend/src` **零命中**。系统当前**完全不处理税**。
- `007_create_customers_purchase_sale_stockcheck.sql` 的采购/销售明细只有 `unit_price` / `quantity` / 表头 `total_amount`（`007:24/27`），**没有任何税额/税率列**；金额是「含税还是不含税」由使用者口径决定，系统不拆分。
- `004_create_products_and_suppliers.sql` 的供应商、`007` 的客户主数据**都没有纳税人识别号 / 开户行 / 开票信息字段**（`grep tax_no/税号/纳税人` 零命中）。

### 1.2 现有「业务财务」盘点（这些正是凭证的业务来源）

会计凭证不是凭空写的，它是对已经发生的业务事实的**投影**。系统里已经落库的、可作为凭证来源的事实有五类：

| 事实 | 表 | 建表迁移 | 关键点 |
|---|---|---|---|
| 应收 / 应付 | `payment_records`（+分录 `payment_entries`） | 054；`type` 1应付 2应收；`UNIQUE(type, order_id)` 幂等（迁移 091）；`confirm_status` 财务确认闸门（118）；`settlement_type` 结算方式快照（135/136） | 全量重算 upsert，非累加 |
| 收 / 付款与核销 | `payment_receipts` + `payment_entries` | 139 | 一笔汇款核销多笔账款，支持部分核销/预收 |
| 汇总对账单 | `reconciliation_statements` + `_items` | 140 | 期间账款汇总，锁定后导出核对 |
| 资金账户与流水 | `finance_accounts` + `finance_account_transactions` | 141 | **流水是唯一事实源，余额是投影**（`141` 头注释） |
| 费用报销 | `expense_claims` + `_items` + `expense_categories` | 143 | **明确不进 `payment_records`**（`143` 头注释：报销是内部经营费用，混进往来账款会污染账龄） |

外加两个**成本/库存事实**，是「结转成本」和「存货」类凭证的来源：

- `product_items.avg_cost`（移动加权成本，**仅入库正向更新，退货/撤回不反冲**——见 CLAUDE.md 第 20 节第 9 条）。
- `sale_order_items.cost_snapshot`（出库时点固化的 COGS，`warehouse-tasks.ship.js:143`）。
- `inventory_logs`（每次库存动作一条流水，带 `unit_price`，`054` 补列）。

### 1.3 结算发生点 —— 凭证自动生成的「挂钩处」

以下五个位置是业务事实**落库的确切时刻**，将来凭证映射就挂在它们之后（读它们的产物，不改它们）：

1. **采购收货上架完成 → 结算应付**：`inbound-tasks.settle.js:140 settlePurchaseOnAudit` → `:15 recomputePurchasePayable`。全量重算 `SUM(putaway_qty × unit_price) − 已退货`，`FOR UPDATE` 防 lost-update（`:36-45`）。会计意义：**借 库存商品 / 贷 应付账款**。
2. **销售出库完成 → 结算应收**：`sale.service.js:202 recomputeSaleReceivable`，全量重算 `SUM(shipped_qty × unit_price) − 已退货`。会计意义：**借 应收账款 / 贷 主营业务收入**。
3. **销售出库完成 → 结转成本**：`warehouse-tasks.ship.js:143`，写 `cost_snapshot = avg_cost`。会计意义：**借 主营业务成本 / 贷 库存商品**。
4. **收 / 付款核销**：`payment-receipts.service.js`。会计意义：收款 **借 银行存款 / 贷 应收账款**；付款 **借 应付账款 / 贷 银行存款**。
5. **费用报销付款**：`expense-claims.service.js`（pay 动作，写 `finance_account_transactions`）。会计意义：**借 管理费用/销售费用 / 贷 银行存款**。

现有「资金看板」`finance-dashboard.service.js` 只做账户余额分布、收支趋势、费用构成（`:2-7` 注释），**不是三大报表**，不要把它当成会计报表的雏形。

## 2. 目标 / 非目标

**本文要解决的问题**：让系统能把上述业务事实转成**标准会计凭证**，从而让会计/税务能拿到可入账、可报税的数据——无论最终是自建总账还是抛给专业财务软件。

**目标**
- 建立**业务事件 → 借贷分录**的映射层（凭证生成引擎 + 可配置的科目映射），这是两个方案共同的地基。
- 凭证**可追溯**（每张凭证锚定到具体业务单据）、**借贷平衡**、**可冲销**（红字凭证）。
- 提供**凭证导出**（标准记账凭证格式 / 金蝶 KIS 导入模板），让专业财务软件能接。（用户 2026-08-09 定案：不做用友模板）
- （视方案）科目表、总账/科目余额、简版三大报表。
- （独立子模块）进项/销项发票管理、价税分离。

**非目标（本期明确不做，避免范围爆炸）**
- **不做完整会计准则实现**：多币种、合并报表、固定资产折旧、长期待摊、预提/待摊分录、外币折算，全部不做。
- **不做期末结转损益的复杂账务**（本期若做报表，用「实时汇总法」而非「结转法」，见第 4.4 节）。
- **不替代专业财务软件报税**：即便自建总账，正式的纳税申报仍建议在金蝶或代账公司完成（除非客户明确要脱离）。
- **不做工资/社保/个税核算**（另立主题）。
- **凭证绝不反向驱动业务**：不能因为「凭证不平」去改 `payment_records` / `inventory_stock` / `finance_accounts`（硬约束，见第 11 节）。

## 3. 方案对比：自建轻量总账 vs 对接专业财务软件 ★

> 这是本文的**核心决策章**。两个方案不是二选一的对立面，而是**同一条路的不同里程**——它们共享同一个「凭证映射层」地基，区别只在「地基之上还要不要自己盖总账和报表」。

### 3.1 方案 A：自建轻量总账

在系统内建完整的会计核算闭环：科目表 → 凭证 → 明细账/总账 → 科目余额 → 简版资产负债表/利润表/现金流量表。

**范围**：第 4 节全部数据模型 + 第 5 节全部映射 + 总账查询 + 报表取数。

| 维度 | 评估 |
|---|---|
| 工作量 | **大**（估 4~6 人周仅后端）：科目体系、会计期间、凭证生成/冲销、总账过账、科目余额滚动、三张报表取数公式，每一块都有会计规则的坑 |
| 技术风险 | **高**：试算平衡、期间损益、报表勾稽（资产=负债+权益、利润表→未分配利润→资产负债表）这些是会计软件成熟度的核心，做错是「静默算错」——界面正常、数字悄悄不对，和库存/账款事故同性质 |
| 业务风险 | **高**：团队无会计软件经验；`avg_cost` 只正向移动（第 1.2 节）意味着存货口径本身就不是严格会计成本，直接出资产负债表的「存货」科目会有偏差 |
| 客户价值 | **中**：单租户中小企业通常已经有会计 + 金蝶/代账公司；系统自出的报表多为「管理层看看」，报税仍走外部 |
| 维护成本 | **高**：会计准则/税率会变，报表模板要长期跟 |

### 3.2 方案 B：只做凭证导出 / 对接金蝶

系统只负责把业务事实转成**标准记账凭证**（落库 + 导出为金蝶 KIS 的凭证导入模板，或通用「记账凭证」Excel），**总账、报表、报税全部由专业财务软件承担**。用友模板已定案不做。

**范围**：第 4.1~4.3 节数据模型（科目 + 凭证 + 分录）+ 第 5 节映射 + 导出。**不做** 4.4 科目余额、不做总账页、不做报表。

| 维度 | 评估 |
|---|---|
| 工作量 | **小**（估 1.5~2.5 人周）：科目表 + 凭证/分录表 + 映射引擎 + 一个导出器 |
| 技术风险 | **低**：只要保证「借贷平衡 + 幂等 + 可追溯」，正确性边界清晰、可自动化校验 |
| 业务风险 | **低**：对接是会计的日常，导入模板是成熟格式；会计在专业软件里仍可调整/补充分录 |
| 客户价值 | **高且立即**：直接省掉会计「照着 ERP 手工敲凭证」的重复劳动，这是最痛的点 |
| 维护成本 | **低**：科目映射变了改配置即可；不承担报表准则 |

### 3.3 推荐 ★

**分阶段走，先 B 后（可选）A：**

1. **先把「凭证映射层」做扎实并落库**（方案 B 的核心，同时是方案 A 的地基）。这一层价值最高、风险最低、且**无论将来是否自建总账都不浪费**。做完就能导出对接金蝶，立刻解决会计手工敲凭证的痛点。
2. **总账 / 科目余额 / 报表（方案 A 的增量）延后**，且**只有当客户明确表示「不再用外部财务软件、要在本系统出报表」时才做**。届时地基（科目 + 凭证 + 分录）已在，增量只是「凭证汇总成余额 + 余额套报表模板」。
3. **发票税务作为独立子模块最后做**（第 4.5 节），它相对独立，不阻塞前面。

推荐理由一句话：**凭证映射层是两个方案的最大公约数，先交付它 = 用最小风险拿到最高价值，并把「要不要自建总账」这个高风险决策推迟到有真实需求信号时再做。**

## 4. 数据模型

> 迁移编号：当前最大编号为 150，新迁移从 151 起顺延；**本文一律用 `迁移 N / N+1 / …` 指代，落地时取「当前最大编号 + 1」，切勿在本文写死具体数字**（硬约束）。命名前缀统一 `acct_`（会计）与 `fin_invoices`（发票）。

### 4.1 会计科目表 `acct_accounts`（方案 A/B 都要）

```sql
CREATE TABLE `acct_accounts` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `code`        VARCHAR(20)  NOT NULL COMMENT '科目编码，如 1001/1122/6001（遵循企业会计准则科目表习惯）',
  `name`        VARCHAR(60)  NOT NULL COMMENT '科目名称，如 库存现金/应收账款/主营业务收入',
  `category`    TINYINT      NOT NULL COMMENT '1资产 2负债 3权益 4成本 5损益(收入) 6损益(费用)',
  `balance_dir` TINYINT      NOT NULL COMMENT '余额方向 1借 2贷（资产/成本借，负债/权益/收入贷，费用借）',
  `parent_id`   BIGINT UNSIGNED DEFAULT NULL COMMENT '上级科目；顶级为 NULL',
  `level`       TINYINT      NOT NULL DEFAULT 1 COMMENT '科目级次',
  `is_leaf`     TINYINT      NOT NULL DEFAULT 1 COMMENT '1明细科目(可记账) 0汇总科目(不可直接记账)',
  `aux_type`    TINYINT      NOT NULL DEFAULT 0 COMMENT '辅助核算 0无 1往来单位 2部门 3项目（本期先支持 0/1）',
  `is_active`   TINYINT      NOT NULL DEFAULT 1,
  `is_preset`   TINYINT      NOT NULL DEFAULT 0 COMMENT '1系统预置(映射依赖，不可删)',
  `sort_order`  INT          NOT NULL DEFAULT 0,
  `created_at`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `deleted_at`  DATETIME     DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_acct_accounts_code` (`code`),
  KEY `idx_acct_accounts_parent` (`parent_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='会计科目表';
```

**预置一套最小科目**（seed 迁移，`is_preset=1`，映射引擎按 `code` 引用）：`1001 库存现金`、`1002 银行存款`、`1122 应收账款`、`1405 库存商品`、`2202 应付账款`、`2221 应交税费`（子级 `进项税额`/`销项税额`）、`6001 主营业务收入`、`6401 主营业务成本`、`6602 管理费用`、`6601 销售费用`、`1901 待处理财产损溢`。

### 4.2 记账凭证 `acct_vouchers`（方案 A/B 都要）

```sql
CREATE TABLE `acct_vouchers` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `voucher_no`    VARCHAR(30)  NOT NULL COMMENT '凭证号 记-YYYYMM-序号',
  `voucher_date`  DATE         NOT NULL COMMENT '记账日期（取业务发生日，非生成日）',
  `period`        CHAR(6)      NOT NULL COMMENT '会计期间 YYYYMM（由 voucher_date 派生，冗余便于按期查）',
  `source_type`   VARCHAR(40)  NOT NULL COMMENT '业务来源类型：purchase_settle/sale_revenue/sale_cogs/receipt_in/payment_out/expense_pay/purchase_return/sale_return/stock_check/manual',
  `source_id`     BIGINT UNSIGNED DEFAULT NULL COMMENT '来源业务单据 id（manual 为空）',
  `source_no`     VARCHAR(40)  DEFAULT NULL COMMENT '来源业务单号快照',
  `summary`       VARCHAR(200) DEFAULT NULL COMMENT '凭证摘要',
  `total_debit`   DECIMAL(16,2) NOT NULL DEFAULT 0 COMMENT '借方合计',
  `total_credit`  DECIMAL(16,2) NOT NULL DEFAULT 0 COMMENT '贷方合计（必须等于借方，入库前 assert）',
  `status`        TINYINT      NOT NULL DEFAULT 1 COMMENT '1已生成(草稿) 2已过账 3已冲销',
  `is_reversal`   TINYINT      NOT NULL DEFAULT 0 COMMENT '1本张是红字冲销凭证',
  `reversed_id`   BIGINT UNSIGNED DEFAULT NULL COMMENT '被本张冲销的原凭证 id',
  `source_hash`   VARCHAR(64)  DEFAULT NULL COMMENT '来源事实的内容指纹，用于重算时判断是否需重生成',
  `created_by`    BIGINT UNSIGNED DEFAULT NULL,
  `created_at`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_acct_vouchers_no` (`voucher_no`),
  -- 历史设计示意；当前幂等锚点含 company_id，采购修订另用 source_root_id（迁移232）
  UNIQUE KEY `uk_acct_vouchers_source` (`source_type`, `source_id`),
  KEY `idx_acct_vouchers_period` (`period`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='记账凭证';
```

**当前实现（2026-09-04 修订）**：来源根凭证以 `(company_id, source_type, source_id)` 唯一定位。采购来源金额变化/归零保留原凭证，通过 `source_root_id` 串联自动红字与新正向凭证（迁移232），`source_hash` 保证重复生成不累加；人工红冲后不自动恢复，已结账期间不可修订。其他来源沿用既有 upsert，不能把采购修订策略当作所有来源都已迁移。

**注意坑：** `source_type` 用**字符串枚举**而非 tinyint——事件类型会随业务演进增加（将来加了预付款、押金等），字符串可读、扩展不撞编号；但**必须在代码里用常量集中定义**（`constants/voucherSource.js`），不散落魔法字符串。

**科目编码/名称按快照存**（同 `expense_claim_items.category_name`、`payment_records.settlement_type` 的既有做法）：科目主数据改了，历史凭证不变。往来科目（应收/应付）带 `aux_id` 指向供应商/客户，为将来「按往来单位出明细账」留口。

### 4.4 科目余额 `acct_account_balances`（仅方案 A 需要）

```sql
CREATE TABLE `acct_account_balances` (
  `id`             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `account_id`     BIGINT UNSIGNED NOT NULL,
  `period`         CHAR(6)      NOT NULL COMMENT '会计期间 YYYYMM',
  `opening_debit`  DECIMAL(16,2) NOT NULL DEFAULT 0,
  `opening_credit` DECIMAL(16,2) NOT NULL DEFAULT 0,

  `period_credit`  DECIMAL(16,2) NOT NULL DEFAULT 0 COMMENT '本期贷方发生额',
  `updated_at`     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

  UNIQUE KEY `uk_acct_balance` (`account_id`, `period`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='科目期间余额（凭证分录的投影）';
```

**这张表是投影，不是事实源**（与 `finance_accounts.current_balance`、`inventory_stock.quantity` 同性质）。两种实现取舍：

- **实时汇总法（推荐本期）**：不落这张表，总账/报表直接 `SUM(acct_voucher_entries)` 按 `period` + `direction` 实时算，期初 = 上期累计。数据量小（凭证条数有限），实时算最简单、绝不漂移。**本文推荐若做方案 A 就用这个，先不建 `acct_account_balances`。**
- **滚动余额法（数据量大后再上）**：落这张表，每张凭证过账时同事务锁行累加。性能好但引入漂移风险，需要对账工具（类比 `resync:inventory-stock`）。

「三大报表」在实时汇总法下就是**取数公式**，不需额外表：资产负债表 = 各资产/负债/权益科目期末余额按模板归集；利润表 = 各损益科目本期发生额；现金流量表**从 `finance_account_transactions` 的 `biz_type` 归集**（本系统现金流本就有独立事实源，比从凭证反推更准）。

**价税分离的两个口径抉择（待确认）**：

1. **发票池独立于业务单据**（推荐本期）：发票只是「进销项发票的登记本 + 认证/抵扣台账」，与采购/销售单**弱关联**（`source_id` 可空、可后补）。**不改** `purchase_order_items` / `sale_order_items`，业务金额继续按现口径（含税总额）走结算，税额只在凭证映射时按 `fin_invoices` 拆分「应交税费-进/销项税额」。风险最低。

## 5. 核心流程：业务事件 → 凭证映射规则

### 5.1 凭证生成的架构原则（最重要）

**凭证由独立的映射引擎从业务事实生成，不塞进结算事务：**

- 结算事务（`recomputePurchasePayable` 等）**只写业务事实**，不生成凭证——保持核心链路简单，且**凭证生成失败绝不能回滚业务**（硬约束）。
- 凭证生成走**独立入口**，两种触发方式二选一（推荐前者）：
  - **（推荐）按需/批量重算**：新建 `modules/accounting/` 的 `voucher-engine`，从既有事实表（`payment_records` / `payment_receipts` / `finance_account_transactions` / `sale_order_items.cost_snapshot` / 退货 / 盘点）**读取并全量重算生成凭证**，`UNIQUE(source_type, source_id)` 幂等。由定时任务（复用 `scheduler.js`）或用户在「凭证」页点「生成本期凭证」触发。**这样凭证与业务彻底解耦，业务事务零负担，凭证可反复重算对齐。**
  - **（备选）事件钩子**：在各结算函数尾部（同事务外，`try/catch` 包裹、失败仅记日志不回滚，类比 `printOptionalSideEffect`）异步入队一个「待生成凭证」事件。实时性好但耦合更紧、失败面更大。
- **凭证是投影**：引擎只 `INSERT/UPDATE acct_*` 表，**绝不** `UPDATE payment_records/inventory_stock/finance_accounts`。若某业务事实缺科目映射或不平，**报错/挂起该张凭证，不动业务数据**。

### 5.3 税额拆分（仅发票子模块上线后）

事件 1（采购）与事件 2（销售）在**价税分离**后各多一条分录：

- 采购：借 库存商品（不含税）+ 借 应交税费-进项税额；贷 应付账款（价税合计）。
- 销售：借 应收账款（价税合计）；贷 主营业务收入（不含税）+ 贷 应交税费-销项税额。

税额来源 = 关联的 `fin_invoices.tax_amount`；**无发票时不拆税**（全额进收入/成本，等取得发票再重算该张凭证——幂等重算天然支持后补发票）。

### 5.4 冲销（红字凭证）

**采购来源采用保留痕迹的自动修订**：金额下降、增加或归零时，先生成当前正向版本的红字，保留被冲销原凭证及分录；新金额非零时再生成正向修订。自动修订的 `source_root_id` 指向原来源锚点，红字的 `reversed_id` 指向被冲销版本。

总账及 Excel 导出包含完整冲销对，不能过滤掉已冲销原凭证；红字与被冲销凭证均不可普通删除。账套行锁串行化凭证写入/期间开关，已闭账期间拒绝改写。人工红冲不触发后续自动恢复；其他来源继续保留既有 upsert 行为。

## 9. 分阶段落地 ★（强烈建议极小步）

> 每个阶段都是**可独立交付、可停下**的完整增量。**强烈建议做完 Phase 1 就上线观察真实需求，再决定是否继续 Phase 2/3。**

**Phase 0 — 科目地基（0.5 周）**
1. 迁移 N：`acct_accounts` + 预置科目 seed。
2. 前端科目表页（查看 + 维护）。
3. `constants/voucherSource.js`：定义事件枚举 + 科目映射规则（此时只有配置，不生成）。
- 交付物：一套可维护的会计科目体系。**风险极低。**

**Phase 1 — 凭证映射 + 导出（方案 B 核心，1.5~2 周）★ 价值最高**
1. 迁移 N+1：`acct_vouchers` + `acct_voucher_entries`。
2. `voucher-engine.js`：实现 §5.2 前 6 类事件的凭证生成（全量重算 + 借贷平衡 assert + 幂等）。
3. 凭证列表/详情页 + 「生成本期凭证」+ **导出金蝶模板 & 通用凭证 Excel**。
4. 退货（事件 7/8）、盘点（事件 9）凭证。
- 交付物：**会计不用再照着 ERP 手敲凭证，一键导出到专业软件。这一步做完就解决了最痛的点。**
- 决策闸门：上线观察——若会计满足于「导出对接」，**可以就此停住**，Phase 2/3 都不做。

**Phase 2 — 自建总账 + 简版报表（方案 A 增量，2~3 周，仅当客户明确要脱离外部财务软件）**
1. 总账 / 明细账 / 科目余额（**先用实时汇总法，不建 `acct_account_balances`**）。
2. 试算平衡表（借贷发生额/余额平衡校验）。
3. 简版资产负债表 / 利润表；现金流量表从 `finance_account_transactions` 归集。
- 决策闸门：只有真实需求信号出现才启动；启动前重新评估「团队是否有会计软件经验」这条风险。

**Phase 3 — 发票管理 + 价税分离（1.5~2 周，独立）**
1. 迁移 N+3：`fin_invoices`；进项/销项发票池 + 认证抵扣台账。
2. 凭证映射接入税额拆分（§5.3），无发票不拆税。
3. （远期、单独立项再评估）业务单据内嵌价税（第 4.5 节口径 2）——**动核心链路金额口径，本文不展开**。

## 10. 验证清单

- **借贷平衡（每张凭证）**：`voucher-engine` 入库前 `assert(total_debit === total_credit)`，且分录 `SUM(借) === SUM(贷)`；新增专项测试 `tests/accounting-voucher-balance`。
- **与业务账款勾稽（对账不变量）**：
  - `Σ 应付类凭证净额（贷2202−借2202）` 应等于 `SUM(payment_records where type=1 的未付余额变动)`；应收侧同理对 1122。
  - `Σ 收付款凭证的银行/现金分录` 应等于 `finance_account_transactions` 的对应流水合计。
  - 提供一个「凭证 vs 业务事实」对账报表/脚本（类比 `GET /inventory/check-consistency`），任何不勾稽项列出来。
- **幂等**：同一业务单据反复触发凭证生成，`acct_vouchers` 不新增、金额收敛到最新值（模拟分批发货 + 退货 + 撤回收货的任意顺序）。
- **不反向影响业务（最关键）**：凭证生成/冲销后，跑 `npm run smoke:mainline` / `smoke:finance` / `GET /inventory/check-consistency`——**业务事实与库存缓存必须零变化**。这是「凭证是投影」的回归保证。
- **导出正确性**：导出的金蝶模板能被目标软件成功导入且借贷平衡（拿一个真实科目表试导）。
- 前端 `tsc -p frontend/tsconfig.app.json --noEmit` + 两端 lint；`npm run test:permissions`（新权限码一致性）。

## 11. 风险与待确认

**硬约束（不可违反）**
- **凭证是业务的投影，绝不反向改业务事实**：不得因凭证不平/冲销去 `UPDATE payment_records` / `inventory_stock` / `finance_accounts` / 采购销售单。凭证引擎对这些表**只读**。
- **不绕过现有结算引擎**：凭证挂在 `recomputePurchasePayable` / `recomputeSaleReceivable` 等**之后读产物**，不改写它们的结算逻辑，不新增第二条应收应付计算路径。
- **新迁移不写死编号**：取当前最大编号（150）+1 顺延；只新增迁移文件，不改已执行迁移。

**待确认（需与用户/会计确认后再定）**
1. **方案抉择（最重要）**：是否认可「先 Phase 1 凭证导出、总账报表按需再说」的推荐？还是一开始就要自建总账+报表？——这决定工作量差一个数量级（2 周 vs 6+ 周）。
2. **冲销方式已落地**：采购金额变化通过红字+新正向修订保留痕迹，详见 §5.4；其他来源的进一步推广需单独确认业务范围。
3. **价税口径**：发票子模块用「发票池弱关联、税只在凭证拆分」（推荐、不动核心链路），还是要「业务单据内嵌价税」（动 `purchase_order_items`/`sale_order_items` 金额口径，风险大）？（第 4.5 节）
4. **成本口径偏差**：`avg_cost` 只正向移动、退货不反冲（CLAUDE.md 第 20 节第 9 条）——若做资产负债表「存货」科目，其账面与严格会计成本会有偏差，需接受或另立成本核算口径。
5. **凭证触发方式**：定时/按需批量重算（解耦、推荐）vs 结算尾部事件钩子（实时、耦合更紧）？（§5.1）
6. **科目表标准**：用「小企业会计准则」还是「企业会计准则」的科目编码？预置科目范围？
7. **调拨/分仓是否需要会计维度**：本期默认调拨不生成凭证；若客户要分仓/分部门核算成本，范围会扩大。

**其他风险**
- **会计正确性是「静默出错」类风险**：和库存/账款事故同性质，界面正常、数字悄悄不对。因此第 10 节的「借贷平衡 + 勾稽对账」必须自动化、进 CI，不能靠人眼看。
- **导出模板碎片化**：金蝶 KIS/K3/云等格式各不相同，导出器要做成可扩展的模板层，别写死一家。（用友模板已定案不做）
- **`exceljs` 导出**：复用现有依赖即可（CLAUDE.md 第 20 节第 12 条已说明其 audit 告警不可达、不必处理）。
