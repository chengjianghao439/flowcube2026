# 设计文档 03 · 多计量单位与单位换算（箱 / 件 / 托）

> 状态：**设计草案，待评审**
> 风险等级：**高（全链路改造）**。本文所有"可机械验证的声明"均对着 2026-07-29 的当前代码核实过（指到 `文件:行`）；实现时若发现代码已变，以代码为准并回来订正本文。
> 中心原则：**库存事实层永远只用「基本单位」记数，多单位换算只发生在录入 / 展示层。** 这条不可谈判，是本设计的骨架（对应 CLAUDE.md 第 9 节库存核心不变量）。

## 1. 背景与现状问题

### 1.1 现状：全系统只有「一个单位」

`product_items` 只有一个自由文本单位字段：

```sql
-- backend/src/database/004_create_products_and_suppliers.sql:9
`unit` VARCHAR(20) NOT NULL DEFAULT '个' COMMENT '单位',
```

它不是主数据，只是一个字符串（"个" / "件" / "箱" 随手填），**没有换算关系、没有辅助单位**。一件商品在整个生命周期里只能用这一个单位记数、下单、扫码、结算。

现实业务里同一 SKU 常有多个计量口径：采购按**箱**谈价下单（1 箱 = 12 件）、库内按**件**存放、大宗调拨按**托盘**。现在系统逼着所有环节都用同一个单位，采购员只能自己心算"5 箱 = 60 件"再手填 60，且单价也要换算成"每件"，极易出错，且单据上看不到"其实是 5 箱"。

### 1.2 数量单位贯穿了哪些表（逐个核实）

数量 + 单位是一条贯穿全系统的主线，下表每一处的数量列**当前都隐式代表「那一个 `unit` 字段的口径」**。这正是改造要格外小心的原因——动了单位口径，下面每一张表都受影响：

| 表 | 单位 / 数量列 | 位置 | 角色 |
|---|---|---|---|
| `product_items` | `unit` | 004:9 | 商品主数据的唯一单位 |
| `purchase_order_items` | `unit` / `quantity` / `unit_price` / `amount` | 007:48-51 | 采购下单量与单价 |
| `inbound_task_items` | `unit` / `ordered_qty` / `received_qty` / `putaway_qty` | 024:29-32 | 收货三段量 |
| `inventory_containers` | `unit` / `quantity` / `remaining_qty` | 016:25-26, 017:7 | **库存唯一事实源** |
| `inventory_stock` | `quantity`（无 unit 列） | 005:8 | 缓存 + 预占账 |
| `inventory_logs` | `change_qty` / `before_qty` / `after_qty`（无 unit 列） | 006:8-10 | 流水 |
| `warehouse_task_items` | `unit` / `required_qty` / `picked_qty` | 012:36-38 | 出库任务量 |
| `sale_order_items` | `unit` / `quantity` / `unit_price` / `amount` / `cost_snapshot` / `shipped_qty` | 007:85-88, 119:15 | 销售下单量、单价、COGS |
| `inventory_check_items` | `unit` / `book_qty` / `actual_qty` / `diff_qty` | 007:118-121 | 盘点账面 / 实盘 / 差异 |
| `purchase_return_items` | `unit` / `quantity` / `unit_price` / `amount` | 055:28-31 | 采购退货 |
| `sale_return_items` | `unit` / `quantity` / `unit_price` / `amount` | 055:62-65 | 销售退货 |
| `return_task_items` | `unit` / `expected_qty` / `received_qty` / `checked_qty` / `putaway_qty` | 085:34-38 | 退货 PDA 作业 |
| `package_items` | `unit` / `qty` | `modules/packages/packages.service.js` | 打包装箱 |

### 1.3 现状里数量口径的「首尾衔接」是隐式一致的

现状能正常运行，靠的是**所有环节碰巧用同一个单位**，于是这些等式天然成立（都已核实）：

- 采购单 `amount = quantity × unit_price` — `purchase.service.js:210`
- 收货任务 `ordered_qty` **直接复制** `purchase_order_items.quantity` — `inbound-tasks.command.js:69,156`
- 上架把 `putaway_qty` 累加成容器 `remaining_qty`，再 `syncStockFromContainers` 刷 `inventory_stock.quantity`
- 采购应付 `= SUM(putaway_qty × poi.unit_price)` — `inbound-tasks.settle.js:37`
- 移动加权成本 `avg_cost = (prevQty × oldAvg + qty × purchasePrice) / (prevQty + qty)`，`qty` 是上架的基本量、`purchasePrice = poi.unit_price` — `inbound-tasks.putaway.js:217-221`
- 销售应收 / 总额 `= Σ(picked_qty × unit_price)` — `warehouse-tasks.ship.js:229,252`；成本快照 `cost_snapshot = avg_cost` — `ship.js:143`

**关键洞察**：这一整条链条里的数量（`quantity → ordered_qty → putaway_qty → remaining_qty → inventory_stock.quantity`）和 `unit_price` 目前是**同一口径**，所以首尾自洽。一旦允许"采购按箱、库内按件"，就必须保证**换算只在进入这条链之前发生**——否则任一处口径错配，都会静默算错库存或钱（`putaway_qty` 按箱、`unit_price` 按件，应付立刻偏 12 倍）。

## 2. 目标 / 非目标

**目标**
- 商品可维护**一个基本单位 + 若干辅助单位**及其换算率（如 1 箱 = 12 件、1 托 = 48 件）。
- 采购 / 销售等单据可**按辅助单位录入**（下 5 箱、报每箱价），系统落库时折算成基本单位，单据与打印**回显录入口径**（"5 箱（60 件）"）。
- 库存事实层（容器 / 缓存 / 流水 / 盘点）**继续只用基本单位**，库存不变量一字不改。
- 金额口径（应付 / 应收 / 成本 / 均价）在多单位下**与合同金额一致**，误差可控且可论证。
- 存量数据与历史单据**零感知平滑**（默认换算率 = 1，语义不变）。

**非目标（本期不做）**
- 不做"变动换算率"（同一 SKU 不同批次箱规不同）。换算率是商品级**当前配置**，单据行只快照下单那一刻的率。
- 不做单位维度的价格体系（每单位不同折扣阶梯）——沿用现有 `product_price_levels`（060），只在录入时按单位折算。
- 不做 PDA 现场"自选单位"（违背"仓库端只执行不决策"，见 CLAUDE.md / MEMORY「仓库侧不能有决策权」）。PDA 用什么单位由系统按作业类型给定。
- 不做重量 / 体积等**异维度**单位（本设计只处理同一实物的整数倍计数换算）。

## 4. 数据模型

### 4.1 单位主数据表（新增，迁移取当前最大编号 + 1）

> 迁移编号不写死。当前 `backend/src/database/` 最大编号约在 150 一带且文档 01 已规划 151，**实现时取实际最大值 + 1**，逻辑名 `product_units`。

换算率放在**商品级**而非"全局单位字典级"：因为"1 箱 = 多少件"是**每个 SKU 各不相同**的（A 商品 1 箱 12 件，B 商品 1 箱 24 件），全局字典无法表达。

```sql
CREATE TABLE `product_units` (
  `id`               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `product_id`       BIGINT UNSIGNED NOT NULL,
  `unit_name`        VARCHAR(20)  NOT NULL              COMMENT '单位名（箱/件/托）',
  `conversion_rate`  DECIMAL(18,6) NOT NULL DEFAULT 1  COMMENT '1 本单位 = N 基本单位；基本单位行恒为 1',
  `is_base`          TINYINT(1)   NOT NULL DEFAULT 0    COMMENT '1=基本单位（唯一）',
  `sort_order`       INT          NOT NULL DEFAULT 0    COMMENT '录入下拉排序',
  `is_active`        TINYINT(1)   NOT NULL DEFAULT 1,
  `created_at`       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_product_unit` (`product_id`,`unit_name`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='商品多计量单位与换算率（换算率商品级）';
```

三条硬约束（写入服务里校验，不能只靠表结构）：
1. **每个商品有且仅有一行 `is_base=1`，其 `conversion_rate` 恒 = 1。** 基本单位即 `product_items.unit`（存量商品默认它就是唯一的基本单位）。
2. **辅助单位换算率必须 > 1 且相对基本单位表达**（不允许"1 件 = 1/12 箱"这种小于 1 的倒数表达，避免除法链）。是否允许**非整数换算率**（1 托 = 12.5 件）是决策点，见第 11 节；默认**只允许正整数换算率**，`DECIMAL(18,6)` 只是给未来留空间。
3. **本表不设 `deleted_at`。** 它是配置：停用某辅助单位置 `is_active=0`；换算率一经被单据快照引用，改动**不回溯**历史单据（历史行有自己的 `conversion_rate` 快照，见 4.2）。

`product_items.unit` 继续保留，语义收敛为"**基本单位名**"，作为 `product_units` 里 `is_base=1` 行的冗余（与现有大量读 `p.unit` 的代码兼容，避免全站 JOIN）。

### 4.2 单据明细行：加「录入口径快照」列，不动既有数量列

**核心手法**：既有数量列（`quantity`/`ordered_qty`/`putaway_qty`/`required_qty`/…）与 `unit_price` 的**语义保持不变——恒为基本单位口径**，下游一切 SQL 因此零改动。只在明细行**新增三列快照录入口径**，纯用于回显 / 打印 / 审计，**不参与任何库存或账款计算**。

对每张"用户录入数量"的明细表（`purchase_order_items` / `sale_order_items` / `purchase_return_items` / `sale_return_items`）新增：

```sql
ALTER TABLE `purchase_order_items`
  ADD COLUMN `entry_unit`       VARCHAR(20)   NULL COMMENT '录入单位（快照，不参与计算）' AFTER `unit`,
  ADD COLUMN `entry_qty`        DECIMAL(18,4) NULL COMMENT '录入单位下的数量（快照）'      AFTER `quantity`,
  ADD COLUMN `conversion_rate`  DECIMAL(18,6) NOT NULL DEFAULT 1 COMMENT '下单时点 1录入单位=N基本单位（快照）' AFTER `entry_qty`;
```

- `quantity`（**基本单位**，= `entry_qty × conversion_rate`）→ 喂给库存链路，语义与现在完全一致。
- `unit_price`（**每基本单位**）→ 喂给结算 / 均价，语义不变。
- `entry_unit` / `entry_qty` / `conversion_rate` → 只给前端和打印回显"5 箱"。
- 存量行：`entry_unit = unit`、`entry_qty = quantity`、`conversion_rate = 1`（迁移里一句 `UPDATE` 回填），语义完全等价。

**收货 / 出库 / 退货作业类明细表（`inbound_task_items` / `warehouse_task_items` / `return_task_items` / `inventory_check_items`）本期不加录入列**：它们是**执行/事实类**，数量恒为基本单位；现场展示要"折算成箱"由前端按 `product_units` 实时算即可（见第 9 节 Phase 1）。这样也守住"库存事实层不引入第二口径"。

### 4.3 容器与缓存：一个字不改

- `inventory_containers`：`remaining_qty` / `quantity` 恒为基本单位；`unit` 列继续冗余基本单位名。
- `inventory_stock.quantity`：恒为基本单位（本就只能由 `syncStockFromContainers` 写，见 CLAUDE.md 第 9 节第 2 条）。
- `inventory_logs`：`change_qty` 恒为基本单位；`unit_price`（054 补齐）恒为每基本单位。

**这是本设计最重要的落点**：换算率**进不了**库存事实层，所以第 9 节的每一条不变量都不受影响。

## 5. 核心换算规则

### 5.1 录入 → 基本单位（进入系统的唯一方向）

```
录入：entry_qty（录入单位）、entry_unit_price（每录入单位价）、conversion_rate（=product_units 当前率快照）
落库：
  quantity   = entry_qty × conversion_rate          -- 基本单位，喂库存/占库/收货
  unit_price = entry_unit_price / conversion_rate    -- 每基本单位，喂结算/均价（高精度，见 5.4）
  amount     = entry_qty × entry_unit_price          -- 金额以录入口径为权威（见 5.2）
```

**方向是单向的**：数据一旦落库即为基本单位，后续所有环节（收货、上架、占库、出库、盘点、退货、结算）都在基本单位上运行，**永不反向换算回箱**去做计算。反向换算只发生在**展示**（把基本单位量 friendly 成 "60 件 = 5 箱"）。

### 5.2 金额一致性论证（为什么 `amount` 以录入口径为权威）

现状 `amount = quantity × unit_price`。多单位下若仍用"基本单位量 × 每基本单位价"会出问题：当换算率除不尽时 `unit_price = entry_unit_price / rate` 必须截断（DECIMAL 有限小数）。例：每箱 100 元、1 箱 = 12 件：

```
unit_price（每件）= 100 / 12 = 8.333333…  →  截断存储
quantity（件）   = 5 × 12 = 60
若 amount = 60 × 8.3333 = 499.998  ≠  合同 5 × 100 = 500
```

因此规定：**`amount` 一律 = `entry_qty × entry_unit_price`（= 现状 `quantity × unit_price` 在录入口径下的自然延续），下单金额永远等于合同金额，零误差。** 这也意味着单据总额 `total = Σ amount` 天然正确。

### 5.3 借鉴 `toQtyUnits` 的整数化，避免换算浮点误差

`packages.service.js:89-99` 用 `QTY_SCALE=10000` 把 DECIMAL 数量乘进整数域再运算、最后 `/10000` 回 DECIMAL，规避浮点累加误差：

```js
const QTY_SCALE = 10000
const toQtyUnits   = v => Math.round(Number(v) * QTY_SCALE)
const fromQtyUnits = u => Number((Number(u) / QTY_SCALE).toFixed(4))
```

换算 `quantity = entry_qty × conversion_rate` 时同样先进整数域再回 DECIMAL，防止 `5 × 12` 之类被浮点带偏。整数换算率（默认约束）下换算是精确的；若未来放开非整数率，则本层用 `QTY_SCALE` 定标后四舍五入，并在明细行**存换算后的绝对值**，杜绝"每次重算率略有出入"。

### 5.4 结算 / 应收口径（本设计唯一必须审视的下游 SQL）

现状两处金额**重算**用的是数量 × 单价，而非直接读 `amount`：

- 应付：`SUM(iti.putaway_qty × poi.unit_price)` — `inbound-tasks.settle.js:37`
- 应收 / 总额：`Σ(picked_qty × unit_price)` — `ship.js:229,252`

它们必须按数量 × 单价重算，**因为部分收货 / 分批发货时结算的是"实际到货 / 实发的那部分"**，不能整单读 `amount`。于是每基本单位单价 `unit_price` 的**精度**直接决定金额误差。给两个方案：

- **方案 A（推荐，改动最小）**：把这些明细表的 `unit_price` **提精度**到 `DECIMAL(18,8)`（当前多为 `DECIMAL(12,4)`）。8.33333333 × 60 = 499.9999998 ≈ 500.00，误差压到亿分位，四舍五入到分（业务展示精度）完全无感。下游 SQL **一字不改**。
- **方案 B（绝对精确，改动大）**：结算改为按"已上架量占下单量的比例 × 录入金额"分摊：`应付 = Σ (putaway_qty / quantity) × amount`。零截断误差，但要改 `settle.js` / `ship.js` 的 SUM 逻辑，并处理部分行 `quantity=0` 兜底，回归风险高。

**推荐方案 A**：守住"下游 SQL 零改动"的核心优势，误差不可见；仅当财务要求账账绝对到厘一致时再上方案 B（列入第 11 节待确认）。均价 `avg_cost`（putaway.js:217-221）用同一个高精度 `unit_price`，同理受益。

### 5.5 换算率快照 vs 主数据（与账款快照同源的道理）

单据行的 `conversion_rate` 是**下单那一刻**从 `product_units` 拷来的**快照**，之后商品改箱规**不回溯**历史单据——与 `payment_records.settlement_type`（136）/ `sale_order_items.cost_snapshot`（119）"首次写入后不追溯"的既有原则完全一致（CLAUDE.md 第 7.1 节）。收货 `inbound_task_items` 从 `purchase_order_items` 派生数量时，读的是**已经折算好的基本单位 `quantity`**（现状 `command.js:69,156` 复制的就是它），所以收货侧连快照都不用存。

| `types/products.ts` | `Product` 加 `units: ProductUnit[]`（`{unitName, conversionRate, isBase}`）；单据行类型加 `entryUnit/entryQty/conversionRate` |
| `pages/products/form.tsx` | 新增"计量单位"Section：基本单位 + 可增删的辅助单位行（单位名 + 换算率），仿现有 `article_number/spec` 字段维护套路 |
| 采购 / 销售建单明细组件 | 数量单元格旁加**单位下拉**（默认基本单位，选辅助单位则显示"= N 基本单位"）；单价 label 随单位变（"每箱价"）；行金额实时 = `entryQty × entryUnitPrice`。**换算与校验只做前端呈现，权威值由后端折算落库**（守 CLAUDE.md 第 13 节"前端不复制后端业务规则"） |
| 列表 / 详情 / 打印 展示 | 数量列回显 `entryQty entryUnit`，副行灰字标基本单位量（"5 箱（60 件）"）；库存 / 盘点 / PDA 页按 `product_units` 把基本单位量 friendly 成辅助单位展示 |

前端**只负责呈现与便捷录入**，绝不把"箱数×率"当权威——落库的基本单位量、单价、金额一律以后端折算结果为准。

- **单位主数据维护复用商品管理权限**（`product.manage` 一类，实现时对齐 `permissions.js` 现有码），不新增权限码——省掉"后端常量 + 前端常量 + seed 迁移"三处手工同步 + `test:permissions` 成本（沿用文档 01 第 8 节同款判断）。

- 展示层（列表 / PDA friendly 显示）纯读，无权限新增。

## 9. 分阶段落地（强制按此顺序，逐段可停可回滚）

> 原则：**先只读、再录入、最后 PDA**。每个 Phase 都能独立上线并回滚，绝不一次性铺开全链路。

**Phase 0 · 单位主数据（纯配置，零链路影响）**
- 迁移建 `product_units` + seed 每商品基本单位行（rate=1）。
- 商品档案维护多单位。此时**没有任何单据 / 库存逻辑读它**，纯配置沉淀。上线风险≈0。

**Phase 1 · 只读展示多单位（不碰录入、不碰库存）**
- 列表 / 详情 / 库存 / 盘点 / PDA 把基本单位量**友好显示**成辅助单位（"60 件 = 5 箱"），纯前端读 `product_units` 计算。
- 不改任何写路径、不改任何数量列。**这一步就已交付大部分体感价值**，且完全无法破坏库存。

**Phase 2 · 采购录入放开（第一条写链路）— ✅ 已本地实现（未 push/发版）**
- 迁移186：`purchase_order_items` 加 entry_unit/entry_qty/conversion_rate + 回填存量行 + `unit_price` DECIMAL(12,4)→(18,8)。
- `purchase.service` 折算（**权威在后端**）：`resolveConversionRate`(按 product_units 查率，基本单位/缺省=1，非法单位 UNIT_INVALID) + `foldEntryItem`(quantity=entryQty×rate、unit_price=entryUnitPrice/rate 高精度、amount=entryQty×entryUnitPrice 零截断)；create/createWithinTransaction/update 三处折算落库，findById 回显 entry 三列。**约定：API 入参 quantity/unitPrice 恒为录入单位口径，entryUnit 缺省=基本单位→rate 1→完全向后兼容**。
- 收货/上架/结算**数量侧零改动**（读的仍是基本单位 quantity/unit_price）。
- 前端采购建单：明细单位下拉（有辅助单位才出现，选中商品拉 product_units）+ 数量下方「= N 基本单位」提示；详情回显「5 箱（60 件）」+「¥100/箱」（每箱价由 amount/entryQty 精确还原，因落库存的是每基本单位价）。
- **验证**：端到端10/10（5箱@100除不尽→qty60/unit_price8.33333333/amount500/★应付=500.00方案A精度；5箱@120整除→600；基本单位录入=旧行为；非法单位拒）+ 浏览器详情回显「5 验收箱（60 个）/¥100/验收箱」+ 全回归 finance103/mainline49/p0-41/p1-44/integration96/tsc0/两端lint0。

**Phase 3 · 销售录入放开**
- 销售明细同样加 entry 三列；建单 / 改单 / 占库 / 出库 / 应收数量侧零改动。
- 重点回归改单链路（`smoke:sale-adjustment`）——改单按 `quantity`（基本单位）算增减量，折算后天然正确。

**Phase 4 · 退货录入 + PDA 现场（最后、最敏感）**
- 退货单按箱录入（比照采购/销售）。
- PDA 收货 / 上架 / 拣货可按**系统给定单位**快捷录入（如"这批按箱收，1 箱记 12 件"），**单位由系统按作业指定、现场不可自选**（守"仓库端不决策"）。数量仍以基本单位落库。
- 全套 smoke 回归。

存量平滑：所有阶段的默认换算率 = 1、`entry_unit = unit`、`entry_qty = quantity`，历史单据与未配置多单位的商品语义**完全不变**。

## 11. 风险与待确认

> 这是全链路最伤筋动骨的改造，风险章从详。

1. **口径错配 = 静默算错（最高风险）**。若某处误把 `entry_qty`（箱）当基本单位喂进库存 / 结算，会静默按 12 倍 / 1/12 倍出错，界面无异常。**防线**：(a) 库存事实层根本不存 `entry_*`（第 4.3），换算率进不了引擎；(b) review 铁律"库存/账款 SQL 禁读 `entry_*`/`conversion_rate`"（第 6 节）；(c) `test:integration` + `check-consistency` 兜底。实现时**每条新 SQL 都要问一句：这里的数量是基本单位吗？**
2. **金额厘位误差（方案 A 的已知取舍）**。除不尽的换算率下，`SUM(基本单位量 × 每基本单位高精度价)` 会有亿分位残差，四舍五入到分无感，但**账账绝对到厘一致**时不成立。**待确认**：财务能否接受方案 A 的分位口径，还是必须上方案 B（按比例分摊录入金额）。建议先方案 A，留 B 为升级路径。
3. **是否允许非整数换算率**（1 托 = 12.5 件）。默认**只允许正整数**，避免"5.5 箱 = 66 件"这类既反直觉又放大浮点风险的情形。若业务确需（散装、称重预包装），再评估——但那更接近"异维度单位"，超出本设计范围。**待确认**。
4. **换算率变更的历史影响**。换算率是单据行快照、不回溯（第 5.5），但**未发货的在途订单**若中途改箱规，其快照率仍是旧值——这是正确语义（下单时怎么谈的就怎么算），但需在商品单位维护页提示"改换算率不影响已建单据"。
5. **`unit_price` 提精度的迁移风险**。`ALTER … MODIFY COLUMN` 到 `DECIMAL(18,8)` 是在线 DDL，大表需评估锁表时间；且要确认所有读 `unit_price` 的前端展示做了四舍五入到分，不要把 `8.33333333` 直接甩给用户看。参考 CLAUDE.md 第 20 节第 8 条"生产 schema 漂移史"——上线前确认生产已跑迁移、列精度真的变了。
6. **`product_items.unit` 冗余与 `product_units` 的一致性**。基本单位名同时存在两处（`product_items.unit` 和 `product_units.is_base` 行），改基本单位时必须同事务同步两者，否则展示与换算基准打架。宁可读一处（推荐以 `product_units` 为准，`product_items.unit` 仅为兼容冗余）。
7. **前端"箱数×率"只是呈现，不得成为权威**。CLAUDE.md 第 13/17 节明令前端不复制后端业务规则。若前端算的基本单位量与后端折算不一致（浮点 / 精度差），一律以后端为准；建单响应回带后端折算后的 `quantity/unitPrice/amount` 供前端校对。
8. **PDA 按箱录入的防错**（Phase 4）。现场按箱扫码收货时，"1 箱 = 12 件"的率由**系统按该商品当前配置给定**，PDA 只显示"本次收 N 箱 = M 件"确认，**不给现场改率的入口**（守"仓库端不决策"，见 MEMORY「仓库侧不能有决策权」）。若到货实物箱规与系统配置不符，走异常上报 / 人工，不在 PDA 现场改数据模型。
9. **盘点账面口径**。盘点账面实时取自 ACTIVE 容器合计（基本单位，CLAUDE.md 第 7.5 节），本设计不动；只在**展示**层可选按箱显示。实盘录入若允许按箱，需折算成基本单位再和账面比，且漂移校验仍在基本单位上做。**待确认**盘点是否需要按箱录入（现场清点常按箱，价值较高，但放到 Phase 4 之后单独评估）。
10. **`docs/` 与代码冲突以代码为准**；本文所有 `文件:行` 已按 2026-07-29 代码核实，实现时若代码已变，先订正本文再动手。
