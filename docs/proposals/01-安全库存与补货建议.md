# 设计文档 01 · 安全库存与补货建议

> 状态：**设计定稿，待实现**
> 关联维度决策：**按仓 + 通用默认**（已确认）
> 本文所有"可机械验证的声明"均对着 2026-07-29 的当前代码核实过；实现时若发现代码已变，以代码为准并回来订正本文。

---

## 1. 背景与现状问题

系统目前是纯"事后记账"：发生了什么记什么，但**不告诉运营该做什么**。补货完全靠人脑记，快卖空了系统不会提醒。

现状里唯一沾边的机制，是通知服务里一句**硬编码告警**：

```js
// backend/src/modules/notifications/notifications.service.js:13
const threshold = 10   // 所有商品，统一"少于 10 个"才告警
```

它的问题：
- **不区分商品**：螺丝钉和冰箱用同一个阈值 10。
- **不区分仓库**：主仓（备 100）和前置仓（备 10）用同一个阈值。
- **是跨仓合计判定**（用 `getProductInventoryProjectionSql()` 按 product 汇总所有仓），单仓缺货被合计数掩盖。

所以本功能不是从零新增，而是把这个拍脑袋的机制**专业化**：给每个商品（每个仓库）设真实的补货基准，在此之上算出"建议补多少"，并把 `LOW_STOCK` 告警换成真基准。落地风险因此很小。

## 2. 目标 / 非目标

**目标**
- 给库存设"该有多少"的基准：安全库存、补货点，**按仓维度**（含通用默认）。
- 系统自动算出"该补多少"：建议采购量 = 目标库存 − 可用 − 在途采购。
- 一个"补货建议"报表页 + 仪表盘小组件，列出需补货的商品。
- 把 `LOW_STOCK` 通知升级为按真实补货点判定。

**非目标（本期不做，留后续文档或 Phase 2）**
- 需求预测 / MRP（另立文档）。
- 采购提前期驱动的补货点自动推算（Phase 2）。
- 从补货建议一键生成采购单（Phase 2，价值最高但要接采购创建链路，单独评估）。

## 3. 核心设计原则（对着不变量核过）

- **只读缓存投影，绝不碰库存扣减判定。** 补货建议是展示统计场景，走 `inventoryProjection.getInventoryDisplayProjectionSql()`（读 `inventory_stock` 缓存），符合该文件头注释声明的使用边界（"仅用于 overview/dashboard/reports/finder/notifications 展示读取"）。**不得**对每个 SKU 循环调 `containerEngine.getAvailableStockForDecision()`——那是带 `FOR UPDATE` 行锁的单点权威判定，批量场景会逐行加锁 + N 次往返。
- **按仓数据权限必接。** 补货是仓库维度，列表查询的仓库列必须过 `warehouseScope.scopeFilter(req.user.warehouseIds, 'ip.warehouse_id')`，否则越权看到别仓。
- **接口挂 `inventory` 模块，不挂 `reports`。** reports 模块整体不接仓库数据权限（controller 不传 `req.user`、service 不用 `scopeFilter`），是全局管理员报表。补货必须照 `inventory.service.getOverview` 的"过滤 + scopeFilter + 分页"三段式写。

## 4. 数据模型（迁移 151）

补货基准不放商品主表（那是全局的，与"按仓"矛盾），单独建表：

```sql
CREATE TABLE `product_stock_policies` (
  `id`            BIGINT NOT NULL AUTO_INCREMENT,
  `product_id`    BIGINT NOT NULL,
  `warehouse_id`  BIGINT NOT NULL DEFAULT 0 COMMENT '0=该商品通用默认；>0=特定仓覆盖',
  `safety_stock`  DECIMAL(18,4) NOT NULL DEFAULT 0 COMMENT '安全库存下限（低于=紧急缺货风险）',
  `reorder_point` DECIMAL(18,4) NOT NULL DEFAULT 0 COMMENT '补货点：可用+在途 低于此即建议补货',
  `target_stock`  DECIMAL(18,4) NULL COMMENT '目标库存，补货补到此值；NULL 则补到补货点',
  `created_at`    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_product_wh` (`product_id`,`warehouse_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='商品补货策略（按仓，warehouse_id=0 为通用默认）';
```

**两个必须注意的坑：**

1. **通用默认用 `warehouse_id=0`，不要用 `NULL`。** MySQL 唯一索引不约束 NULL——用 NULL 时 `(商品A, NULL)` 可插入任意多行，"默认值"就不唯一。用 0（非法仓库 id）当哨兵，`UNIQUE(product_id, warehouse_id)` 才真正锁得住。
2. **本表不设 `deleted_at`。** 它是配置而非单据，软删会和唯一键打架（软删一行后再设同商品同仓即撞键）。写入走 `INSERT ... ON DUPLICATE KEY UPDATE`（upsert）；"取消某仓特殊设置"就直接 `DELETE` 那行，回落到默认。

**取值规则**：任何地方取某 `(product_id, warehouse_id)` 的基准，一律
`COALESCE(本仓策略行, warehouse_id=0 默认行, 0)`。
→ 商品表单只维护 `warehouse_id=0` 那一行就覆盖大多数场景；个别仓要差异化，再单独覆盖。

## 5. 补货公式与数据口径（已对代码核实）

```
可用量      = GREATEST(0, inventory_stock.quantity - reserved)
在途采购    = Σ(已提交PO下单量) - Σ(已上架量 putaway_qty)
建议采购量  = GREATEST(0, target_stock - 可用量 - 在途采购)
需补货判定  = (可用量 + 在途采购) < reorder_point
日均销量    = 最近 N 天真实出库量 / N     （用于 Phase 2 自动建议补货点、及页面参考展示）
```

**一个容易算错的点：可用量已扣过预占（reserved），公式里不再 `+ 已占用`。** 若基数改用 `quantity`（含预占）才需要补回预占；用"可用量"当基数时再加就是重复扣、补货量虚高。

| 口径项 | 数据源 表.列 | 现成可复用 |
|---|---|---|
| 可用量（批量展示） | `inventory_stock.quantity / .reserved`；可用 = `GREATEST(0, quantity-reserved)` | `inventoryProjection.getInventoryDisplayProjectionSql()`；列表模板 `inventory.service.getOverview` |
| 在途采购 | `purchase_orders`(status=2 已提交, warehouse_id 在**单头**) 的 `purchase_order_items.quantity` − `inbound_task_items.putaway_qty`（via `inbound_task_items.purchase_order_id`） | 收货聚合模式见 `purchase.service.js:98` |
| 日均销量 | `warehouse_tasks`(task_type='sale_out', status=7 已出库, `shipped_at`) + `warehouse_task_items.picked_qty`（实拣=实发） | 直接 GROUP BY |
| 数据权限 | `req.user.warehouseIds` | `warehouseScope.scopeFilter(ids, 'ip.warehouse_id')` |

**口径要点：**
- 在途采购减 `putaway_qty`（已上架）而非 `received_qty`（已收货未上架）——这样和"可用量=已上架容器"首尾衔接，"已收未上架"的量仍算作在途/在路上，不留空档、不漏计。
- 日均销量**必须用真实出库量**（`warehouse_tasks` 已出库任务的 `picked_qty`），**不能**用 `sale_order_items.quantity`（那是下单量，含没发的、取消的，会让补货虚高）。`task_type='sale_out'` 过滤掉采购退货出库。

**补货建议主查询骨架**（`inventory.service.js`，实现时精修表名/列名）：

```sql
SELECT p.id, p.code, p.name, p.unit, ip.warehouse_id, w.name AS warehouse_name,
       GREATEST(0, ip.quantity - ip.reserved)                    AS available,
       COALESCE(pt.in_transit, 0)                                AS in_transit,
       COALESCE(sp_wh.reorder_point, sp_def.reorder_point, 0)    AS reorder_point,
       COALESCE(sp_wh.safety_stock,  sp_def.safety_stock,  0)    AS safety_stock,
       COALESCE(sp_wh.target_stock, sp_def.target_stock,
                sp_wh.reorder_point, sp_def.reorder_point, 0)    AS target_stock
FROM (SELECT product_id, warehouse_id, quantity, reserved FROM inventory_stock) ip
JOIN product_items p        ON p.id = ip.product_id AND p.deleted_at IS NULL AND p.is_active = 1
JOIN inventory_warehouses w ON w.id = ip.warehouse_id           -- 表名以 warehouses 模块实际为准
LEFT JOIN product_stock_policies sp_wh  ON sp_wh.product_id = ip.product_id AND sp_wh.warehouse_id = ip.warehouse_id
LEFT JOIN product_stock_policies sp_def ON sp_def.product_id = ip.product_id AND sp_def.warehouse_id = 0
LEFT JOIN ( /* 在途采购: GROUP BY po.warehouse_id, poi.product_id */ ) pt
       ON pt.warehouse_id = ip.warehouse_id AND pt.product_id = ip.product_id
LEFT JOIN ( /* 最近N天出库: GROUP BY wt.warehouse_id, wti.product_id */ ) sold
       ON sold.warehouse_id = ip.warehouse_id AND sold.product_id = ip.product_id
WHERE p.deleted_at IS NULL /* + keyword / warehouse 过滤 */ ${scope.sql}
HAVING (available + in_transit) < reorder_point                 -- 只列需补货的
ORDER BY (reorder_point - available - in_transit) DESC          -- 缺口大的排前
LIMIT ? OFFSET ?
```

建议采购量在应用层或 SELECT 里算：`GREATEST(0, target_stock - available - in_transit)`。

## 11. 风险与待确认

- **表名核对**：仓库主表在 SQL 里写作 `inventory_warehouses`，实现前用 `warehouses` 模块确认真实表名。
- **`inventory_stock` 缓存漂移**：补货建议读缓存，若缓存与容器漂移会误判。本功能不写库存，不引入新漂移；但展示可加一句"数据基于库存缓存"。
- **在途采购口径边界**：只算 `status=2` 的开口采购单；草稿(1)不算、已完成(3)不算。短装结案(`close`→3)的单其未收部分**不再计入在途**（已结案），符合预期。
- **性能**：主查询有两个聚合子查询 JOIN，商品×仓库量大时关注执行计划；必要时给在途/出库子查询限定时间窗与仓库范围下推。
