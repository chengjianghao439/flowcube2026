# 设计文档 13 · 条码与序列号融合

> 状态：**设计草案，待评审**
> 决策依据：2026-08-04 与用户确认的三条取向——
> ① **唯一身份用系统自己打印的条码，不用厂家机身码**（标签会一直贴在货上，售后凭标签追溯）；
> ② **一物一码由系统自动判定**，不再靠商品级手工开关；
> ③ **`product_serials` 整套彻底废弃，功能并进容器**。
> 本文所有"可机械验证的声明"均对着 2026-08-04 的代码核实过，行号会漂，实现时以代码为准。

---

## 1. 为什么要融合

系统里现在有**两套一物一码机制在并行**：

| | 容器条码 | 序列号 |
|---|---|---|
| 载体 | `inventory_containers.barcode`（`I…`/`B…`） | `product_serials.serial_no` |
| 来源 | 系统生成（`generateContainerCode`） | 厂家机身码，PDA 逐台扫入 |
| 唯一性 | 全局唯一 | `UNIQUE(product_id, serial_no)` |
| 流水 | `inventory_logs`（带 `container_id`） | `serial_events` |
| 归属 | 自己就是容器 | `container_id` 指向容器 |

当商品"一件一容器"时（大件商品的常规收货方式，PDA 逐箱录入填 1 即可），**这两套记的是同一件事**：容器有唯一条码、有商品/仓库/库位/批次/来源单据/流水，序列号再挂一行上去，只多了一个厂家码字段。

两套并存直接产生了三块**纯负担型功能**：

1. `GET /serials/check-consistency` —— 校验"容器 `remaining_qty` == 挂在它上面的在库 SN 数"。这个校验存在的唯一理由就是两套数据可能不一致。**合并后不存在两套，校验自然消失。**
2. `GET /serials/import-candidates` + `POST /serials/import` —— 历史库存补录厂家码。**合并后系统自己的码天然存在，无需补录。**
3. `serialEngine.assertSerialCountMatchesContainer()` —— 每次容器变动后的不变量断言，同上。

外加一处已经过期的残留：`containerEngine.js:715` 的 `SERIAL_STOCKCHECK_UNSUPPORTED`（"盘点差异需逐台核对"拦截）是 v0.4.53 的产物，而序列号级盘点已在其后完整实现（`stockcheck.service.js` 的 `saveItemSerials` / `serialPlan`），这条拦截已无对应场景。

## 2. 核心模型：两类容器，各司其职

系统里的容器本来就是两种东西，融合方案必须先把它们分开——**混为一谈是上一版设计草稿犯的错**。

| | **库存容器**（`I…`，`container_type=1`） | **塑料盒**（`B…`，`container_type=2`） |
|---|---|---|
| 产生方式 | 收货时按箱生成，一次性 | 手工建盒或拆分生成，**常驻** |
| 物理对应 | 一箱/一件到货的货 | 散件库位上固定摆着的周转盒 |
| 生命周期 | 货出完即 `EMPTY`，记录留档不复用 | **货出完盒子还在，等下一批货** |
| 商品绑定 | 随货，一次性 | **一盒绑定一个商品**，扫码按绑定鉴别对错 |
| 适用商品 | 大件、按台论 | **小而多的散件**，这是散件出货的唯一方式 |
| 是否参与一物一码 | **是**（`initial_qty=1` 时） | **否**，永远是数量制 |

**塑料盒是散件库位上不可缺少的常驻容器，本方案不动它的任何机制**——不禁止复用、不禁止并货、不改绑定规则。空盒（`remaining_qty=0`）是它的正常状态，不是异常。

### 2.1 一物一码的判定

**只有库存容器可能是个体：`container_type = 1 且 initial_qty = 1`。**

两个条件缺一不可：

- **限定 `container_type=1`**——塑料盒是常驻复用的，同一个 `B000456` 今天装 3 件、出空后明天再装 5 件，这样的码不能当个体身份。而拆分生成的塑料盒 `initial_qty` 等于拆分数量，拆出 1 件时会是 1，若只看数量就会误判成个体。
- **用 `initial_qty` 而非 `remaining_qty`**——出库后 `remaining_qty` 归 0、状态变 `EMPTY(2)`，但**这条记录不删除**，它就是这件货的完整履历（哪张采购单进、放过哪个库位、哪张任务出、卖给谁）。判定必须看入库时的数量。

收货时填"每箱 1 件"，系统建的库存容器天然是个体；填"每箱 500 件"就是数量制。不需要商品级开关，不需要新编号体系。

### 2.2 唯一需要加的约束：个体不并入塑料盒

个体容器一旦被并进塑料盒，身份就丢了（盒里混着若干件，盒码只标识盒子）。所以 `splitContainer` 的并货路径要拒绝源为个体容器的情况。

实际上这条约束几乎不会被触发——个体容器数量为 1，本就无可拆分；而塑料盒服务的是"小而多的散件"，这类商品不会走一物一码。两条路天然不相交，加这个约束只是把边界钉死。

**塑料盒自身的复用机制完全不变。**

### 2.3 字段映射：容器能不能装下序列号现有的信息

| `product_serials` 字段 | 容器侧对应 | 状态 |
|---|---|---|
| `serial_no` | `barcode` | ✅ 已有 |
| `product_id` / `warehouse_id` | 同名列 | ✅ 已有 |
| `container_id` | 自己就是 | ✅ 天然 |
| `inbound_task_id` / `inbound_task_item_id` | 同名列 | ✅ 已有 |
| `purchase_order_id` | `source_type='inbound_task'` + `source_ref_id` | ✅ 间接可得 |
| `status`（1在库/2已出库/3已退货/4盘亏） | `status`（1ACTIVE/2EMPTY/3VOID/4待上架/5待质检/6拒收） | ⚠️ 语义映射见 2.4 |
| `warehouse_task_id` | `locked_by_task_id`，**出库时被 `unlockContainersByTask` 清空** | ❌ 需靠流水 |
| `sale_order_id` / `shipped_at` | 无 | ❌ 需靠流水 |
| `return_ref_type` / `return_ref_id` | 无 | ❌ 需靠流水 |

缺的三项都能从 `inventory_logs` 还原：出库时 `warehouse-tasks.ship.js:87-96` 写入 `refType='warehouse_task'`、`refId=任务ID`、`refNo=任务号`，再 JOIN `warehouse_tasks` 即可拿到销售单与客户。**追溯链完整，不需要在容器上补冗余列。**

`serial_events` 同理由 `inventory_logs` 承担——它已带 `container_id`、`ref_type/ref_id/ref_no`、`operator_id/name`、`move_type`，唯一缺的是 `from_status/to_status`，而容器状态流转本就可由 `move_type` 推出。

### 2.4 状态语义映射

个体容器直接复用容器状态机，不再有第二套：

| 原序列号状态 | 容器状态 |
|---|---|
| 1 在库 | `ACTIVE(1)`（已上架）/ `PENDING_PUTAWAY(4)`（待上架） |
| 2 已出库 | `EMPTY(2)` 且 `remaining_qty=0` |
| 3 已退货待处理 | `PENDING_QA(5)` |
| 4 盘亏丢失 | `VOID(3)` + `remark` 注明盘亏 |

原序列号状态里的"已退货"在容器侧本就有更精确的 `PENDING_QA(5)` / `REJECTED(6)` 两档，映射后表达力不降反升。

## 4. 融合后各链路的样子

### 4.1 收货

现状：非序列号商品扫商品 + 填逐箱数量；序列号商品额外弹面板逐台扫 SN。

融合后：**只有一条路径**——扫商品 + 填逐箱数量。填 1 就是一件一码，系统建 N 个 `initial_qty=1` 的容器、打 N 张标签；填 500 就是一箱一码。**扫码次数从"商品 1 次 + 逐台 N 次"降到"商品 1 次"**，标签本来就要打，等于零额外成本。

这是融合最大的效率收益：现在序列号商品收 20 台要扫 21 次，融合后扫 1 次填个数量。

### 4.2 出库

现状：扫箱码 + 若含序列号商品则弹面板逐台扫 SN 核销（`pda/ship.tsx:129`）。

融合后：拣货时扫的容器码**已经**唯一确定了每一件（个体容器一件一码），出库扫箱码即可，**逐台扫 SN 那一步整个消失**。核销就是容器扣减本身，不再有第二套核销动作。

代价要说清楚：逐台扫 SN 原本兼具"物理二次核对"作用。融合后核对点前移到拣货扫码——拣错容器当场就是拣错货，且标签贴在货上、肉眼可核，风险可控。

### 4.3 盘点（用户点名的重复功能）

现状**两套**：
- ERP 盘点：填实盘数量，账面取 ACTIVE 容器合计
- 序列号盘点：`pda/stockcheck.tsx` 逐台扫 SN，`stockcheck.service.js` 用"账面集 vs 现场集"算 missing/surplus，且序列号商品**禁止手填实盘数**

融合后**一套**：盘点一律扫容器码。
- 数量容器（`initial_qty>1`）：扫码后填该容器实盘数
- 个体容器（`initial_qty=1`）：扫到即计 1，没扫到就是盘亏，扫到账面没有的就是盘盈

两种情况共用"扫码集 vs 账面集"同一套比对逻辑，`inventory_check_item_serials` 表和 `saveItemSerials` 那条专用链路整体删除。

### 4.4 拆分

现状：序列号商品拆分须逐台扫"要拆出的具体台"（v0.4.52）。

融合后：个体容器**不存在"拆分"**（数量 1 无可拆）；数量容器拆分维持现状，拆出的部分若为 1 件即成为新的个体容器。`moveSerialsOnSplit` 整个删除。

### 4.5 改单减量归还

现状：序列号商品已拣货后减量要 PDA 逐台扫"要放回的那几台"（v0.4.54）。

融合后：扫要归还的**容器码**即可——个体容器一码一件，扫码就是指定件。`splitTaskLockedContainerForReturn` 的 `serialNos` 参数删除。

## 6. 风险与须确认事项

1. **生产是否已有序列号真实数据**——序列号是灰度功能、默认关闭，本机开发库里 1752 个商品中仅 12 个开启且全是测试商品。删表前必须确认生产为空或已归档。**这是唯一不可逆的一步。**
2. **售后追溯依赖标签不脱落**——用户已确认"标签会一直贴在货上"。若某类商品标签易损，该类商品的售后追溯能力会低于原方案（原方案靠厂家刻码）。建议对这类商品在标签工艺上加固（如覆膜、贴机身而非包装）。
3. ~~**`initial_qty` 的历史数据**~~ **已核实，基本排除**（2026-08-04 本机开发库 4151 个未删除容器）：`initial_qty` **无 NULL、无 0**，判定规则安全。分布为 `=1` 631 个（15%）、`>1` 3520 个；按前缀 `I` 3660（其中单件 586）、`B` 388（其中单件 42）、`C` 103（`CNT…` 历史前缀，单件 3）。生产库须再核一次同样的口径。
   - **注意 `B` 码里有 42 个 `initial_qty=1`**——这正是 2.1 必须同时限定 `container_type=1` 的原因：只看数量会把这 42 个拆分生成的塑料盒误判成个体。
   - 存在 103 个 `CNT…` 前缀的历史容器（`generateContainerCode` 至今仍兼容该前缀）。术语统一时这批老码需要一并纳入，不能只处理 `I`/`B`。
   - 开发库里 `initial_qty=0` 的空盒为 0 个，**这只是测试数据特征，不能推断生产**。塑料盒在生产是散件库位的常驻容器，空盒是正常状态。
4. **一箱多件商品不受影响**——本方案不强制所有商品一件一码，收货时填几就是几，小件商品照旧按箱管理。
5. **条码消耗量取决于收货方式，不因本方案上升**——一物一码商品收 20 台就建 20 个容器打 20 张标签，这是现在填"每箱 1 件"时**已经在发生**的事，本方案没有额外增加。塑料盒复用机制不变，`B` 码消耗也不变。
