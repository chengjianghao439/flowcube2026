## 1. 背景与现状

系统的出库链路目前止步于"物理出库"：拣货 → 分拣 → 复核 → 打包（出箱贴）→ 出库确认扣库存写应收。**箱子出了门，系统就不再知道它去了哪。** 没有运单号、没有和快递平台的任何对接、没有物流轨迹、没有运费核对。发货后客户问"我的货到哪了"，只能人工登快递官网查。

但基础设施并非从零——**面单打印的"壳"已经铺好，缺的是"取号闭环"**：

- **承运商主数据已存在但只是 CRUD**。`carriers` 表（`backend/src/database/021_carriers.sql`）+ 迁移 078 补的 `type` 字段（`078_formalize_runtime_additive_schema.sql:135`，express/freight/logistics/delivery），服务层 `carriers.service.js` 只有增删改查，权限码 `carrier.view/create/update/delete`（`constants/permissions.js:46-49`）。**没有任何"平台对接凭据"字段。**
- **面单打印类型在打印链里是一等公民**。面单打印机 `printers.type=2`（`033_create_printers_and_print_jobs.sql:8`，"1=标签 2=面单 3=A4"）；打印机绑定 `printer_bindings.print_type='waybill'`（`034_create_printer_bindings.sql:6`）；派发解析已识别 `waybill` 用途并给了 fallback 链（`print-dispatch.js:22,37,`『waybill:['waybill']』）；甚至逾期告警都已在统计 waybill 打印失败（`notifications.service.js:158-168`，`ref_type='waybill' OR job_type='waybill'`）。
- **但 waybill 打印任务没有"正向入队"入口**。搜 `print-jobs.label-command.js`，只有 `reprintLogisticsBarcode`（:388-410）能"重打一个已存在的 waybill job"，**没有 `enqueueWaybillLabelJob`**——因为从来没有第一次入队它的地方。这就是"有壳无闭环"最直接的证据。
- **销售单甚至已经预留了物流字段**。迁移 078 给 `sale_orders` 加了 `carrier`(承运商名)/`carrier_id`/`freight_type`(1寄付 2到付 3第三方付)/`receiver_name`/`receiver_phone`/`receiver_address`（`078:38-43`）；v0.4.37 还上了"客户常用地址簿"（`sale_customer_addresses`）。收件信息与承运商归属**已经有落点**。

**唯一确定缺失的东西**：`grep -rn "tracking_no\|运单号"` 全仓为空——**没有运单号字段、没有快递平台 API 调用、没有轨迹表**。所以本功能不是推倒重来，而是把已铺好的"面单打印壳 + 承运商主数据 + 销售单物流字段"接上"平台取号—轨迹—对账"这条闭环。落地风险集中在**外部依赖**与**幂等取号**两处（见第 11 节），代码改造面反而可控。

## 2. 目标 / 非目标

**目标**
- 每个发出的包裹拿到真实**运单号 `tracking_no`**，并把电子面单打出来（走现有 print_jobs / waybill 打印机链）。
- 对接**一类电子面单平台**（快递鸟 / 菜鸟 / 顺丰丰桥等聚合或直连），实现"下单取号"。
- 提供**物流轨迹**查询（订单 / 运单维度）。
- 提供**运费对账**：把平台回传的实际运费与承运商归集，生成对承运商的应付。
- 全程**不违反两条铁律**：取号/轨迹/对账的 HTTP 调用绝不进库存或出库事务；面单打印只走 ZPL 队列。

**非目标（本期不做，留后续）**
- 智能选快递 / 运费比价路由（谁便宜发谁）。
- 揽收预约、上门取件调度。
- 快递面单模板可视化编辑器（沿用平台返回的云面单 ZPL，本地不自绘面单版式）。
- 退货/逆向物流的自动取号（销售退货目前是客户寄回，本期只做正向出库取号）。
- 国际物流 / 报关。

## 4. 数据模型

> 迁移编号一律取"当前最大 + 1"，**不在本文写死**（硬约束）。以下按建表先后排列，编号在实现时确定。

### 4.1 承运商加"平台对接配置"（ALTER `carriers`）

```sql
ALTER TABLE `carriers`
  ADD COLUMN `platform_code`    VARCHAR(30)  DEFAULT NULL COMMENT '电子面单平台标识：kdniao/cainiao/sf/none' AFTER `type`,
  ADD COLUMN `platform_carrier` VARCHAR(30)  DEFAULT NULL COMMENT '平台侧快递公司编码，如 SF/YTO/ZTO' AFTER `platform_code`,
  ADD COLUMN `monthly_account`  VARCHAR(60)  DEFAULT NULL COMMENT '月结账号/客户编码（非密钥，可入库）' AFTER `platform_carrier`,
  ADD COLUMN `net_site_code`    VARCHAR(60)  DEFAULT NULL COMMENT '网点/收件网点编码' AFTER `monthly_account`,
  ADD COLUMN `credential_ref`   VARCHAR(60)  DEFAULT NULL COMMENT '密钥引用名（指向 env 中的凭据组，不存明文）' AFTER `net_site_code`,
  ADD COLUMN `waybill_enabled`  TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '1=已开通电子面单取号 0=仅线下' AFTER `credential_ref`;
```

**密钥绝不入库明文（硬约束）。** `carriers` 只存**非敏感**对接信息（平台标识、快递公司编码、月结账号、网点）。真正的 `app_id / app_key / app_secret` 走**环境变量**：
- 单租户、承运商数量少，首选把凭据整组放 `.env`（如 `WAYBILL_KDNIAO_APP_KEY` / `WAYBILL_KDNIAO_APP_SECRET`），`carriers.credential_ref` 只存"用哪一组"的引用名（如 `kdniao_main`），运行时由 `config/env.js` 解析映射。`.env` 已 gitleaks 扫描 + gitignore（CLAUDE.md 第 12 节）。
- 若确有"同平台多套凭据需运营在界面维护"的诉求，退而求其次用**加密列**（AES-256-GCM，主密钥在 env，密文入库，读时解密），**绝不明文**。默认走 env 方案，加密列作为 Phase 2+ 的可选增强。

### 4.2 运单主表 `logistics_waybills`（新建）

```sql
CREATE TABLE `logistics_waybills` (
  `id`               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `waybill_no`       VARCHAR(30)     NOT NULL COMMENT '内部单号 WB+序列，与快递单号解耦',
  `sale_order_id`    BIGINT UNSIGNED NOT NULL COMMENT '销售单',
  `warehouse_task_id`BIGINT UNSIGNED DEFAULT NULL COMMENT '出库任务',
  `package_id`       BIGINT UNSIGNED DEFAULT NULL COMMENT '包裹（一箱一单）',
  `carrier_id`       BIGINT UNSIGNED DEFAULT NULL,
  `platform_code`    VARCHAR(30)     DEFAULT NULL COMMENT '取号时快照的平台标识',
  `tracking_no`      VARCHAR(60)     DEFAULT NULL COMMENT '快递运单号（取号成功后回写）',
  `status`           TINYINT         NOT NULL DEFAULT 1 COMMENT '1待取号 2取号中 3已取号 4取号失败 5已作废/退单',
  `freight_type`     TINYINT         DEFAULT NULL COMMENT '快照 1寄付 2到付 3第三方付',
  `est_freight`      DECIMAL(12,4)   DEFAULT NULL COMMENT '平台预估运费',
  `receiver_name`    VARCHAR(100)    DEFAULT NULL COMMENT '收件人快照',
  `receiver_phone`   VARCHAR(50)     DEFAULT NULL,
  `receiver_address` VARCHAR(255)    DEFAULT NULL,
  `print_data_ref`   VARCHAR(60)     DEFAULT NULL COMMENT '面单打印数据类型：zpl_inline / image_url / pdf_url',
  `request_key`      VARCHAR(120)    DEFAULT NULL COMMENT '取号幂等键，防重复扣费',
  `error_message`    VARCHAR(500)    DEFAULT NULL,
  `retry_count`      TINYINT         NOT NULL DEFAULT 0,
  `last_tried_at`    DATETIME        DEFAULT NULL,
  `created_by`       BIGINT UNSIGNED DEFAULT NULL,
  `created_at`       DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`       DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_waybill_no` (`waybill_no`),
  UNIQUE KEY `uk_package` (`package_id`),      -- 一箱一单：同一包裹只允许一条运单，天然防重复取号
  KEY `idx_sale_order` (`sale_order_id`),
  KEY `idx_status` (`status`),
  KEY `idx_tracking` (`tracking_no`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='物流运单';
```

**关键点：**
- `waybill_no`（内部单号）与 `tracking_no`（快递单号）**解耦**。内部单号在写"待取号"记录时就生成，取号成功才回写 `tracking_no`；这样取号失败/重试期间也有稳定主键可引用、可打印占位。
- `UNIQUE(package_id)` 是**防重复取号的第一道物理闸门**：一箱一单，包裹已有运单就无法再插第二条，DB 层挡死"连点两次取两个号"。
- 状态机是**内联**的（像 `return_tasks`，不进 `documentStatusRules.js`），service 内用 `SELECT … FOR UPDATE` 锁行 + CAS 推进（`1待取号 → 2取号中 → 3已取号 / 4取号失败`；`4` 可重试回 `2`；作废/退单到 `5`）。

### 4.4 运费对账 `logistics_freight_bills`（新建，Phase 4）

```sql
CREATE TABLE `logistics_freight_bills` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `carrier_id`    BIGINT UNSIGNED NOT NULL,
  `waybill_id`    BIGINT UNSIGNED DEFAULT NULL,
  `tracking_no`   VARCHAR(60)     DEFAULT NULL,
  `bill_period`   VARCHAR(7)      DEFAULT NULL COMMENT '账期 YYYY-MM',
  `actual_freight`DECIMAL(12,4)   NOT NULL DEFAULT 0 COMMENT '承运商回传实际运费',
  `weight`        DECIMAL(10,3)   DEFAULT NULL,
  `reconciled`    TINYINT(1)      NOT NULL DEFAULT 0 COMMENT '0待核对 1已核对入应付',
  `source`        VARCHAR(20)     DEFAULT NULL COMMENT 'import 人工导入 / api 平台回传',
  `created_at`    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_bill` (`carrier_id`,`tracking_no`),
  KEY `idx_period` (`carrier_id`,`bill_period`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='运费对账明细';
```

**运费应付落点**：只有 `freight_type=1 寄付`（我方付）才产生对承运商的应付；`2 到付`（收件人付）/`3 第三方付`不产生。按 `carrier_id + bill_period` 汇总 `actual_freight`，生成一条对承运商的 `payment_records(type=1, party_name=承运商名)`。注意 `payment_records` 有 `UNIQUE(type, order_id)`（`091`）——运费应付没有采购/销售 `order_id`，需以"承运商月账"为单据主体（可用一张 `logistics_freight_settlements` 汇总单头承接 `order_id`，或评审后决定是否放宽该唯一键的语义。**不要直接把多条运费塞进同一个 order_id 冲突。**）。运费应付同样要接 `settlement_type` 快照与 `confirm_status` 财务确认闸门，不走裸 INSERT。

## 5. 核心流程（取号异步，绝不进事务）

### 5.1 为什么取号必须异步

"下单取号"是一次**对快递平台的 HTTP 调用**。CLAUDE.md 第 11 节铁律：**事务内禁止外部 I/O**。如果把取号塞进打包完成或出库确认的事务里：
- HTTP 慢/超时 → 持有库存行锁的事务被 HTTP 拖住 → 并发出库全线阻塞（"系统卡住"）。
- HTTP 失败回滚 → 连累已经算好的库存扣减 / 应收，本来该成功的出库被外部快递故障拖垮。

正确模型完全照搬现有**打印解耦**（第 7.6 节）：业务动作只"入队一条 DB 记录"，真正的外部交互由**进程外/进程内的异步 worker** 完成。取号就是"打印"在快递场景的同构翻版。

### 5.2 取号时序（推荐：打包完成触发）

```
[打包完成，事务内] packages.finishPackage(packageId)
  → 完成箱（status=2）+ enqueuePackageLabelJob（箱贴，现有逻辑）
  → 若该承运商 waybill_enabled=1：INSERT logistics_waybills(status=1 待取号, waybill_no, package_id, 收件快照, request_key)
     ↑ 只是写一条 DB 记录，零 HTTP，事务照常提交
  --- 事务结束 ---

[异步 worker，事务外] scheduler 每 N 秒扫 status=1/4(可重试) 的运单
  → CAS 1/4 → 2 取号中（抢占，避免多 worker 重复取号）
  → HTTP 调平台"下单取号"（幂等：以 waybill_no 作平台 orderCode，平台按 orderCode 幂等返回同一单号）
  → 成功：UPDATE tracking_no + status=3 已取号 + est_freight + print_data_ref
          → 若返回可直接打印的 ZPL：enqueueWaybillLabelJob(面单 ZPL) 入 print_jobs
          → 若返回图片/PDF：见 5.4 例外方案
  → 失败：status=4 取号失败 + error_message + retry_count++，由 worker 退避重试；超阈值告警（复用 notifications waybill 失败告警口径）
```

**为什么选"打包完成"而非"出库确认"**：打包完成时箱数、箱内容、重量（可由 package 明细估算）、收件信息都已定，是取号信息最齐全的最早时机；且与现有 `enqueuePackageLabelJob` 是同一时序点，PDA 打包页天然能顺带展示"面单打印中"。**出库确认（`warehouse-tasks.ship.js` 的 `completeShip`）保持纯粹**——只扣库存/写应收，不碰 HTTP。若评审倾向"出库才取号"，则把"写待取号记录"挪到 ship 事务内即可，worker 逻辑不变。

### 5.3 面单打印（只走 ZPL 队列）

取号成功后，**面单打印复用现有 print_jobs 链**：新增 `enqueueWaybillLabelJob({ conn?, waybillId, warehouseId, content(ZPL), createdBy, jobUniqueKey })`，落 `job_type='waybill' / ref_type='waybill'`，`content_type='zpl'`。派发链、fallback、幂等唯一键、桌面客户端拉取全部现成，无需新造。补打走现成 `reprintLogisticsBarcode`（`label-command.js:388`）。

**注意**：面单打印的 ZPL **不经本地模板**。ZPL 标签模板体系是 type 5–9（`labelZplTemplate.js:17`），面单模板 type=2 是老的 A4/HTML 单据模板、**不产 ZPL**。电子面单的版式由**快递平台**决定（含快递 logo、大头笔、条码），平台"云打印"模式直接返回可打印的 ZPL，我方原样入队即可，**不要在本地自绘面单版式**。

### 5.4 平台只返回图片/PDF 的例外方案

部分平台/部分快递只提供面单**图片（PNG/Base64）或 PDF**，而队列**只接受 ZPL**（`print-jobs.command.js:69`，非 zpl 一律 `PRINT_CONTENT_TYPE_UNSUPPORTED`）。三条处置路径，按优先级：
1. **优先选支持 ZPL 云打印的平台/快递**（快递鸟、菜鸟、丰桥主流快递都支持热敏 ZPL 输出），从源头规避。
2. 图片/PDF 面单**不进 ZPL 队列**，改由**桌面端浏览器打印/系统打印**（与单据打印同路径，见 CLAUDE.md"单据打印走浏览器打印或导出"），`logistics_waybills.print_data_ref` 标记为 `image_url`/`pdf_url`，前端提供"打印面单"按钮触发本地打印。
3. **不得**为了塞进队列而把图片伪装成 zpl 或放开 content_type 校验——那会破坏"队列只 ZPL"的全局不变量。

### 5.5 轨迹拉取（Phase 3）

第二个异步 worker（`scheduler.js` 新增）按节流策略轮询"已取号且未终结"的运单，HTTP 拉平台轨迹，写 `logistics_tracking_events`（`uk_event` 去重）。到达"已签收"等终态后停止轮询该单。**同样在事务外做 HTTP**，写库是短事务批量 upsert。若平台支持轨迹**推送回调**，则加一个公开度受控的回调接口（带签名校验，参考桌面 `ack_token` 的校验思路），优于轮询。

## 9. 分阶段落地（每阶段独立可用、可验证）

**Phase 1 · 手工录运单号（先把数据结构和展示跑通，零外部依赖）**
1. 迁移：`carriers` 平台字段 + `logistics_waybills` 建表 + 权限 seed。
2. `packages.finishPackage` 写"待取号"记录（此阶段状态可直接停在"待录号"）。
3. 运单列表页 + 销售单物流页签 + **手工填写 `tracking_no`**（承运商还没对接时，运营手抄快递单号也能闭环）。
4. 面单此阶段走**现有物流条码重打**或不打，先不接平台。

**Phase 2 · 平台取号（接第一个适配器 + 异步 worker + 面单 ZPL 打印）**
- `config/env` 凭据、`carrier-adapters/kdniao.js`（或选定平台）、取号 worker、`enqueueWaybillLabelJob`。
- 幂等取号（`uk_package` + `request_key` + 平台 orderCode 幂等）**必须在本阶段落死**。

**Phase 3 · 物流轨迹**
- 轨迹拉取 worker + `logistics_tracking_events` + 前端时间线 + 签收终态停轮询。

**Phase 4 · 运费对账**
- `logistics_freight_bills` 导入/回传 + 按承运商月账汇总 + 生成 `payment_records` 应付（接 `settlement_type`/`confirm_status`）。

## 11. 风险与待确认

1. **外部依赖是最大不确定性**。快递平台 API 有配额、限流、sandbox 与生产差异、偶发抖动。所有取号/轨迹调用**必须**：事务外、超时保护、失败可重试、失败不影响已完成的出库与应收。worker 要有退避与熔断，避免平台故障时疯狂重试打爆配额。
2. **幂等取号 = 防重复扣费（最高优先级）**。每次取号可能消耗快递面单额度/预付费。三道闸门缺一不可：① `logistics_waybills.uk_package` 物理唯一；② 取号动作接 `X-Request-Key` / `beginOperationRequest`；③ 传给平台的 `orderCode` 用稳定的 `waybill_no`，让平台侧也按 orderCode 幂等返回同一单号。worker 抢占用 CAS（`1/4 → 2`）防多实例并发取号。
3. **密钥管理**。凭据走 env（`credential_ref` 映射），`carriers` 只存非敏感项，前端永不出现密钥。若上加密列方案，主密钥仍在 env、绝不入库/入日志/入前端。
4. **面单格式与"只 ZPL"约束的张力**。优先选支持 ZPL 云打印的平台；只出图片/PDF 的快递走浏览器打印例外（5.4），**绝不放开 content_type 校验**。
5. **一箱一单 vs 一单一箱的边界**。本文取"一箱一运单"（`uk_package`）。若出现"整单一个大件多箱走一个母运单 + 子单"的诉求（子母件），需扩展运单表支持父子关系，评审时确认业务是否需要。
6. **运费应付与 `payment_records UNIQUE(type,order_id)` 的冲突**。运费没有采购/销售 order_id，需以"承运商月结汇总单"为账款主体承接 order_id，或评审后决定唯一键语义。**不要把多条运费硬塞同一 order_id。**
7. **`freight_type` 决定是否产生应付**。只有 `1 寄付` 计我方应付；`2 到付`/`3 第三方付`不计。对账汇总务必按此过滤，否则虚增应付。
8. **取号时机若改到出库确认**，`warehouse-tasks.ship.js` 的出库事务里也只能"写待取号记录"，**HTTP 仍在事务外 worker**——这条边界不因时机变动而松动。
9. **轨迹推送回调（若启用）**需签名校验 + 幂等（`uk_event`），且是少数需要放宽鉴权的公开接口，参照 CLAUDE.md 对公开接口的严格约束设计，别成为注入口。
10. **PDA 侧不新增决策权**：PDA 打包只是触发"写待取号记录"，选哪家快递、能否取号由系统/后端决定，**仓库操作员不做承运商选择判断**（CLAUDE.md 仓库端只执行不决策）。
