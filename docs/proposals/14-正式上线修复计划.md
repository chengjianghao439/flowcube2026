# 14-正式上线修复计划（上线前 P0/P1/P2 路线图）

> 文档性质：修复计划（非方案文档）。依据 2026-08-09 对 flowcube 的 7 路深度审计（安全 / 代码质量 / 测试 / 前端 / 数据库 / 运维 / 业务流程）编写。所有结论均经源码交叉验证。
>
> **关键前提：系统尚未正式投入使用。** 本机为开发版，GitHub 与服务器上有正式版但还没有真实业务数据开始运行。这意味着：
> - 数据库里没有必须保全的历史数据 → 结构类修复（补索引、改迁移、清数据）成本极低，无需写数据迁移预案；
> - 没有正在进行的业务流 → 行为变更（加审批、改权限模型、加校验）不会打断真实作业；
> - 没有对外承诺的 SLA → 发布门禁、监控、备份的修复可以在上线前从容完成。
>
> **这是修复成本最低的窗口期。** 优先级排序以此为前提：**上线后极难修、且上线后必然出事的项（数据权限、测试盲区、发布门禁、日志无界增长）优先；纯新增能力（审批流、离线队列）排后。**

---

## 1. 审计结论摘要

系统内核质量**明显高于同规模团队平均水平**，距"可正式商用"差的不是地基，而是三类能力：

| 短板 | 一句话概括 | 后果 |
|------|-----------|------|
| 数据权限漏（H2/H3） | 销售写接口 + 导出/报表/看板/通知完全无视仓库 scope | 受限仓用户可读/改全公司数据 |
| 测试覆盖极不均 | 51 模块仅约 7 个有直接测试；前端/桌面零测试；v0.4.60/0.4.61 两大新功能无测试 | 上线后回归靠人工，静默出错无保护 |
| 发布运维断点 | CI 跳过 release-gate；备份从未演练；4 张日志表无界增长；oplogs 清理未自动执行 | 坏版本可上生产、数据/日志无法溯源 |

另有：销售模块水平越权（H2 是唯一"已能在测试环境复现"的高危漏洞）、PDA 设备密钥明文入日志（H1，一行修复）、打包接口可伪造 PDA 头（H4）、打包/拆箱等核心路径无测试。

**强项（勿因修复破坏）**：容器级库存引擎 + 14 条不变量、并发控制（FOR UPDATE + CAS + 幂等键）、金额全 DECIMAL、参数化 SQL 彻底、审计追溯（opLogger + 业务事件表）、前端 strict 全开 + Keep-Alive 架构。

## 2. 修复原则（贯穿全部工作）

1. **上线前能改的都改**。一切"上线后要写数据迁移"的项（索引、约束、权限、状态机）在无数据期直接改迁移文件或新增迁移，不必向后兼容。
2. **安全优先**。数据权限（H2/H3/H4）是唯一"真实漏洞"，先修；且都在后端 service 层收敛，改动面可控。
3. **测试跟上**。每修一个高危项，就补一条对应测试（参照 `tests/` 现有 `smokeTestKit` 模式），不让修复本身成为新的无保护代码。
4. **不追求一步到位**。P1/P2 是增量，P0 是门槛；先让"核心数据链路 + 权限 + 测试 + 发布"闭环，再谈完善。
5. **沿用现有模式**，不另起炉灶：scope 用 `warehouseScope.js` 的 `assertInScope/scopeFilter`；敏感字段清理补进 `opLogger.js` 的 `SENSITIVE_FIELDS`；清理任务挂进 `scheduler.js` 的 `startCleanupSweeper`。

## 3. P0 — 上线阻断级（不做不能上线）

### 3.1 数据权限补全（最高优先，安全高危 H2 + H3）

**问题**：销售模块 11 个接口只有 `list` 传了 `scopeWarehouseIds`；`export/reports/dashboard/notifications` 四个模块完全不接仓库权限。配置了 `user_warehouse_scope` 的用户可越权。

**修复范围**（全部在 service 层，参照 purchase 模块的正确模式）：
- `backend/src/modules/sale/sale.service.js`：`findById / update / requestAdjustment / ship / cancel / deleteOrder / reserve / release` 内加 `assertInScope(scopeWarehouseIds, warehouse_id, '销售单')`；`sale.controller.js` 各接口补传 `req.user.warehouseIds`。
- `export.service.js`：各 `get*ExportPayload` 加 `scopeFilter`（按导出的单据类型带 warehouse_id）。
- `reports.controller.js` / `reports.service.js`：各报表函数加 `scopeWarehouseIds` 透传 + `scopeFilter`（报表聚合本就带 warehouse 维度，改动小）。
- `dashboard.service.js`、`notifications.service.js`：按当前用户 scope 过滤。

**验证**：写 `tests/warehouse-scope.smoke.test.js` 的增量用例——受限仓用户调用 sale 详情/导出/报表应 403 或只见本仓数据（参照现有该测试的断言模式）。

### 3.2 opLogger 敏感字段补全（安全高危 H1，一行修复）

**问题**：`opLogger.js` 的 `SENSITIVE_FIELDS` 是精确键匹配，`device_secret`/`session_token`（snake_case）漏网，PDA 设备密钥明文落库。

**修复**：`backend/src/middleware/opLogger.js` 的 `SENSITIVE_FIELDS` 集合追加 `'device_secret', 'session_token', 'deviceSecret', 'sessionToken', 'idempotency-key'`；或对键名做 `snake_case → camelCase` 归一化后匹配（更稳）。

**验证**：`tests/` 补一条纯函数单测：`sanitizeBody({device_secret:'x', session_token:'y', password:'z'})` 应全部输出 `***`。

### 3.3 packages 写接口补 `pdaSessionRequired`（安全高危 H4）

**问题**：`packages.routes.js` 的 create/add-item/remove-item/void/finish 只挂可伪造的 `pdaOnly` 头，未挂 `pdaSessionRequired`（对比 warehouse-tasks/inbound-tasks/return-tasks 都是双闸）。

**修复**：`backend/src/modules/packages/packages.routes.js` 5 处写接口补挂 `pdaSessionRequired()`；service 内补 `assertInScope`。

**验证**：扩展 `tests/pda-device-session.smoke.test.js`——无 `X-PDA-Session` 调 packages 写接口应 403。

### 3.4 用户权限提权路径（安全中危 M1）

**问题**：有 `user.update` 权限者可把任意账号 `roleId` 改为 1 → 变超管。

**修复**：`users.service.update` 禁止把 `roleId` 设为 1（除非调用方是超管）；`users.routes.js` 的 schema 对 roleId=1 拦截；seed 迁移明确只有受信角色可被授予 `user.*` 权限。

### 3.5 会计结转/期间锁定 + PDA 扫码盘点补回归测试

**问题**：v0.4.61 的 `closePeriod/reopenPeriod/generateClosingVouchers` 与 v0.4.60 的 `POST /stockcheck/:id/items/:itemId/scan` 均零测试——恰恰是"静默出错"风险最高的资金/库存类新功能。

**修复**：参照 `tests/accounting.smoke.test.js`（事务+rollback 模式）补：
- 结转：损益结转凭证借贷平衡、结账后写凭证被拒、反结账恢复、多级科目试算平衡上卷、幂等（重复结账不重复生成）。
- 盘点：个体容器扫到计 1、数量容器预填账面、未扫即盘亏扣减、无 PDA 会话被拒。

### 3.6 CI 发布链去掉 `SKIP_RELEASE_GATE=1`

**问题**：`deploy-browser.yml:101` push main 自动部署时显式跳过 release-gate（页面烟雾+对账回跳），坏版本可直接上生产。

**修复**：将 `SMOKE_USERNAME/SMOKE_PASSWORD` 作为 GitHub secrets 注入 CI，去掉 `SKIP_RELEASE_GATE=1`；或在 test.yml 增加 Playwright job 覆盖 `smoke-pages` + `smoke-reconciliation-jumps`，release-gate 退化为服务器终检。

### 3.7 日志类数据挂自动清理（数据库无界增长）

**问题**：`scan_logs/inventory_logs/print_jobs/pda_error_logs` 无任何自动清理；`operation_logs` 的 `clearOld` 只手动触发。

**修复**：
- `scheduler.js` 增加 `startCleanupSweeper` 调 `oplogs.service.clearOld()`（每 6 小时，TTL 30 天）。
- `print-jobs.dispatch.js` 的 sweeper 增加"完成/失败超 N 天物理删除"（保留幂等窗口后清理）。
- `scan_logs/inventory_logs` 加按月份分区或 TTL 清理任务。

### 3.8 001 迁移移除硬编码密码哈希（数据库安全）

**问题**：`001_create_sys_users.sql` 硬编码一个 bcrypt 哈希（虽默认禁用，但违反"口令不入库"原则，且无法确认对应明文）。

**修复**：改为不 INSERT admin（或只插 username、password 留 `'!'` 占位），由 `bootstrap-admin.js` 完整建号。

## 4. P1 — 上线 3 个月内（重要）

### 4.1 前端 pageSize=99999 业务大表改真分页

**问题**：33 处全量拉取，其中销售/采购/退货/调拨/收货/付款/费用/操作日志/库存流水 9 类业务大表是伪分页（后端 `LIMIT ? OFFSET ?` 已支持，前端不用）。oplogs 是全库最大表之一。

**修复**：参照 `pages/accounting/vouchers/index.tsx`（PAGE_SIZE=20 真分页）迁移这 9 类列表页；基础资料页与 Finder 全量保留并加注释说明"为何全量"。同步给后端 pageSize 加全局 clamp（`Math.min(pageSize, 500)`）。

### 4.2 双 toast 治理（前端体验）

**问题**：61 处 mutation `onError` 与全局拦截器重复弹错误 toast。

**修复**：页面 `onError` 要么传 `skipGlobalError` 只做状态清理，要么删掉 toast 交给全局拦截器。

### 4.3 前端测试从零搭起

**问题**：369 个前端文件零测试（CI 只跑 eslint+tsc）。

**修复**：引入 vitest + @testing-library/react，先覆盖高价值纯逻辑：`lib/labelGeometry.ts`（几何镜像）、金额/辅助单位换算工具、单据状态推导、权限码渲染守卫。前端测试脚本挂进 test.yml。

### 4.4 数据库补索引（无数据期成本最低）

| 表 | 索引 | 依据 |
|----|------|------|
| `printers` | `idx_printers_client_id (client_id)` | 桌面每 60s 轮询 `claim-client`，全系统最高频查询之一，目前全表扫描 |
| `inventory_logs` | `(product_id, warehouse_id, type, created_at)` | 流水查询组合过滤；另补 `container_id`（容器追溯路径） |
| `warehouse_tasks` | `(status, created_at)` 或 `(warehouse_id, status, created_at)` | 列表按 `priority, created_at` 排序，无排序索引 |
| `sale_order_items` | `(order_id, product_id, warehouse_id)` | 分仓发货热路径，现仅 `idx_order_id` 前缀 |

**验证**：跑 `tests/` 确认无回归；迁移用 information_schema 幂等护栏（参照 068+ 模板）。

### 4.5 备份恢复演练 + 异地副本（运维）

**问题**：备份与数据同机、从未演练恢复、`docker-compose.backup.yml` 缺失。

**修复**：
- 补 `scripts/restore-check.sh`：取最新 `.sql.gz` 在临时 MySQL 导入 + 校验行数/表数（作为"备份可用性"证明，建议每季度演练）。
- 补 `docker-compose.backup.yml` + rclone/scp 到第二台机器或对象存储。
- cron 安装脚本化（`scripts/install-cron.sh` 幂等）+ daily-report 校验"今日是否有新备份"，无则告警。

### 4.6 报表数值正确性测试 + 并发压力测试重写

**问题**：reports 只测"结构存在"；`concurrency.stress.test.js` 过期 4 版本未挂 CI。

**修复**：给 `reports.query/metrics/trends` 补数值断言（与底层表核对）；按新状态机重写并发压力测试并挂 CI（独立 job、限定集成测试库）。

### 4.7 采购审批环节（业务流程 P0）

**问题**：采购单"提交即采购"，金额/价格无人把关。

**修复**：采购单加"提交→审批→确认"，金额超阈值（可配 `sys_settings`）必须审批；审批人≠制单人（复用 expenseClaim 的骨架）。属新功能，排在 P1 是因为它改动销售/采购状态机，且上线前没有真实审批数据可验证流程。

### 4.8 出库环节信用复查（业务流程 P0）

**问题**：信用只在占库拦截，出库时不复查。

**修复**：`warehouse-tasks.ship.js` 在出库前复查该客户已用额度 + 本单额度，超限且无 override 则拦截。

### 4.9 死代码清理（代码质量）

- 删除 35 个前端零引用的 API 函数（price-lists 全套、getStockPoliciesApi、getTaskStatsApi 等）。
- 删除 3 个真死组件：`PrintOrderDialog`、`SaleOrderPrintTemplate`、`GlobalDesktopUpdateDialog`。
- 统一 32 个 routes 文件的内联 `vBody` 到 `utils/route.js` 的 `validateBody`（消除 30+ 份重复 + 统一错误通道）。
- `printers.controller.js` 的 5 个直写 SQL 函数下沉 service 并修 N+1。

### 4.10 迁移编号校验（数据库技术债）

**问题**：057/064/089 重复编号、缺 008/009/040、`052` 要求人工跳过。

**修复**：`migrate.js` 加"编号连续性 + 唯一性"校验（遇重复/缺号 console.warn 不中断）；`052` 改 information_schema 护栏；补 `--check-gaps` 选项进 CI。

## 6. 修复顺序建议（分阶段执行）

```
阶段一（立即可做，1-2 天）：
  3.2 opLogger 敏感字段（一行）→ 3.3 packages 补闸 → 3.4 禁 roleId=1 → 3.8 迁移去哈希
  → 各补一条测试

阶段二（安全补全，3-5 天）：
  3.1 数据权限（sale + export + reports + dashboard + notifications）
  → warehouse-scope 测试扩展

阶段三（测试加固，1 周）：
  3.5 结转/盘点回归测试 → 4.3 前端测试起步 → 4.6 报表数值 + 并发压力重写

阶段四（发布与运维闭环，3-5 天）：
  3.6 CI 去 SKIP_RELEASE_GATE → 3.7 日志自动清理 → 4.5 备份演练 + 异地副本

阶段五（性能与技术债，1 周）：
  4.1 前端真分页 → 4.4 补索引 → 4.9 死代码清理

阶段六（业务闭环，上线后 3 个月）：
  4.7 采购审批 → 4.8 出库信用复查 → 5. P2 增量项
```

## 8. 风险与注意

1. **本工作区有未提交改动**（本次会话删了报表版采购计划/来料质检合格率/审批与提醒、合并库位五段编码、润色文案，共 24 个文件变更），修复计划落地前建议先 commit 或 stash，避免与后续改动混淆。
2. **`avg_cost` 退货/撤回不反冲是刻意简化**（CLAUDE.md 第 20 节），修复时不"顺手修正"，成本失真靠报表口径兜底。
3. **`pdaOnly` 头可伪造**，只能当 UI 提示，不能当安全边界；统一以 `pdaSessionRequired` 为准。
4. **生产库 schema 漂移史**：改动依赖新列时先确认生产已跑过对应迁移（未上线前提下此风险低，但保留记录）。
5. **测试隔离**：现有 smoke 测试共享 SMOKE-P001 商品有累积污染，新增测试尽量用独立随机商品（参照 integration 的 `INTEG-${randomRef()}` 模式）。
