## 1. 背景与现状

系统目前**对客户完全没有授信/赊账约束**：无论一个客户欠了多少未清应收，只要有库存就能继续下单、占库、发货。缺的是一道"这个客户还能赊多少"的闸门。

现状里已经具备的、可直接复用的三块地基：

- **客户主数据表是 `sale_customers`**（`backend/src/modules/customers/customers.service.js:5` `const TABLE = 'sale_customers'`；建表见 `backend/src/database/007_create_customers_purchase_sale_stockcheck.sql`）。当前列：`code / name / contact / phone / address / settlement_type / payment_terms_days / remark / deleted_at`。**grep `credit_limit` 全仓为空——授信额度这个字段还不存在。**
- **客户已有结算方式**：`settlement_type`（迁移 135，TINYINT 默认 2）与 `payment_terms_days`（迁移 120）。枚举与到期日规则集中在 `backend/src/constants/settlementType.js`：`1 现结 / 2 月结`，`buildDueDateSql()` 统一算到期日，`normalizeSettlementType()` 归一旧值。
- **应收落在 `payment_records`**（建表 `backend/src/database/054_create_payments_and_inventory_log_compat.sql:3`）：
  - `type`（1 应付 / 2 应收）、`order_id`、`order_no`、`party_name`、`total_amount`、`paid_amount`、`balance`、`status`（1 未付 / 2 部分付 / 3 已付清）、`confirm_status`（财务确认闸门）、`settlement_type`（**快照**，迁移 136）、`due_date`。
  - `UNIQUE(type, order_id)` 做幂等（`recomputeSaleReceivable` 靠它 upsert）。
  - 索引 `idx_payment_records_type_status(type, status)`。
  - **注意：`payment_records` 没有 `customer_id`/`party_id` 列，只有 `party_name` 文本快照**。这是本功能"按客户聚合已用授信"的第一个坑，见第 5 节。

应收是怎么产生的（决定"已用授信"口径的关键）：`recomputeSaleReceivable`（`backend/src/modules/sale/sale.service.js:202-253`）在**每个仓库任务出库完成时**被调用，按 `SUM(shipped_qty * unit_price)` 全量重算、扣掉已入库的销售退货金额，然后 `INSERT ... ON DUPLICATE KEY UPDATE` 到 `payment_records`。也就是说：

> 应收记录**要到发货（出库完成）才存在**；一张"已占库但还没发货"的订单，此刻在 `payment_records` 里没有任何记录。

这条事实直接决定了"已用授信"不能只看 `payment_records`，还要把"已承诺但未转应收的在途订单"算进去（第 5 节）。

## 2. 目标 / 非目标

**目标**
- 给客户主数据加**授信额度** `credit_limit`（每客户一个额度；NULL = 不启用信控）。
- 定义**已用授信**口径：未清应收 + 在途订单敞口，且与账款页口径一致。
- 在**销售占库**环节做 `已用 + 本单 ≤ 额度` 的校验，超限**硬阻断**；有授权权限者可**一次性放行**（带留痕）。
- 并发安全：同一客户两单并发占库，额度只够一单时**必须恰好放行一单**，杜绝"两单都读到旧已用值、双双通过"。
- 前端：客户表单额度字段、占库超限提示 + 放行入口、客户用信展示、授信预警看板小组件。

**非目标（本期不做，留后续 Phase 或另立文档）**
- 完整的"超额放行审批单"工作流（Phase 2，借鉴 `expenseClaim`）。
- 授信额度的自动评级/动态调额（按历史回款表现算额度）。
- 信用**冻结**（拉黑客户、到期不还自动停止赊销）与**临时额度**（Phase 3）。
- 采购侧供应商授信（本文只做客户端应收方向）。

## 4. 数据模型

### 4.1 `sale_customers` 加授信额度列（新迁移，编号取当前最大 +1）

```sql
ALTER TABLE `sale_customers`
  ADD COLUMN `credit_limit` DECIMAL(14,4) NULL DEFAULT NULL
    COMMENT '授信额度：NULL=不启用信控（不校验）；>=0=启用，0 表示现款现货（任何赊欠都拦）'
  AFTER `payment_terms_days`;
```

**为什么用 `NULL` 而不是 `0` 当默认值**（与文档 01 的哨兵取舍正相反，要区分开）：
- 这里 `NULL` 和 `0` 是**两种不同的业务语义**，都要能表达：`NULL` = "这个客户不做信控，随便赊"（存量客户默认不受影响，落地零风险）；`0` = "这个客户不许赊账，有任何未清应收/在途就拦"。
- 因为 `credit_limit` 是**普通列不是唯一键**，不存在文档 01 里"NULL 不被唯一索引约束"的坑，可以放心用 NULL 表达"未启用"。
- 存量客户 `ALTER` 后全为 `NULL` → **默认不启用信控，上线不改变任何现有行为**，信控是"逐客户显式开启"的增量能力。

### 4.2 授信调整流水表（Phase 1 建表、Phase 1/2 写入，新迁移）

额度是敏感字段（直接决定能赊多少钱），改动必须留痕：

```sql
CREATE TABLE `sale_customer_credit_logs` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `customer_id`   BIGINT UNSIGNED NOT NULL,
  `old_limit`     DECIMAL(14,4) NULL COMMENT '变更前额度（NULL=此前未启用）',
  `new_limit`     DECIMAL(14,4) NULL COMMENT '变更后额度（NULL=关闭信控）',
  `reason`        VARCHAR(255) NULL COMMENT '调整理由',
  `operator_id`   BIGINT UNSIGNED NULL,
  `operator_name` VARCHAR(100) NULL,
  `created_at`    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_credit_logs_customer` (`customer_id`, `id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='客户授信额度调整流水（审计）';
```

> 本表是流水/审计，只增不改，不设 `deleted_at`。客户 `update` 里检测到 `credit_limit` 变化时写一条。

### 4.3 一次性放行记录（Phase 1 用事件表，Phase 2 升级为独立单）

Phase 1 的"超额放行"不建新表，直接**写进销售单事件流** `sale_order_events`（`appendSaleEvent`，`sale.service.js:115-129`），`event_type='credit_override'`，`payload_json` 记录 {额度, 已用, 本单, 超出额, 放行人}。理由：放行是"就这一单、就这一次"的动作，绑在订单事件上足够追溯，不必先上一张表。Phase 2 若要"申请—审批"两步，再建 `sale_credit_overrides` 单据表并套 `expenseClaim` 式状态机。

## 5. 核心校验流程（本文重点）

### 5.1 在哪个环节卡额度——选**占库（`reserve`）**

三个候选环节，逐个对代码分析：

| 环节 | 代码位置 | 语义 | 是否适合卡额度 |
|---|---|---|---|
| 下单（`create`） | `sale.service.js:586` | 仅生成草稿，未占用任何资源 | ✗ 太早。草稿可反复改、可能永远不发，此时拦截干扰正常报价/建单 |
| **占库（`reserveStock`）** | `sale.service.js:930-989` | **把库存 `reserved` 锁给这个客户**，是"我承诺给你留货"的第一个实质承诺点 | ✓ **推荐**。承诺资源 = 承诺信用敞口，语义最贴合；且此处已在事务内、已锁单头，插校验成本低 |
| 发起出库（`ship`） | `sale.service.js:991-1051` | 建仓库任务、进入拣货 | ✗ 太晚。货都占了、马上要发，此时才拦，占用的库存已经把别的客户挡在外面了；且分批发货会多次经过此处，语义混乱 |

**结论：在 `reserveStock` 里卡。** 占库 = 对客户的第一次实质承诺，也是"把货从可用池里划走"的时刻，正是应该问"这个客户的信用还够不够"的点。下单阶段可选做**软提示**（不阻断，仅展示，见 5.5），出库阶段不再重复卡。

### 5.2 "已用授信"口径

```
已用授信(customer) = 未清应收余额合计  +  在途订单敞口
```

**(A) 未清应收余额合计**——`payment_records` 里该客户 type=2、未付清的 `balance` 之和：

```sql
SELECT COALESCE(SUM(pr.balance), 0) AS used_receivable
FROM payment_records pr
JOIN sale_orders so ON so.id = pr.order_id
WHERE pr.type = 2
  AND pr.status IN (1, 2)          -- 1未付 2部分付；3已付清不算
  AND so.customer_id = ?
```

口径要点：
- **必须经 `order_id → sale_orders.customer_id` 归户**，不能按 `party_name` 文本匹配（改名即断），因为 `payment_records` 没有 `customer_id` 列（第 1 节）。应收全部由销售单产生，`order_id` 一定指向 `sale_orders`，这条 JOIN 是可靠的。
- **用 `balance`（未付余额）而非 `total_amount`**：已收的钱要释放对应额度。`balance` 由 `recomputeSaleReceivable` 维护（`= GREATEST(0, total_amount - paid_amount)`，`sale.service.js:248`）。
- **不看 `confirm_status`**：财务确不确认不改变"客户欠你这笔钱"的事实，未确认的应收同样占用授信。
- **与账款页同源**：都读 `payment_records` 的 `balance/status`，口径天然一致（第 10 节验证清单里要断言这一点）。退货冲减已由 `recomputeSaleReceivable` 在 `balance` 里体现，无需在此另算。

**(B) 在途订单敞口**——已承诺但还没转成应收的订单金额。因为应收要到发货才生成（第 1 节），"已占库(2)"和"拣货中(3)未发货部分"是应收看不到的敞口：

```sql
SELECT COALESCE(SUM(GREATEST(0, so.total_amount - COALESCE(pr.total_amount, 0))), 0) AS used_open
FROM sale_orders so
LEFT JOIN payment_records pr ON pr.type = 2 AND pr.order_id = so.id
WHERE so.customer_id = ?
  AND so.status IN (2, 3)          -- 2已占库 3拣货中（履约中）
  AND so.deleted_at IS NULL
```

口径要点（**防双算**是关键）：
- 每张在途订单只算 `订单总额 − 已生成应收总额` 的差额：已发货部分已进 (A) 的应收，这里减掉，剩下的才是"还没发、纯敞口"的部分。
- 已占库(2)订单通常还没任何应收（`pr` 为 NULL），`total_amount − 0 = 全额`计入敞口——正确，因为已承诺留货但一分钱应收都还没落。
- 拣货中(3)订单可能已分批发了一部分：已发部分进 (A)，未发部分 = `total_amount − 已生成应收` 进 (B)，两者不重叠。
- 草稿(1)不算敞口（还没承诺）；已出库(4)/已取消(5)不算（要么全进应收、要么已释放）。

> **本单自己**：占库时本单还是草稿(1)，既不在 (A)（无应收）也不在 (B)（status=1 被排除），所以校验式用 `已用(A+B) + 本单 total_amount` 补上本单，**不会重复计**。本单占库成功后状态变 2，会自然进入下一单校验的 (B)。

### 5.3 校验判定与超限处理

在 `reserveStock` 事务内、拿到客户行锁后：

```
credit_limit = 该客户 credit_limit
若 credit_limit IS NULL           → 跳过校验（未启用信控）
used   = 已用授信(A+B)             （在同一事务连接上查，见 5.4）
this   = 本单 total_amount
若 used + this <= credit_limit    → 放行，正常占库
否则（超限）:
   若请求带 confirmCreditOverride=true 且当前用户有 sale.credit.override 权限
        → 放行 + 写 credit_override 事件（记录 limit/used/this/超出额/放行人）
   否则 → 抛 AppError('客户授信额度不足', 409, 'CREDIT_LIMIT_EXCEEDED',
              { creditLimit, used, thisOrder: this, overBy: used + this - credit_limit })
```

**Phase 1 选硬阻断 + 一次性放行确认**（不是全套审批流）：
- 与系统里成熟的**超收确认范式一致**（`confirmOverReceive`）：默认拦，前端拿到 `CREDIT_LIMIT_EXCEEDED` 弹窗展示缺口，有权限者勾选"授权放行"后带 `confirmCreditOverride:true` 重试。轻量、无新状态机、留痕在订单事件流。
- **放行权限在服务端校验**，不能只靠前端隐藏按钮（CLAUDE.md 禁止事项 9）：即便请求伪造了 `confirmCreditOverride:true`，无 `sale.credit.override` 权限一律照样 409。
- Phase 2 若需要"销售员申请→主管审批"两步异步流程，再照 `expenseClaim` 建独立放行单（第 9 节）。

### 5.4 并发加锁（设计难点）

**问题**：两张单 A、B 属于同一客户，并发调用 `reserveStock`。若各自事务独立读"已用授信"，两者都读到占库前的旧值 `used0`，各自判断 `used0 + 本单 ≤ 额度` 都成立 → **双双放行、合计超限**。这是典型的"读—校验—写"竞态，`compareAndSetStatus` 挡不住（它只保证单张订单状态不被并发推进，管不了跨订单的额度总量）。

**解法：按客户维度加行锁，把同一客户的占库串行化。**

在 `reserveStock` 事务开头、算已用额度**之前**，对该客户的 `sale_customers` 行加 `FOR UPDATE`：

```js
// reserveStock 事务内，紧跟 lockSaleOrderRow 之后、算库存之前
await conn.query('SELECT id, credit_limit FROM sale_customers WHERE id = ? FOR UPDATE', [order.customer_id])
```

- 同一客户的第二个占库事务会在这行 `FOR UPDATE` 上**阻塞**，直到第一个事务 COMMIT。等它拿到锁再执行 5.2 的两条聚合查询时，第一单的应收/敞口**已经落库**（第一单已占库→进入在途敞口 (B)），于是第二单读到的 `used` 已含第一单，校验会正确地把它拦下。
- **算已用额度的 SELECT 必须在拿到客户行锁之后、同一 `conn` 上执行**——这是整个方案的命门。放锁前查、或用 `pool` 另开连接查，都会读到旧值，锁就白加了（CLAUDE.md 硬约束：不能用非事务裸查做额度校验）。

**加锁顺序**（防死锁，必须全局一致）：`reserveStock` 现有顺序是先 `lockSaleOrderRow`（锁 `sale_orders` 单头，`:932`）再逐行 `lockStockDimension`（锁库存维度，`:945`）。新增的客户行锁插在**最前**，形成统一顺序：

```
客户行(sale_customers) → 订单单头(sale_orders) → 库存维度(lockStockDimension) → 单个容器
```

- 一张销售单只属于一个客户（`sale_orders.customer_id`），所以"先锁客户再锁本单"不会与其它事务交叉成环。
- 任何将来也要"锁客户 + 锁订单"的新逻辑都必须沿用这个顺序（CLAUDE.md 第 11 节）。

**幂等**：`reserveStock` 当前未接 `X-Request-Key`（幂等键列表里只有 `sale.create/sale.adjust`，无 reserve）。重复占库由状态机兜底——第二次 `assertSaleAction('reserve', RESERVED)` 会因状态已非草稿而拒（`sale.service.js:934`），不会重复占用、也不会重复放行。信用校验是"读+阻断"，本身无副作用（放行才写事件，且写在校验通过分支），重放不会产生脏数据。

### 5.5 下单软提示（可选，Phase 1 附带或 Phase 2）

`getReservePreview`（`sale.service.js:900-928`，只读、非事务、占库前预检库存缺口）可顺带返回信用预检结果 `{ creditLimit, used, thisOrder, willExceed }`，让销售员在点"占库"之前就看到"这单会超额"，而不是提交后才被 409 打回。**注意：预检是提示，不是判定**——真正的拦截只在 5.4 的事务内做，预检的 `used` 是非事务快照、可能过时，绝不能用它替代事务内校验（CLAUDE.md：前端不得复制后端业务规则、不得以预检结果替代权威判定）。

**`reserveStock` 校验插入位置（骨架，实现时精修）**：

```js
async function reserveStock(id, operator, { confirmCreditOverride = false } = {}) {
  return withTransaction(async (conn) => {
    const order = await lockSaleOrderRow(conn, id)          // 现有：锁订单单头
    if (!order) throw new AppError('销售单不存在', 404)
    assertSaleAction('reserve', order.status)

    // —— 新增：信用校验（在锁库存之前）——
    const [[cust]] = await conn.query(
      'SELECT id, credit_limit FROM sale_customers WHERE id = ? FOR UPDATE',  // 客户行锁：串行化点
      [order.customer_id],
    )
    if (cust && cust.credit_limit != null) {
      const used = await getCustomerCreditUsed(conn, order.customer_id)       // 5.2 (A)+(B)，同一 conn
      const thisOrder = Number(order.total_amount) || 0
      if (used + thisOrder > Number(cust.credit_limit)) {
        const canOverride = confirmCreditOverride && operator?.permissions?.includes('sale.credit.override')
        if (!canOverride) {
          throw new AppError('客户授信额度不足', 409, 'CREDIT_LIMIT_EXCEEDED', {
            creditLimit: Number(cust.credit_limit), used, thisOrder,
            overBy: used + thisOrder - Number(cust.credit_limit),
          })
        }
        await appendSaleEvent(conn, id, 'credit_override', '超额授信放行', null, operator, {
          creditLimit: Number(cust.credit_limit), used, thisOrder,
        })
      }
    }

    // —— 以下为现有占库逻辑：逐行 lockStockDimension + reservationEngine.reserve + compareAndSetStatus —— 
    // ...（不动）
  })
}
```

> `operator.permissions` 是否已带在 operator 里**待实现时确认**：若现有 `operator` 只有 `userId/realName`（见 `appendSaleEvent` 的用法 `:125-126`），则改从 `req.user`（`loadRolePermissions` 中间件挂的权限集）传入，或在 service 里回查角色权限。roleId===1 超管跳过所有校验（含信控放行），与全站一致。

## 10. 验证清单

- **并发（必测，本功能核心风险）**：仿 `npm run smoke:concurrency-guards` 写一条——同一客户、额度只够一单、两单并发 `reserveStock`：断言**恰好一单成功、另一单 `CREDIT_LIMIT_EXCEEDED`**，且成功后该客户 `used` 恰好等于第一单金额（绝不能双双放行）。这是"两单并发都通过"竞态的回归守卫。
- **口径一致**：造 1 张已发货未收款 + 1 张已占库未发货的订单，断言 `getCustomerCreditUsed` = 账款页该客户未清应收 balance 合计 + 在途敞口，且与 `payment_records` 口径对得上（`npm run smoke:finance` 一并跑，确认没算错欠款）。
- **防双算**：一张拣货中(3)订单分批发一半，断言其敞口 = `total_amount − 已生成应收`，已发部分不被 (A)(B) 重复计。
- **放行权限**：无 `sale.credit.override` 权限带 `confirmCreditOverride:true` → 仍 409；有权限 → 放行成功且 `sale_order_events` 有 `credit_override` 事件。
- **未启用信控**：`credit_limit IS NULL` 的客户占库完全不受影响（存量行为不变）；`credit_limit = 0` 的客户任何赊欠都被拦。
- **快照不回溯**：客户额度调小后，已生成的应收 `payment_records` 不变（快照语义，CLAUDE.md 第 7.1 节）；只影响之后的占库校验。
- `npm run smoke:mainline`（主链路不回归）、`smoke:sale-adjustment`（改单不受影响）。
- 前端 `./frontend/node_modules/.bin/tsc -p frontend/tsconfig.app.json --noEmit` + 两端 lint（`npm --prefix backend run lint` / `npm --prefix frontend run lint`）。
- `npm run test:permissions`（新权限码前后端一致）。
- 手测：设客户额度 1000，制造未清应收 600 + 已占库在途 300 → 已用 900；再占一张 200 的单 → 应被拦（900+200>1000）；有权限授权放行 → 成功且留痕。

## 11. 风险与待确认

- **`payment_records` 无 `customer_id`（已核实）**：已用应收必须经 `order_id → sale_orders.customer_id` 归户（5.2）。**待确认**：系统是否存在"非订单来源的手工应收"（`order_id` 为 NULL 的 `payment_records`）——若有，这类欠款无法经 order 归户到客户，会漏计已用授信。`054` 建表里 `order_id` 可空（`DEFAULT NULL`），需实现前确认目前有无手工应收入口；若有，应补一个客户归户列或专门口径。
- **`operator.permissions` 是否已就绪（待实现时确认）**：`reserveStock` 判 `sale.credit.override` 需要当前用户的权限集。确认 `operator`/`req.user` 是否已带 `permissions`（`loadRolePermissions` 中间件），否则在 controller 传入或 service 回查角色权限。
- **在途敞口是否计入 / 口径是否可配**：Phase 1 默认计入已占库(2)全额 + 拣货中(3)未转应收部分（5.2-B）。若业务只想按"已确认欠款"控额（不含在途承诺），可把 (B) 做成开关。**待确认业务偏好**——保守做法是含在途（承诺即敞口），本文按此设计。
- **额度=0 的语义**：本文定义 `0 = 现款现货（任何赊欠都拦）`、`NULL = 不启用`。需在客户表单 UI 上把这两者讲清楚（一个"启用信控"开关 + 额度输入），否则运营容易把"不想管"误设成 0 导致该客户完全无法赊账下单。
- **性能**：`getCustomerCreditUsed` 两条聚合走 `order_id`/`customer_id` 索引即可，单客户数据量小、占库是低频写操作，无性能顾虑；`sale_orders(customer_id, status)`、`payment_records(type, order_id)` 有索引支撑（后者已有 `idx_payment_records_type_status`，前者**待确认**是否有 `customer_id` 索引，无则补一个）。
- **锁竞争**：客户行 `FOR UPDATE` 会把同一客户的并发占库串行化。正常业务下同一客户同时占多单极少，影响可忽略；但要避免在持客户锁期间做慢查询/外部 I/O（CLAUDE.md 第 11 节：事务内禁外部 I/O），信用校验只有两条本地聚合，满足要求。
- **对账口径漂移**：已用授信与账款页若将来一处改口径、另一处忘改，会出现"账款页显示欠 500、信控按欠 600 拦"的不一致。把口径收进 `utils/creditExposure.js` 单一实现，验证清单里保留"口径一致"断言长期守护。
- 迁移编号**不写死**，落地时取当前最大 +1（当前已到 150，故新迁移大概率从 151 起，但以落地时实际最大值为准）。
