## 1. 背景与现状

系统内目前有 **4 个各自独立实现的审批点**，全部是「**单级、固定语义、服务层手写**」：

| 审批点 | 载体 | 状态机 | 内控 |
|---|---|---|---|
| 费用报销 | `expenseClaim`（`expense-claims.service.js`） | 草稿→待审批→已批准→已付款 | 审批人≠申请人（`expense-claims.service.js:176`） |
| 采购请购 | `purchaseRequisition`（`purchase-requisitions.service.js`） | 草稿→待审批→已批准→已驳回→已取消→已转采购 | 审批人≠申请人（`:181`） |
| 采购单金额阈值 | `purchase`（迁移 196，`purchase.service.js`） | 超阈值单停在待审批(5)，审批通过回已提交(2) | 审批人≠制单人（`purchase.service.js:405`） |
| 呆滞处置 | `inventoryDisposal`（`disposal.service.js`） | 草稿→待审批→已批准→已处置 | 无显式内控（仅权限码） |

共同点：**一张表存 `approved_by/approved_at/reject_reason` 单节点快照**，`approve/reject` 各写一段几乎相同的代码（`lockStatusRow → assertStatusAction → compareAndSetStatus → UPDATE 快照列`）。差异仅在于单据状态值不同。

**局限**（P2-7 要解决的）：
1. **无"按金额分级"**——万元和百元的单走同一个审批人，无法"小额免审/一审、大额二审/三审"。
2. **无"多级顺序审批"**——不能"部门主管 → 部门经理 → 总经理"逐级。
3. **无部门概念**——`sys_users` 无 `department_id`，无法按部门找上级、按部门配置审批链。
4. **重复代码**——四份手写 `approve/reject`，下一张要审批的单据又得抄第五份。

**本功能目标**：建一张**可配置的审批流**（按单据类型 + 金额区间定义审批节点序列），落一个**通用多级审批引擎**，并把**采购请购单**接为第一个业务（保持现有行为：未配置审批流时退回原单级逻辑，不破坏已上线的报销/采购单/处置三个审批点）。

**非目标**：报销、采购单、处置单本期**不迁移**到引擎（它们的单级审批已生产验证、语义固定；引擎先落地，后续按需逐个迁移）；不做会签/或签/条件分叉等复杂 BPMN 语义；不做审批流版本管理（编辑生效即最新）。

### 2.1 部门 `sys_departments` + `sys_users.department_id`

### 2.2 审批流配置 `approval_flows` / `approval_flow_steps`

```sql
CREATE TABLE IF NOT EXISTS `approval_flows` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `biz_type`    VARCHAR(40)     NOT NULL COMMENT '业务类型 purchase_requisition / expense_claim / ...（唯一可配）',
  `name`        VARCHAR(80)     NOT NULL COMMENT '流程名称，如「请购单多级审批」',
  `min_amount`  DECIMAL(14,2)   NOT NULL DEFAULT 0 COMMENT '适用金额下限（含），金额在该区间走本流程',
  `max_amount`  DECIMAL(14,2)   DEFAULT NULL COMMENT '适用金额上限（含），NULL=不设上限',
  `is_active`   TINYINT(1)      NOT NULL DEFAULT 1,
  `remark`      VARCHAR(200)    DEFAULT NULL,
  `created_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_af_biz` (`biz_type`, `is_active`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='审批流配置（多级审批引擎）';

CREATE TABLE IF NOT EXISTS `approval_flow_steps` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `flow_id`     BIGINT UNSIGNED NOT NULL,
  `step_order`  INT             NOT NULL COMMENT '节点序号 1,2,3...',
  `approver_type` TINYINT       NOT NULL DEFAULT 1 COMMENT '审批人类型 1=指定角色 2=部门负责人 3=指定用户',
  `role_id`     BIGINT UNSIGNED DEFAULT NULL COMMENT 'approver_type=1 时：角色ID',
  `department_id` BIGINT UNSIGNED DEFAULT NULL COMMENT 'approver_type=2 时：部门ID（0=申请人所属部门）',
  `user_id`     BIGINT UNSIGNED DEFAULT NULL COMMENT 'approver_type=3 时：用户ID',
  `created_at`  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_afs_flow` (`flow_id`, `step_order`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='审批流节点';
```

> 节点语义：按 `step_order` 升序串行执行，**上一节点通过后才轮到下一节点**。审批人类型三选一：指定角色（该角色任一用户可批）、部门负责人（该部门 manager_id 指向的用户，或部门 0=申请人所属部门）、指定用户。本期不做"或签"（节点内任意一人批即过——这是默认行为，等同"该角色任一成员"）。

### 2.3 审批实例 `approval_instances` / `approval_instance_tasks`（运行期）

```sql
CREATE TABLE IF NOT EXISTS `approval_instances` (
  `id`           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `flow_id`      BIGINT UNSIGNED NOT NULL,
  `biz_type`     VARCHAR(40)     NOT NULL,
  `biz_id`       BIGINT UNSIGNED NOT NULL COMMENT '业务单据主键',
  `applicant_id` BIGINT UNSIGNED NOT NULL COMMENT '申请人（发起审批的用户）',
  `applicant_name` VARCHAR(50)   NOT NULL,
  `amount`       DECIMAL(14,2)   NOT NULL DEFAULT 0 COMMENT '提交时金额快照（用于选流与展示）',
  `current_step` INT             NOT NULL DEFAULT 1 COMMENT '当前待处理节点序号',
  `status`       TINYINT         NOT NULL DEFAULT 1 COMMENT '1审批中 2已通过 3已驳回 4已撤销',
  `reject_reason` VARCHAR(500)   DEFAULT NULL,
  `finished_at`  DATETIME        DEFAULT NULL,
  `created_at`   DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`   DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_ai_biz` (`biz_type`, `biz_id`),
  KEY `idx_ai_applicant` (`applicant_id`),
  KEY `idx_ai_status` (`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='审批实例';

CREATE TABLE IF NOT EXISTS `approval_instance_tasks` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `instance_id`   BIGINT UNSIGNED NOT NULL,
  `step_order`    INT             NOT NULL,
  `approver_type` TINYINT         NOT NULL,
  `approver_role_id`   BIGINT UNSIGNED DEFAULT NULL,
  `approver_department_id` BIGINT UNSIGNED DEFAULT NULL,
  `approver_user_id`   BIGINT UNSIGNED DEFAULT NULL,
  `approver_name` VARCHAR(50)     DEFAULT NULL COMMENT '快照：实际审批人姓名（通过/驳回时写）',
  `status`        TINYINT         NOT NULL DEFAULT 1 COMMENT '1待审批 2已通过 3已驳回',
  `action_at`     DATETIME        DEFAULT NULL,
  `comment`       VARCHAR(500)    DEFAULT NULL,
  `created_at`    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_ait_instance` (`instance_id`, `step_order`),
  KEY `idx_ait_pending_role` (`status`, `approver_role_id`),
  KEY `idx_ait_pending_user` (`status`, `approver_user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='审批实例节点任务';
```

> 建实例时**展开**节点：从 flow_steps 复制每节点的审批人类型/角色/部门/用户到 instance_tasks，此后**流程配置修改不影响运行中的实例**（快照语义，符合审批留痕要求）。`approver_name` 记录实际经办人姓名，含超管代批。

## 3. 审批流引擎 `engine/approvalEngine.js`

引擎只做「审批编排」，**不知道**业务单据怎么算钱、怎么改状态——业务自己决定何时提交/通过/驳回后的动作。

```js
// 接口（全部在调用方已开启的事务连接 conn 上执行，引擎不开事务；与 containerEngine 同范式）
await approvalEngine.startApproval(conn, {
  bizType: 'purchase_requisition', bizId, amount, applicantId, applicantName,
})                                    // 建实例 + 展开节点；返回 instanceId 或 null（无匹配流程时返回 null，业务退回单级审批）
await approvalEngine.approveStep(conn, { instanceId, operator, comment })   // 当前节点批过 → 推进或实例通过(2)
await approvalEngine.rejectStep(conn,  { instanceId, operator, comment })   // 驳回 → 实例状态 3，当前 task 置 3
await approvalEngine.cancelInstance(conn, { instanceId, operator })         // 申请人撤销 → 实例 4，未处理 task 置驳回
await approvalEngine.getInstance(conn, { bizType, bizId })                  // 取实例 + tasks 列表（含审批进度）
await approvalEngine.resolveApprovers(conn, { flowId })                     // 解析各节点审批人（角色→成员集合、部门→负责人）
```

**核心规则**：
1. **找流**：`startApproval` 时按 `biz_type` + `is_active=1` + `amount BETWEEN min_amount AND max_amount` 取**一个**流程（多条命中取 `min_amount` 最大的一条——最精确匹配；无命中返回 null，业务按原逻辑走）。
2. **串行推进**：`approveStep` 只处理 `status=审批中` 且 `current_step` 指向的 `step_order` 的待审批 task。批过后若存在下一节点 → `current_step+1`；否则实例 → 已通过(2)。
3. **审批人校验**：待办任务的审批人 = 该节点的角色成员 / 部门负责人 / 指定用户；操作人必须命中（**超管 role_id=1 恒可代批**，留 `approver_name` 记录实际经办人）。**申请人不得批自己的单**（无论是否在审批人集合内，照 expenseClaim 内控）。
4. **并发**：`startApproval` 依赖 `uk_ai_biz` 唯一键防重复实例；`approveStep/rejectStep` 用 `UPDATE approval_instance_tasks SET status=2 WHERE id=? AND status=1` 的 affectedRows 判断（CAS，并发下只有一方成功，另一方差 409）。
5. **业务联动**：引擎**只改审批实例的状态**，不碰业务单据状态。业务在 `approveStep/rejectStep` **返回后**自己读实例状态决定动作（如请购：实例通过 → 请购 2→3 已批准；驳回 → 请购 2→4 已驳回）。

## 4. 请购单接入（`purchase-requisitions.service.js`）

**兼容策略**：提交时先尝试 `startApproval`。**有匹配流程** → 走多级引擎（请购单保持 `待审批(2)`，审批进度挂在 `approval_instances`）；**无匹配流程** → 完全回退现有单级 `approve/reject`（现行为不变）。

```js
// submit：草稿→待审批（原逻辑）
const inst = await approvalEngine.startApproval(conn, { bizType:'purchase_requisition', bizId:id, amount:estimatedAmount, applicantId, applicantName })
// inst 非 null ⇒ 启用多级；approve/reject 走引擎；null ⇒ 单级快照列

// approve（多级路径）：approvalEngine.approveStep → 返回后读实例状态
//   status=已通过 ⇒ 请购 2→3 已批准 + 写 approved_by/approved_at（沿用原快照列，前端兼容）
//   status=审批中 ⇒ 请购保持 2，仅写 approved_by=当前审批人（留痕）
// reject：approvalEngine.rejectStep → 请购 2→4 已驳回 + 写 reject_reason
// withdraw（待审批撤回）：approvalEngine.cancelInstance → 请购 2→1
// cancel（草稿/已驳回/待审批取消）：有进行中实例则 cancelInstance
// findById：附带 approval.instances（含 tasks 进度），前端展示"第 1/3 级：部门经理 ✔ 待财务总监审批"
```

权限：审批动作**仍校验 `purchase.requisition.approve` 权限码**（能否进入审批页），引擎在 service 层再加"是否当前节点审批人"硬校验。节点审批人来自流程配置而非权限码——`approve` 权限码不 seed，由管理员按需授予（现有约定不变）。

## 7. 测试

`tests/approval-flow.smoke.test.js`（进 CI test.yml），覆盖：
1. 配置 3 级流程（角色 → 部门负责人 → 指定用户），发起请购提交 → 实例审批中、current_step=1。
2. 第 1 级非审批人审批被拒；审批人通过 → 推进到第 2 级。
3. 第 2 级驳回 → 实例驳回、请购→已驳回、写 reject_reason。
4. 全批通过 → 实例已通过、请购→已批准。
5. 申请人自批被拒；超管可代批。
6. 金额不在任何流程区间 → `startApproval` 返回 null，走单级（回归现有行为）。
7. 并发：两个审批人同时批同一节点 → 一方成功一方 403/409（CAS 防护）。
8. 申请人撤回待审批请购 → 实例撤销，不留孤儿；撤销后重新提交可新建实例。

> ⚠️ 测试**开头和结尾都会清空全部审批流配置与实例**——审批流是全局配置，残留会污染金额区间匹配（曾导致用例 6 误命中旧流程）。

**门禁**：`test:permissions`（6 新码双向一致）、后端 lint、前端 lint/tsc、`smoke:mainline`（请购链路不回归）、`smoke:warehouse-scope`。实跑：approval-flow 30/30、mainline 49/49、warehouse-scope 34/34、p0-regression 41/41 全绿。

## 8. 风险与待确认

- **请购 `withdraw` 时机**：引擎实例已创建后撤回请购，实例标记撤销(4)，不能留"审批中"孤儿实例。
- **已驳回重提**：请购驳回 → 改单 → 重新 submit，应**复用原实例还是新建**？本期设计：驳回实例保留留痕，重提时 `startApproval` 因 `uk_ai_biz` 唯一键被占——**需在驳回时把实例置终态(3)并解除唯一键占用**（加 `closed_at` 或驳回即 `finished_at`，`startApproval` 查找时忽略已结束实例）。实现时确认 `uk_ai_biz` 是否该带 status 条件。
- **部门负责人离职**：manager_id 指向已禁用/删除用户时，该节点审批人集合为空，实例卡死。本期：启动时校验每个节点至少解析出 1 个审批人，空则 400 拒绝提交并提示"该流程第 N 级无审批人"。
- **多流程区间重叠**：取 `min_amount` 最大者，文档写明。
- **请购单估计金额为 0**：`estimated_amount=0` 会命中 `min_amount=0` 的流程。若不想让 0 元单走审批，需在提交时对 `estimated_amount<=0` 直接走单级。实现时确认。
- **既有四审批点不动**：本版只接请购。报销/采购单/处置的多级迁移列入后续，改完需重跑各自 smoke。
