# 设计文档 12 · 技术债与架构改进汇总

> 状态：**评估文档，非新功能**
> 本文对现有系统"不好的地方"做评估 + 改进路线，逐条给：现状 → 问题 → 影响 → 改进方案 → 工作量/风险 → 优先级。**本文只评估不实施**；凡建议动库存/状态机/迁移的，实施前必须读完整调用链 + 用户确认（CLAUDE.md 第 17 节）。

---

## 概述

Flowcube 的**核心引擎是扎实的**（容器为库存事实源、三大引擎、状态机 CAS、幂等回执、锁顺序、财务快照）。本文列的技术债，几乎都不在核心账务正确性上，而在**可维护性、schema 治理、决策口径的边缘一致性**。按"该不该动、性价比"分四档，末尾给汇总表与"建议不动"清单——**避免后人重复折腾已评估过的项**。

---

## 逐条评估

### ① `avg_cost` 只正向移动，不反冲 —— 成本口径分裂

- **现状**：`product_items.avg_cost`（移动加权成本）仅在收货上架时正向更新，退货/撤回收货**不反冲**（CLAUDE.md 第 8 节、第 20.9）。利润分析另用 `sale_order_items.cost_snapshot`（下单/出库时的 COGS 快照）——两套成本口径并存。
- **问题**：退货/撤回频繁的品类，`avg_cost` 会**单调漂移、越来越不准**；而它是"库存金额""毛利估算"等展示的隐性输入。
- **影响**：库存估值与部分毛利展示在退货多的品类上偏差累积。**已成交订单的利润不受影响**（那用 `cost_snapshot` 快照，是准的）。
- **改进方案**：**不要"顺手修正"去做反冲**——CLAUDE.md 明确这是刻意简化，反冲会引入新的复杂度与错账面。正确做法是提供**成本对账工具**：一份"`avg_cost` vs 期间实际采购加权均价"的对账报表，把偏差暴露出来；如确需，再提供按商品的**成本重算脚本**（只读重算、灰度执行），而非在业务链路里实时反冲。
- **工作量**：中（对账报表小；重算脚本中）。**风险**：中（动成本口径要谨慎，务必先只读对账）。
- **优先级**：**中低**。先做"暴露偏差"的对账报表，重算按需。

### ② 权限码两份手工同步 —— 靠纪律维持一致性

- **现状**：`backend/src/constants/permissions.js` 与 `frontend/src/lib/permission-codes.ts` 各约 145 个权限码**手工维护**，`npm run test:permissions` 双向 diff 兜底（CLAUDE.md 第 12 节、第 20.6）。新增权限要改三处（两份常量 + seed 迁移）。
- **问题**：单一事实源缺失，靠测试事后兜。虽有兜底，仍是重复维护、易漏、CI 变红后才发现。
- **改进方案**：**单一事实源 + 代码生成，范本现成**——`scripts/generate-status-constants.js`（`package.json` 的 `generate:status`）已经在做"从后端常量生成 `frontend/src/generated/status.ts`"。照此把权限码也改为**后端 `permissions.js` 为唯一源 → 生成前端 `permission-codes.ts`（或 `generated/permissions.ts`）**，前端不再手维护。seed 迁移是数据授权，另一回事，仍人工。
- **工作量**：小-中（照现成范本加一个生成脚本 + 前端改用生成物）。**风险**：低（生成物，`test:permissions` 继续兜）。
- **优先级**：**中（高性价比）**。范本现成，能消除一整类"两处不一致"隐患。

### ③ 状态机分散在多处 —— 找不全、易漏锁

- **现状**：`constants/documentStatusRules.js` 是主入口，但**不在其中的还有**：`return_tasks` 内联状态机（`return-tasks.service.js` 的 `RT_TRANSITIONS`）、财务三表（`payment_receipts` / `reconciliation_statements` / `finance_accounts`）各自在 service 里用"事务 + `FOR UPDATE` 锁单头 + 校验 + `UPDATE`"实现（CLAUDE.md 第 10 节末）。它们与 `compareAndSetStatus` 等效、并发安全，只是没走统一入口。
- **问题**：找状态机要翻多处；新人容易漏掉某处、或照裸 `UPDATE` 抄出不加锁的版本。
- **影响**：维护成本 + 潜在并发 bug 风险。
- **改进方案**：**分两步**——(a) 低风险先行：在 `documentStatusRules.js` 或一处文档里**建索引**，列出全部状态机位置（含内联的）；(b) 渐进收敛：把 `return_tasks` 与财务三表的流转迁到 `assertStatusAction` + `compareAndSetStatus` 统一入口。**注意**：CLAUDE.md 第 17.12 明确要求重构状态机前读完整调用链，(b) 不可轻率。
- **工作量**：(a) 小 / (b) 中。**风险**：(a) 极低 / (b) 中高（动状态流转，须跑齐 smoke）。
- **优先级**：**中**。先做 (a) 索引，(b) 排后。

### ④ 迁移编号重复/缺号 + 生产 schema 漂移史 —— 库存安全隐患

- **现状**：`backend/src/database/` 150 个迁移，**重复编号已核实**（`057_add_page_inbound_permission` 与 `057_inbound_task_multi_purchase`；`064` / `089` 同样各两个文件），**缺号** 008/009/040，靠文件名 lexical 排序执行。生产出过"迁移未真正生效导致缺列"（记忆 `prod-warehouse-tasks-schema-drift`）与"迁移文本声明了生产从没有过的列"（CLAUDE.md 第 20.8）。
- **问题**：编号非唯一/非连续，排序脆弱；无 schema 对账机制，漂移只能靠 `check-consistency` 或人工事后发现。新迁移取"当前最大+1"在多人/多分支并行时会撞号。
- **影响**：**这是库存系统最该收紧的一条**——schema 漂移直接威胁库存正确性。
- **改进方案**：(a) **CI 加"迁移编号唯一"校验**（最低成本、最高收益，先做）；(b) 编号规则改时间戳或强制唯一；(c) **schema 快照对账工具**——比对迁移预期结构与实际库结构，部署后自动跑并告警；(d) `db_migrations` 记录迁移文件哈希，防止已执行迁移被事后篡改（配合第 17.10"不改已执行迁移"）。
- **工作量**：中（都是加校验/工具，不动业务）。**风险**：低。
- **优先级**：**中高（高性价比）**。至少先落 (a) CI 编号唯一校验。

### ⑤ COLUMN_COMMENT 反复过期 —— "schema 即文档"失灵

- **现状**：列注释曾大面积过期，迁移 133/146 已系统订正大部分，仍有残留；语义**一律以 `constants/` 为准**（CLAUDE.md 第 8 节、第 20.5）。
- **问题**：注释不可信、还要额外维护。
- **改进方案**：从 `constants/`（状态语义）**反向生成列注释**的脚本；或明确放弃维护、在规范里固化"注释不可信、以 constants 为准"（现状已如此）。
- **工作量**：小。**风险**：低。
- **优先级**：**低**。已有 constants 兜底，属锦上添花。

### ⑥ PDA 与 ERP 同一份前端、同路由树 —— 耦合 + 包体积

- **现状**：PDA 与 ERP 是同一份 React 代码、同路由树（`/pda/*`），靠 `CrossClientNavigationGuard` 运行时拦截跨端跳转，构建时用 `VITE_CAPACITOR` / `VITE_ELECTRON` 区分 target（CLAUDE.md 第 13/14 节）。
- **问题**：PDA APK 背着整个 ERP 代码（包体积）；一个 Guard 兜所有跨端安全；两端演进耦合、改一端易误伤另一端。
- **影响**：PDA 现场设备加载偏重；耦合风险。
- **改进方案**：评估按 target 做更激进的代码分割（route-level lazy + 构建期 tree-shake 掉另一端页面树），长期可考虑拆成两个前端应用共享 `lib/`。较大工程，收益主要是包体积与解耦。
- **工作量**：大。**风险**：中。
- **优先级**：**低-中**。现状能用；除非 PDA 包体积/加载成为现场痛点，否则不急。

### ⑦ 单租户架构 —— 商业化前的战略决策

- **现状**：整个系统单租户（无 `tenant_id`，数据/配置/部署单实例单库）。
- **问题**：若要 SaaS 化，多租户改造伤筋动骨（每张业务表加 `tenant_id` + 全局数据隔离 + 按租户权限/配置/限流/备份）。越晚改越贵。
- **改进方案**：这是**产品战略决策，不是纯技术债**。若确定商业化，现在就要选路线——物理隔离（一租户一库/一实例，改动小、边际成本高）vs 逻辑隔离（共享库加 `tenant_id`，改动巨大但省成本）。本文只给方向。
- **工作量**：极大。**风险**：极高。
- **优先级**：**取决于商业化战略**。技术上"知道就好"，除非确定 SaaS 化否则不动。

### ⑧ exceljs 依赖链高危告警 —— 评估后建议不动

- **现状**：CLAUDE.md 第 20.12 已详述——`exceljs@4.4.0`（已是最新）固定依赖 `archiver@5 → glob@7 → minimatch@3 → brace-expansion@1`，9 条 `npm audit` 告警同源，**无可升版本**，`audit fix --force` 只会破坏依赖。
- **风险实际不可达**：该 DoS 需攻击者控制传给 `glob` 的模式串，而项目只用 exceljs 读写文件、glob 模式全是库内部固定路径、不接受用户输入。
- **结论**：**评估后建议不动。** 解除条件：exceljs 发布带 `archiver@6+` 的版本，或改用别的导出库。
- 记录此条是为避免后人重复折腾（记忆里已有此教训）。

## 汇总优先级

| 档位 | 项 | 建议动作 |
|---|---|---|
| **高性价比先做** | ② 权限码生成、④ 迁移编号唯一校验 + schema 对账 | 都是加"生成/校验"，低风险高收益，范本现成 |
| **中，按需** | ① avg_cost 对账报表、③ 状态机文档索引→渐进收敛、⑤ 注释反向生成 | 先做低风险部分（对账/索引），重构排后 |
| **低 / 战略** | ⑥ 前端 PDA/ERP 拆分、⑦ 多租户 | 除非成为现场痛点 / 确定商业化，否则不动 |
| **评估后不动** | ⑧ exceljs 告警 | 不可达 + 无可升版本，等上游 |

## 明确"建议不动"清单（避免误改）

1. **⑧ exceljs 告警**——已评估，风险不可达，无解，等上游。
2. **① 的"反冲 avg_cost"**——只做对账报表/按需重算，**不要**在业务链路里实时反冲（CLAUDE.md 明确的刻意简化）。
3. **⑦ 多租户**——除非确定商业化，否则不启动（伤筋动骨）。
4. 任何 **③ 状态机 / ④ 迁移** 的重构——实施前必须读完整调用链 + 跑齐 smoke + 用户确认（第 17.10/17.12）。

## 风险与实施纪律

- 本文所有建议**不得违反 CLAUDE.md 第 17 节硬约束**。
- 高性价比的 ②④ 是"加校验/生成物"，不动业务逻辑，可优先安排。
- ①③⑥⑦ 涉及口径/结构/架构，须单独立项、灰度、回归。
