# 履约及时刷新与待办检索（2026-09-12）

本文记录工作区实现和本轮验证，不代表已经发布、生产验证或压力验收。没有新增数据库迁移。

## 提交与刷新边界

业务事实仍由原事务提交。`fulfillment.refresh.js` 提供显式 `commitFulfillment(conn, type, id)`：先等待原 `conn.commit()` 成功，再向内存队列发送提示。通知不读写数据库，不等待检测；提交失败、回滚与常规幂等重放不会入队。提示失败不会让已提交业务误报失败。没有修改连接对象、拦截 SQL，也没有在 GET 中补写事项。

当前接入点为销售建单/编辑/占库/释放/改单/派发/取消/删除，采购建单/编辑/确认/撤回/审批/驳回/短装结束/取消，收货建单/提交/收货/关闭/取消/上架/撤回，调拨建单/编辑/确认/出入库/取消/强制关闭，以及仓库出库、仓库取消、改单拆箱/实物归还、取消实物归还。履约交期和事项写事务也发送提示。仓库方法由外部事务调用时仍由事务所有者提交；不在内部提前通知。

仓库出库先直接刷新所属销售，包括刚刚发完而进入结束状态的销售。采购与收货供应变化按**商品和仓库**关联销售，既包含有效采购绑定，也覆盖已解除绑定的候选供应。调拨覆盖源仓、目标仓；销售占用变化覆盖同商品同仓的其他销售。混合收货先按采购 ID 游标通知关联采购，再遍历销售。每次依赖查询最多 25 个订单 ID，后续页留在队列；下游销售仅检测自身，不再次扩散。

销售草稿编辑、执行/占库期改单、占库改仓和部分取消删行，以及采购/调拨编辑，在原事务内、修改前捕获旧商品仓库维度；提交成功后与当前订单提示一并发布。销售仓库使用 `COALESCE(行仓,头仓)`，调拨覆盖两端仓。旧维度独立按 `productId:warehouseId` 合并，新维度仍从提交后当前明细展开，删行或改仓不会漏掉已释放供应的其他销售。回滚与幂等重放不发送旧维度提示。占库入口的旧维度读取位于客户 `FOR UPDATE` 与授信读取之后、明细改仓之前，避免普通 SELECT 提前建立 RR 快照而看不见等待客户锁期间其他订单提交的授信占用。

每次旧维度查询最多 501 条，保存前 500 个 distinct 维度；超过时提交后递增 `snapshotOverflow`，未进入快速路径的部分交给完整轮询兜底，不将截断快照视为完整通知。维度提示与单据提示共享 1,000 项容量、版本防丢和有限重试；每个维度仍按销售 ID 每页 25 单，只查询该商品该仓库，不扩到全仓。未接入提示的其他业务入口仍由完整轮询兜底，不新增持久化事件设施。

## 资源、重试和等待时间

- 每个 Node 进程一个队列，按类型和单据 ID 或商品仓库维度合并，最多 1,000 项（含正在处理的项）。满时拒绝新增提示并计数；已有项仍可合并。
- 调度器每 1 秒尝试一轮，队列自身与调度器均防重入。每轮最多处理 25 项，超过 250 毫秒后不再启动下一项；已经开始的 SQL/检测不会被强行中断。
- 每轮只处理开始时的快照；新通知下一轮处理。处理中直接业务变化增加版本并重启依赖展开，完成时不会误删新变化。依赖提示只要求复检自身，不重置正在展开的游标；如果自身已检测或正在运行，记录待复检标记，在展开结束后追加一次自身检测且不再扩散。尚未开始的自身检测直接合并依赖提示。分页续跑项/重试项移至队尾，减少长期占住首批的情况。
- 同一版本失败最多尝试 3 次，间隔至少 1 秒、2 秒；耗尽后释放并计数，周期扫描继续兜底。新业务变化可以重新触发。
- 无积压时，直接单据通常在下一次 1 秒 tick 开始检测，依赖销售再多一个 tick；混合收货、分页、重试会增加轮次。它不是硬性一秒完成承诺。
- 原每 30 秒、每类最多 25 单的扫描保留。30 秒是扫描轮次间隔，不是全量完成上限。每类待扫描 N 单，一次完整循环约需要 `ceil(N / 25)` 轮；满 25 的最后一页还需要空页才能归零。若错过当前游标，需等下轮完整循环。
- 1,000 项容量限制内存，不构成固定墙钟等待上限。慢 SQL、锁等待、依赖分页、持续流量和进程停止都可能延迟；需要结合积压年龄诊断。进程重启丢提示、队列溢出、有限重试耗尽均依靠扫描恢复。当前是单实例部署适用的优化；多实例时各自合并，不具备跨实例去重，但事项事务/唯一键保持幂等。

## 诊断

管理员可通过 `GET /api/fulfillment/refresh-status` 读取本进程匿名统计；接口在鉴权后检查 `roleId=1`，普通业务用户返回 403。GET 不触发同步。

返回容量、批量上限、积压数量、最老积压年龄、运行标记，合并/队列溢出/旧维度快照截断（snapshotOverflow）/成功/失败/耗尽计数，以及最近成功时间、失败时间和单次处理耗时。时间是 Unix 毫秒；尚未发生为 null。没有单号、客户/仓库信息、凭据、堆栈或原始错误文本。累计值在进程重启时归零。

## 职责与列表契约

- `fulfillment.events.js` 承担事件写入/读取，worker 不再循环引用 service。
- `fulfillment.query.js` 承担列表与筛选，使用最多三条查询（摘要、计数、当前页）和按主键的四类业务表关联，不逐事项查询业务单据。
- `fulfillment.refresh-queue.js` 为无数据库依赖的有界队列与提交通知语义；`fulfillment.refresh.js` 负责依赖展开和运行实例。
- `fulfillment.service.js` 保留原有 `event/events/listIssues` 兼容导出和业务命令；消费者无需同时迁移。

`GET /api/fulfillment/issues` 新增可选 `documentType=sale|purchase|inbound|transfer`、`keyword`。关键字裁剪至 100 字，参数化搜索标题、原因、业务单号、客户/供应商、仓库快照名称。列表增加：

| 字段 | 类型 | 来源 |
|---|---|---|
| documentNo | string 或 null | 销售/采购/调拨单号，收货 task_no |
| partyName | string 或 null | 业务快照客户或供应商；调拨为 null |
| warehouseName | string 或 null | 业务快照仓库；调拨为“源仓 → 目标仓” |

权限与仓库条件同时作用于名单和计数，销售头仓与全部行仓必须都在授权范围，调拨沿用至少一端可见规则；不借业务名称 JOIN 扩大可见范围。分页沿用 `normalizePagination`，最多 500 条，排序末尾为唯一事项 ID。`pagination.total` 与筛选后的列表使用完全相同条件；`summary` 继续表示用户全部授权事项概览，不受关键字、单据类型和所选状态筛选影响。

业务交期与事项处理期限是不同字段。刷新发现/解除和更新原因不擅改已有事项的人工处理期限；新建/重新打开事项仍按现行规则带入检测期限。本轮不改变期限优先级，也不将承诺交期每次覆盖到 `due_at`。
