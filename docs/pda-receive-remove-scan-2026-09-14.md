# PDA 收货页去掉扫码框（2026-09-14）

## 决定

按用户判断，PDA 收货页**移除「扫描商品条码」输入框**，同时移除配套的
「未经扫码核对 → 再点一次提交」闸门。收货改为：点选「待收商品」卡片 → 逐箱填数量 →
点一次「打印并登记」即提交。

## 为什么

收货页原来的扫码框只匹配两种值：

- 商品编码 `product_items.code`（如 `P111135`）；
- `P<商品ID>` / `PRD<商品ID>` 形式的商品条码（由 `parseBarcode` 解析出 id）。

而现场情况是：

- 来货没有任何条码，**商品条码字段的功能已经从 ERP 商品表单删除**；
- 生产库 124 个商品里维护过 `barcode` 的是 **0 个**，只有系统生成的商品编码。

也就是说这个框**永远扫不出有效结果**：扫到别的码要么提示「扫描商品条码」，要么
「商品不在本收货单」。于是「未核对 → 再点一次」这道本来是给"偶发无条码商品"留的例外闸门，
变成**每一次收货都要多点一次**的固定摩擦，且没有起到防错货的作用。

注意：收货时实物上也不可能有系统生成的条码——容器条码（`I000001`）是**收货成功之后**
才生成并打印、贴上箱子、留到**上架**环节扫的。

## 保留了什么

- 后端 `POST /api/inbound-tasks/:id/receive` 的 `scannedBarcode` 校验**保留**（可选参数，
  未传即跳过）；前端 `ReceiveParams.scannedBarcode` 类型也保留，避免破坏 API 契约。
- 其它闸门全部保留：超收确认（409 → 弹窗选原因码）、重复扫码确认（409 → 再点一次）、
  批次/效期校验、采购来源完整性、设备仓与用户仓库范围。
- 商品仍按明细行锁定，不属于本单的商品本来就进不来；收货页继续展示商品名/编码/应到·已收·剩余，
  选错商品时数量与剩余会立刻失真，属于可用的兜底。

## 受影响文件

- `frontend/src/pages/pda/receive.tsx`：删除 `PdaScanner`/`PdaBottomBar` 与 `handleScan`、
  `scanVerified`、`noScanArmed` 状态；空态文案改为引导点选商品（全部收完时提示可继续上架）；
  一个商品收完后**自动切到下一个未收完的商品**（按旧快照挑选时排除刚收完的那行）。
- `frontend/src/pages/pda/receive.test.tsx`（新增）：断言不再渲染扫码框、**点一次即提交**、
  收完一个商品后**自动切到下一个未收完的商品**（第二次提交落到下一个 productId）。

## 已知取舍

- 若将来重新给商品维护条码（或来货统一贴商品编码标签），可以再恢复扫码核对；
  此时前端还需补上"匹配 `barcode` 字段"（后端本来就接受，前端目前只认 `code`/`P<id>`）。
- 自动切换只看页面上已有的明细快照，两个商品各自剩余量都大于 0 时才会切；若其它商品刚好
  被别处收完，刷新后会落到空态提示，需要重新点选。
