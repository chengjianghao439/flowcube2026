# 核心业务语义

> **来源**：本文件由 `AGENTS.md` 的 §7 迁出（2026-09-19 文档体系重构，原文见 `docs/agents-md-archive-2026-09-19.md`），内容为无损搬运。
> **何时必须读**：改动采购收货/上架、销售占库与 ATP、拣货到出库执行链、退货、调拨、盘点、履约刷新时。
> **约定**：能机器验证的规则一律以 `tests/` 守卫为准；本文件写「为什么」与「边界」，与守卫冲突时先核实代码，再同步两者。

- **采购收货（2026-10-01 边收边上架）**：采购提交仍按当前审批阈值判断；收货订单 → PDA 实收建待上架容器 → 原扫码上架。任务状态 2/3 均允许已实收容器上架（`putaway.from=[2,3]`），状态 1/4/5 拒绝；未收到的货不能上架。状态 2 即使当前实收已全部上架仍开放收货、`audit_status=0`，本批不生成应付。全部明细收满自动 2→3，或主管在 ERP 对有实收的任务短装结束 2→3；同事务复用 `tryFinishTask`，只有收货结束且全部实收已上架才 3→4、自动结算。已提前全部上架的短装单立即完成，无需等待不存在的下一箱。原混单来源/数量精度/超收和重复确认、采购剩余/销售绑定、已付与首次账期、退货扣减策略保留；不逐箱结算。PDA 保持原硬件扫码，手动输入与任务归属校验不变；ERP 不新增直接放行库存入口。撤回仍走 void-receipt 并反冲，已使用、拣货、拆分、调拨或付款等保护不放宽。2026-09-16 的“收满才上架”政策为历史规则。
- **收货保护**：超收确认与疑似重复扫码确认分别沿用 `confirmOverReceive` / `confirmDuplicate`；阈值读 `inboundThresholds` 和配置。容器保留 `inbound_task_item_id`，按归属行回写上架量和采购价，不能串单结算。
- **采购来源完整性保护（v0.9.10）**：收货/上架/撤回复用 `inbound-purchase-source.js`，每行必须有合法采购及明细 ID，且明细所属订单、商品一致，空来源不再跳过取消校验。应付重算前拒绝缺关联的有效收货或未归入收货明细的旧直接入库，不能用空 JOIN 的零金额冲掉历史应付。线上启用状态须以同 SHA 部署及迁移结果核实；生产历史记录另走有备份和审计的定向修复，见 `docs/purchase-repair-2026-09-08.md`。
- **销售分仓/按量占库**：行级 warehouse_id 必须参与关联；同商品多仓不能 JOIN 放大。订单头仓库和每条明细的目标仓库都必须通过当前用户仓库范围校验。`reserved_qty` 是已占量，`dispatched_qty` 是已派发量；销售数量允许正小数，发起出库可按明细指定本批数量但不得超过已占未发差额，部分占、补占、释放、分批发货和改单保持数量账一致。改单、取消、删除等写操作必须携带稳定请求键以防重试重复执行。
- **销售 ATP**：总可占量 = ACTIVE 实物 + 采购未上架总量 − 全部有效预占；预计量不能先减绑定后再减 reserved。绑定只表示尚依赖采购的数量，上架按采购明细 FIFO 兑现，不减少销售预占；出库只能使用本单已有实物份额及未分配实物，不能截断其他订单合法的预计预占。采购撤回、驳回、取消、减量/删行和短装关闭均保护有效绑定；撤回上架不能移除支撑现有销售承诺的供应。多商品释放先按统一顺序锁全部库存维度，再锁预占/预计绑定；旧快照漏维度返回 409 重试。规则与回归见 `expectedStock.js`、`sale-atp.smoke.test.js` 和 `audit-inventory.smoke.test.js`。
- **可承诺与当前可拣分开**：销售占库预览的 ATP 可承诺量仍按上式计算；界面“当前可拣现货”只汇总同仓未被其他任务整容器独占的 ACTIVE 容器，作为作业可执行性参考，不增加或减少合法预占。拣货推荐无候选时按同仓范围返回至多 3 个占用任务摘要，PDA 提示等待任务完成或逆向归还后刷新，不指引盲扫已锁容器。扫描与出库仍由事务内的容器锁和预占检查最终裁决。独立库回归见 `smoke:concurrency-guards` 的 5 件容器 A 拣 3、B 占 2 场景。
- **销售执行**：拣货 → 分拣 → 复核 → 打包 → 出库，各阶段校验闭合；执行期减量、取消涉及已搬动物料时走 PDA 物理确认/逆向归还。销售关联仓库任务禁止从仓库任务入口单独取消，必须从销售订单统一取消同单任务和剩余预占。已有部分出库时取消剩余需保留已发事实，按实发原值比例保留整单折扣并重算应收，不能整单当未发取消。**执行期取消且没有任何已出库任务时必须把明细 `reserved_qty`/`dispatched_qty` 一并归零**（2026-09-17 验收修复：此前只释放预占账与任务，明细仍显示已占/已派发，开发库累积 56 张此类单据）；有实发时按实发精简明细的分支不变。执行期改单仅支持单个仓库任务且所有明细已完整占库、完整派发的订单；同仓多任务或部分派发返回 409，列表和详情同步禁用入口。重建执行期明细必须写回 reserved_qty/dispatched_qty，不能只写旧 dispatched 标记。待实物归还期间 reserved_qty 按实际有效预占账保留，可暂大于改单目标量；PDA 确认释放后同事务同步已占量，dispatched_qty 表示调整后的派发目标。占库期或执行期改单重算货款后必须再次校验原折扣不超过新合计。同商品分仓的扫描记录必须同时按任务仓库与商品归属，不能只按 product_id 混在多条明细上。
- **改单只修改商品明细（2026-09-29 修复）**：占库期（2/6）与执行期（3）改单由服务端只更新商品明细与订单金额（状态机 `adjust.from=[2,3,6]` 的文案即「修改明细」）；订单客户、出库仓库、承运商、运费方式与收货信息**一律不被更新**。前端 `SaleOrderHeaderFields` 在改单视图传 `headerReadOnly`（客户/仓库/承运商/运费/收货信息只读、隐藏「从地址簿选择」），并在提示条写明「改单仅修改商品明细」。此前这些字段在界面上可编辑、`PUT /sale/:id/adjust` 返回 200 却**静默丢弃**，其中**改客户**还会按新客户价格表重算单价并把金额写回订单（订单客户仍是原客户），属静默不一致（2026-09-29 隔离库 GUI 实测：载荷带 `customerId=2`、`unitPrice` 100→10、订单 `customer_id` 仍为 1、`total_amount` 500→50）。
- **分拣格耗尽后的恢复**：销售出库仓库任务创建时允许暂不占格；主管可在分拣格管理页对同仓销售出库任务补分配，但只限拣货中或待分拣、未绑格、无取消或改单挂起。采购退货跳过分拣阶段，不参与补分配。无空格时明确 409，等待空格释放后重试；不改变任务状态、容器锁、库存或销售数量。PDA 发现任务未绑格时暂停本次分拣，待主管补分配后刷新并重新扫码商品和格码；后端分拣完成接口也拒绝未绑格任务，不能通过直调跳过恢复。
- **销售主数据快照**：建单和草稿编辑时，客户、默认仓库、明细仓库、商品与承运商名称及商品编码、单位、供应商型号、型号、颜色、成本均从当前启用的服务端主数据生成；不能信任客户端传入的显示名称。停用或删除的客户、仓库、商品、承运商必须拒绝保存。
- **退货**：采购退货走标准仓库出库并冲减应付；销售退货走收货、质检、上架并冲减应收。部分质检必须保留合格、拒收、未检三份数量并守恒，未检容器可继续质检；收货/分箱标签与数量变化同事务入队，回传容器条码、打印任务及无打印机提示。上架扫码经当前任务范围解析真实容器/库位 ID，提交再次校验归属、状态、设备仓与权限；不能将完整条码直接转 Number，也不能通过列表选 ID 代替扫码。return_tasks 有内联状态机，不能仅查 documentStatusRules。

- **销售退货返货出库（2026-09-26，任务 1 第二期）**：退货单取消时，已入库的货**退回给客户**，走**独立的返货出库任务**（`warehouse_tasks.task_type='sale_return_out'`、`return_id = sale_returns.id`），**出库完成才真正取消**（退货单停在状态 2，页面显示"待返货出库"）。三个与销售出库不同的点：① **跳过复核与打包**——`warehouse-tasks.pick.js` `readyToShipWithinTransaction` 把 `purchase_return | sale_return_out` 统一当 `isReturnOut`，拣货完成目标状态直接是 `WT_STATUS.SHIPPING`，只有 `sale_out` 才进 `SORTING`；② **没有包裹与物流箱码**，PDA 扫箱码出库那条路扫不到它，改由独立待出库列表 `GET /warehouse-tasks/return-out-pending`（`task_type IN ('purchase_return','sale_return_out') AND status=待出库`，叠加用户仓库范围与**绑定设备仓**过滤，权限 `WAREHOUSE_TASK_SHIP`）由仓库点着出库；③ **重复取消是幂等**——`returns-sale.service.js` `enterSaleReturnReverse` 先按 `task_type='sale_return_out' AND return_id=? AND status NOT IN (已出库,已取消)` 查既有单，命中即原样返回 `{pendingReverse:true, taskId, taskNo, alreadyRequested:true}`，**不返回 409**（一张退货单只允许一张进行中的返货单，重复点击属幂等重放）。**会计全程一分不动**：可取消的退货单只有状态 1/2，此时应收**从未冲减**、退货凭证**从未生成**（引擎取数条件 `sr.status = 3`），所以**既不加回、也不冲减**——加回（+）会**多收**客户、收入虚增，再冲减（−）会**少收**客户、收入虚减；应收保持未冲减的全额才与"货退回客户"的事实自洽。`ship.js` 的应收重算由 `sale_order_id` 驱动，返货该字段必须为 NULL（非空直接 500，不静默），天然不进入重算。返货出库明细按行关联 `sale_return_items` 取退货单价（迁移 `262_warehouse_task_item_sale_return_link.sql`）；PDA 拣货推荐按 `taskType` 只展示本任务预锁的原批次容器（`onlyLockedByTask`）。自动化证据：`tests/sale-return-cancel-guard.smoke.test.js`、`frontend/src/api/warehouse-tasks.return-out-paging.test.ts`；**PDA 真机尚未验证；浏览器返货卡片已于 2026-09-27 实测通过**（`ReverseTaskCard` 挂进退货详情页渲染树，`tsc -b`/eslint 过，并在独立可弃验收库里对真实单据走了一遍「部分上架 → 取消 → 看卡片 → 重复取消幂等提示」，验收后该库已重建为干净迁移态）。设计见 `docs/sale-return-reverse-flow-2026-09-26.md`。
- **调拨**：列表批量返回本页已授权单据的逐行计划、已出、已收数量，不做逐单N+1；在途且任一行尚未出完时，PDA列表保留源仓出库入口，全部出完才隐藏。源仓扫码出 → 在途 → 目标仓扫码入；在途不可普通取消，异常走有独立权限的 force-close。正常完成须每行计划量=已出量=已收量且无在途容器，部分发收不能提前结束。重复商品行合法，整箱按商品合计余量校验，再按行 ID 用百分之一整数单位分配；不拆实物容器。创建、读写沿用至少一端在用户仓库范围的跨仓规则。扫码 action 为 `transfer.scanOut.<id>` / `transfer.scanIn.<id>`，执行及重放先验单据、仓库范围和设备仓；旧固定 action 只兼容资源归属一致的回执。自有回执查询保留权限调整后的读取契约，不等同于再次执行权限。
- **盘点**：账面读取 ACTIVE 容器；提交前整单检查账面漂移，任一漂移拒绝整单，刷新账面会清空对应实盘值。差异调整走引擎。
- **商品快照**：已有业务快照读快照，无快照的过程表按既定 JOIN 读取主档。`article_number` / `articleNumber` 语义为供应商型号，不恢复随机生成；`spec` 为系统型号，不能因改展示名擅改历史列名。

- 履约及时性（2026-09-12）：关键业务提交成功后以 `commitFulfillment` 合并通知，在事务外按有界批次刷新本单及相关销售供应依赖；回滚不通知。删行或改仓前在事务内捕获旧商品/仓库维度，提交后同时通知旧供应依赖；每单最多保留 500 个维度（读取第 501 项检测截断），截断计入 `snapshotOverflow`，不能为获取快照提前到授信所需客户锁之前。单据和库存维度提示共享 1,000 项有界队列，相关单据分批推进游标；普通依赖刷新不得重置已有展开游标。原 30 秒周期游标扫描保留为重启/丢通知兜底。队列的积压和处理时间决定实际延迟，不承诺全量单据每秒完成。业务交期与事项人工处理期限分开，不因刷新擅自覆盖人工期限。查询和事件职责从 service 拆出并保留兼容导出。待办显示业务单号、往来方及仓库，支持单据类型和关键词筛选；状态/类型按用户保存在本机，关键词和业务数据不持久化，返回原工作区保留筛选和滚动位置。详见 `docs/fulfillment-refresh-2026-09-12.md`。
- **数量精度（迁移 254/255）**：数量存储和执行的最小单位是 0.01，所有数量列统一 `DECIMAL(_,2)`。用户原始数量超过两位有效小数必须以 400 `QTY_DECIMALS_EXCEEDED` 拒绝，不能先四舍五入后保存；`1.230` 等尾零可接受，机器浮点运算噪声不当作第三位输入。录入单位数量和未经取整的基本单位换算结果都先校验；确认合法后才用 `unitConversion.roundQty` 归一化执行中的累加、差额与状态判定。`allow_decimal_qty=0` 另外按基本单位拒绝非整数（`QTY_INTEGER_REQUIRED`）；收货、退货质检、扫码盘点逐箱/逐项检查，禁止以合计整数代替。录入模块共用 `foldEntryItems()`；占库、释放、发货、拆分、装箱、退货和拣货执行入口也独立校验。安全库存、补货点、目标库存、采购包装/MOQ与计划调整量遵循同样约束。采购单及 PDA 拆分原有更严格的整数录入规则保留。金额、单价、授信和单位换算率保持原精度，不套用数量校验。迁移 255 曾按用户要求将存量数量四舍五入到两位，已执行迁移不改写。守卫：`npm run test:qty-precision`、`npm run test:qty-precision-coverage`；实际 MySQL 拆分守恒及迁移重放：`npm run smoke:qty-precision`。修改精度仍须逐项核对全仓 `10000` 的乘除含义，避免误改金额、百分比、超时与分页上限。

### 采购预测预览的跨页一致性（2026-09-23）

`GET /inventory/procurement-plan` 首批仍完整读取授权来源仓，计算跨仓净需求、保护来源仓自身需求的调拨候选，并按既有规则排序；续批必须携带首次返回的 `snapshotId`。预览结果绑定当前用户 ID、当前仓库范围、筛选参数和批次大小，只有完全匹配才可复用。分页不再次执行预测计算，内部采购计划生成、转单及实时校验仍调用事务内 `getProcurementPlan`，不得复用预览。

预览有效期固定 120 秒，访问不续期；每进程最多保留 8 份、累计 20,000 行、16 MiB 序列化 Buffer，超预算先淘汰最早结果；每 30 秒清理过期结果，读写时也清理。单次预览最多读取 20,000 个来源商品×仓库维度，超限或序列化结果超预算明确返回 413，要求缩小筛选。过期、淘汰、缺少续批 ID、进程重启/跨实例丢失或身份/范围/条件变化均返回 409 `PROCUREMENT_SNAPSHOT_RESTART`，要求刷新重读，不能悄悄重算后拼接。内存预算限定常驻预览数据；首次实时计算及单页解码仍有临时内存开销。

### 2026-09-23 销售与盘点审计修复

- 销售部分发货结案按已发量乘基本单价并逐行 `round2`，再汇总，与建单/改单行金额口径一致；不改变折扣比例或已收款记录。
- 草稿保存通过稳定请求键及单据 ID、载荷指纹防重；相同保存重试不重建明细、不重复写事件。后续内容不同的编辑仍可保存。
- 盘亏提交不得侵占现货预占；扫码账面中的拣货锁定容器不会作为实际盘亏扣减。实盘记录可保留，阻断只发生在落账提交。

### 请购转采购（2026-09-29）

- **转单只生成采购单草稿**：`POST /purchase-requisitions/:id/convert`（`convert.from=[3]`，需 `purchase.requisition.convert`）按 `supplierId` **分组各建一张 PO 草稿**（`source_requisition_id` 回指请购单），写 `purchase_requisition_conversions` 并累加 `purchase_requisition_items.converted_qty`；**全部明细转完**才 `3→6` 结案。**只建草稿、不入会计**（不生成凭证、不记账）。
- **可转余量是硬闸门**：每行 `转采购数量 ≤ (quantity − converted_qty)`；重复执行同一意图**不会**突破该闸门，但会在余量足够时**多建一张采购单**（这是重复执行的后果，**不是**超量）。
- **幂等靠请求键，不靠载荷比对**：`beginOperationRequest` 以 `action = purchase.requisition.convert.<id>` + `X-Request-Key` 判定重放；**同键重放返回原回执**（不再次建单、不再次累加），**换键即视为新请求**。因此前端必须在**同一次转单意图内保持同一个键**，只有拿到**确定结果**（成功 / 明确 4xx）才轮换；超时、断网、**服务器 5xx** 一律保留（见 `docs/frontend-pda-conventions.md`）。用户**改了转单内容**再提交属新意图，但若上一次**结果未确认**，必须先查回执（`/api/system/request-status/:key`）再改，否则后端会沿用上次内容、用户误以为新内容已生效。
- **真实证据（2026-09-29，隔离库）**：受控代理实现「后端 200 后丢弃响应」⇒ 前端出现「未确认」提示条、原样重试后**只有 1 张 PO、`converted_qty=5`**；随后**主动**再转剩余 5 ⇒ 正常建第 2 张 PO、`converted_qty=10`、请购单结案（**未因幂等挡掉合法后续转单**）。修复前同场景实测**重复建 2 张 PO**。

### 成套配件基础切片（C2b-1，2026-10-01）

套件是独立商业组成版本，不是虚拟库存商品。C2b当时只维护主档、版本快照及 `POST /api/kits/preview` 的只读组成/分摊/当前现货解释；后续销售保存与履约见本文件下方C2段。套数量为正整数；版本默认分摊依据锁定**明确提交组成时**的商品 A 价×每套基本量，亦可整套明确指定非负权重；商品日后改价不会重算历史版本，单独修改套报价沿用原参考依据，需明确重新提交组成才能更新默认依据。createdAt是版本创建时间，未保存原始采样时刻，referenceSnapshotAt为空。金额以独立商业组保存归属，物理需求按真实商品和仓库汇总；同商品作为普通行另卖时仍有独立商业组。

A套100、B套200共享铰链1/螺钉4且权重80:20 ⇒ A组件80/20、B组件160/40，物理铰链2金额240/螺钉8金额60，总300；加普通铰链1金额30 ⇒ 商业组三组，物理铰链3金额270/螺钉8金额60，总330。套组父金额按原四位单价×原两位数量定点 half-up 到分（kit `1.005×1=1.01`）；ordinary商业组沿原entry fold round2预算（`1.005×1=1.00`），既有普通销售规则未改；组件金额按整数分分配尾差，合计守恒。库存判断只说明本次整个向量的**当前现货可用**，不能把每种套的独立可成套数相加；例如只有铰链1/螺钉8，每种套单独各可参考1套，同时选择两套仍缺铰链1。该结果不是 ATP 承诺、可拣保证或交期。缺件只发完整套与按原订单组件分摊价退款的政策已确认，其订单/出库/退款在C2b当时未启用，后续接点见下方C2段。

finder 的单套现货参考先将投影的 ACTIVE 实物量与预占量分别转成两位数量的百分整数单位，相减后除以每套组件的百分整数单位；不对浮点可用量直接除法取整。实际现货0.30、每套0.10时参考3套，销售预占0.20后参考1套，与同一状态下预览一套零缺量一致。公共库存引擎与普通销售数量规则未改。

### 商业行分批金额与来源组件退款纯规则（C2c-1，2026-10-01）

`sale.commercial-money.math.js` 只提供无数据库、无状态的金额投影；C2c-1当时未接入正式套单保存、占库、派发、出库、退货或会计，后续接点见下方C2段。现有普通销售路径不调用它，折扣、税、付款、成本与期间规则保持原有实现。

三个接口：`projectCommercialCumulative(snapshot, quantity)` 投影累计金额；`projectCommercialBatch(snapshot, {beforeQty,afterQty})` 返回累计差额；`projectCommercialRefund({sourceAmount,sourceQty,beforeQualifiedQty,afterQualifiedQty})` 返回本次及累计退款。快照固定为 `{kind,originalQty,unitPrice,grossAmount,components:[{id,sortNo,allocatedAmount}]}`，组件按冻结 `sortNo/id` 顺序解释，不修改输入。组件 ID 是可安全表示的正整数、顺序是可安全表示的非负整数，数值相同的字符串 ID 视为重复。组件 1–50 个，ordinary 恰好一个真实商品组件；本纯函数只验证结构与金额，不查商品主档。

套行原量 Q 与累计 q 为整数套，原四位套价 P 冻结，父累计分额 `T(q)=halfUp(P*q,100)`（P 为四位整数单位）。ordinary 新商业行使用原基本百分量 Q/q 与录入单位数量×录入价折算后冻结的毛额 G：`T(q)=halfUp(G*q,Q)`；可携带展示单价，但不读取它。例：1箱3件成交1元，近似基本单价 `0.33333333` 不决定收入，累计1/2/3件为0.33/0.67/1元。套价0.0049、原2套共0.01元，累计1套仍为0，不能把原毛额比例舍入成0.01元。

组件预算 Ci 的和必须等于 G，套行还必须满足 `T(Q)=G`。分配采用单调循环槽：`b=G div Q,m=G mod Q,E(q)=T(q)-b*q`；先按父累计是否产生额外分，依次访问高槽 `[0,m)` 或低槽 `[m,Q)`。每组件每槽先分 `Ci div Q` 分，再按冻结组件顺序把 `Ci mod Q` 个尾分布置在循环槽范围。闭式前缀计数 `F(t,q)` 为 `t<=m ? min(t,E) : E+min(t-m,q-E)`，跨 Q 的范围拆为两段；全程 O(组件数)，不枚举 Q。累计各组件非负单调、累计和为 T(q)、最终等于各 Ci；本批为累计后减累计前，因此本批分额也非负且和等于父本批。零预算不取得尾分。旧累计组件前缀比例相减不满足单调：Q=3、Ci各1分，第二组件累计0/1/0/1，第二批负1分，已作为反例守住。

退款只接受该来源组件原已确认金额 B 与实际已发基本百分量 D>0，以及调用方提供的累计合格退量 x：`R(x)=halfUp(B*x,D)`。本次退款为累计差额，最终合格退完等于 B；1分/3件分3次退的本次退款为0/1/0分。A套来源铰链金额80、实发1件，退1件退80，不能用A/B合并实物均价120。零预算组件可以合法退实物并退0元。草稿、取消、拒收数量不由计算函数推断或维护。

内部复用现有无数据库 `decimalUnits/halfUp`，不先把 DB decimal 字符串转 Number。输入支持符合精度及范围的有限 JSON Number 与 DB 普通 DECIMAL 字符串；字符串长度≤128，科学表示字符串指数明确限±100，沿用原纯解析器边界，不额外归一化放宽。即使数值为零，字符串 `0e101` 仍409拒绝；JSON解析后的有限 Number `Number('0e101')=0` 正常接受。内部快照不需要超长科学表示，避免扩大数字格式维护范围。金额两位、套价四位、基本量两位；有效位超精度、负数、非数值类型、NaN/Infinity、格式或数值超界、快照预算不符或区间逆序统一409 `SALE_COMMERCIAL_MONEY_INVALID`，尾零可接受。套价≤99999999.9999、基本量≤9999999999.99、毛额与分额≤9999999999.99；输出是安全 Number 的 `grossCents/grossAmount` 与 `{componentId,amountCents,amount}`，退款为 `refundCents/refundAmount/cumulativeCents/cumulativeAmount`，不把 BigInt 放入 JSON。业务接入必须在同 conn 锁来源、当前读真实已发及合格退量并冻结执行回执，不重新排序或改历史退款；这些业务锁与持久化已由下方C2接点实现，纯计算模块不维护它们。

### 2026-10-01 C2 成套销售后端履约与原批次退货

正式销售沿现 `/sale` 接口支持 `commercialModel: 'kit-v1'`。套定义首版是固定组成、每套基本单位数量、单仓整数完整套数；不替代、不嵌套、不制造、不跨仓拼套。ordinary 混排仍按原辅助单位 fold 规则：默认/客户价是基本单位价，先乘权威换算率成为录入单位价；手动价是原录入单位价。ordinary 预算冻结原 `entryQty × entryUnitPrice` 的 round2 金额，基本量及八位展示价不倒算预算；套父成交额用定点 half-up。未配置零参考报价可只读预览，正式父成交价必须正数，组件分摊零金额合法。

成交组保存原版本、原数量、原报价依据、原毛额与组件预算；合法减量只改 target，并按累计投影取得当前额。增加、改价或改组成保存新快照。未变旧组保留原停用/旧版本与手动成交依据；草稿换客户时，ordinary 非手动价按新客户重新解析。真实商品同仓仅一条 stable sale_item_id 物料行，组件直接引用它；预占、预计绑定、采购与 WMS 只使用这一份基本量。历史物料行保 ID、实发与成本/退货引用，移出当前需求时 quantity/amount 为0，不删除证据。

派发按成交组与数量汇总共享组件，缺任何组件不发不完整套。派发归属不是收入；正常拣货、分拣、复核、单商品装箱、打包/打印确认后，实发事务重读本批 WTI 与成交映射，完整数量闭合后扣真实容器，WT转7并固化原成本、冻结本批成交金额，再同步实发与应收。任务创建先后不决定金额尾差。授信仍按原整单未收敞口；成本沿真实唯一物料行原 cost_snapshot，每个真实 WTI 只计一次。

零实发取消保留原成交目标与金额历史，取消状态退出需求。已拣实物尚未归还的 kit 保留对应预占，未拣部分释放；正常 PDA 退回后才释放剩余。这是套单的明确例外，普通单原取消 reserved/dispatched 清零规则不改。部分实发关闭剩余把当前目标与头额投影到真实已发成交组，保留 original 快照、IDs 和退货来源。执行改单仍受原单仓、零实发、单执行任务限制；挂起物理归还时不能再次派发/实发，真实 PDA 归还后才清理预占与 WTI 数量。

套单退货必须明确原真实 WT7 配件来源，按 source 和 stable 物料行双重申请余量约束。同一退货单同SKU同仓首版只允许一个 distinct(组件,原出库批次)，跨来源分单；PDA 原 FIFO 与容器仅绑定退货任务的能力保持。草稿/确认/未完成取消及返货出库不冲应收。实际质检合格且入仓完成时冻结累计退款毛额；全拒收也正常完成并记录0。

退款来源毛额预算与实际账款减少分列。首次真实实发冻结原整单 gross/discount，后续沿同一依据，关闭剩余不改该依据。新套单反向复用原 calculateDiscountApplied 的整单比例差分，按累计已退毛额取得四位实际 financial_amount；100/10全退保存 gross100、实际减应收90。预计退款用保守上界，确认资金预判封顶同次读取的真实账款 total_amount；实际完成不截断，仍由原行锁资金闸门检查已付金额。净退款凭证按同单实际执行 receipt ID 顺序累计 financial4，再用原 half-up 作两位累计差分，避免两次 .005 各冲 .01；0收入冲回仍保留真实成本冲回腿。普通单退货/折扣/资金/期间规则不改。

履约日期沿既有批量供应分配，成交组消费同一份共享组件分配；齐套日取所有组件已知日期的最晚值，缺日期返回 null 及解释。现货参考不承诺可拣。报表/导出沿当前头额与唯一物料行分摊金额，不把成交父行与组件重复加总，不新增利润算法。

C2规格复审收口保持业务规则：退货完成看全部真实明细的当前收货/质检/合格入仓事实，不能因等待前快照让实物已齐而任务卡住。两组件合格入仓与两组件全拒收均收口，普通销售使用相同可靠性门控；没有增加可写数量事实或修改QA合格规则。套单历史quantity0物料仓库仍属于资源范围，不能用移到允许仓的新payload绕过原保留仓的授权。

C2品质复审补齐散件取消归还口径：I码散拣锁整容器，但取消需保留的量是本任务有效PICK记录的实际量，不是容器全部余量。预占5、容器余10而只拣1，取消先释放4，正常归还该容器只释放1；两个容器各拣1时，第一份归还后仍保留第二份的1。归还记录也保存该实际拣货量，原库存实物不扣减，另一销售单的预占不受影响。缺少有效PICK、来源不符或本单预占不足均整笔拒绝回滚，不能以容器余量猜测或截断释放额。普通单取消立即清零预占和原归还记录余量规则保持。

C2归还权限复审：销售员按整单范围发起取消，PDA员工只执行自己仓库任务的实物归还。套单头仓与本任务仓不同时，只要当前用户可操作本任务仓且真实设备绑定仓相同，合法归还可执行；销售单详情仍可能因整单范围403。归还中的销售单锁只协调预占，不授予查看或修改销售单权限，原数量/库存/账款规则不变。


### C2 只读派发与归还事实接点（2026-10-02）

`GET /sale/:id` 对 kit-v1 的 `commercialGroups[]` 新增 `dispatch`：`confirmedShippedQty` 只累计有 `confirmed_at` 且真实销售出库 WT.status=7 的派发数量；`outstandingQty` 只累计 active=1、WT非取消且未软删的未确认派发；`activeAllocatedQty` 完全沿原 dispatch.select 的 used 口径（active=1、WT.status<>8、未软删，**包含已确认**）；`availableQty=targetQty-activeAllocatedQty`。这些数是既有派发事实的只读投影，不是新的数量/收入账，也不代表已取消或待归还的订单可以再次派发，仍须满足原状态/版本/挂起闸门。

组内 `dispatch.facts[]` 及单头 `commercialDispatches[]` 返回同一事实：`dispatchGroupId/groupId/taskId/taskNo/warehouseId/taskStatus/quantity/active/confirmedAt/confirmedShipped/outstanding/allocated/taskDeletedAt`。单头集合另保留已经 superseded 的 inactive 未确认历史行；当前组投影不把旧版本撤回事实计为本组额度。执行期改单的 `replaceUnconfirmed` 把旧组 active 置0并在同WT插入新组；WT后来实发7时，旧inactive且未确认行仍只作撤回历史，不能计为已发、待执行或额度。真实已确认历史不因 active=0、任务软删或关闭剩余而消失，确认事实却没有 WT7、active未确认却WT7、跨订单/仓库或缺关联均 409 `SALE_COMMERCIAL_DISPATCH_SOURCE_INVALID`，不截断数量、不按共享物料已发量猜套归属。新增事实查询只有一个批次；原头仓和全部 stored physical 行（含 quantity=0）的范围核对在商业 DTO 暴露前执行。普通销售详情不新增商业字段。

`GET /warehouse-tasks/:id/cancel-return-detail` 对来源 kit-v1 的容器新增 `taskReturnQty/remainingQty/quantitySource:'active_pick'`。`taskReturnQty` 来自当前任务仍锁定容器的 `COALESCE(scan_purpose,1)=1` 实际 PICK 汇总，并核 own WT/item/container/product/warehouse、ACTIVE未删实物、正数量、容器余量和任务 picked_qty；不从 I 条码余量推归还份额。原 `qty` 仍为整容器 `remaining_qty`，普通单 DTO 不新增这些字段，盒/普通原写规则不改。只读份额只解释任务归还，不扣 I 库存、不加台账、不改变取消/释放数量；缺源/串 item/超量继续 409 `SALE_COMMERCIAL_PICK_SOURCE_INVALID`。批量读 items+PICK，不加 FOR UPDATE/FOR SHARE；仓库范围仍按当前 WT，不额外要求 SO 头仓。
