# 统一销售开单恢复与现场验收

## 原因与实现

用户发现销售列表仍有「新建销售」和「开单方式」。当场核对发现 main 基线 `66fa87e` 未包含原隔离工作树的 `97bff81`（成套商品资料）与 `d54dac6`（普通与成套统一开单）。清理本地分支时保留了独有提交和 detached 工作树，但没有将这些实现整合到 main；开发预览切到 main 后显示旧流程。这是工作树集成遗漏，并非用户此前没有确认统一入口。

本增量将这两份已确认实现的 54 个文件与 main 现有未提交界面改动逐文件三方合并。三处冲突分别保留两批文档、成套资料来源错误提示和本轮可读错误文字角色。其余工作区文件及暂存区保持原状；没有创建分支、提交或推送。

采用 impeccable 的 distill 与 clarify 方法：销售列表只有一个主动作「新建销售」，同一张表单可添加普通商品与成套配件，不要求员工先选择开单模型。纯普通明细转换为原普通销售 DTO，含成套明细走既有 `kit-v1`；保留原数量、报价、折扣、仓库范围、幂等与结果恢复规则。原 `/sale/new-kit` 是历史链接兼容入口，没有常驻列表按钮；历史普通编辑、改单和处置来源保持原调用。

## 本地库字段偏差

自然失败为 `Data too long for column 'remark'`。隔离副本继承原开发库的 `sale_orders.remark VARCHAR(30)`、`receiver_name VARCHAR(5)`、`receiver_phone VARCHAR(11)`、`receiver_address VARCHAR(30)`；既有迁移 007 定义备注为 500，078 定义收货姓名/电话/地址为 100/50/255。迁移的 IF NOT EXISTS / 只补缺列不会修正既有窄列。

本轮在已有归属及 UUID 校验、私有备份后，仅将隔离副本这四列对齐现有定义；未增加或修改业务迁移、未缩短员工输入、未修改原库。恢复成套资料需要的既有迁移 282 也只执行于副本，重复执行幂等通过。原开发库的字段偏差仍在，生产形状未核实；后续环境治理应独立核对，而不能据本轮副本结果声称其他库已修复。
