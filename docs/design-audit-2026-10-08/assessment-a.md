## 整体印象与反模式判断

系统已经有足够成熟的产品界面骨架，问题是使用骨架不彻底。最有价值的重构不是再造一套设计语言，而是让每个列表和每次提交遵守同一套可见状态、来源身份和草稿保护合同。

源码及代表页面共同展示克制的工具界面：中性色背景、单一蓝色主操作、语义色状态、固定字号和密集数据表。`frontend/src/index.css:4`、`components/ui/button.tsx:7`、`components/shared/PageHeader.tsx:13` 支持这一判断。现场未出现需要归为“明显 AI 生成外观”的特征，已有界面更像长期演进的 ERP 产品。供应商退款的动作位置、裸表格、原生选择器和连续约束说明确实脱离了其他页面组件语法；合理的资金边界说明应保留，但应重排层级。

## 优先问题

### A1 [P1] 读取失败被列表画成“暂无数据”或继续显示旧数据

**证据。** `purchase/index.tsx:94`、`returns/index.tsx:86`、`refunds/index.tsx:48`、`finance/accounts/index.tsx:111`、`finance/transactions/index.tsx:154`、`accounting/vouchers/index.tsx:348` 均只取数据和加载状态；最终直接渲染 DataTable。客户同样只取 `isFetching`（`customers/index.tsx:68`）。`PaymentsView.tsx:98` 已读 `isError`，但 `:190` 仍无错误分支。DataTable 在非加载且空数组时只显示 `emptyText`（`:250`）；它不能替页面解释 API 失败。退款详情 `RefundDetailDialog.tsx:28` 与 `:147` 没有失败/重试呈现。

**用户影响。** 财务用户无法区分“没有待收款”与“没有读取成功”；采购用户容易把错误当无单。已有缓存时又可能把旧行当刚核对的事实。全局 toast 是瞬时反馈，不能替代持续的页面状态与可重试入口。

**现场确认。** 合成全权账号访问 `/refunds` 实际收到 API 500，加载结束后页面显示“暂无数据”和“共 0 单”，没有持续错误区或重试入口，见 `screens/before/a-refunds-error-empty.png`。这是实际失败呈现，不能以该页没有生成退款数据解释。主任务另行核实了后端限定仓库 SQL 拼接错误；本报告不改后端、不将该错误归为 UI 引起，也不将后端错误与本项 UI 缺少状态混为一个修复。

**最优已有模式 / 修复。** 采用销售列表 `sale/index.tsx:290` 的 `QueryErrorState`，为列表和详情分别提供重试。按用途决定旧数据能否保留，但明确标示旧数据，并在未新鲜核验时暂停写动作和来源交接。总数未读成功不应无条件显示“共 0”。不得改全局重试与缓存来掩盖页面缺状态。

**验收反例。** 首次读取 500、已有数据后刷新 500、离线暂停、详情单独失败、手动重试；每个页面都必须能看出“失败/旧数据/真实空结果”。建议命令：`harden`。

### A2 [P1] 供应商退款把用户识别任务转成记忆数字 ID，与客户侧交互标准脱节

**证据。** `supplier-refunds/index.tsx:31`–`:35` 仅列退款号、原采购退货 `#ID`、金额、日期和状态，无供应商、搜索、日期/状态筛选或专门操作列；客户 `refunds/index.tsx:75`–`:109` 列客户、销售单、创建时间、查看/处理，并提供查询。供应商详情 `RefundDetailDialog.tsx:57` 使用原采购、账户、付款分配数字 ID 及长段落；其创建页 `CreateRefundPage.tsx:49`–`:54` 使用裸 table、原生 select/type=date，并把原行编号与约束说明连续并列。DTO `types/supplier-refund.ts:58` 本身只给 supplier_id 等 ID，没有可直接使用的名称/来源单号展示字段。路由 `routeDefinitions.ts:516`–`:541` 把两个退款入口分在“资金往来”和“往来账款”。

**用户影响。** 同额多笔退款难以识别，财务人员需要往返原采购退货核对对象；新用户无法仅凭“退货退款单”识别客户侧。重要金额、资金状态和来源身份被内部信息压在同一层级。

**最优已有模式 / 修复。** 统一两页 PageHeader 的对象说明、查询位置、状态组件、四态动作位置和来源身份语法。供应商列表需要后端提供已授权的人类可读身份与筛选字段，禁止前端按名称拼关联或请求当前主档冒充历史身份。详情用同样的概览/来源/分配/结果层次，金额对齐、原单号可识别，技术身份按需展开。主行动仍分别为“执行退款”和“登记实际已收到”，保持原恢复存储及原请求身份合同。将两个入口收在一个用户能理解的退款分段，并使客户侧对象明确。

**验收反例。** 同供应商同额两笔、缺历史名称、长单号、无完整查看权、已到账但凭证待核对、补录待审批；不得把缺名字或失败读画成可执行的新鲜来源。建议命令：`clarify`、`layout`、`harden`。

### A3 [P1] 无写权限用户仍看见可填写并提交的写入口

**证据。** `BaseCrudPage.tsx:88` 默认 `canCreate=true`，默认编辑/删除列也没有对应权限参数。供应商页 `suppliers/index.tsx:96`–`:119` 未传 `canCreate`，新增/导入/编辑/删除均可见。客户页对新建与导入守 `CUSTOMER_CREATE`（`:120`），但编辑、绑定价格和删除仍不守各动作权限（`:101`–`:109`）。采购列表 `purchase/index.tsx:326` 的新建也不守权限；销售对比 `sale/index.tsx:262` 有 `SALE_ORDER_CREATE`。后端客户/供应商 routes 分别在 `customers.routes.js:37`–`:39`、`suppliers.routes.js:40`–`:42` 使用独立 create/update/delete 权限。

**用户影响。** 只读员工花时间填写后遭拒，界面暗示的岗位能力和服务端能力不一致。这是可用性问题；源码证据不意味着后端越权。

**最优已有模式 / 修复。** 使用现有 `usePermission`，逐动作守真正的 create/update/delete/price 权限。只读仍保留详情与合法往来查询。共享骨架不要用一个 `canCreate` 代替所有写权限，也不要默认“能进入列表就能编辑”。

**验收反例。** 仅 view、view+create、view+update、view+delete、仅合法往来查看、打开后撤权；可见按钮、弹窗和提交时检查要一致。建议命令：`harden`。

### A4 [P1] 提交在途时可以关闭、重开另一草稿，旧成功回调会关闭新工作

**证据。** `BaseCrudPage.tsx:100`–`:105` 成功统一 `setFormOpen(false)`；`:167` 的关闭回调和 `:183` 的取消按钮均未按 `saveMut.isPending` 阻止关闭，`:119`–`:121` 可换编辑对象。客户退款创建 `refunds/index.tsx:162`–`:173` 成功后无目标检查即 reset/onClose；`:182` Dialog 的 onOpenChange 在提交中仍 reset/onClose。按钮的 pending 禁用没有覆盖 Esc、遮罩关闭等路径。相对而言，客户退款详情 `RefundDetailDialog.tsx:120` 已按 actionLocked 保护关闭，供应商写流程保留完整原请求和当前身份。

**静态反例。** 保存供应商 A → 关闭弹窗 → 打开 B 并输入 → A 返回成功 → 共享 onSuccess 关闭 B。创建客户退款 A → 提交 → Esc 关闭 → 重开输入 B → A 成功 reset B。此反例由控制流建立，本阶段未在浏览器触发，不能写成实测事故。

**用户影响。** 用户未保存工作被旧请求结束动作破坏，可能误以为 B 已保存；“页面切换保留草稿”的承诺失效。

**最优已有模式 / 修复。** 提交期间对所有关闭通道给出一致锁定；若业务允许离开，应捕获原提交目标并在成功回调核验活动与草稿身份，只处理原对象的回执，不能自动清新草稿。保留失败输入。先不改变后端资金或幂等语义。

**验收反例。** 延迟成功/失败、Esc、遮罩、取消、隐藏页、A→B→A、工作区切换；需测试旧结果不清新输入。建议命令：`harden`。

### A5 [P2] 同类表单和子视图的可访问性合同不一致

**证据。** 客户退款新建 `refunds/index.tsx:187`–`:211` 的可见 Label 没有 htmlFor，Input/SelectTrigger/DatePicker 无对应 id 或 aria-label；供应商主档 `suppliers/index.tsx:168` 已关联 Label 与控件，供应商退款金额 `CreateRefundPage.tsx:53` 也明确 aria-label。账款“按单登记/核销”切换按钮 `PaymentsView.tsx:169`–`:181` 没有 aria-selected/current、tablist/tabpanel 或键盘横向移动；单据详情 `OrderDetailSections.tsx:66`–`:75` 已提供完整实现。发票 `invoices/index.tsx:193`、`:198` 的编辑/删除主要依赖 title 名称，仍应核浏览器可访问树与可见提示。

**现场确认与扩展。** 客户退款创建的可访问树实际出现无名称的 spinbutton、combobox 和备注 textbox；资金账户创建也出现无名称的类型、期初余额和若干文本控件，其源码 `finance/accounts/index.tsx:260`–`:292` 同样缺少 label 关联。对照客户/供应商主档创建和设置编辑，相关控件均有明确名称。这个结果证明了可访问名称缺口，不等于已完成读屏实机验收。

**用户影响。** 只用键盘或读屏的用户在同一系统里无法复用相同操作习惯；视觉字段名不一定是控件可访问名称。

**最优已有模式 / 修复。** 引入稳定 useId 关联标签/控件与错误说明，切换控件统一为真正 tab 模式或带 aria-current 的导航，采用现有 `OrderDetailSections` 的键盘合同。图标动作有可读名称，窄视口验证焦点与滚动。不要用 wrapper 上统一 aria-label 代替各控件名称。

**验收反例。** 键盘完整走退款创建、Tab 能辨字段、读屏辨当前账款子视图、方向键/Home/End、一倍和两倍缩放。建议命令：`audit`、`harden`。

## 认知负荷与情绪旅程

**认知负荷。** 销售列表页头最多同时包含导出、查询、新建、开单方式四个入口（`sale/index.tsx:255`）；采购同样四个（`:315`），不是单凭按钮数量就判定过载。真正负担来自供应商退款在一个分配行里同时显示原分配 ID、付款单号、日期、原本金、剩余额度和金额输入（`CreateRefundPage.tsx:53`）。应让用户先识别付款单与可退款额，再输入金额，其余证据渐进展开。供应商详情应把“已收款”“凭证待核对”和“尚未收款”放在清晰位置，不混在连续解释段落。

**情绪谷底。** 只读用户填完整个表单才遇到 403；财务列表失败却是“暂无数据”；刚输入新草稿被旧请求关掉。这些会让用户怀疑自己的工作和资金事实。最好的安心点已经存在：原回执恢复明确“上次提交是哪一笔”、来源缺失人工核对、成功提示区分申请提交与资金已记账。重构应让这种严谨语义变得容易读，不能删掉资金事实边界去换简短成功 toast。

## Persona 红旗

- **Alex（熟练经办人）**：供应商退款列表缺关键词与对象列，核对多笔同额退款需往返原退货；相比客户侧多出无必要记忆步骤。账款子视图切换未沿用现有键盘标签合同。
- **Sam（键盘 / 读屏用户）**：客户退款创建多个可见字段名未关联控件；账款页当前子视图状态不可从属性获知。表格列宽已有键盘实现是积极参考，不能在样式改造中退化。
- **Riley（主动测试边缘的用户）**：保存后迅速换目标会撞上 A4；读取失败与空结果混淆；供应商退款多重读/写权限组合与普通页面写入口呈现不一致。

## 次要观察与需避免的错误统一

- 标题与动作词可收敛：“新增/新建”“详情/查看/查看处理”“时间/创建时间”现在分散。先定义语义，再统一文案；“查看/处理”要随实际权限选择恰当动词。
- 对应表格金额口径应可见。成套销售退货 `returns/index.tsx:237` 的“预计最多冲减”只在 title 中；非悬停用户不会知道草稿金额尚非最终财务事实。
- `DataTable.tsx:163` 的“选择当前页全部行”与多数页面取消分页、取齐结果的语义不一致；应按当前实际选择集合表达。实际作用仍是传入数据中可勾选行（`:58`）。
- 客户页筛选栏与底部两次显示总数（`customers/index.tsx:128`、`:159`），供应商只底部；这类冗余可作为 polish 的后续项，不应优先于错误态和草稿安全。
- `QueryFormLayout.tsx:6` 固定两列，供应商主档 `suppliers/index.tsx:161` 固定两列，客户退款详情 `RefundDetailDialog.tsx:149` 同样两列。尚不能仅凭源码宣称窄窗口已经溢出；需在浏览器确认窄视口、长字段和两倍缩放后决定结构断点。
- 金额两/四位、符号有无、客户授信/供应商提前期、PDA扫码默认不聚焦、真实到账与待审批、资金已记账与凭证待核对均是业务差异，不能用一个通用“标准化”开关拉平。
