# 发版流程优化方案（2026-09-22）

状态：按用户最新免费优先偏好，实施可选本地自动中转，准备 v0.10.4 实测。OSS 未开通且暂缓；下文长期架构建议不代表全部已实现。

## 依据与目标

v0.10.3 最终应用提交到完整收尾为 29 分 44 秒，首次启动到完成为 1 小时 34 分 48 秒。除跨境传输，还出现生产 Python 兼容、页面门禁路由与真实应用不一致、GitHub 草稿查询问题。原 tag 工作流失败后，经原包补发布完成，不能记为一次全绿。证据见 [发布结果](release-v0.10.3-result.md)。

目标（按用户后续指示修订）：不以 15 分钟限制选型，优先保证发布可靠、无人值守、可恢复及维护成本可控。耗时作为观测数据，排队、冷缓存、大迁移与故障恢复均保留，不能通过换起点隐藏问题。阶段超时仍须有界，且保留迁移与回退安全窗口。

## 本轮采用：不新增付费云资源

GitHub Actions 构建 → 本机既有代理下载原始 Actions artifact → 核对 ZIP 摘要及来源 → 复用 SSH 上传生产暂存路径 → CI 接收端独立验原包 → 原部署与线上门禁。

仓库为公开仓库，继续使用现有标准 GitHub hosted runner；不新增对象存储、中转 VPS、云加速服务或依赖。免费边界指不新增服务采购，已有服务器、网络与本机电力仍是现有成本；不能把付费代理称为新增免费资源。

- `scripts/local-release-relay.py` 随 `release:prod` 显式启用，推送前预检，结束自动清理；Mac 在线期间无需人工下载上传。中断时仍保留原有直连和有界 SCP 回退。
- 来源固定完整 SHA、push 事件、指定工作流、main/tag、run attempt、artifact ID/digest；镜像、APK、EXE 均使用 GitHub 原始字节。
- 每批并发下载最多 32 个 2 MiB 分片，每批及重试重新获取短期 URL；API token 不发给生产机，签名地址不打印到日志。
- 服务器收到 ready 后还要独立核对 runner 提供的摘要，接收工作流完成前不清理暂存文件。记录下载、上传与端到端时间，区分实际 relay/direct 路径。
- 代价是操作端必须在线；这不是无需本机的托管方案。若以后明确要求电脑离线也能稳定跨境发布，再重新比较有真实免费额度的托管路径和付费路径，不能假定当前账号享有未验证的免费资源。

验证计划见 [本地中转实测计划](superpowers/plans/2026-09-22-local-relay-validation.md)。

## 后续架构建议（本轮不扩大实现）

```text
确定版本、说明、不可变应用 SHA
  → 并行：测试与安全检查 / Linux 镜像 / Windows EXE / PDA APK
  → 汇总门禁及产物身份，预置到生产可稳定访问的存储
  → 验证所有安装包及镜像就绪，准备 GitHub 草稿和附件
  → 短时占部署锁：兼容性迁移、应用切换、真实页面/API/权限验收
  → GitHub 转正并核验，发布客户端更新清单
  → 实际下载摘要与线上版本验收，记录完成状态
```

### 一次构建，统一编排

- 保留 GitHub Actions，增加统一 release 编排入口，普通 push 跑 CI；正式部署由明确发布动作触发。变更触发语义前迁移现有门禁与恢复入口。
- Windows main 验证包与 tag 正式包合并为同一次构建产物，tag 负责绑定与发布原产物；门禁失败不得发布。Linux/PDA/Windows 并行构建，只有生产变更步骤串行持锁。
- 发布清单固定 version、完整 SHA、PDA versionCode、构建 run/artifact ID、镜像 digest、安装包 sha256、迁移集合与验证结果。构建产物字节不变，发布阶段状态单独持久化。
- 重试只续跑失败阶段；每阶段先验证已有结果再执行，重复请求不重复切换、不换包。不能借用另一个 SHA 的绿灯。

### 将跨境传输移出生产部署临界区

**暂缓的付费候选：GitHub Actions 构建 + OSS 传输加速上传 + 生产同地域私有 Bucket + 内网拉取。** 这是基于现有项目规模与链路的工程判断，尚未完成本账号网络实测。历史运维记录表明使用阿里云；实施前核对当前实例类型、地域、内网 OSS 可达性与已有资源。

- 镜像归档、APK、EXE 使用同一个产物交付协议，先保留现有镜像归档格式。上传直接从构建 runner 发往 OSS 加速入口，不必先绕经 Actions artifact 再由生产跨境下载；原 CI artifact 保留作证据与恢复来源。
- OSS 通过就近接入与云骨干网络优化远距离传输；生产从同地域内网 Endpoint 获取产物。加速不能消除全部跨境波动，必须测量两段持续吞吐、失败率及恢复效果。
- 产物按完整 SHA、类型与内容摘要定位；发布清单固定来源 run/artifact ID、大小和 SHA256。只在完整上传并核对对象后标为就绪，生产下载到临时文件、验证原始 SHA256 与镜像 revision 后采用。OSS 分片 ETag 不能当作文件 SHA256。
- 分片上传与断点续传显式启用。恢复状态须能跨临时 runner 保存，绑定原对象与原始字节；重试只续传原包。跨工作流复用断点需验证工具对源路径/文件属性的要求；无法可靠恢复时重新传原包，不能重新构建。指数退避、有界重试，失败保存诊断信息。
- 上传完成不代表已部署。所有产物就绪后才进入生产部署锁；跨境上传失败时旧应用继续服务。SSH 只负责短控制命令并复用连接，控制失败查询同次发布状态后恢复，避免重复执行迁移或切换。
- CI 优先通过 GitHub OIDC 换取限本仓库和发布身份的临时云权限，生产优先使用实例角色只读目标产物。Bucket 保持私有；回退版本与未完成发布保留，过期临时产物及失效分片另设清理规则。
- 操作端 Mac/个人代理只作明确记录的应急恢复。正式链路不依赖个人电脑在线，也不需要先购置香港中转机或维护国内 Windows runner。

**为何暂不选择跨境 ACR 双仓库：** 镜像仓库可以复用层，但 APK/EXE 仍需要对象存储；海外/国内实例同步增加一条发布链路，默认同步加速还使用共享带宽。当前先统一产物交付、更易诊断和恢复。未来实测若镜像重复层传输或生产加载 IO 成为主要成本，再评估国内 OCI 仓库及云侧导入/镜像同步；不把镜像仓库升级列为上线前置条件。

**验收方式：** 在 GitHub Linux、Windows runner 和实际生产下载路径分别测试；覆盖高低峰、重复发布、上传中断、runner 更换、重复请求、摘要不符和清单未就绪。记录完成率、恢复是否需要人工、耗时分布及实际费用；上线前完成整条无人值守发布和失败恢复演练。取消此前 90 秒上传、30 秒下载及 3 分钟总传输的硬阈值，按实测设置合理的阶段预算。

存储、请求、加速流量及可能的公网流出分别计费，先核验账号价格及小规模试传费用。本方案不授权采购或新建收费资源。

### 对外发布顺序与恢复边界

- 安装包先完整落地并验摘要，再推进公开发布状态与客户端更新指针。GitHub 草稿用 Release ID 管理，核验附件后转正；客户端可发现更新前必须确认其下载源可用。
- GitHub、数据库、三端清单无法形成一个跨系统原子事务。统一状态需反映部分成功，失败可恢复；最终成功以所有必需输出核验为准。
- 新后端必须兼容旧客户端；数据库采用先增加兼容结构、后迁移使用、另版清理的方式。应用回退不等于迁移回滚。不可兼容迁移走单独停写/备份恢复方案，时长按实际迁移评估。
- 候选实例预热或双实例切换需先核对服务器内存和 IO 余量；当前阶段不引入 Kubernetes，也不在资源不足时强开双实例。

### 把真实故障提前到部署之前发现

- 在隔离测试库运行构建后的真实应用，覆盖发布所用页面、跳转、登录与权限；模拟页面夹具仅补充边界情况，不能作为唯一门禁依据。
- 部署工具使用固定运行时，或在实际生产运行时对应环境回归。覆盖草稿 Release、附件已存在、断网恢复、摘要不一致、阶段重复执行。
- 上线后保留真实页面/API/权限与完整下载核验。Windows/PDA 真机安装和更新弹窗另列验收，不能从 CI 成功推断。

## 优先级与验收

| 顺序 | 工作 | 验收标准 |
| --- | --- | --- |
| P0 | 统一发布身份、原包恢复、阶段耗时及真实环境门禁 | 已完成步骤重跑不换包；失败阶段可定位；保留原失败记录 |
| P1 | Windows 只构建一次、并行构建、缩短部署锁范围 | 三端来自同 SHA；tag 复用已验产物；没有等待其他 job 的持锁自锁 |
| 暂缓 | OSS 加速上传、同地域内网拉取及统一产物恢复 | 两段吞吐分别可测；断网恢复后摘要一致；无需操作端在线 |
| P2 | 候选预热、兼容性回退演练与长期统计 | 在资源预算内完成切换；回退边界清楚；持续记录正常与异常耗时 |

验收优先级为：产物身份和发布结果正确 → 故障可恢复且不损坏线上状态 → 无需人工中转 → 成本与维护可控 → 基于数据继续改善耗时。取消固定总时长预算，不降低验证强度，也不取消阶段超时、失败告警与回退窗口。

实施分批交付，每批保留上一条可用路径。完成代码、隔离验证与恢复演练后，再按授权范围上线；不要把本设计直接写成现行能力。
