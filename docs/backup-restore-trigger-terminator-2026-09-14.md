# 备份恢复演练失败排查与修复（2026-09-14）

## 结论

钉钉告警「备份导入失败 —— 备份可能损坏」是**误报**。2026-09-14 02:00 的备份文件完整、
数据可信；失败发生在恢复演练的导入环节，根因是 **mysqldump 导出的触发器函数体带着一个
越界的结尾分号**，导入时触发 `ERROR 1064`。本次同时修好了恢复路径（A）和产生脏函数体的
根源（B）。

## 现象与证据

- 触发：`restore-check.sh`（每周一 05:00），2026-09-14 05:00:20 报错退出。
- 演练日志只留下 `[ERROR] 备份导入失败 —— 备份可能损坏`：旧脚本把导入命令的
  stderr 重定向到 `/dev/null`，真实原因被吞掉。
- 手工复现得到真实报错：

  ```
  ERROR 1064 (42000) at line 2373: You have an error in your SQL syntax ... near ' */' at line 3
  ```

- 出错语句是 dump 里第一个触发器 `trg_party_ledger_receipt_insert`，形如：

  ```sql
  /*!50003 CREATE*/ /*!50017 DEFINER=`flowcube`@`%`*/ /*!50003 TRIGGER `...` AFTER INSERT ON `...` FOR EACH ROW INSERT INTO ...
  VALUES (...); */;;
  ```

  可执行注释里的 `;` 会提前结束语句，剩下的 `*/` 成了非法字符。
- 备份本身完好：`gzip -t` 通过、结尾有 `-- Dump completed on 2026-09-14 2:00:05`、
  含 143 条 `CREATE TABLE`。把它按下面的规范化导入临时容器：导入 rc=0，144 张对象、
  4 个触发器，关键表行数与生产一致（差异仅为备份后新增的单据）。

## 根因链

1. `backend/src/database/migrate.js` 用 mysql2 `multipleStatements: true` 把整个迁移文件
   当成**一条多语句**发给 MySQL；
2. 当 `CREATE TRIGGER ... <单语句>;` 后面还有别的语句时，MySQL 会把结尾的 `;` 一起写进
   `information_schema.triggers.ACTION_STATEMENT`（实测：同一文件里非末条触发器保留 `;`，
   末条不保留）；
3. 生产库 4 个触发器里有 3 个带结尾分号——唯一干净的 `trg_party_ledger_entry_insert`
   恰好是 `238_party_ledger.sql` 的最后一条语句；
4. mysqldump 把该函数体包进 `/*!50003 ... */`，导出成 `... ); */;;`；
5. 导入时该分号提前终止语句，剩下的 `*/` 触发 1064，`mysql` 客户端不带 `--force` 时中断，
   于是演练判失败。

触发器来自 v0.9.10 的迁移 238/239/240（2026-09-08 部署）。因此 9/1–9/8 的备份正常、
**9/9 起的每日备份按演练脚本和 runbook 手工命令都无法导入**；9/7 是上次周一演练（当时
尚无这些触发器），9/14 是首次暴露。

## 修复

### A. 恢复路径（立即止血）

- `scripts/restore-check.sh`
  - 导入前规范化 mysqldump 的已知导出缺陷：把函数体结尾的分号移出可执行注释。
    只作用于导入管道，**不改写备份文件本身**（演练保持只读）。
  - 不再吞掉导入错误：捕获 MySQL stderr 并将首条错误写入日志与钉钉，恢复演练能区分
    「文件截断/损坏」与「导入语法问题」。
- `docs/runbooks/failure-recovery.md`：手工恢复命令补上同一口径的规范化。

效果：9/9 起的既有备份立刻恢复可用（实测 9/14 备份 rc=0），并在导入时顺带把函数体
存成干净形态。

### B. 根因（防复发）

- `backend/src/database/sqlStatements.js`（新增）：词法感知的语句切分，识别字符串、
  反引号标识符、`-- ` / `#` / `/* */` 注释中的分号。
- `backend/src/database/migrate.js`：改为**逐条执行**迁移语句。每条 `CREATE TRIGGER`
  单独发送即为「末条」，函数体不再吞掉结尾分号。
- `backend/src/database/241_normalize_party_ledger_trigger_bodies.sql`（新增）：
  重建生产存量的 3 个触发器（语义与 238/240 完全一致，不改数据、不改账款），
  让既有库也回到干净函数体。运行器修复只影响后续新执行的迁移，存量必须靠本迁移清理。

## 验证

全部在生产服务器上的**临时 MySQL 容器**内进行，不读写生产库；容器与临时文件均已清理。

| 验证项 | 结果 |
|---|---|
| 切分模块单测 + 240 个真实迁移文件可安全切分、无残留分号 | 7/7 通过 |
| 恢复演练：导入前规范化越界分号、不改写备份、失败透出真实报错 | 3/3 通过 |
| 既有恢复相关回归（`round2-restore` / `ops-monitor-restore`） | 21/21 通过 |
| 9/14 备份按规范化完整导入 | rc=0，144 张对象、4 个触发器，行数与生产一致 |
| 人为制造脏触发器后再执行 241 | `[;]` → `[)]`，rc=0 |
| 清理后的库重新 mysqldump | `; */;;` 出现 0 次 |
| 该新 dump **不做任何规范化**直接导入 | rc=0，144 张对象、4 个触发器 |

以上均为当次实测；生产存量触发器仍要在正式部署执行 241 后才真正变干净，此前依赖 A 的
规范化保证可恢复。生产部署、发版与真机验证不在本次范围。

## 后续

- 部署链路执行 241 后，用 `information_schema.triggers` 复核 4 个触发器的
  `ACTION_STATEMENT` 末尾都不再是 `;`。
- 后续新增触发器迁移会走逐条执行，无需再手工处理；若引入 `DELIMITER` 等客户端指令，
  需先扩展 `sqlStatements.js`（当前明确不支持）。
