# 极序 Flow 缺陷定位与回归

## 六步，顺序不可跳

### 1. 建立预期
先写下「正确行为应该是什么」，来源必须是权威文档或既有测试，不能是想当然：
- `docs/business-semantics.md`（业务规则）、`docs/inventory-transaction-invariants.md`（一致性不变量）、`docs/finance-permission-time.md`（账款/权限）。
- 已有契约测试（`tests/*.test.js`）与 `package.json` 的 `test:*`/`smoke:*` 脚本。

预期没写清，后面的「修复」就没有验收标准。

### 2. 复现
- 记录最小复现步骤与命令，**先复现再改代码**。
- 涉及数据库时用隔离测试库：`set -a; source ~/.config/flowcube/operations20260912-test.env; set +a`，脚本按精确 ID 自清理。
- 不能复现的，写「未能复现」并列出已试条件，不要靠猜改代码。

### 3. 定位根因
- 走 `flow-business-audit` 的六段链路，找到**断在哪一段**。
- 区分根因与症状：编译/类型通过不代表行为正确。
- 检查同类拷贝：同一判式/同一查询常有多处重复（历史记录显示同一逻辑全仓 4 处拷贝并不罕见），根因可能不止一处。

### 4. 最小修改
- 只改达成预期所必需的部分；不做顺手重构、不加未要求的抽象。
- 遵守 `AGENTS.md` §0.1 红线与 §0.2 守卫；改共用函数或路由契约后，发版前需跑全量套件。
- 修改后立即 `git status --short` 核对改动范围，确认没有夹带。

### 5. 相关回归
按 `docs/verification-commands.md` 选**受影响**的套件，不是无脑全量：
- 库存/状态/并发主链路、财务、权限、打印各自有对应矩阵。
- 修复后又改了代码，只补跑受影响部分。
- 本机 Node 26 下前端单测有 9 文件/56 用例既有假失败（`localStorage is not available`），**只看是否新增失败**。

### 6. 证据交付
输出必须包含：复现命令 → 修复前结果 → 改动文件与行 → 修复后结果 → 跑了哪些套件及结果 → 未跑的检查（明确写「待发版前验证」）。

**不得因为「编译通过」或「类型检查通过」宣布问题解决。**

## 交给 DeepSeek 实施时的任务书

需要别的模型动手时，任务书必须含五块，缺一块就可能被改坏：

1. **事实**：现象、复现步骤、根因位置（`文件:行`）、已确认的边界。
2. **修改范围**：允许改哪些文件；不允许碰哪些（构建产物、`.env`、真实 `deploy/production*.json`）。
3. **不可破坏的规则**：从 `AGENTS.md` §0.1/§0.2 摘出**与本任务相关**的条目（不要整份复制）。
4. **验收用例**：可执行的命令或步骤 + 期望结果，必须能判定通过/失败。
5. **非目标**：本次明确不做什么（避免顺手重构）。

## 独立验收（DeepSeek 完成后）

- **只看真实 diff 和实际测试结果，不相信完成说明。**
- 逐一核对：改动是否落在允许范围、是否破坏 §0.1 红线、验收用例是否真的通过、是否新增失败。
- 完成说明与 diff 不一致时，以 diff 为准，并把差异指出来。

## 边界

- 不擅自改业务规则；需要业务决策的，先问用户。
- 不为通过验收而放宽断言、跳过守卫或加兼容分支。
- 不执行 `git push`、发版、重启生产、删数据 SQL（除非本次已明确授权）。
