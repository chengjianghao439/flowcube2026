# 极序 Flow 业务闭环审查

## 何时用 / 不用

- **用**：跨模块一致性、业务闭环是否闭合、改动影响面、历史缺陷复查。
- **不用**：单文件语法或写法问题（直接读代码）；发布流程（用 `flow-release-check`）；落地修改（用 `flow-debug-verify`）。

## 第一步：读权威文档，不要凭记忆

按主题取用，不要通读 `docs/`：

| 审查主题 | 必读 |
|---|---|
| 采购/销售/退货/调拨/盘点/履约刷新 | `docs/business-semantics.md` |
| 库存、容器、预占、状态机、幂等回执 | `docs/inventory-transaction-invariants.md` |
| 账款核销、凭证结账、发票、权限与仓库范围、账套 | `docs/finance-permission-time.md` |
| 后端 routes/controller/service、SQL、迁移 | `docs/backend-api-sql-conventions.md` |
| ERP 页面组件、PDA 扫码交互 | `docs/frontend-pda-conventions.md` |
| 打印、发布部署、CI 门禁 | `docs/print-deploy-ops.md` |

约束入口是根 `AGENTS.md`（§0.1 无守卫红线、§0.2 有守卫规则）。**不要把规则正文抄进本技能**——它们会过期；只引用路径。

## 追踪链路（六段，逐段走完再下结论）

1. **前端** — 哪个页面/组件发起，参数如何组装，前端是否另有校验。
2. **接口** — 路由 → controller；是否挂 `requirePermission`；是否做仓库范围校验；写操作是否有 `X-Request-Key` 幂等。
3. **服务** — 业务规则落点、状态机流转、边界分支（0 值、空范围、已终态、并发）。
4. **事务** — 锁顺序、同一 `conn` 传递、失败是否回滚、是否 fail-loud。
5. **事实数据** — 改了哪张表哪个字段；库存唯一事实源是 ACTIVE 容器的 `remaining_qty`。
6. **结果展示** — 列表/详情/报表是否读同一事实源；缓存 `inventory_stock.quantity` 是否只经 `syncStockFromContainers()` 写入。

跨模块缺陷多在第 3→4 段（事务断裂）或第 5→6 段（事实源与展示不一致），优先看这两处。

## 证据分级（每条结论必须标注，不得省略）

| 标记 | 含义 |
|---|---|
| 【代码确证】 | 逐行读过该代码，行号与行为直接来自源码 |
| 【数据库核对】 | 在隔离测试库实跑查询/脚本并得到结果 |
| 【接口验证】 | 真实调用接口并核对返回 |
| 【守卫验证】 | 对静态守卫做过变异注入，确认能抓错 |
| 【待核实】 | 只做了机制核对，未走通完整调用链 |

**没有标记的结论不成立。**

## 边界

- **只产出发现**：不自动修改业务代码、不自动简化、不提交 PR 评论、不推送。
- **历史不是现状**：`docs/audit-*.md`、`*_fix_*.md`、`*_result.md` 是当时快照，用前按现行代码核对。
- **业务规则不单方面决定**：证据无法判定方向的，列入待决策清单交用户。
- **数据库只连隔离测试库**：`set -a; source ~/.config/flowcube/operations20260912-test.env; set +a`，不碰生产、只读为主。

## 完成证据

一条发现一行：位置（`文件:行`）、触发条件、后果、证据等级、建议动作。
无法验证的部分单独成节，写明「缺什么才能验证」。
