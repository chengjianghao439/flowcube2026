# 极序 Flow 界面验收

## 先确认工具，再动手

| 目标 | 首选工具 | 说明 |
|---|---|---|
| 网页（ERP/PDA 路由） | `Claude_Browser` MCP（`preview_*`） | 导航、点击、填写、截图、控制台与网络错误 |
| 已启动服务的脚本化验收 | `agent-browser` CLI | 项目既有验收链路，含加密凭据档 |
| Electron 桌面窗口 / 系统级操作 | `peekaboo` CLI | 需屏幕录制 + 辅助功能权限；未授权时如实报告阻塞 |

**不要同时启用多个功能重叠的浏览器方案**：已有可靠能力时先验证它是否满足需求，缺什么补什么。

## 环境安全判断（不能只看 localhost）

- 前端 dev 的 `/api` 代理目标由 `DEV_API_TARGET` 决定，默认 `http://localhost:3000`（本地后端，安全）。
- `.claude/launch.json` 中的 `frontend-dev-prod-api` **显式指向生产** `https://jixuflow.com`——只有该配置会连生产，**不要用它做验收**。
- 判定顺序：看启动配置 → 看实际代理目标 → 确认后端连的是本地库（3307 开发库）还是生产。
- 验收动作默认**只读或可回退**；任何写操作先说明会改哪张表、可否回退。

## 启动本地栈

```bash
npm --prefix backend run dev      # :3000，连 127.0.0.1:3307 开发库
npm --prefix frontend run dev     # :5173
```

或使用 `Claude_Browser` 的 `preview_start`（配置在 `.claude/launch.json`）。

## 验收步骤

1. 明确**验收对象与通过标准**（要证明什么，什么算失败）。
2. 启动服务，用浏览器打开目标页面。
3. 执行真实交互：导航 → 点击 → 填写 → 提交，至少覆盖一条主路径和一个边界（空值/超出/已终态）。
4. 记录**截图 + 操作步骤 + 实际结果**；控制台错误与失败请求作为辅助证据。
5. 结论区分「工具可用」与「项目可访问」——工具能跑但页面打不开，是项目问题，不是工具问题。

## 四种界面不要混为一谈

| 类型 | 证据强度 | 备注 |
|---|---|---|
| 网页（浏览器打开 `/` 路由） | 中 | Vite dev 或已部署站点 |
| Electron 桌面窗口 | 高（桌面专用） | 需 Peekaboo + 系统权限，窗口须显式指定 |
| PDA 网页模拟（浏览器开 `/pda/*`） | 低 | **不等于真机**，扫码/原生能力无法覆盖 |
| PDA 真机 | 最高 | 需 Android 设备，本机不覆盖时**明确写未验证** |

## 边界

- 只操作明确指定的测试窗口/页面；不采集无关私人窗口，不操作聊天软件，不发送外部消息。
- 不用后台接口调用替代用户明确要求的界面操作。
- 系统权限（屏幕录制、辅助功能）必须正常授权；**未授权不得声称已授权**。
- 仅保存截图文件 ≠ 完成视觉检查——截图必须真实传回并核对内容。

## 完成证据

输出：验收对象 → 环境（哪个后端/哪个库）→ 步骤 → 截图/结果 → 通过或失败 → 未覆盖项。
未覆盖的部分写「未验证」，不写「应该没问题」。
