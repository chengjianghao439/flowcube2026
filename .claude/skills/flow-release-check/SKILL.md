# 极序 Flow 交付前核对

## 铁律：从文档和脚本读流程，不凭记忆

流程会变，记忆会过期。执行前必读：

| 要知道什么 | 读哪里 |
|---|---|
| 完整发布链路、tag 与版本规则 | `docs/RELEASE.md` |
| 部署步骤、环境、回退 | `docs/DEPLOY.md`、`docs/print-deploy-ops.md` |
| 故障处置 | `docs/runbooks/failure-recovery.md` |
| 实际执行的脚本 | `scripts/release-prod.sh`、`scripts/release-gate.sh`、`scripts/release-desktop-tag.sh`、`scripts/complete-release.js`、`scripts/verify-live-release.cjs` |
| 版本号与更新内容 | `.claude/skills/release-flowcube/SKILL.md`（发版专用技能） |

**真正发版时用 `release-flowcube` 技能**；本技能负责「发版前的状态核对」。

## 六种状态必须分开说

| 状态 | 判定方式 |
|---|---|
| 已修改 | `git status --short`、`git diff` |
| 已测试 | 实际跑过哪些套件，套件名与结果；没跑就写「未执行」 |
| 已提交 | `git log --oneline -n`，提交是否存在 |
| 已推送 | `git status -sb` 与 `git log origin/main..HEAD` |
| 已部署 | CI run 结果（`gh run list --branch main`）、部署日志、产物时间戳 |
| 已验证 | 部署后真实核对过（接口/页面/版本号），**未核对不得写已验证** |

常见错误是把「已推送」当成「已部署」、把「CI 绿」当成「线上生效」。

## 核对清单

1. **工作区**：`git status --short --branch`——有没有未提交改动、是否夹带无关文件。
2. **本批改动范围**：列出文件与用途；业务代码与其说明文档同批；技能/环境整理与发版分开组织。
3. **验证覆盖**：按 `docs/verification-commands.md` 确认受影响端的 lint、类型检查、构建、专项/全量回归**是否真的跑过**（无输出的错误命令不算通过）。
4. **文档同步**：改动的行为约束是否已同步到对应主题文档（`AGENTS.md` §0「改动同步到对应主题文档」）。
5. **版本与更新内容**：三端版本号是否一致、`docs/release-notes/<version>.md` 是否存在（发版时）。
6. **回退方案**：出问题怎么退，退到哪一版，历史产物在哪。

## 边界（严格遵守）

- **默认只做检查与准备**，不代替用户做发布决策。
- **提交、推送、打 tag、迁移、生产部署**：必须有当次明确授权。已授权的同一操作不重复询问；需要新授权时先停手问清楚。
- 不执行会删数据的 SQL，不重启生产服务（除非明确授权）。
- 部署相关凭据不读取、不复制、不写入任何文档或提交。
- 生产服务器只在授权范围内操作，SSH 必须复用连接（见 `AGENTS.md` §0.1）。

## 完成证据

交付一张状态表：每个环节（改动/测试/提交/推送/部署/验证）标注当前状态与判定依据；
列出「下一步需要什么授权或操作」，以及回退方式。状态不确定就写「待核实」，不写「应该没问题」。
