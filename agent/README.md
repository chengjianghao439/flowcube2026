# 小满运行与接口

来源：用户提供的 Muse `jixu-agent-0.1.0.zip`（SHA256 `71561ea798de9f917390a76b05be120bcd615bc2313e9d234cc40ed2445e3b95`）。原包沙箱记录不代表当前环境验收。

Node 22 运行，业务只调用正式 Flow HTTP API。模型只把自然语言解析成受校验的任务意图；模型名只读环境变量 `AGENT_MODEL_NAME`，代码不写死名称。库存、价格、账款来自后端。写入必须通过预览卡人工确认。已冻结的业务编排由 `src/runtime.js` 统一分发，正式后端与本地独立服务共享运行入口。开放讨论已关闭，不再进入 `G-chat`。

## 运行

正式入口是原后端 `/api/assistant`，与当前 ERP API 同源、同认证及凭据续期。后端通过当前 `authMiddleware` 和仪表盘/报表任一入口权限后，才解析最多 32KiB JSON；继续沿用全局 CORS、限流、并发与停机守卫。健康也需认证。正文不能提供身份、权限或仓库范围，内部 API 客户端仅使用本机实际监听端口与当前访问令牌，不接受请求 Host 或外部 Flow 地址。每个业务入口仍保留原权限、确认、原请求键与回查核验。

镜像把包声明与运行源码复制到 `/opt/flowcube-agent`，原后端进程按固定可信路径懒加载；不增加微服务、监听端口或镜像。Compose 仅向后端注入 `AGENT_MODEL_*`，任务保存在 `assistant_data` named volume 对应的 `/var/lib/flowcube/assistant`，目录权限 0700、任务文件 0600。当前由单个后端进程持有运行实例和任务锁；同一私有任务目录由一个进程写入。模块导入与迁移命令不会启动监听或加载任务。

可选本地独立服务仍使用原入口：

```sh
FLOW_BASE_URL=http://127.0.0.1:3893 AGENT_DATA_DIR=/absolute/private/agent-tasks AGENT_ALLOWED_ORIGINS=http://127.0.0.1:5198 npm run dev:agent
```

`AGENT_MODEL_BASE_URL`、`AGENT_MODEL_NAME`、`AGENT_MODEL_API_KEY` 通过进程环境注入。服务不自动读取或写入密钥文件；示例只说明变量名，不包含凭据。任务文件含业务预览，须放在仓库外私有目录。服务仅监听 `127.0.0.1:8932`，Origin 必须精确匹配允许列表。

前端使用 `/api/assistant`，不依赖独立 8932 服务、Vite 专用代理或开关。独立服务仅供本地调试，保留其回环监听和精确 Origin allowlist。

## 接口与边界

以下相对路径在正式后端均加 `/api/assistant` 前缀，并使用 `{success:true,message,data}` 成功信封，失败沿 `AppError` 统一信封。独立服务保留原无前缀、无外层成功信封的本地接口；独立健康探针只返回配置状态。

- `GET /health`：正式入口需认证；仅返回配置状态，`planner=llm` 不代表实际模型调用已验证。
- `GET /me`、`GET /tools`：正式入口由原后端认证核对当前身份，独立服务每次向 Flow 核对。
- `POST /chat {message, taskId?, choiceId?}`：查询或生成待确认任务，不接受文字代替确认。招呼和少数已核对的业务概念只在本地短回，不建任务、不调模型。`taskId` 是当前选中记录；原候选选择和明确改数量沿该任务继续，完整的新问题另建业务任务。`choiceId` 必须属于原候选集合，并重查原搜索；不可用任意 ID 绕过搜索。
- `GET /tasks`：最多 30 条当前用户仍可访问的任务，最近更新在前；`GET /tasks/:id` 返回单条同形状安全视图。字段为 `id/graph/state/userText/reply/preview/result/error/candidates/revision/createdAt/updatedAt`。不返回原请求键、内部载荷、私有库存字段、角色权限或凭据；撤查看权、撤仓后隐藏原快照，预览超过有效期显示 `EXPIRED`。
- `POST /tasks/:id/resume`：续办原查询，或核对已尝试提交的原回执和详情。仍待确认的草稿只返回原预览，进入写入需要单独使用确认接口。
- `POST /tasks/:id/confirm {revision?}`：仍兼容不传版本的原调用；提供旧版预览版本返回 `409 PREVIEW_REVISION_CONFLICT`。选择、改量、确认、恢复共用任务锁。执行中的任务按原键及领域 action 查回执恢复，不重发写请求；已完成任务返回原结果，原收款任务恢复原第二段核销卡。
- `/chat` 与 `/confirm` 响应仍为 `{reply, task:{id,graph,state,revision,userText}, preview?, result?, candidates?, diffs?}`。待确认时优先返回持久化预览，首次即包含与原任务相同的 `builtAt/expiresAt`，版本与恢复结果一致。候选项至少 `id/title`，可含 `type/subtitle/details`；资金账户未选时 `preview.account=null`、`preview.accounts` 保留，账户序号回复继续可用。

销售占库确认卡按原单行和仓库显示本次占库数量与预计累计已占量。收款核销确认卡显示原收款余款、逐单应收与适用的月结对账单欠款的前后值。销售单和收款单入口沿当前查看权限打开正式原单。过期或待核对时收起预计值，取得有效预览后再展示。

例如先发送 `{ "message": "合成铰链库存" }` 得到候选，再发送 `{ "message": "选这个", "taskId": "原任务ID", "choiceId": 2 }`；待确认销售预览可发送 `{ "message": "把刚才的数量改成五个", "taskId": "原任务ID" }`。单行或明确行号才可改量，重读商品策略、客户价和库存后增加 `revision`，不执行写入；多行未指明时停下，执行中或结果未知时禁止修改和换键续写。

已支持：查库存、销售草稿、销售占库、补货建议、采购草稿、往来台账、分两步登记收款与核销、仓库作业卡点、经营简报。口语「做个订单」「开单」「下一单」进入销售草稿；缺客户或商品时追问，不回一整份能力清单。正式全局搜索另需仪表盘权限，建单后的核验另需单据查看权限，不代授权限。完整列表最多核对 2000 条，超限/重复/总数变化停步。

已匹配库存查询规则的业务提问，在模型未识别意图时继续按现有规则查询。明确指定仓库时，只查询当前账号可见的指定仓库，仍按现行规则处理未知仓库和无权仓库。

库存查询以员工原话明确指定的仓库为准。模型给出的其他仓名不能替换原仓。单独说「先别开单」时简短应答，「只查……库存，别开单」只走库存查询，已在处理的草稿保留。

明确说「先查二仓的某商品库存，够两个再给某客户开单」时，先用原仓库和商品查库存，再按商品当前固定单位核对可用量。单位、客户或数量未明确时先提示核对，查库发现量不足就停在只读结果。符合条件时生成绑定同一仓库和商品的待确认草稿；确认前再次核对单位与可用量。换商品要重新查库，草稿仍由本人点击确认。

按补货建议建采购草稿时，逐仓核对建议的仓库身份和有效供应商。有缺项的批次停在试算，说明需要维护的商品或仓库。预览按供应商和目标仓库分组，确认前重新校验建议和成本价。批量执行断线后，逐张查询原请求回执，并核对回执对应采购单的仓库、供应商和金额。已核实的单号可回看，其余保留待核对，查询过程只读。

只看补货建议使用只读工具，先核报表与仓库查看权。员工明确暂缓建采购单时，同行的补货查询仍可继续。只有明确要求生成单据才进入采购试算。

仓库列表沿正式分页读取。占库使用完整销售单号核对查询结果，试算和确认使用每条销售明细的实际仓库。相同商品、同仓的明细共用可分配量。正式占库事务在订单锁内核对原预览依据，订单或行仓变化后须重新试算。套单另校验原商业版本；断线时按单据类型查询原回执，并回查行仓及数量。占库历史按订单头仓和全部行仓校验。

登记收款有多个可选账户时，明确选中原预览中的序号或完整账户名才能继续确认。回复里有多个账户或名称有歧义时继续等待选择。

按客户名称查应收台账需同时拥有收付款查看、经营看板查看和客户查看权限。缺少搜索权限时指出缺项。仍有收付款查看权的岗位可在客户往来按原单核对。旧台账任务回看时复核这些权限。

可从原话明确取到客户名时，查账及到账试算保留原名和分店名称。销售数量缺失或是「二三个」「五到六个」时追问明确数量，已提供的客户保留；收款金额仍按原文和分位核对。

有多笔收款待选账户时，先打开对应的收款任务，再回复序号或账户名。新业务问题可以单独查询，原收款保留待选状态。经营简报按当前仓库范围读取库存种类及到货，采购日期按北京时间分到逾期、今天和未来七天。待审批权限收回后需要重新生成简报。卡点或简报的各段失败时保留其他可用事实，全部未取得时显示查询失败。

仓库卡点按当前权限分别查询作业统计、待分配分拣格或收货。只有收货查看权的岗位也能看到可读的收货段。撤销曾用于该卡片的查看权后需要重新生成。库存来源取数失败时返回失败和重查提示，不用零数量表示故障。

商品搜索里，编码或名称完全一致且只剩一条时可以直接用。模糊品名即使只剩一条，也只列出当前仓库范围内的候选让人选，不自动替换；候选带仓库却不在范围内、或库存只落在无权仓库时不出现。没有候选或对不上范围时说明原因，不改查其他仓库。

不做：退货任务完整汇总暂不支持，按不可用呈现；取消订单、改价、审批、付款、发货不做。这类拒答会写明可打开的菜单（销售订单、采购订单、库存管理、客户往来、供应商往来、待审批、发货出库、商品资料），不只列能力。卡点只覆盖仓库执行（拣货、分拣、复核、打包、待出库、分拣格和收货任务），本轮不扩到商务卡点。大额量级提示本轮暂无。最近记录只保留走过业务图的任务；招呼、本地短回和闲聊不进列表。

证据边界：月结和客户退款跨期补录通过合成数据、隔离 MySQL 和浏览器验收。多仓多供应商的组合场景、生产并发和真机还需要各自的验证。

库存查询保留指定仓库并先验范围，不能把“二仓”扩成全授权仓。销售预览逐行读当前商品数量策略，整数商品 `0.5` 在出预览前拒绝，确认时再次核对。台账按客户 ID 的事件归属、未结列表按来源订单关联，手工与历史未关联账款不按同名绑定；`unassignedCount` 是应收侧全局未归属事件数，不能认定属于当前客户，也不能凭关联列表为空或余额零宣称全部结清。卡点和简报列出接口返回的可见单号、库存和异常事实，不编卡住原因。

补货主建议接口读取失败（包括 403/503）必须失败，不能冒充成功空集合或生成采购确认卡；成功的空集合仍可报告没有建议。经营简报对全部并行请求立即接住拒绝，每段独立保留成功数据或真实失败提示，不能因后段先失败而终止服务。

到账金额统一由 `src/receipt-amount.js` 从原文核对，规则、模型意图及规则回退共用边界。带货币标记/单位的到账前金额与到账后金额都核对，`5元到账` 与 `到账5元` 都是 5 元，客户编码数字不据此当成金额。保留负号与前导小数，`.5元` 为 0.50 元；非正金额、超出分位、多个金额及不能可靠识别的中文金额/倍率等表达要求重述，不会舍入、丢符号或变成未结全额。只有确实没写金额、且模型未提供有争议的金额时，才按关联未结全额试算；模型提供金额但原文缺少证明或不一致时停步。选账户和确认时也用相同解析复核原文、整数分值与登记载荷，旧版错误快照不能直接沿用。

## 会话记录与复盘

项目内的复盘入口和本地验收见[小满会话复盘](../docs/xiaoman-conversation-review.md)。

正式服务和本地独立服务从启用后的第一轮开始，在私有 `AGENT_DATA_DIR/conversations/` 按 UTC 日期追加记录。前端点「新对话」开始一组新记录，打开历史任务接回原组。有效的已登录聊天即使没生成业务任务也会记录。确认、续办和草稿操作按原任务关联。进入运行时的请求分别记录接收和结束，保留岗位编号、耗时、业务类型和状态，用于区分已回复、被拒或没有收到结束记录。

记录只取对话文字和结果状态。凭据特征命中的整条文字会被过滤，常见手机号、邮箱和长标识也会遮盖。鉴权头、原请求键、工具载荷、预览金额对象和错误堆栈不进日志。文字仍可能包含正常业务名称和明细；逐轮回看由有权读取私有运行目录的人员在本机执行。日志目录权限 0700，文件权限 0600。写日志失败不会重试业务或改变业务结果，后端会告警。启用前的完整对话无法从旧任务快照补出。

```sh
npm run assistant:conversations -- --data-dir /absolute/private/agent-tasks --days 7
npm run assistant:conversations -- --data-dir /absolute/private/agent-tasks --days 7 --session 0123456789abcdef0123456789abcdef
```

第一条仅显示数量、耗时和会话索引。第二条按指定编号输出逐轮记录，把示例编号替换成汇总里的会话编号。默认读最近七个 UTC 日及最新 50 组索引，可通过 `--days` 和 `--limit` 调整。镜像内可执行 `node /opt/flowcube-agent/src/conversation-report.js --data-dir "$AGENT_DATA_DIR"`。工具没有跨账号的网页接口和外发步骤。读取窗口只影响本次报告，日志文件按日留存。

## 补信息、改口和换话题

- 「帮我处理一下」先问要查什么或办哪件事。「有笔收款要登记」先询问付款客户全称及准确到账金额。
- 「只查二仓的库存」先记下仓库，再问商品名称或编号。员工在同一条记录补齐后，按当前授权重新核对指定仓库。
- 销售草稿逐行记录明确信息。一个商品缺数量时可以直接补「三个」。有多行缺量时请说对应商品或行，范围数量需要澄清。
- 预览有效期内支持「不是两个，是三个」「客户改成某某公司」「不是长款铰链，换成短款铰链」等明确更正。改量核对固定单位，改口时保留原仓。确认按钮使用最新试算版本。多行草稿换商品时请明确所指的原商品。库存条件草稿换商品需要重新查库。
- 「这单先放着，另外问下……」单独处理后续问题。「换个话题」收起原卡片，可从最近记录继续原任务。

## 一句话多步查询与续办

- 「先查一仓库存，再查二仓库存，最后看经营简报」会按原句顺序处理，单条至多三项已支持的查询。需要补充目标或有失败的一步会暂停，其余步骤显示未执行。恢复后的答复保留先前完成的结果与各自的查询时点。
- 条件开单只生成待确认草稿。例如「先查二仓的长款铰链库存，如果可用量不少于十个，再给某客户开单：长款铰链两个」。库存门槛和开单数量分别比较，当前商品固定单位、原仓和原门槛在确认前再核对。库存不足时停在查库结果。
- 「继续原任务」或工作区续办按钮从当前暂停步骤继续。跨账号、撤权或仓库授权变动仍按正式权限核对。确认响应丢失时用原请求回执和对应详情核实；停在待确认的草稿须由本人再点击确认。已生成的条件草稿从原查询可回到同一张卡。

## 单据、客户和仓库之间切换

- 在同一工作区，可以说「看看上一张单」回到上一条匹配的记录。只有一张对应单据时，「刚才那单」可以接续。两张都符合时，小满会收起确认卡并问指哪一张，可以直接答「上一张单」或打开对应记录。刷新后可从最近记录重新打开要办理的任务。
- 「第二个」按当前看到的候选顺序选择。候选变化后需要核对新列表。库存结果有多个仓时，可以指定「第二个仓库」或回复「仓库是」加完整仓名，小满会沿用原商品。查「上一位客户的应收」时按已明确的客户编号查询。
- 明确为另一位客户开单会使用独立草稿。缺商品或数量时先问。单据号不明确时，占库先问完整单号。「还是按原来的」会保留已明确的当前版本，有另一条记录或需要区分更正前后版本时先问清。实际写入仍由本人核对对应卡片后点击确认。

## 隔时续办

- 刷新或重新登录后，可以打开最近记录，也可以说「继续上次的任务」或「继续某某公司的销售草稿」。只有一条能确定的原任务时直接接续；有多条时问区分用的客户、单号或仓库，直接补这一项即可。核对范围包含本人历史中符合条件的记录，最近记录栏仍显示 30 项。
- 恢复待确认卡前复核当前权限和原单。过期或事实变化时，销售草稿、占库、指定原收款单的核销和符合条件的退款用原业务对象重新试算，递增原任务版本。核对后由本人确认新版本。原收款单若已有该目标的新增核销，先说明已有分录，再请财务明确是否另核一笔。
- 确认结果不明时按原单及本人原请求回执核对。超时、响应中断或暂未找到回执时保留原任务及请求键。看到原销售单已作业，或原退款单已有出账，可说明当前进度。另一经办人的回执由其本人核对。
- 恢复已完成的占库和核销会重新读取原单。按原占库事件和后续释放记录说明已释放、仍占及后续重占。核销沿原回执的分录身份区分同源冲回、新的核销和独立退款。能复办时先明确本次意图和金额，再用新任务试算。旧确认只复核旧任务。
- 多次释放和重占按销售单的事件顺序显示。跨同事接班可报完整原销售单或原收款单号。小满按原批次和已核验回执逐笔说明补办人与数量或金额、当前余量及负责岗位。可以说「第 2 次释放后重新占库 本批第 1 行 2 个」或「第 2 笔冲回后重新核销 2 元」。余量核实且当前账号有办理权限时生成新预览，由本人确认。缺失、错配或未注明归属的回执会指向具体事件或分录核对。 查看某批之后可说「刚才那批」。说「把剩下的补了」时，已选定批次或只剩唯一待补批次可以按该批的最新余量试算。多批同时待补时只选一批。收款单内不同销售单的冲回序号相同时，可以给原分录编号。 同单一批回执存疑时，仍逐批显示已经核实的补办量。可以说「先补能核实的，待核的先放着」，存在唯一可办批次时按它的当前余量试算。点过待核批再说「刚才那批」时，会指向该批待核的回执。 补齐或更正后可说「这笔回执更正了，重新核对」。小满对照原事件或分录并把同事期间办过的量计入当前余量。说「刚才那批」仍指已选原批，明确说「按更正后的归属继续补办」才沿已核实的现归批次生成新卡。 同一回执再次更正、撤回或改回时，可继续用该回执重查。小满会说明对话中上次核实的归属、当前结果，并计入同事期间的已办量。回执待核时只核该笔，原已落库业务以当前正式单据为准。
- 同一张单多笔回执交叉更正时，可说「这两笔回执的更正顺序对不上，重新核对」。小满逐批汇报已确认的同事办理、还剩多少和下一步由谁处理。多笔有疑点时给出其中一笔的事件或分录编号即可继续核对。需要先办证据齐全的批次时，可以说「先补能核实的」。
- 一笔先核清、另一笔还待核时，可说「还剩哪笔回执待核」查看各批最新进度。切到待核回执后，说「按核清的那批继续补办」会重新对照刚核清的原回执和同事期间办成的量。该批已补完时会说明结果。若还有可补余量且当前账号可办理，会出新版预览，由本人确认。
- 第一批已补完后，可说「另一笔待核回执后来也核清了，重新核对」。小满会按原单报告两批当前进度。如果回执改归已补完批次导致超额，会列出超出的数量或金额、对应回执和负责核对的岗位。
- 超量回执可继续说「这笔超量回执只更正了一部分，重新核对」或「超出的部分撤回了，重新核对」。小满核对前后回执、各批的当前数量或金额，以及同事期间新增的成功办理。有待核证据时只定位相应的回执。确认改归后可说「按更正后的归属继续补办」，由当前有权限的人核对新卡。
- 核对同一原单的多笔回执时，可以带上原单号，说「这几笔回执 #123 和 #456，看看各批还差多少」。同一对话内可接着说「先别补，看看各批现在还差多少」。小满按正式记录重算各批已补量、余量和待核回执。需要续办时，可说「就补刚对上的那批，先给我看看」或给出对应回执编号，再按当前权限和余量生成新预览。多批都可办时，「先补能核实的」会请你选一批。

## 语音转写、简称和客户转发

- 「语音转写：小满，呃，只查２号倉的 Ｐ １１０００１ 库纯」可按第二仓及商品编号查询。仓号以当前可访问仓库目录为准，独立查库遇同号仓时用「仓库是……」在原任务补全仓名。货号中的字母和数字按原义区分。
- 「铰连」之类的常见同音字可帮助找商品候选。客户简称仍保留名称前缀和完整分店号。相近对象由本人选择，单条候选也要核对。已有一行待补销售数量时可以答「俩」「仨」，「两三个」需要给确定值。
- 直接发客户原话时，小满会提示说出本人要做的事。有闭合引号时，可以另起一行写本人要求。例如 `客户原话：「客户：某某公司；商品：长款铰链」`，下一行写 `我的要求：按这条留言准备销售草稿`。这时只追问缺少的商品、客户或数量。引号内的确认、改口和发货指令不进入任务，草稿试算后由本人在界面确认。

- 粘贴完整的默认单号时，允许全角字母数字以及编号内的空格或制表符。例如「销售退货 ＳＲ ２０２６１１２２ ００９」。按完整单号查原单。尾号、分开的金额、数量和跨行数字仍需核对。同一句给出两张销售单时，先选要查的那张。
- 「客户发微信」也按转发处理。有闭合引号并在外面写「我的要求」时，可以明确指定本人要查询的原收款单或销售交接。

## 按原销售单交接

- 接手人用自己的账号说「交接销售单 SL20261122011」。小满按当前权限和仓库范围核对销售状态、仓库任务和关联应收，说明已办、卡点和下一责任岗位。缺少或混用单号时直接补一张原单的完整销售单号。自定义前缀请加「销售单号」。
- 在该交接记录里问「现在该谁接」或「这单现在到哪了」会重新核对原单。刷新、重新登录或打开这条最近记录时，先用当前权限复查进度，再显示结果。复核成功继续使用原任务编号。
- 「继续上次的销售单交接」按本人历史的原单查找。同一销售业务和追查目标的重复记录视为同一对象。不同单据时只问完整销售单号。换班同事可以说「刚接班，销售单 SL20261122011 这班接着从哪一步做」，按自己的权限查询原单。
- 有占库权限且阶段允许时可说「接着占库」，先核对原单并沿可复用的待确认预览办理。写入由本人点击确认。仓库作业、授信审批和财务处置由相应岗位按正式入口办理。
- 可以问「这张销售单的异常先处理哪个」。有实物归还或改单挂起时先找仓库处理原任务，再核对授信和供货，采购可同时核实补货。财务可并行对照原应收、实际到账和核销明细。已确认账款的金额对不上时，会列出账面余额、按应收减已收计算的应余和差额，提供客户往来入口。每个岗位看到其有权核实的环节。
- 说「卡点解除后接着办」时，小满重新读取同一原单。遇到仍挂起或事实暂时无法核对时，按当前事实说明责任和下一步。可以占库时在原任务重算并更新版本，再由本人确认。已经提交且结果待核时继续查原回执。说「账款对上了，接着办」会沿财务事项跟进。
- 「追查销售单 SL20261122011 的仓库任务、退货和分笔收款核销」按当前权限显示订购、派发与实发，逐个核对仓库批次、关联退货和已落到本单的核销。可以接着给一个完整的仓库任务号、退货单号或收款单号。小满会核对它确实关联当前销售单。找不到明确对象时，只补要查的完整单号。仓库、退货和资金操作由对应岗位在正式入口办理。

## 岗位待办、退货与收款状态

- 销售草稿、客户台账和收款试算从员工原话提取客户关键词，保留名称前缀与门店。不能可靠定位时请员工补全。搜索结果中的同名客户继续由员工选择。
- 「我今天先做什么」按当前权限汇总可见的销售、采购、仓库、收货和收款积压。仓库作业可问「我今天负责打包，先看哪几单」，按正式列表顺序取前三张并标记紧急单。个人分派需到对应作业页核对。
- 「退货卡点」分采购退货和销售退货列出草稿、已确认待执行数和最多两张关联任务。给出完整退货单号可查单据和关联仓库状态，包括详情接口提供的返货任务。环节和异常以详情为准。
- 「收款单 RC20261122001 核销了吗」按完整单号解释登记状态、已核销额和收款单余额。查询用正式客户往来权限，客户整体应收是另一项核对。历史四位小数按原值展示。自定义单号前缀时请一并说明单据类型。
- 「查收款单 RC20261122001 的分次核销和预收余款」从原收款单累计每张销售单的核销分录，同时显示各单当前欠款。预收款分别说明客户归属和待分配的销售单用途。分录缺失或账款关联无法复核时提示财务查原单。
- 继续动用原预收款时，给出完整收款单号、各张销售单号及逐单金额。缺一个金额时可直接补该金额，已明确的其他行继续保留。现结核销需要当前收款查看与执行权限。点击当前预览版本后才提交，旧预览失效，提交结果未知时先查原回执。同一组分配确需再办时，明确说「再核一笔」并给出逐单金额。
- 「查月结对账单 SC20261122001 的分次收款核销」列对账确认状态、各销售单欠款和每笔收款对该单的实际核销。报差异时会指出原单、金额和需核对的财务凭据。要继续办理，请给完整对账单号、原收款单号和本次准确金额。使用自定义前缀时，标明是月结对账单还是收款单。已确认的客户月结单按老账顺序出试算卡，草稿确认由有权限的财务在原页面办理。
- 「核对销售单 SL20261122011 退货后的应收冲减、部分退款和月结差异」沿当前权限显示入仓、拒收、实际冲减、净实收及欠款。有退款单查看权限时，另核原退款出账和已确认待退。指定关联退货单、收款单或对账单时，先按原销售及应收分录核对关联。 原应收、对账行或退款出账对不上时，按各自已核对的来源列出两边金额和差额，指向对应的财务入口。
- 「执行退款单 RF20261122016」只续办有权限的已确认原退款，金额、账户、日期、应收和对账单必须能复核。卡片确认后沿正式退款接口登记出账。任何相关金额或原凭据有差异时请财务先核实，响应丢失时只查原退款回执。
- 「核对销售单 SL20261122011 跨月退货、退款和补录分别记哪一期」可追加完整退货、收款、对账、退款或补录单号。小满区分原销售和收款凭证期间、退货实际执行和冲减月份、对账区间、退款真实业务日期及调整凭证期间。凭证证据以现行凭证查看权限和原业务来源为准。
- 「为退款单 RF20261122016 申请跨期补录」需要当前退款及补录权限和可核验的闭期原单。缺原因时只追问原因。申请经版本确认后进入待审批，由另一位有审批权限的财务办理。按原申请查询或重试时，小满分别说明待审批、已批准待执行、审批期间已结账和已记账待凭证。调整凭证待生成时，从原补录审批页继续。
- 查询在本地分流，只读正式接口，历史回看重新核对本人、来源查看权限和相关仓库范围。补录待确认任务重查原业务及审批阶段，结果待核时按原申请或原请求键回查。

## 人格与本地短回

人格与本地短回集中在 `src/persona.js`，通过实际消息入口生效，用户可见名称只有“小满”。“在吗 / 叫什么名字 / 谢谢 / 你没听懂”只在本地短回，不建任务、不调模型。阅读习惯、天气、苹果公司等无关话题直接说明范围，零模型、零 Flow 调用。

不再提供用法闲聊或 `G-chat`。页面设计、排错闲聊、使用讨论和产品讨论都直接拒绝，不调用意图模型，也不调用讨论模型。预占、现存与可用，以及“审批是什么意思”，仍由本地稳定短回说明：预占不扣实存在库、不等于发货；列表可用、含预计可承诺和当前可拣分开说明。审批短回只区分有权人员的业务审批与预览确认，不代审批。这些短回不是开放讨论。

`src/routing.js` 集中定义入口分类与规则任务图，避免入口白名单漏掉后续已支持的“欠款”等问法。实际单据、账款、库存查询以及正式编号优先进入业务；“这张单 / 那笔款 / 刚才那个”等缺少明确身份时先澄清，不交给模型猜对象。仅添加“在极序里”前缀、或明确把极序放一边，都不能放行其他话题。问句里包含“设计 / 讨论”不能把真实业务查询转去讨论。明确“换个话题”时，只用最后的新目标判断归属。整句中的绕规则请求仍优先拒绝。业务图外取消、付款、发货、改价及绕规则请求在调用模型前拒绝。

凡要调用模型，只走意图解析，模型名取 `AGENT_MODEL_NAME`。历史 `G-chat` 记录不出现在 `GET /tasks`，也不提供详情恢复；不删除原持久化数据。业务任务和待确认预览仍沿原授权完整保留。

已有历史文件若损坏、不是数组、任务编号重复或记录不完整，停止加载并保留原文件，正式接口返回脱敏 `503 ASSISTANT_HISTORY_UNAVAILABLE`，请管理员核对修复；不会默默清空历史或覆盖原请求键。缺少 `updatedAt` 的旧有效记录继续兼容。

单价和成本保留来源精度，十进制相乘后才对行额取分；实际收款遇历史非分账款先停下。采购批次部分成功时保留原任务，不重新建整批。

## 任务存储、导入与恢复

新任务写入私有卷的 `tasks-v2/`。一次保存只替换原任务的文件，每个文件先同步内容再原子替换。收款完成与其第二段核销预览共用一个原子文件，单独保存其中一段时沿用另一段已提交的快照。任务运行时按账号编号建立内存索引，保留无编号历史按账号名匹配的原规则。最近 30 条先按本人取分页候选，再逐条检查当前权限及仓库范围。冷启动读取并重建索引，任务锁依然按任务编号互斥。

首次打开只有 `tasks.json` 的目录时，验证完整数组、任务身份和状态，先写独立导入目录，再一次原子发布 `tasks-v2/`。`.manifest.json` 记录源文件 SHA-256 和已导入任务编号，源文件字节原样保留。导入和冷启动读盘在独立线程完成。首次批量导入须由单个运行实例完成。同一个目录供该实例持有。目录发布后的坏清单、损坏记录和缺失导入记录会阻断历史访问。保存失败后的相关任务暂停读取，修复磁盘后重启，沿已提交状态和原请求键核对；已发布的新版目录优先于导入来源。

备份和还原以私有卷的完整快照为单位。容量检查使用备份端的 32,768 文件和 256 MiB 原始数据上限，历史源文件也计入预算。新代码可读旧版备份。使用已产生新版任务的卷恢复时，应用也须支持新版格式。原请求回执仍从 Flow 按原任务键查询。

在本机 Node 22 用 20 个合成账号、每任务 12 项结果和 16 次保存，`node agent/scripts/benchmark-task-store.js` 比较了原版和本版的热保存与同进程回环探针。将脚本放到旧版检出的同一路径可以重跑原实现。

| 样本任务数 | 写入 p95 原版 / 本版 | 并发轻量探针 p95 原版 / 本版 |
|---:|---:|---:|
| 100 | 2.74 / 8.77 ms | 4.67 / 10.37 ms |
| 1,000 | 14.83 / 8.47 ms | 16.67 / 10.18 ms |
| 10,000 | 153.45 / 8.08 ms | 156.31 / 9.81 ms |

同一次 10,000 条本版测量中，原始历史约 56.7 MB，新目录约 45.8 MB。首次导入用时约 34.9 秒，导入时同进程轻量探针 p95 为 2.94 ms，重新读取目录约 0.50 秒。测量只反映此机的合成负载及事件循环争用，正式 ERP 路径和生产并发需独立验收。
